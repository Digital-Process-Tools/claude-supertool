# The watch fleet's gh-token budget section goes silent when the process scan fails, not just when the fleet is empty

Found by `oss:auditor` reviewing #2509's own fix. `presets/watch/dispatcher.py:641-654` gates the whole
fleet-budget section on `if census.get("scan_ok"):`, with no `else`. When `transport._ps_rows()`
fails (`scan_ok=False`) but this channel's own PID files still produce non-empty `rows`, `cmd_list`
never enters the branches (`dispatcher.py:663-690`) that print `_scan_unavailable_reason()` -- the
only scan-failure notice left in the render is a line printed *after the entire watcher table*
(`dispatcher.py:870-873`), phrased only about "untracked pollers," never mentioning the budget.

A caller reading `watches`' output near the top, where the new budget section lives, sees exactly
the same thing -- nothing -- whether the fleet genuinely has zero gh-backed pollers or the scan
feeding the projection is broken. This is this repository's own named defect class (an absence
produced by the tool read as an absence in the world), reintroduced in the one new section that was
otherwise built carefully against it: `ratelimit.render_budget_lines` already has a real three-state
answer for a failed `gh api rate_limit` read; the scan failure one level up does not.

Ranked `misreports` per `skills/manager/phases/findings.md`'s table -- non-blocking. What a fix
might look like: when `scan_ok` is false, print the budget section's own disclosure line (reusing
`_scan_unavailable_reason()`) rather than skipping the section silently.
