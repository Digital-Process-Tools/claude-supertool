`tests/test_monkeypatch_target_exists_2706.py`'s `_patch_targets()` AST walk
(added by #2706 step 1, the vim-split) recognizes two call shapes:
`monkeypatch.setattr(supertool_or__supertool, "NAME", ...)` and
`mock.patch("supertool.NAME"/"_supertool.NAME")` (the string form). It does
not recognize `mock.patch.object(supertool, "NAME", ...)` -- a third, equally
common shape (`ast.Call` with `func.attr == "object"`, not `"setattr"` or
`"patch"`).

This idiom is already in live use against `supertool`/`_supertool` targets in
this exact suite: `grep:patch\.object\((supertool|_supertool),:tests` returns
37 hits across at least 6 files (`tests/test_map_ctags_cascade_913.py`,
`tests/test_tree_sitter_compat.py`, and others). None of today's 37 target a
name #2706 moved, so the guard is not wrong about that diff -- but the
guard's whole stated purpose ("a future refactor that re-exports a moved name
... would make that monkeypatch call succeed again, patching an attribute
the real call site no longer reads") is exactly as exploitable via
`patch.object` as via `setattr`, and the census is structurally blind to the
former. A `patch.object(supertool, "_vim_render_lint", ...)` test would stay
green under `test_every_patched_supertool_name_is_still_defined_there` even
if `_vim_render_lint` were later removed from `_supertool.py` with no
forwarder left behind.

Found during #2706's own self-review (`oss:auditor` spawn), ranked
`misreports`, non-blocking per `skills/manager/phases/findings.md`'s table --
not fixed in #2706 itself since the guard test already does its one job for
the diff it was written to cover, and widening its AST matching is a small
but separate piece of work. The shape of a fix, if this is promoted: add a
third branch to `_patch_targets()` matching `ast.Call` with
`isinstance(func, ast.Attribute) and func.attr == "object"`, checking
`node.args[0]` against `SUPERTOOL_MODULES` the same way the `setattr` branch
already does, with `node.args[1]` as the name.

Also noted by the same reviewer, not promoted to its own finding: the same
function's `test_dir.glob("test_*.py")` is non-recursive, so a `test_*.py`
dropped into a subdirectory of `tests/` would not be censused either. Not
live today -- zero such files exist in this tree -- so this is a latent
fragility rather than a present gap.
