Writing a TDD regression test for #2256 (em-dash crashes a Windows console at
a legacy codepage), I first built it against cp1252, following the issue's
own premise that cp1252 was the crashing codepage. It never went red: a
temporary removal of `use_utf8_stdout()` from `presets/github/job.py` still
left the test green, because `'—'.encode('cp1252')` succeeds — cp1252
has an em dash at byte 0x97 and does not raise `UnicodeEncodeError` on it at
all. This repo's own `tests/test_encoding_seam.py` (the census behind #1388)
already documents this split in a big comment block: "cp1252 encodes —, …,
•, and ·, so only → (starred.py), ★ (find_starable.py) and ↳ raise there …
cp437 / cp850, the actual default of a US Windows console, encode none of
the em dashes, so all 27 raise" — but nothing in the *issue text itself*
(#2256) or in `CLAUDE.md`'s cross-platform-hazard section names which
specific codepage actually fails on which glyph; both just say "the
console's codepage (typically cp1252)" as an example, without stating that
cp1252 in particular is safe for an em dash.

Cost: a full RED/GREEN cycle built and run against the wrong codec before
noticing the RED phase never went red (i.e. the test passed even with the
fix removed) — about 20 minutes and two test-file rewrites, caught only
because the brief mandated *actually proving* red rather than assuming it.
Confirmed directly: `'—'.encode('cp1252')` → `b'\x97'`, no exception;
`'—'.encode('cp437')` → `UnicodeEncodeError`. Anyone writing a codepage-crash
regression test for a *specific glyph* in this repo should check that
glyph's encodability against `tests/test_encoding_seam.py`'s own cp1252 vs
cp437/cp850 split before picking cp1252 as "the" crashing codepage — it is
the crashing codepage for some glyphs (arrow, star, hook) and not others
(em dash, ellipsis, bullet, middle dot).
