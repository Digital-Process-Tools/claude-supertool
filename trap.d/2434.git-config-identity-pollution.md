While working #2434 in worktree <worktree-2434> (shared
.git/config with <main-clone>),
the shared repo's `.git/config` had `user.name=T` / `user.email=t@t` at the moment I ran
`git-commit`, instead of the maintainer's real identity (`Florian DAVID
<150798857+fdaviddpt@users.noreply.github.com>`, confirmed as the author of the three
most recent commits on origin/master at the time). The commit `git-commit` produced was
authored `T <t@t>` as a direct result -- the op does not check identity plausibility, it
just runs `git commit` against whatever `user.name`/`user.email` resolve to.

`T <t@t>` is exactly the `_HERMETIC_ENV` identity `tests/test_worktree_setup_teardown_532.py`
(and likely other tests under this suite) use for their own throwaway git repos --
`GIT_AUTHOR_NAME=T`, `GIT_AUTHOR_EMAIL=t@t`. Those tests set that identity via env vars
passed to `subprocess.run`, scoped to the test's own temp-dir repos, and should not be
able to touch the primary clone's real `.git/config` at all. I did not track down which
process actually wrote `user.name=T` into the shared `.git/config` (it may predate this
session -- another concurrent lane's test run, sharing the same `.git/config` across
worktrees since it's the common dir, not worktree-scoped config) -- I only discovered the
symptom (wrong commit author) after committing, and fixed it locally (`git config
user.name`/`user.email` back to the real identity, then `git commit --amend
--reset-author --no-edit`) rather than root-causing the write.

Cost: one extra round of investigation + an amend, after the fact, because nothing
flagged the mismatch at commit time. `git-commit`'s receipt names HEAD before/after and
staged paths but never echoes the resolved author identity, so a polluted config is
invisible in the op's own output -- you have to think to check `git log -1 --format='%an
<%ae>'` separately.

Not sure this is a repo-wide "always verify identity before committing" rule (that's a
real cost on every commit) versus something narrower -- e.g. the hermetic test env
somehow leaking, or `git-commit`'s receipt gaining an author-identity line so a mismatch
against the last few commits on the branch is at least visible without a second command.
Logging it either way.
