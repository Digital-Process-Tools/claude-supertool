Observed during the #2536 self-review (oss:auditor pass on commit 47c72e4b, `presets/watch/sources/github-pr-feed/poller.py:206-217`, function `pr_only()`).

`pr_only()` -- the function this fix added so `github-pr-feed`'s own `spawn_watcher` resolves the same `pr_exclude_events` list `heal()` already resolves -- wraps its whole body in `try: ... except Exception: _pr_only_cache = []`. That one except clause collapses two genuinely different causes onto the identical answer, `[]` (unfiltered):

1. `SUPERTOOL_RADAR_TIERS` is simply absent or names no `gh-prs` tier -- the documented, intentional "a feed started by hand keeps today's behaviour" case.
2. The env var IS present but carries a malformed `pr_exclude_events` -- invalid JSON, wrong type, or an unknown event key -- and `gh_prs.exclude_events()` raised `RadarError`; or the lazy `importlib` load of `radar.py`/`tiers/gh_prs.py` itself failed for some unrelated reason.

Case 2 is a real misconfiguration an operator would want to know about -- radar itself refuses loudly and names the exact bad key when the same config reaches `radar_report()` (`gh_prs.py`'s own `RadarError` message, e.g. "pr_exclude_events names event key(s) github-pr cannot emit: coment_addd"). Nothing on this path does the equivalent. The feed poller's stdio is silenced (`_silence_stdio()` dup2's stdin/stdout/stderr to `/dev/null`), so even a bare `print` on the except branch would go nowhere -- any fix here needs a channel that actually reaches an operator: the poller's own state file (`transport.write_state`, already carries the poller's `only` filter today) is the most obvious candidate, or an event emitted through the normal `emit_event` path the way `prs_unreachable` already is for a fetch failure.

Cost if unfixed: an operator who mistypes an event key in `pr_exclude_events`, expecting radar's own loud `RadarError` to catch it, gets exactly that refusal from `radar_report()` on the *board* -- but the *feed's own* per-PR forks silently fall back to unfiltered instead of also failing loudly, which is a second, quieter disagreement with what the board already told them. Whether that's worth fixing (and where the disclosure channel should be) is a design question outside a one-line fix, which is why this is logged rather than fixed inline.

Confirmed by reading `pr_only()`'s body and `gh_prs.exclude_events()`'s own `RadarError` raise sites; not reproduced against a live poller process.
