# #2429 review — `worktree:teardown:force` (single colon, PATH omitted) is misparsed

**What was observed:** both the Explore reviewer and `oss:auditor`, independently, found
that the natural single-argument invocation of #2429's new force flag —
`worktree:teardown:force`, PATH omitted, meant to force-teardown the *current* worktree —
is misparsed by the colon-tokenizer. `presets/worktree/dispatcher.py`'s positional
parsing reads `argv[2]` as `path_arg` and `argv[3]` as `flag`; with PATH omitted the
tokenizer produces `argv = ["teardown", "force"]`, so the string `"force"` lands in the
path slot, never the flag slot. `oss:auditor` reproduced this live:
`python3 supertool.py 'worktree:teardown:force'` in the #2429 worktree ->
`ERROR: not a directory: .../force` — a bogus error blaming the literal word "force" as a
path, with no mention of teardown or staleness at all. The only form that actually works
is the double-colon empty-placeholder form, `worktree:teardown::force` (or spelling PATH
out, `worktree:teardown:.:force`).

**Where:** `presets/worktree/dispatcher.py:33-42` (positional argv parsing); the
misleading syntax notation appears in three places that all need the same correction —
`presets/worktree.json:9`, `docs/presets/worktree.md:44`, and the `_remove_copy` refusal
hint text in `teardown_op.py`, which actively reinforces the broken single-colon form
(`"rerun worktree:teardown:PATH:force..."`) rather than warning about it.

**What it cost:** nothing in production yet — caught in review before merge. Worst case
per `oss:auditor`'s ranking (`misreports`, not a destructive/containment defect): a
caller who does not spell PATH gets a wrongly-worded refusal rather than force actually
applying — the dispatcher never reaches the destructive path with the wrong target
(`resolve_target("force")` fails before any manifest/filesystem mutation), so this is a
misleading error, not silent data loss.

**Why the tests didn't catch it:** `tests/test_worktree_setup_teardown_532.py`'s
`_run_op()` helper synthesizes `argv = [..., mode, "", "force"]` whenever
`path_arg=None, flag="force"` — inserting an empty-string PATH token the real
colon-tokenizer never produces for the literal string `"teardown:force"`. Both new
force-flag tests go through this synthetic argv shape, so the gap between "how the test
calls it" and "how a caller actually types it" is exactly what hid the bug.

**How it was confirmed:** two independent reviewers (Explore + `oss:auditor`) against
issue #2429's committed diff (worktree `/Users/floriandavid/Documents/st-wt/2429`, commit
`e38986f0`); `oss:auditor` reproduced it live and confirmed via `git status --porcelain`
that the reproduction call itself mutated nothing.

**Left as a trap, not a blocking issue:** `oss:auditor`'s own ranking table grades this
`misreports` — ships behind a fragment rather than blocking. The real fix (fix the
dispatcher's positional parsing to accept `worktree:teardown:force` directly, and correct
the syntax notation + hint text in the three places above) is a small, well-scoped
follow-up.

**Secondary note, same review:** `oss:auditor` also disclosed that its own reproduction
call (`worktree:teardown:force`) was a write-class op run during a read-only audit brief
(`worktree` is `!`-flagged in `ops:roster`) -- confirmed harmless only after the fact via
`git status --porcelain`, not verified safe in advance. Worth a look at whether
`agents/audit/shared.md`'s read-only convention needs a stronger guard than "check the
roster yourself" for a case where reproducing a parsing bug requires invoking a write op
to observe the failure.
