Issue #2672's fix (`_probe_open_request` in `presets/git/_git_common.py`) filters
cross-repository rows out of a gh `pr list --head BRANCH` result by checking
`isCrossRepository` per row, over the first `--limit 5` rows the CLI returns.
If a genuine same-repo match exists but sits behind MORE than 4 fork rows
sharing the same branch name (plausible on a busy repo, or for a common
branch name like `main`/`fix`), the loop exhausts all 5 fork rows and falls
through to `return None, "answered", ""` -- the identical return value a
branch with NO MR at all produces. The caller (`push.py`'s `_open_mr_line`
and `_dead_mr_lines`) cannot tell "genuinely no MR" from "a same-repo MR
exists but we didn't look far enough" -- this repository's own standing
defect class (an absence produced by the tool's window, read as an absence
in the world), reached here by the very fix meant to close #2672.

Found during self-review (oss:auditor spawn) of the #2672 fix itself,
2026-09-23. Verified by reading the loop and the raised `--limit` (5, up
from 1); NOT verified against a real multi-fork repository returning that
many same-named-branch rows -- reasoned, not observed.

Auditor's own ranking: `misreports` in the maintainer's findings table --
non-blocking, ships behind this fragment rather than gating #2672's own PR.
Possible directions: page past `--limit 5` when every row fetched is a fork
(keep asking gh for more until a same-repo row is found or the CLI runs
out), or add a fourth MrLookup state distinguishing "no MR" from "looked
but every candidate was a fork, more may exist" so the caller can render it
as unknown rather than silently as none.
