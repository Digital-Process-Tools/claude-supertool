# The new py-escape advisory silently never fires for a ~-relative payload path

Found by `oss:auditor` reviewing #2493's own fix. `_payload_target_path_for_label`
(`_supertool.py:29874-29896`) keys its dict entry on `os.path.abspath(target)` computed from the
raw, un-expanded payload `path` field (`_supertool.py:29927`). `_atomic_write`'s own key
(`_supertool.py:11586,11594`) is `os.path.abspath(path)` computed *after* `path = _expand_home(path)`.
For a `~`-relative payload `path` (e.g. `path = "~/foo.py"`) the two keys differ -- verified
directly: `os.path.abspath("~/2493_probe.py")` from cwd yields `.../~/2493_probe.py`;
`os.path.abspath(_expand_home("~/2493_probe.py"))` yields the real home-relative path. `MATCH:
False`.

A caller whose payload genuinely exempted a doubled-backslash typo in a home-relative `.py` write
gets no advisory at all -- indistinguishable from "nothing was exempted". None of the fix's own new
tests use a `~`-prefixed `path`, so this is untested.

Ranked `misreports` per `skills/manager/phases/findings.md`'s table (the mirror-image direction --
an advisory that should exist silently does not, rather than one that shouldn't existing anyway) --
non-blocking, ships behind this fragment. What a fix might look like: expand `~` in
`_payload_target_path_for_label` the same way `_atomic_write` already does, before computing the
abspath key.
