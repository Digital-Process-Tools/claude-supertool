While implementing #2469 (a new pytest file that spawns channel.ts under
`node --experimental-strip-types`), the oss:auditor review found a real but
non-blocking diagnostic gap in the node-version gate.

`tests/test_notifiers_claude_channel_node_2469.py` has a `_node_version_ok()`
helper that runs `node --version`, parses the `vX.Y.Z` output, and returns
`False` on `except Exception`. That bare except collapses three different
causes into one downstream message via `require_or_skip(..., "no node >= 22.6
on PATH", promised=js_promised())`:

  1. no `node` binary on PATH at all
  2. a genuinely too-old node (< 22.6)
  3. an unexpected parse failure -- e.g. a version manager wrapper (nvm,
     corepack shim) printing a banner line before the real `vX.Y.Z`, or a
     future node emitting a differently shaped version string

The important half of #557's contract still holds: `promised=True` (the
notifiers CI job sets `SUPERTOOL_REQUIRE_JS=1`) still raises
`ToolchainPromiseBroken` and turns the leg red rather than silently skipping.
The gap is purely diagnostic quality on an already-red path -- a reader
debugging a red `notifiers` leg is told "no node on PATH" even when node is
present and something else about parsing its `--version` output broke, and
the raw stdout / exception text that would settle it is discarded.

Ranked (against skills/manager/phases/findings.md) as `misreports` --
non-blocking, can ship behind this trap.d fragment. Not fixed inline: the
honest fix is threading the raw `--version` output or the caught exception's
text into the skip/raise reason, which needs the reason string built lazily
(pytest marks are constructed at collection time, before the reason string is
otherwise final) rather than the one-line tweak it looks like from outside.
Worth a look if `_node_version_ok()`'s shape is reused elsewhere.
