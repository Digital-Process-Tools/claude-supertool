# gh api rate_limit's failure stderr is only .strip()'d, not fenced, before it reaches the watches render

Found by `oss:auditor` reviewing #2509's own fix. `presets/watch/ratelimit.py:59` (`_run_gh`'s
failure arm) does `(r.stderr or "gh failed with no stderr").strip()` -- `.strip()` removes only
leading/trailing whitespace, never embedded newlines. That string becomes `rate_limit_why` and is
interpolated into one `render_budget_lines` return line, which `dispatcher.cmd_list` prints as
`print(f"watches: {line}")` per line -- an embedded newline in `gh`'s own stderr would render extra
text at column 0 with no `watches: ` prefix.

This repo already treats this exact shape of gh-stderr text as needing fencing elsewhere --
`presets/github/run.py`'s unparseable-JSON arm wraps a similar failure in
`_untrusted.fence()`/`banner()` "because an unparseable body keeps its lines... the markers are the
structure" (#1648) -- `ratelimit.py` does not apply the same treatment to its own stderr-derived
`why`.

**Caveat, carried from the audit that found this**: `gh api rate_limit`'s own stderr is local tool
output, not remote/user-authored text in the checklist's usual adversarial sense, so this is a
rendering-boundary gap analogous to the untrusted-text class rather than a confirmed adversarial
instance of it. Not run against a live multi-line `gh` stderr to confirm the shape is reachable in
practice -- reasoned from the code, not observed.
