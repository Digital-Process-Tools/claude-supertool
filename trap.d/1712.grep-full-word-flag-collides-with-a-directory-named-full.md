Issue #1712 added `full` to the set of trailing word-flags `_grep_peel_trailing` peels off
a grep call before splitting PATTERN from PATH (alongside the pre-existing `count`
and `no-auto-read`). This is the same architectural tradeoff those two already made
-- a colon-CLI grep call has no quoting, so a trailing token that matches one of
these three literal words is always read as the flag, never as a directory of that
name -- and #1712's own diff did not introduce that tradeoff, it extended the same
peel set by one word.

The self-review's `Explore` spawn flagged it as worth a second look precisely
because `full` (unlike `no-auto-read`) is a plausible real directory or fixture
name -- `tests/full`, `data/full`, `full-backup` -- so the diff measurably widens
an already-accepted footgun's blast radius:

```
python3 -c "
import supertool
print(supertool._parse_grep_args(['grep', 'NEEDLE', 'full']))"
# -> ('NEEDLE', '.', 10, 0, False, False, True)   # searches '.', not a dir named 'full'
```

No error, exit 0, silently wrong scope: `grep:NEEDLE:full` searches the whole tree
from cwd instead of the directory literally named `full`. The identical collision
already exists today for `grep:NEEDLE:count` and `grep:NEEDLE:no-auto-read` against
directories named `count` / `no-auto-read` respectively -- unconfirmed whether
anyone has ever hit either of those in practice, and unconfirmed whether `full` is
common enough as a directory name to be materially more likely to bite than the
first two. Not evaluated here: whether the peel should require `len(args) >= 3`
(pattern *and* an explicit path token before the flag word) the way the trailing
numeric peel already does for LIMIT/CONTEXT, which would fix all three words at
once but changes what `grep:PATTERN:no-auto-read` (two tokens, no path) means
today.
