# One `|force` token buying both the publish confirmation and a guard override

## What was observed

`presets/youtube/comment.py` read a single `|force` flag twice:

```python
require_confirm("youtube_comment", body, force=force)   # the shared publish confirmation
...
if verdict != "ok" and not force:                       # the sentinel: duplicate + 5/hour cap
```

`|force` is also the token the op's own usage string tells an operator to pass in order to
publish at all. So the duplicate guard and the rate cap were disarmed on every invocation
that actually published. Only a user who had set `no_publish_confirm: true` in
`.supertool.json` (and therefore never typed `|force`) ever got the sentinel.

That sentinel is the guard the whole preset is justified on: the op has no delete
counterpart, so a duplicate comment is a public artifact it cannot remove.

## Where

- `presets/youtube/comment.py` (PR #2543, fixed in `ffdcf8d`)
- **`presets/bluesky/publish.py:191` and `:194` have the identical shape and are still
  unfixed** — `require_confirm(..., force=force)` then `if reply_uri and not force:` over
  the duplicate-root check. Not touched by #2543.

## What it cost

Caught in review before merge, so nothing shipped. The cost was the review round plus six
tests and a doc pass. Had it shipped it would have been silent: the guard never fires, and
a guard that never fires looks exactly like a guard with nothing to refuse — the absence
class this repo keeps filing, wearing a permission's clothes.

## How it was confirmed

Four tests written first and watched red (`4 failed, 6 passed`): `|force` alone on a video
already in the sentinel log, `|force` alone on an unreadable log, `|force-dup` actually
overriding, and `|force-dup` alone still failing the confirmation. Green after splitting
the flag: 43 on the file, 241 passed / 1 skipped across the publish, registry, encoding,
path-detector, replaces-census and syntax-floor lanes.

## The shape, if this is worth a rule

An op that takes a confirmation token and also takes an override token must not read the
same flag for both. The test that catches it is the negative-with-positive-control pair:
assert the guard refuses **while the confirmation token is present**, not merely that it
refuses. Every pre-fix test passed because each one either confirmed or triggered the
guard, never both in the same call.

Possibly broader than these two ops: anything calling `require_confirm(..., force=...)`
and then branching on the same name. Worth a census across `presets/`; I did not run one.
