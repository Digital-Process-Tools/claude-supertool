oss:auditor review of #2578 (`e510e0e9`..`67c676be`), a platform-band finding, ranked `fails-to-preserve` (non-blocking, low reachability).

`validators/common/spawnable.py`'s `_refuse_spawn(name)` docstring guarantees the returned path raises `FileNotFoundError` specifically -- never `NotADirectoryError`, `PermissionError`, or another `OSError` sibling -- "on either platform". That guarantee was verified (this PR) for an ordinary `name` on POSIX, but `_cwd_only_match()`'s only guard is `os.path.dirname(name)`; it does not exclude a `name` that is a Windows reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`9`, `LPT1`-`9`, case-insensitive) or contains a character invalid in a Windows path component (`< > : " | ? *`).

`os.path.join(os.sep, "supertool-2578-refused-<uuid>", name)` with such a `name` would build a path Windows treats specially -- a reserved-device open, or an invalid-path-syntax error -- rather than a simple missing-file lookup, plausibly raising a different `OSError` subtype that escapes every caller's narrow `except FileNotFoundError` arm, uncaught.

Reachability: low. Every call site found in this repo passes either a hardcoded tool literal (`"tsc"`, `"cargo"`, ...) or an operator-supplied `_BIN` env var -- not anything attacker-controlled via the repository under inspection. An operator who sets e.g. `RUFF_BIN=con` already controls their own execution environment. Not observed on real Windows; reasoned from documented Windows reserved-name semantics.

No test in this diff exercises a reserved-name or invalid-character `name`, on any leg -- nothing would currently catch a regression here either way.

Fix shape, not designed here: `_cwd_only_match()` (or `_refuse_spawn()` itself) could reject/pass through a reserved or invalid `name` before building the path, falling back to the genuine-absence bare-name arm instead.
