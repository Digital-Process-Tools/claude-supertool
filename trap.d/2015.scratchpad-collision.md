Scratchpad filename collision across concurrently running lanes, observed live (2026-09-04,
issue #2015 lane, worktree /Users/floriandavid/Documents/st-wt/2015).

I wrote an intermediate TOML payload to the session scratchpad at a generic filename
(`.../scratchpad/note.toml`) rather than one discriminated by branch+timestamp -- exactly the
mistake agents/developer/report.md already warns against ("never a bare fixed name under the
shared scratchpad"). Between the `open(...).write(...)` that created it and a later `cat` of the
same path, its content changed underneath me: what I read back was not my own #2015 note payload
but the full note content of a different, concurrently-running lane (fix/2169 -- a real worktree
on this machine's board at dispatch time, `/Users/floriandavid/Documents/st-wt/2169`, unrelated
issue).

Cost: one paste call was sent with the wrong payload (targeting `notes/fix-2169-...md`, not my
intended `notes/fix-2015-...md` -- my own note never got written on that attempt), one round trip
diagnosing it (md5 + head on both the scratchpad source and the destination file), and a second,
careful write-verify-consume cycle to recover. No lasting damage: the destination `paste` reported
"rewrote ... 5941 -> 5941 bytes" (byte-identical), so the collision happened to be a same-content
no-op on the other lane's file rather than a real corruption -- that was luck, not something the
tooling guaranteed.

What is unresolved: whether the scratchpad directory named in this session's own system prompt
(`/private/tmp/claude-501/-Users-floriandavid-Documents-claude-supertool/<session-uuid>/scratchpad`)
is genuinely shared across sibling lanes in the same fleet despite carrying what looks like a
per-session UUID, or whether some other mechanism (a stale leftover from a prior session reusing
the same UUID; a race in how the scratchpad directory gets provisioned) produced the same
observed effect. I did not investigate further -- confirming would need visibility into how the
fleet allocates these paths, which I do not have from inside one lane. Recorded as observed, not
diagnosed.

The mitigation the brief already prescribes (branch+timestamp-discriminated scratchpad filenames
for every intermediate, not just the three named destination writes) would have prevented this
entirely, and did prevent a recurrence once applied: I re-wrote using
`fix-2015-20260904T144845Z-note.toml`, verified its content with `md5`/`head` immediately before
and immediately after the write, and the follow-on paste landed correctly. Worth widening the
existing instruction from "the note, the report and the PR payload" to every intermediate
scratchpad file a lane creates, since this is exactly the shape the instruction already
anticipated -- it just had not yet been observed happening.
