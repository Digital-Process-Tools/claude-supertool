Second-pass audit of #526 (devto-engagement/bluesky-engagement watch sources) found that
`devto-engagement/poller.py`'s per-article comment fetch (`fetch_comment_ids`) discards its own
error string on failure: `comment_rows, _c_error = fetch_comment_ids(aid, api_key)` with `_c_error`
never read. For a transient failure this is fine -- the article's previous comment_ids are carried
forward unchanged, or (after the #526 self-review fix) the baseline is deferred to a later tick --
but if one specific article's `/comments` endpoint fails on *every* tick from then on (a
persistently 500-ing endpoint, a deleted-but-still-listed article, a private/restricted one), that
article is silently excluded from `new_known` forever. `poll()` never emits any event about it and
the population-level `engagement_unreachable` never fires either, since the population fetch
(`/articles/me/published`) itself keeps succeeding -- only the one article's sub-fetch is broken.
The watcher just quietly stops covering that one article, with no `*_unreachable` line and no
count anywhere naming it.

This is not new to #526's diff in kind -- a per-article failure was already silent before the
self-review fix, which only replaced "records a false empty baseline forever" with "never records
anything for this article, forever." Both are silent; the second is honest about not knowing rather
than confidently wrong, which is why the self-review fix was still worth making. But neither
surfaces to an operator, and fixing that properly (an edge-triggered per-article unreachable event,
or a stall counter that ages an article out and reports it, mirroring `gitlab-mr-feed`'s
`mr_unreachable`) is more than a one-line change and touches the same population/state shape this
source already leans on `gitlab-mr-feed` for.

Ranked non-blocking (`misreports`, ships behind this note per the audit) because: the population as
a whole is still correctly reported as reachable, the failure mode is "one article goes dark," not
"the whole source lies," and no existing test or doc claims per-article-level `*_unreachable`
coverage that this contradicts. Worth a look next time this file's population/state handling is
touched, or if `gitlab-mr-feed`/`github-issue-feed` grow a per-member reachability signal this
source could mirror.
