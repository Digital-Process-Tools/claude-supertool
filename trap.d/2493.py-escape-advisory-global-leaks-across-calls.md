# The new _PAYLOAD_PY_ESCAPE_ADVISORY global can leak an advisory from a refused call into a later, unrelated call

Found by `oss:auditor` reviewing #2493's own fix (a `.py`-only receipt advisory for a
`literal_backslashes`-exempted doubled-backslash escape). Reproduced live, in-process, not only
reasoned.

`_load_at_file_raw` seeds `_PAYLOAD_PY_ESCAPE_ADVISORY` (`_supertool.py:30274-30276`) before the
last refusal check in that function, `_payload_shell_quote_escape_refusal`
(`_supertool.py:30278-30280`). `_atomic_write` consumes and pops it
(`_supertool.py:11651-11656`). A `depth<=1` backstop at the tail of `_dispatch_impl`
(`_supertool.py:33028-33029`) is meant to clear any leftover the same way `_PAYLOAD_WARNINGS`
already is -- but the single-op named-field `@file` write route (`edit:@file`, `paste:@file`, any
`_generic_preset_route` write op) has its own early `except ValueError`
(`_supertool.py:32109-32117`), which `return`s **before** the big `try:` block at
`_supertool.py:32225` whose tail runs that backstop. That early-return path drains
`_PAYLOAD_WARNINGS` (`_take_payload_warnings()`, same line) but never touches
`_PAYLOAD_PY_ESCAPE_ADVISORY`.

So: a payload that seeds the advisory for one field, then gets refused for an unrelated reason in a
different field (the last check `_load_at_file_raw` runs), leaves the seeded entry un-popped. A
**second, unrelated, clean** call in the same process -- no `@file` payload, no backslashes at all --
can then surface an advisory about a write it never sent. `batch:@file` calls are NOT affected (its
own `except ValueError` at `_supertool.py:32571` falls through normally, inside the big try).

Ranked `misreports` per `skills/manager/phases/findings.md`'s table -- non-blocking, ships behind
this fragment. What a fix might look like: pop `_PAYLOAD_PY_ESCAPE_ADVISORY` in the same early
`except ValueError` block that already drains `_PAYLOAD_WARNINGS`, at `_supertool.py:32109-32117`.
