# `gh-branch` rendered a failed API read as `NO RUN`, twice in seven minutes

## What was observed

Polling `supertool 'gh-branch:master'` every 90s while CI ran on `ffdcf8d` (the #2543
squash merge), two of the polls came back:

```
Branch master: NO RUN
Verdict: NO RUN — zero workflow runs on ffdcf8d; the head commit is 4m old, inside the
~15min window in which a first run has always appeared, so a run is still expected.
Nothing has passed and nothing has failed.
```

The polls immediately before and after both reported 3 runs and 21 legs on the same SHA —
`14 passed, 0 failed, 7 pending` one minute after the second `NO RUN`. The runs existed
the whole time. The first occurrence was at 09:17 CEST (commit 4m old), the second at
09:24 (11m old). Same command, same SHA, same session.

"Zero workflow runs on this commit" and "I could not read the runs for this commit" are
being rendered as the same verdict. The sentence is even confident about it — it names the
15-minute window and concludes a run is still *expected*, which is reasoning built on an
answer the tool did not actually get.

Suspected cause, **not confirmed**: a `gh` rate-limit or secondary-limit response read as
an empty list. This repo has six token exhaustions on `fdaviddpt` recorded in 12h, and
`gh api rate_limit` is known to report 5000/5000 during a 403. I did not capture the
underlying HTTP status at the moment it fired, so this is a hypothesis with a matching
history, not a diagnosis.

## What it cost

It broke the watcher I had armed. My monitor's break condition was
`if ! echo "$out" | grep -q "pending"; then break; fi` — and a `NO RUN` body contains no
"pending", so the loop exited on a transient bad read and reported the wait as finished.
Ten minutes, and a wrong "CI settled" I had to retract.

Two defects, worth separating:

1. **`gh-branch` itself.** This is CLAUDE.md's named class landing on an instrument, the
   same shape as #2208: an absence produced by the tool read as an absence in the world.
   `NO RUN` and `could not read` must be different states, and the second must not carry a
   confident sentence about what is expected next.
2. **The watcher I wrote.** I keyed a terminal condition on the *absence* of a token.
   Fixed by breaking on a positive state instead — `^Verdict: GREEN` or
   `Legs: .*, [1-9][0-9]* failed` — which held through the second `NO RUN` correctly.

## How it was confirmed

Re-ran `supertool 'gh-branch:master'` by hand ~40s after the first `NO RUN`: `8 passed, 0
failed, 13 pending`, both CodeQL runs concluded `success`. Getting the answer a second way
is what separated the two readings; nothing in the first output flagged itself as
uncertain.

## The shape, if this is worth a rule

Two candidates, and I am not sure which:

- an op that reports a count of remote objects must distinguish "the API said zero" from
  "the API did not answer" — probably a `gh-branch` fix rather than a rule.
- a polling loop must break on a positive terminal state, never on a missing token. That
  one generalises past this op and past this repo: any `until ... grep -q` over tool output
  has it.
