While fixing the #1783 review finding that a broken/unreadable
`_shipped_reference.py` (the pip-route fallback module) collapsed to the
`absent` verdict instead of `unreadable`, I noticed a smaller, second-order
inaccuracy in the same code path that I chose not to fix in the same pass
(kept the diff to the one mechanism the review actually flagged).

`op_help()`'s "unreadable" message reads:

    "A reference does ship beside this binary and it could NOT be read...
    Check the file's permissions and that it is a JSON object:
    {_shipped_reference_path()}"

`_shipped_reference_path()` unconditionally returns the path to
`.supertool.json`, never `_shipped_reference.py`. On the clone/plugin
routes that is correct -- `.supertool.json` is the only file that can ever
produce `unreadable` there. But now that the pip-route fallback can also
produce `unreadable` (when `_shipped_reference.py` itself is present but
broken), the same message names the wrong file (`.supertool.json`, which is
genuinely absent on that route) and asserts the wrong claim ("check... that
it is a JSON object" -- `_shipped_reference.py` is a Python module, not
JSON).

Not fixed here because it needs a small plumbing change (track which of the
two paths was actually implicated when `_SHIPPED_CONFIG_STATE` is set to
"unreadable" -- a module-level path variable, or threading a reason string
through) to say the honest thing, and the review's own finding was about
the *state* being wrong, not the message text once the state is right. A
future pass through this fallback should either add that plumbing or fold
`_shipped_reference_path()` into something that checks which file is
actually on disk at message-render time (cheap, not a re-introduction of
the exists()-pre-check defect item 2 fixed, since by that point the state
is already correctly determined -- this would only be for picking which
filename to display).
