Moving a TOML mini-parser''''s own source through the `paste:@-` TOML-literal payload
convention collides with itself: the documented triple-single-quoted literal-string
form (triple-single-quote delimited) for embedding large text in a TOML payload breaks when the
content being embedded is a TOML parser''''s own source, because that source
legitimately contains many literal triple-single-quote runs as part of its own parsing logic --
those runs prematurely close the TOML literal block partway through the payload.

Observed moving `_supertool.py`'''s TOML mini-parser (~160 KB) into a new
`_supertool_payload.py` file during the #2706 payload-part split (one of six
parallel wave-1 lanes).

Cost: one failed `paste:@-` TOML-literal attempt before switching approach.

Worked around by building the payload as JSON instead of TOML --
`{"path": ..., "content": ...}` generated via a read-only
`python3 -c "print(json.dumps(...))"` that only reads the source file and prints
to stdout, piped into `python3 supertool.py 'paste:@-'`. `paste:@-` auto-detects
JSON vs TOML from the first non-whitespace character, and JSON'''s backslash-based
string escaping has no equivalent collision with this file'''s own triple-quote content.

Not sure whether this generalizes beyond "the payload itself contains a literal
triple-single-quote run" (any large embedded text with that exact 3-quote run would hit the
same wall, not just TOML-parser source) -- logging as observed rather than deciding
the dimension. Other wave-1 sibling lanes on #2706 (config, parse, presets,
read+grep, edit) may hit the same collision if any of their moved spans contain
triple-single-quote sequences.
