# #2449 review round 2 — pid_probe misses a collateral desync during the respawn window

**What was observed:** reviewing #2449's round-2 fix for the `force_respawn` collateral-kill
finding (a `pid_probe` parameter to `call_with_retry` that retries a collateral caller's
plain `RuntimeError` when the daemon pid changed under it), a follow-up review found the
guard has a blind window: `force_respawn` (`presets/mcp/_spawn.py`) deletes the pidfile via
`reap`/`cleanup` *before* `ensure_daemon` writes a new one, and that window can span the
full `SPAWN_TIMEOUT_SEC` (up to 60s for slow validators like phpunit/phpstan). If a
collateral caller's second `pid_probe()` read lands inside that window, `daemon_pid()`
returns `0` (falsy), `pid_before and pid_after` evaluates false, and the collateral failure
is read as "pid unchanged" -- not retried, reporting a plain unretried `RuntimeError`
exactly as it did before this fix.

**Where:** `validators/common/ndjson_scan.py` (`call_with_retry`'s `pid_probe` check,
~line 394) and `presets/mcp/_spawn.py` (`force_respawn`, `reap`/`cleanup` then
`ensure_daemon`, ~lines 410-416).

**What it cost:** nothing yet -- caught in review before merge. This narrows the original
finding (force_respawn can kill a healthy in-flight collateral client) rather than leaving
it fully open: the common case (pid changes cleanly between reap and respawn) is now
retried correctly, per `tests/test_ndjson_desync_retry_2449.py`'s positive/negative
controls. Only the specific timing where a collateral caller's probe lands exactly inside
the gap between the old pidfile's deletion and the new one's creation still falls through
to the pre-fix behavior.

**How it was confirmed:** follow-up Explore review of commit `531794d7` (branch `fix/2449`,
worktree `<worktree-2449>`), reasoned from reading `force_respawn`'s and `call_with_retry`'s
code together -- not observed under load or reproduced live.

**Left as a trap, not a blocking issue:** narrows rather than reopens the original finding;
the common case is fixed and tested. A full fix (e.g. a probe that distinguishes "no pidfile
because respawn is mid-flight" from "no pidfile because nothing is running") is a
well-scoped follow-up rather than a release blocker.

**Two smaller test gaps from the same review, logged together rather than as separate
fragments:** (1) the round-2 test for randomized initialize ids does not force a mocked
collision (both `randrange` calls returning the same value) to exercise the collision-nudge
branch directly. (2) the timeout-budget arithmetic verified as correct does not account for
`LOCK_WAIT_SEC` (60s) being acquired twice in the `force_respawn` -> `ensure_daemon` path
under lock contention -- a pre-existing property of the locking design, not introduced by
this fix, but worth knowing the new timeout margins do not cover it.
