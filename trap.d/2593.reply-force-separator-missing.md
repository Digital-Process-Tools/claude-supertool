Release audit (round 2, v0.62.0..HEAD delta, dispatch token 409586369e15):
`presets/youtube/reply.py:67` parses its body argument as
`arg.split("|")`, with no `:::` separator. Issue #2600 (`de88ba38`) fixed
the identical shape in `comment.parse_args` -- a body whose last `|`-segment
happens to spell `force`/`force-dup` was silently satisfying the publish
confirmation gate, and the fix added a `:::` separator so the sentinel can
only ever come from an explicit argument position, never from body text.

`reply.py`, merged afterwards in the same delta (issue #2593, `0ca6b6d8`),
copied the pre-fix parser; its own docstring at `:66` still claims it
"mirrors `comment.parse_args`", which is no longer true.

Concretely: `youtube_reply:ID|may the|force` publishes the reply with
"force" dropped from the body text and the confirmation gate satisfied by
that body text rather than an explicit confirm argument.

Neither issue #2600's nor issue #2593's diff, taken alone, shows this; only
the composed range does, because the two PRs touched sibling files in
parallel.

Ranked `misreports` (non-blocking) -- the receipt reports a confirmed
publish the operator did not explicitly confirm via the `:::` contract.
`forges` considered and rejected: the text is the operator's own argument,
not a stranger's. Settling fact: whether `youtube_reply` is meant to share
`comment.py`'s `:::` contract at all -- `presets/youtube.json:135` documents
its syntax with `|` only, so this may be a docstring/consistency fix rather
than a behaviour change.
