Observed on PR #2560 (fix/2536, issues #2536/#2544), reported back by a downstream session after CI went red on `tests/test_meta_doc_figures_1783.py::test_the_footer_reports_the_render_and_the_doc_quotes_the_difference`.

`scripts/lane_setup.py --lane presets/watch.json --lane presets/watch/transport.py --lane docs/operations/meta.md` (run from inside this same lane, after the CI failure was reported) answered "none of the lane's files match a known cross-cutting guard" -- so the guard-derivation step the developer brief mandates (`agents/developer/review.md`'s "A narrowed run can be green while a guard it never touched fails on CI" clause) did not, and structurally could not, catch this. The actual guard is `tests/test_meta_doc_figures_1783.py`, which pins two exact byte counts in `docs/operations/meta.md` against the live rendered size of `presets/watch.json`'s op descriptions (`ops:full` minus `ops`). Any edit that lengthens or shortens an op's `description` string in ANY preset's `.json` -- not just `presets/watch.json` -- moves this figure and reddens this one test, and nothing in `CROSS_CUTTING_GUARDS` (or wherever `lane_setup.py` derives its list from) currently maps "touched a `description` field in a presets/*.json file" to this guard test.

This is the same class the brief's own guard clause exists to catch (#432's `oss_config.scaffolded_changelog_gate` example), just a different concrete mapping missing from the derived list. Whether the fix is a new entry in `lane_setup.py`'s guard table keyed on `presets/*.json` description-length changes, or something narrower (only op descriptions that reach `docs/operations/meta.md`'s two pinned numbers), is a design decision for whoever curates that table -- logged here rather than decided.

**Update, second round-trip.** The first fix (bumping `docs/operations/meta.md`'s two figures) cleared `test_meta_doc_figures_1783.py` but not the two sibling guards pinned on the exact same root cause -- both went red on the *next* CI run, on the same commit, because the first round only checked the one guard the report named rather than sweeping every guard the class could reach:

- `tests/test_description_is_not_a_changelog_1774.py` -- a hard ratchet: an op already in `_OVER_BUDGET` (the twelve-entry ledger of descriptions already over the 2000-char cap) may only shrink, never grow. `radar`'s description had grown from 2134 to 2365 chars (the new desktop-notification sentence), which is not a staleness the ledger number can be bumped to absorb -- the fix has to be shrinking the description back down (or moving the addition elsewhere), never editing the ledger's recorded value upward. Root-caused and fixed by removing the sentence from `radar`'s description entirely (kept only in `watch`'s, which is far under budget and not in the ledger) rather than reworded to fit; the docs pages already carried the full explanation.
- `tests/test_render_size_claims_1877.py` -- four files (`docs/operations/index.md`, `docs/contributing.md`, `hooks/session-start.sh`, `docs/operations/meta.md`) each quote `~86.89KB` for `ops:full`'s rendered size; the same description growth moved it to `87.11KB` (recomputed a third time after the `radar` revert above landed, since removing the `radar` sentence changed the render size again).

So the guard-derivation gap this note describes is not "one test missed," it is a **class of at least three sibling guards**, all keyed off the same underlying signal (an op description's byte length) and none reachable from `presets/watch.json`'s own filename by any mapping `lane_setup.py` currently has. A `--lane` guard lookup keyed on the touched *file* cannot catch this class at all; it would need to be keyed on the touched *field* (any `description` value inside any `presets/*.json`), which is a different kind of rule than the file-path table this tool currently is.

Total cost: two full CI round-trips (three ubuntu legs red identically, twice) before all three guards were green on the same commit. Confirmed by reproducing all three locally after each report, before and after each fix: `test_meta_doc_figures_1783.py` failed with 82,633 bytes (first report) then 82,402 (after the `radar` revert, needing a second bump of the same two figures); `test_description_is_not_a_changelog_1774.py` failed with `[('radar', 2134, 2365)]`; `test_render_size_claims_1877.py` failed on all four files with `86.89KB` vs the live `87.11KB` (later `87.12KB` before the `radar` revert, then `87.11KB` after).
