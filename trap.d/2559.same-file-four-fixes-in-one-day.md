what was observed: `tests/_go_warmup_lock.py` (and `serialize_once` inside it) took four
correct, independently-landed fixes in one calendar day (2026-09-16) -- #2552, #2555, #2559,
plus #2548 on the poller beside it -- each one closing a real bug, and each one uncovering
the next rather than the file settling. #2559 in particular was a residual left by #2555 (a
retry loop that fixed a real race but paid the full timeout on a genuinely-unusable
lock_dir), and #2559's own merge immediately surfaced a further residual (#2563: the
write-probe's own fail-open path on a transient failure, not only a genuine one).

where: `tests/_go_warmup_lock.py`, `serialize_once`, `_lock_dir_usable` -- one small,
heavily-shared locking primitive.

what it cost: four separate developer-lane dispatches plus one maintainer-authored follow-up
issue in a single day, on one file, each review genuinely clean at merge time and each one
still leaving something for the next pass.

how it was confirmed: coordinator review of PR #2559's diff (the fourth of the four) named
the pattern explicitly while reading it, rather than a lane discovering it independently --
worth noting because nothing in the review checklist currently prompts a reviewer to ask
"has this exact file had this many landings today" before approving one more.

unsure whether it belongs elsewhere / is a real rule: possibly. The candidate rule is
something like "a shared low-level primitive (locking, retry, serialization) that has taken
N fixes in one day is a signal to widen the review -- read the whole function fresh rather
than just the diff's own hunk -- because each fix so far has been locally correct and
non-locally incomplete." Whether that generalizes past this one file, or is specific to
small concurrency-primitive files where correctness depends on the interaction of several
failure branches at once, is a judgment for the curate pass with more instances visible.
