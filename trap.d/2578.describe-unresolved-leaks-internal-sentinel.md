oss:auditor review of #2578 (`e510e0e9`..`67c676be`), Class A finding, ranked `misreports` (non-blocking).

`validators/common/bin_resolve.py`'s `resolve_bin_cmd()` -> `_spawnable()` -> `_refuse_spawn()` now returns a synthetic, unpredictable sentinel path (`/supertool-2578-refused-<uuid>/<name>`) when a `_BIN` env var names a bare tool that only resolves via a cwd-only match. `describe_unresolved(raw, resolved)` then sees `resolved != raw` and appends `(configured: "<raw>")`, producing a message like `GLAB_BIN not found: /supertool-2578-refused-3f2a.../glab (configured: "glab")`.

An operator reading that message sees an internal sentinel path they never configured, with no indication that the real reason is "a cwd-only match existed and was refused for security" -- that fact lives only in a code comment, not in anything the caller can read. It reads as a path-configuration bug rather than what actually happened.

Reachability: narrow but real. Requires a `_BIN` env var set to a bare name (not a path), no genuine PATH entry for it, and a cwd-only match (a same-named file at the repo root) -- an operator who ships a tool's shim only at their repo root without it in their real PATH.

Fix shape, not designed here: either have `describe_unresolved()` special-case a path under the refused-spawn prefix and say "cwd-only match refused" explicitly, or have `_cwd_only_match`/`_refuse_spawn` return something `describe_unresolved` can detect structurally (a marker attribute, a distinguishable prefix constant it can check) rather than an opaque string.
