Release audit of v0.61.0..HEAD (dispatch token 95999d02ddecfeac, round 2)
found: `presets/_publish_safety.py:399-405` (`_mode_bits_are_enforced`),
consumed at `:442-452` (`check_token_file_mode`). Both `except OSError` arms
return `False` -- "this filesystem does not enforce mode bits" -- including
when the *probe itself* could not be created (unwritable or full `TMPDIR`).
A loose-mode credential file then takes the soft arm and prints `WARNING:
... this filesystem reports 0o644 for every file and does not enforce POSIX
mode bits`, asserting a filesystem property that was never measured, instead
of the hard `ERROR ... exit(2)`. What a caller gets: a world-readable OAuth
refresh token accepted on a POSIX box, under a sentence blaming Windows
semantics. The one fact that settles it: `_mode_bits_are_enforced` has no
third return value -- probe-failed and bits-not-enforced are the same
`False`.

Row: misreports (ranking table). Non-blocking, carried forward past gate 3's
round-2 cap per the release phase's own rule (a non-blocking finding may
ship, filed here for a later pass). Fix: give `_mode_bits_are_enforced` a
third state (could-not-tell) for a probe-creation failure, distinct from a
measured "not enforced", and have `check_token_file_mode` treat could-not-tell
as its own case rather than folding it into the soft warning.
