Dispatched to worktree <worktree-1253>, branch fix/1253, for issues #1253
and #1868. The worktree was NOT fresh: the branch already carried a merged PR (#2554, closing #1532)
from a prior bundled dispatch that had grouped #1532, #1253 and #1868 into one lane.
`git-worktrees` reported the tree as `[merged, clean]` with status "cannot tell" whether it was
still occupied (index written 54m ago, no positive process signal either way).

`git-status` (via the branch's own supertool.py) showed `2 ahead, 4 behind` master, because master
had moved on since the squash merge (squash merges leave no ancestor relationship a local
`is-ancestor` check can see). Working in that state would have based new commits on stale content
and produced a diff polluted by re-adding already-merged changes.

Fix: `git fetch origin`, then `git rebase origin/master` (not `reset --hard` or `checkout -B`, both
of which the auto-mode classifier blocked outright as destructive even though nothing unique would
have been lost). The rebase hit one add/add conflict on the already-merged changelog fragment for #1532
(which CHANGELOG.md now records; the fragment itself is gone as of the next release tag) —
resolved with `git rebase --skip`, since the content was already on both sides. Git's own
patch-equivalence detection then auto-dropped the second commit ("patch contents already upstream")
without any prompting. End state: branch at 0 ahead/0 behind master, a clean base for new work.

Lesson for whoever curates this: when a worktree/branch is reused across a multi-issue lane where an
earlier pull request from the same branch has already merged, check `git-status`'s ahead/behind line
before writing anything. A `[merged, ...]` worktree from `git-worktrees` does not by itself mean the
branch is caught up with the current default branch tip, only that its own commits are
(transitively) merged.
