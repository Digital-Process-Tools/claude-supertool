Issue #2599's fix wrapped four raw error-body/scope-print sites in
`presets/youtube/comment.py` and `presets/youtube/auth.py` with
`repr(safe_short(str(e), 300))`. A self-review (Explore reviewer, spawned
from the #2599/#2600 developer lane) found the identical unescaped shape
still live in three untouched sibling files in the same preset directory:

- `presets/youtube/list.py:98` and `:119` -- `except YouTubeAPIError as e:
  sys.stderr.write(f"ERROR: {e}\n")`
- `presets/youtube/search.py:61` -- same shape
- `presets/youtube/read.py:106` -- same shape for its own `main()`, and
  separately `read.py:125` embeds `e.message` unescaped directly into
  `comments_note`, which then flows into `print(render(...))` mixed with
  genuine video/comment content -- arguably worse than the four #2599
  fixed sites, since it is rendered output rather than a terminal error
  path.

All four carry Google's `body[:300]` via the same `_yt._format_oauth_http_error`
this repo already classifies as "misreports, not forges" (the same reasoning
issue #2599 itself cites from `trap.d/227.oauth-error-body-unescaped-in-receipt.md`,
which has since been promoted/removed from trap.d per its own lifecycle --
see `git log --follow` on that path, c500a4c1). Non-blocking under that same
classification, and out of #2599's stated scope (its issue body names only
`comment.py`/`auth.py`). Worth its own small issue or fold into a
follow-up sweep of `presets/youtube/*.py` for the whole "raw {e} to
stderr/stdout" shape rather than one-file-at-a-time discovery.
