Second self-review round on #227 (youtube preset) surfaced: `presets/youtube/_yt.py`'s
`_format_http_error()` embeds up to 300 characters of the raw HTTP error-response body
(from `googleapis.com`, decoded UTF-8 with `errors="replace"`) directly into a one-line
error string (`f"403 Forbidden (...): {body[:300]}"`) without stripping newlines. Google's
JSON error bodies are commonly pretty-printed with real newline bytes between fields, so the
first 300 characters can span several lines and break the single-line framing a caller
relies on -- e.g. `read.py`'s `--- comments unavailable: {e.message} ---` note, meant to be
one line inside a rendered block.

Not something #227 invented: the identical pattern (unstripped `body[:300]` embedded in an
f-string) already exists in `presets/bluesky/_atproto.py::_format_http_error` (verified with
`grep -n _format_http_error presets/bluesky/_atproto.py presets/youtube/_yt.py`), so this is
a pre-existing repo pattern mirrored rather than a new one. The text is remote-server text
(Google's own error page), not attacker-controlled in the adversarial sense -- a channel or
video owner does not control it -- so this reads more as an occasional framing break than a
forgery vector, but a `.replace("\n", " ")` on the truncated body before it enters the
f-string would remove the ambiguity in both `_yt.py` and, if anyone picks this up, in the
older `_atproto.py` copy it was mirrored from.
