Observed during self-review of #2645 (`presets/watch/sources/gitlab-mr/poller.py`).

`_fetch_approvals(iid)` returns `(None, error)` on any failure -- `_glab_api` erroring, a non-dict payload, or a missing `approved` key. `poll()` binds that error to `_approved_error` and never reads it again: no line is appended anywhere, no event is emitted, and the state carries the last known `approved` value forward unchanged. Nothing distinguishes "still not approved" from "the approvals endpoint has been failing on the one confirming tick, repeatedly, for a week" -- a maintainer watching the channel sees identical silence in both cases.

Compare the *primary* MR fetch in the same file: `_fetch` failing emits an explicit `mr_unreachable` event with `notify_title: f"!{iid} — cannot tell"` (`poller.py:410-429`). The new confirm-tick fetch has no equivalent surfaced state.

This is narrower than it first looks, after the cost-gate fix that came out of the same review round: the confirming request now fires on at most one tick per genuine transition out of `detailed_merge_status == "not_approved"` (never on every tick of the streak), so a failure here is bounded to that one tick, not an ongoing silent outage. Still, if that one tick's request fails, the poller currently has no way to retry or report it -- it simply waits for `not_approved` to reappear before trying again, which for an MR that then sits in some other blocking state indefinitely means the "confirm" story never resolves and nothing says so.

What would settle it: either a dedicated event (`approved_unreachable`, mirroring `mr_unreachable`), or extending the existing warning-line vocabulary this poller does not currently have at all (it only ever returns `(events, new_state)`, no `lines`). Either is a real design decision -- new event key, new state field, new test coverage -- rather than a one-line fix, and the auditor ranked it non-blocking (`misreports`, ships behind trap.d) rather than something to fix inline on a priority-low issue.
