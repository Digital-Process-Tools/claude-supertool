`_doctor_symlink()` in `_supertool.py` (fixed under #2611 to route `shutil.which("supertool")` through `_which_excluding_cwd("supertool")`, same commit fe5db701) traded one defect for another, found by `oss:auditor` in a second self-review round.

`_which_excluding_cwd()` deliberately skips any `PATH` entry whose absolute path equals the current working directory -- correct for its usual job of resolving a binary that is about to be *spawned* (a repo-planted shim at cwd must never win over the real tool on Windows). But `_doctor_symlink()`'s `which` value is also *displayed to the user* as "where does `supertool` resolve on your PATH" -- and if a user legitimately `cd`s into their own install directory (e.g. `cd ~/.local/bin`, exactly the directory `_doctor_symlink()`'s own docstring describes inspecting) before running `doctor`, the function now reports `which: None` for a binary that genuinely resolves via `shutil.which()`. `_supertool.py` around line 20427 renders that identically to a real absence (`- not found on PATH`), so the diagnostic cannot currently tell "genuinely absent" from "excluded only because cwd happens to coincide with a legitimate PATH entry".

Observed directly (not via pytest): `cd ~/.local/bin && python3 -c "import _supertool as st, shutil; print(shutil.which('supertool'), st._which_excluding_cwd('supertool'))"` prints a real path from `shutil.which()` and `None` from `_which_excluding_cwd()`.

Ranked `misreports`, non-blocking. The fix needs a decision this lane was not briefed to make: whether `_doctor_symlink()` should report a raw `shutil.which()` result for DISPLAY purposes while still resolving the SPAWN target (`[which, "version"]`) through the cwd-excluding path, or whether it should note the exclusion explicitly in its output rather than silently rendering as absent. Either way the fix belongs in `_doctor_symlink()`'s own logic/rendering, not in `_which_excluding_cwd()` itself, whose cwd-exclusion is correct for every one of its other (spawn-only) call sites (`_has_rtk()`, `_has_ctags()`, `validators/`-style adapters via the sibling copies in `validators/common/spawnable.py` and `presets/_spawnable.py`).
