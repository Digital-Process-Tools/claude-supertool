`presets/watch/dispatcher.py`'s `_reload_poller`, added by #2694, does a
read-modify-write on the watcher's state file after a successful reload:

```python
published = transport.read_state(source, watcher_id)
...
published["reloaded_at"] = ...
transport.write_state(source, watcher_id, published)
```

`write_state`'s own docstring (`presets/watch/transport.py`) says it returns
`""` when the write landed, and a non-empty string naming why not otherwise --
and explicitly frames swallowing that return as the bug class #1540 fixed.
Two existing callers in the same file already honour that contract:
`record_death` and `clear_deaths` both do `return not write_state(...)`.

`_reload_poller`'s new call discards the return value. If `write_state`
fails (a squatted state directory, disk full, a permission error -- the
exact failure modes its own docstring enumerates), the in-memory poller
module is still swapped and returned to the caller -- the reload genuinely
happened -- but the state file is left without `reloaded_at`. The next
`watches` render then shows plain `STALE` and the `:reload` remedy again:
the identical loop #2694 exists to close, now reachable through a write
failure this diff gave no visibility into.

Found during #2694's own self-review (`oss:auditor` spawn), ranked
`fails-to-preserve`, non-blocking per `skills/manager/phases/findings.md`'s
table -- not fixed in #2694 itself to keep that diff's blast radius to the
render bug it was filed for. The shape of a fix, if this is promoted: check
`write_state`'s return in `_reload_poller` the same way `record_death`/
`clear_deaths` already do, and fold the failure into the `RELOAD_FAILED_EVENT`
path (or a new, distinct event) rather than reporting `RELOAD_EVENT`
unconditionally.

Also worth noting for whoever promotes this: the pre-existing fork-time
write in `_run_poll_loop` (`published["forked_fingerprint"] = ...;
transport.write_state(...)`, unchanged by #2694) has the identical
discarded-return-value shape and predates this issue -- the reviewer that
found this one flagged it as out of #2694's own diff scope and worth its
own filing rather than folding in here.
