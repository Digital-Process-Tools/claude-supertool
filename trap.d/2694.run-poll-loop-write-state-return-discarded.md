`presets/watch/dispatcher.py`'s `_run_poll_loop` writes the fork-time
fingerprint to the watcher's state file, unchanged by #2694/#2695:

```python
fingerprint, fp_why = transport.source_fingerprint()
published["forked_fingerprint"] = fingerprint
published["forked_fingerprint_error"] = fp_why
transport.write_state(source, watcher_id, published)
```

`write_state`'s own docstring (`presets/watch/transport.py`) says it returns
`""` when the write landed, and a non-empty string naming why not otherwise --
and explicitly frames swallowing that return as the bug class #1540 fixed.
Two existing callers in the same file already honour that contract:
`record_death` and `clear_deaths` both do `return not write_state(...)`.

This call discards the return value the same way `_reload_poller`'s new
write did before #2695's fix (see
`trap.d/2694.reload-poller-write-state-return-discarded.md`). If this write
fails (a squatted state directory, disk full, a permission error), the
poller still forks and runs, but the state file is left without
`forked_fingerprint` -- `version_state_of` then reads that as `unknown`
(no fingerprint recorded) rather than as a genuine fork-time failure, and
nothing else in this loop learns the write did not land.

Found during #2694's own self-review (`oss:auditor` spawn), named in
`trap.d/2694.reload-poller-write-state-return-discarded.md`'s own text as
"out of #2694's own diff scope and worth its own filing" -- filed here
separately during #2695's review pass so it carries its own receipt rather
than staying a note inside a sibling fragment. Ranked `fails-to-preserve`,
non-blocking per `skills/manager/phases/findings.md`'s table.

The shape of a fix, if this is promoted: check `write_state`'s return in
`_run_poll_loop` the same way `record_death`/`clear_deaths` already do, and
report the failure rather than letting the process continue as though the
fingerprint were recorded.
