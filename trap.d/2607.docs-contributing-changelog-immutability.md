Both self-review spawns (Explore, twice) independently flagged the same gap while
reviewing a fix to CHANGELOG.md's already-tagged `## [0.62.0]` section (issue #2607,
commit 9247266d): `docs/contributing.md`'s "Changelog fragments" section states
unconditionally "Do not edit `CHANGELOG.md` in a pull request. Add a file to
`changelog.d/` instead," with no carve-out for correcting an entry in a section that
has already been tagged and released (fragments for a released version are deleted at
release time, so there is no `changelog.d/` file left to edit for it).

The repo has real precedent for editing an already-tagged CHANGELOG.md section in
place: commits `54ae5c4a`/`d01879d7` (issue #2440) directly edited the v0.34.0
`#1317` entry, years after that version was tagged, to redact a leaked username, with
no fragment involved for that specific edit (a `changelog.d/2440.fixed.md` fragment
was added, but only for the new unreleased work in that same PR).

So the written rule and the actual practice disagree for exactly this "already
released, needs a factual correction" case, and nothing in `docs/contributing.md`
says which one governs. A reviewer applying the written rule literally would flag any
such correction (including this one) as a violation, even though it matches existing
precedent. Worth a decision (and a sentence in `docs/contributing.md`) on whether an
already-tagged CHANGELOG.md entry may be corrected in place for factual-accuracy
reasons, and if so, whether that needs any marker (a note in the entry, a changelog.d
fragment for the *next* release documenting the correction, or neither).

Not decided here on purpose -- this is a repo-convention question, not a call to make
mid-fix.
