## [Unreleased]

### Fixed

- **Supertool could not start under a C locale, and presets still died printing their own success line on a Windows console.** [#418](https://github.com/Digital-Process-Tools/claude-supertool/issues/418) collected four defects that came out of one seam over an afternoon; [#415](https://github.com/Digital-Process-Tools/claude-supertool/pull/415) fixed the two that were blocking its own CI and left the rest deliberately. They were only ever found one at a time because nothing in this suite had run supertool as a **real subprocess under a non-UTF-8 environment** — every test calls `main()` in-process under pytest's UTF-8 capture, where all four are invisible by construction, and the suite was green through every one of them. So the detection came first, as its own commit: a static AST scan enumerating every text read/write in shipped code that leaves the codec to `locale.getpreferredencoding()`, plus five live pins that drive the real binary under `-X warn_default_encoding` with `EncodingWarning` promoted to an error ([#431](https://github.com/Digital-Process-Tools/claude-supertool/pull/431)'s technique, generalised), under `PYTHONIOENCODING=cp1252`, and under a C locale with PEP 538/540 coercion disabled so it stays ASCII. All seven fail against the pre-fix code on Linux and macOS — no Windows runner needed, which matters because every member of this family so far was found by a platform the author was not sitting on. The scan named **69** call sites, against the handful the issue listed: `.supertool.json` and every preset JSON, but also the validator cache, the notifier debug log, `op_diff`, `op_around_line`, the tree-sitter fallback extractor, and 38 preset scripts reading the markdown bodies and auth tokens users hand them. That gap between what we knew and what was there is the argument for building the enumerator before fixing the known list.
- **An unreadable config took the whole tool down instead of the ops that needed it.** `_load_config` and `_merge_presets` caught `JSONDecodeError` and `OSError`; `UnicodeDecodeError` is a `ValueError`, so it went straight past both as a startup traceback — for every op, including the ones that never touched the config. `presets/git.json` holds `—` and `✓`, so under a C locale the file that could not be decoded was one we ship. It is now caught and the file skipped, which is what the loader has always done with unusable state — it already walked past malformed JSON to the parent directory. But it did so in silence, and `_preset_warnings` had been collected since it was introduced and never printed by anyone, so a skipped preset meant the user's ops were simply absent with nothing on screen connecting that to a file. Both now report on stderr, once, before any op output. The except clauses name `UnicodeDecodeError` rather than widening to `Exception`: the same `try` covers `_merge_presets` and the MCP block, and a `TypeError` out of either is a bug in this file that must not be filed under "bad config".
- **`PYTHONIOENCODING=utf-8` is now set for every child process supertool spawns.** The reader was pinned to UTF-8 in #415; the writer was left to the console. A preset is a separate process and inherits none of supertool's stream reconfiguration, so on a cp1252 console it dies with `UnicodeEncodeError` while printing its own `✓` — the worst failure mode available to a tool that mutates state, because the work lands and the receipt says it crashed, which invites the operator to do it again. Setting it once at the top of `main()` covers all four spawn sites and every preset, rather than depending on each of ~50 scripts to remember a call; an explicit `VAR=… cmd` prefix on an op still overrides it. All twelve `presets/git/*.py` entry points additionally adopt `use_utf8_stdout()`, since those get run straight from a shell mid-conflict with no supertool in front of them, and `diff.py`'s inline copy from #308 collapses onto the shared helper — a duplicate is what lets two implementations drift, and it was the reason the other eleven looked like they had a licence not to bother. The non-git presets print more non-ASCII than the git ones do, not less (`gitlab/mrs.py` alone prints `·»Δ—…→⊘◌●✋✓✗`), which is why the fix for them is at the spawn point rather than 50 copies of a line.

- **The test suite's git-state guard blamed a sibling worktree's commit on whichever test was in teardown.** `_guard_repo_git_state` exists to catch a test that runs git against the real repository — the [#416](https://github.com/Digital-Process-Tools/claude-supertool/issues/416) damage, where a leaked `GIT_DIR` put fixture commits on master and flipped `core.bare`. It fingerprinted `config`, `HEAD` and every ref under `refs/heads/`, and `refs/heads/` lives in the **common** git dir that every linked worktree shares. So an agent working in `st-wt/424` committing at 16:41 failed the suite running in `st-wt/422`, at the teardown of a test that had touched nothing — the `st-wt/NNN` convention exists precisely so several changes can be in flight, so this is normal usage, not abuse. A guard that reports a violation nobody committed is the defect class this repo has been clearing: the first few false positives teach you to skip its output, and it is the real ones you then miss. Worse here than usual, because the failure lands on an *innocent* test and the message therefore points away from the cause. The guard now asks "did **this test** mutate the repo", not "did the repo change". The fingerprint is a mapping rather than a hash — a hash can only answer the second question — and a detected change is *attributed* before it is reported. `config`, this worktree's `HEAD`, and the branch `HEAD` points at are what a test running git against the ambient repo moves, and what no sibling can touch, since a checked-out branch is exclusive to one worktree: any of them moving is this test's doing, siblings present or not, so the #319 tripwire keeps its teeth. Refs checked out in other worktrees, read from `git worktree list --porcelain`, are theirs by definition. Three calls worth naming. (1) **Anything left over is reported as `inconclusive`, not as a failure** — a stray branch or a rewritten `packed-refs` could be this test or could be a sibling's `git branch`/`gc`, and an honest "cannot tell, re-run with no other worktree busy" beats a confident wrong accusation; the *only* thing that buys silence is the presence of a sibling, so **in CI, and in any single clone, the guard is bit-for-bit as strict as before** — an unattributable change with no sibling to blame is still a failure. (2) **Attribution is on the slow path only.** The before/after mappings are compared first and `git worktree list` runs solely when they differ, so the ~7k per-test teardowns cost no subprocess; a per-test `worktree list` would have added minutes to the run to answer a question that is almost always "nothing changed". (3) **Narrowing the fingerprint to exclude sibling refs was rejected as the whole fix** — it needs the worktree list to be current, and `git worktree add -b` creates a worktree *and* its ref mid-run, so a list captured earlier would silently mis-attribute exactly the case that motivated the issue; classifying at teardown reads the list after the fact instead. The failure message now names the keys that moved (`refs/heads/master`, `config`) rather than the generic "config/HEAD/refs changed". Proven from both ends by three subprocess tests that run the real guard, from a real conftest copy, over a real repo with a real linked worktree: a sibling committing during a test leaves it green, a test committing into its own repo still fails, and an unowned branch beside a live sibling warns instead of accusing — the first two both go red against the pre-fix guard. **Identifying our own worktree by path is Windows-fragile**, so two things guard it. `_same_path` compares through `os.path.normcase`, because NTFS is case-insensitive and `C:\\Repo` versus `c:\\repo` would otherwise make this checkout a sibling of *itself* — flipping `has_siblings` true on a lone Windows clone and softening the unattributable bucket to a warning where it must still fail. And ownership in `_classify_git_state_change` is derived from the `HEAD` bytes and tested **before** the sibling set, so even a completely mis-parsed sibling list cannot excuse a commit on the checked-out branch; that ordering is the invariant, and a test pins it by passing our own branch inside `other_branches` and requiring `mutated` anyway. Both are pinned from any runner rather than left to a Windows leg: the CRLF case feeds `\\r\\n` porcelain directly (a `split("\\n")` would leave a trailing `\\r` on every branch name), and the case-folding case forces `ntpath.normcase` under `monkeypatch`. Closes [#428](https://github.com/Digital-Process-Tools/claude-supertool/issues/428).

- **A read-only status query could terminate the process it was asked about.** `os.kill(pid, 0)` is the POSIX idiom for "does this PID exist" — the null signal is delivered to nothing and only the error tells you the answer. On Windows there is no signal delivery, and Python routes any signal other than `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` to `TerminateProcess`, so the idiom does not ask whether a process is alive: **it kills it**. [#422](https://github.com/Digital-Process-Tools/claude-supertool/issues/422) replaced the probe in `presets/watch/transport.py` with a read-only `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess`, but deliberately scoped itself to one file — and the idiom lived in **seven** call sites across six others (`gitlab/mrs.py`, `github/prs.py`, `mcp/status.py`, `mcp/daemon.py`, and twice in `mcp/stop.py`). `radar` reaches `mrs._watched_iids()` on every run. Reachability is bounded today — it needs a live PID in a `supertool-watch-*.pid` file on Windows, and `_spawn_poller` needs `os.fork` — but the guard rails are incidental rather than designed: the helper scans `/tmp` for *any* such file with no check that this tool wrote it, PIDs get recycled by the OS, and "we cannot spawn on Windows" is a limitation someone will reasonably lift one day without suspecting it arms a process killer inside a status command. The probe now lives in **one** place, `presets/_proc.py`, alongside the existing presets-root helpers `_board.py` and `_publish_safety.py`; `transport.py` became a consumer too rather than keeping the copy that would have started the next divergence. Three copies of the same six lines is what produced both this bug and the `WinError 87` escape #422 fixed — two copies had the `except OSError` and the third did not — so the shape of the fix matters as much as its content. Kept from #422: the probe asks for `PROCESS_QUERY_LIMITED_INFORMATION` rather than `PROCESS_ALL_ACCESS`, so it never holds a handle powerful enough to terminate what it inspects; the `kernel32` calls sit behind a seam whose test stub raises on any attribute other than the three read-only ones, so a probe that ever reaches for `TerminateProcess` fails loudly in tests rather than quietly in production; and an unanswerable question resolves to **not alive**, because a duplicate poller is visible and cheap while a phantom one is silent blindness. The regression is pinned by post-condition, not proxy — a test asserting only "returns False for a bad pid" passes on the destructive implementation, so the pin probes a **real live subprocess** under simulated Windows semantics and asserts it is still running afterwards (it fails with `returncode -9` on the old code). A further test walks the preset tree with `ast` and fails on any `os.kill(x, 0)` outside `_proc.py`, so a future copy is a red test rather than a silent reappearance. Closes [#429](https://github.com/Digital-Process-Tools/claude-supertool/issues/429).

- **`radar` was hardcoded to `author=@me`, so the MRs least likely to have a human watching them were the ones it could not see.** `radar.py` built its query inline as `{"author": "@me", "state": "opened"}`: `main(argv)` ignored `argv` entirely, and the filter bypassed `defaults.py` — the module whose stated purpose is that `radar` and `watch-mine.sh` "cannot drift apart". Editing `DEFAULT_FEED` to follow a second author moved the shell supervisor and silently did not move `radar`, so the anti-drift mechanism had a hole in precisely the field a user would want to change. The motivating case is an automated agent opening Draft MRs under `modular.system`: bulk changes that appear with nobody sitting at a terminal, and unlike stale discovery, re-running does not help — another author's MRs are permanently out of scope, not stale. `radar` now takes the `gl-mrs` filter vocabulary (`radar:author=modular.system`, `radar:reviewer=@me`), inherited by reusing that parser rather than growing a second one, so `gl-mrs:X` and `radar:X` describe the same population by construction. **The load-bearing part is that one filter drives all three views.** Filtering only the watcher fleet while `live_open_mrs()` kept its hardcoded author would satisfy the feature request and still be broken — that is already reachable today by spawning watchers directly through `watch-mine.sh`, and it produces a session receiving `pipeline_failed` for an MR the board does not list, while the board still renders as a complete picture of the world. Same failure class the module docstring names for a different cause: silent incompleteness, arriving through another door. So `live_open_mrs()`, `heal()` and the feed scope all read one resolved filter, and the default comes from a new `defaults.DEFAULT_FILTER` that `DEFAULT_FEED` is now built from, closing the drift hole rather than papering over it. Three calls worth naming: (1) **Multi-author is a repeated key, not a plural `authors=`.** GitLab takes one `author_username`, so several authors must fan out to N `glab` calls unioned by iid; `author=@me,author=modular.system` reuses the existing comma tokenizer as-is, whereas `authors=a,b` would need a second value separator inside a syntax whose separator is already the comma. `_parse_multi` is now the single tokenizer and `_parse_args` is its scalar view (last value wins), so both readings come from one place and a single-valued filter produces byte-identical argv to before. One failing query in a fan-out fails the whole board: a partial union is a board quietly missing rows, which is the exact thing `RadarError` exists to prevent. (2) **The snapshot is now keyed by a hash of the normalised filter.** It was one fixed path — safe only while exactly one population could exist. The moment `radar` takes args, `radar` and `radar:author=modular.system` compare against each other's snapshot: every MR in one reads as new, every MR in the other as gone, and the delta column actively lies. The key ignores key and value order (the same population, written two ways, is one snapshot) but not identity. (3) **The feed poller was retrofitted to the same plural filter.** #422's `gitlab-mr-feed` already accepted a literal `gl-mrs` filter as its scope, so the board's filter reaches the discovery tier unchanged and only `fetch_population` needed the fan-out; a filter that expands to one of the feed's own aliases resolves back to the alias, because the scope is a PID filename and `@me` versus its expansion would otherwise be two pollers over one population, i.e. two copies of every `mr_opened`. A non-default board now prints its filter in the footer, since two radars in one window otherwise render as one board printed twice. Closes [#425](https://github.com/Digital-Process-Tools/claude-supertool/issues/425).

- **Discovery ran once, so a radar session went stale the moment a new MR appeared.** `radar` conflated two tiers: *reconcile*, which runs once when a human types it, and *watch*, which runs continuously but polls **one known iid**. Nothing in the running system could therefore discover an MR that did not exist at spawn time, which makes an idle radar session structurally blind to every new MR until someone re-runs the command. Observed in the watcher start times: !33176 opened between a 16:38 radar run and a 16:44 one, and only the second found it. In between, the board was not visibly wrong — it was confidently complete and missing an MR, which renders identically to all-green. That indistinguishability is the whole failure class this subsystem exists to remove. The fix is a new first-class watch source, `gitlab-mr-feed`, fitting the existing `sources/<name>/{events.json,poller.py}` contract rather than adding a subsystem: its state is the population returned by a `gl-mrs` filter, a new iid spawns `watch:gitlab-mr:<iid>` and emits `mr_opened`, and a vanished iid is reported as what actually happened to it. `radar` now reconciles once **and** ensures exactly one feed poller is alive. The ID is a *scope* — `@me` and `@reviewer` alias `gl-mrs` filters, anything else is a literal filter — so a team radar can cover review requests, which `author=@me` never returns. Interval is 300s (MRs appear on human timescales; the per-MR pollers already carry the 30s traffic) and each poll is one `glab mr list` with **no** pipeline enrichment, because the feed's job is "which MRs exist" and the per-MR watcher's is "what is happening to this one". Four calls decided explicitly: (1) **`is_terminal` is never** — a population has no final state, and a feed that stopped itself would restore the blindness silently, so it ends only on `unwatch`, SIGTERM or the machine going away; idempotence is enforced by short-circuiting on a live PID, since N radar runs stacking N feeds means N copies of every `mr_opened`. (2) **`mr_opened` is on by default** via a separate `DEFAULT_FEED_ONLY`, and deliberately *not* added to `DEFAULT_ONLY` — that filter belongs to the `gitlab-mr` source, which cannot emit `mr_opened`, and listing an event beside a source that never emits it is simply untrue. (3) **Vanished is not merged.** An iid leaving `author=@me,state=opened` could have merged, closed, been reassigned, or the filter could have changed; guessing `mr_merged` is right most of the time and confidently wrong the rest, so the feed spends one `glab api` lookup on the truth (departures are rare, so the call is too). Only a confirmed terminal state stops the watcher, and `mr_merged`/`mr_closed` are emitted without a desktop notification because the per-MR watcher reaches the same conclusion within 30s and owns that ping. A still-open MR gets `mr_left_feed` carrying the real state and **keeps** its watcher — following an MR the feed no longer returns is legitimate, the same distinction `radar`'s prune already makes. (4) **A dead feed is reported, not silently absent** — the footer always carries `feed ok` / `feed respawned` / `feed DOWN`, and a down feed (or one alive but erroring every tick, which `watches` renders as perfectly healthy) prints an explicit `WARNING` line that survives delta suppression. A first poll records its baseline without emitting, because announcing every MR that was already open is a notification storm rather than a discovery, and a failed fetch returns no events and keeps the known set, because an unreachable GitLab must never read as "everything vanished". Two supporting fixes: the dispatcher now clears `last_error` after a successful poll so a reported error is current rather than a scar, and `SOURCE`/`ID` reject `/` alongside `__` now that a feed id can be a filter string interpolated into a `/tmp` path. Closes [#422](https://github.com/Digital-Process-Tools/claude-supertool/issues/422).

- **`watch-mine.sh` watched only MRs that were *already* failing, so it could never see one go red.** The feed default was `gl-mrs:author=@me,failed,iids`, which means an MR that is green or running when watchers are spawned is never watched at all — the exact event the tool exists to catch is the one it is structurally blind to. Observed: !33172 was `running` when watchers were spawned and went green 30 minutes later, never appearing in `watches` and never firing an event. The default is now `state=opened` — watch everything open and let `only=` filter at the event level, which is where filtering belongs. Cost is one poller per open MR (~7 for an active dev), each a 30s `glab api` poll. The `only=` default had the mirror-image problem: `pipeline_failed,merged` means you only ever hear bad news, so the loop red → fix → push → *?* never closes and the user goes back to polling by hand to learn the fix worked — the behaviour being eliminated. `pipeline_succeeded` was already emitted by the poller and merely filtered out at the default; it is also the only signal that an automated fix actually worked. The default is now `pipeline_failed,pipeline_succeeded,merged,closed,conflicts_appeared`: `closed` because it is terminal and stops the poller, `conflicts_appeared` because it is actionable and otherwise entirely silent (observed live on !19509). `pipeline_running` stays out (you just pushed; it carries no information) and `comment_added` stays out because GitLab's `user_notes_count` counts *system* notes, so every pipeline transition would fire twice. Both defaults moved into `presets/watch/defaults.py` and are read from there by the shell script, because `radar` must heal with the identical filter and two literals in two languages drift silently — with a symptom of a watcher that exists but never notifies. Part of [#417](https://github.com/Digital-Process-Tools/claude-supertool/issues/417).

- **A watcher that reached a terminal state left its state file behind forever.** `watches` sweeps stale *PID* files but never touched `/tmp/supertool-watch-{source}__{id}.state.json`, so a poller that exited correctly on `merged` still left a file on disk reading `mr_state: "merged"` — observed for !33136 and !33137 a full day after they merged. Any consumer that globs the state files therefore reports long-merged MRs as live watches, which is precisely what the new `radar` op does. The file is now deleted by the dispatcher when the poll loop breaks on `is_terminal`, alongside the PID file it already removed: the poller is gone, so the file is not a record of anything live. Retention was considered and rejected — keeping it would push the filtering onto every present and future consumer, and a consumer that forgets is silently wrong rather than loudly broken. `radar` prunes terminal files independently as part of its reconcile, since the dispatcher's cleanup only covers the case where the process lived long enough to run it; a poller killed by a reboot leaves its file behind whatever the happy path does. Files belonging to a *live* poller are never pruned by either path — the owner clears its own. Part of [#417](https://github.com/Digital-Process-Tools/claude-supertool/issues/417).

- **`paths = [...]` in an `@payload` did not parse on Python 3.9 or 3.10.** `_mini_toml_loads` — the fallback that runs wherever stdlib `tomllib` is absent — was written with "no inline arrays" as a deliberate limit, which was true right up until [#340](https://github.com/Digital-Process-Tools/claude-supertool/issues/340) gave payload fields a *variadic* form. A variadic field is written as a list, so `git-commit:@-` with `paths = ["src/Foo", "src/Bar"]` — the shape the op's own description documents — died with `ERROR: @file TOML parse error: unknown value type for 'paths'` on a third of the supported matrix (`requires-python = ">=3.9"`). It parsed fine on 3.11+, so nothing local caught it and the documentation described a form that did not work. The value parser is now one `_toml_parse_value` function that inline arrays recurse into, so elements get every scalar type the parser already had and arrays nest; whitespace, newlines, comments between elements and a trailing comma are all accepted, per TOML. A malformed array raises rather than returning a short list — a silently truncated `paths` would commit the wrong set of files, which is worse than the parse error it replaces. The new cases call `_mini_toml_loads` directly rather than going through a payload, so they run on **every** interpreter: routed through the `@file` loader they would only execute on 3.9/3.10, and the 3.11+ jobs that stayed green throughout would keep proving nothing.
- **`git-commit` crashed on a non-UTF-8 console, reporting a crash for a commit it had already made.** `supertool.py` reconfigures its own stdout to UTF-8, but every preset runs as a *separate* process and inherits none of that. `commit.py` prints `✓`/`✗` in its receipt, so on a Windows cp1252 console the first success line raised `UnicodeEncodeError: 'charmap' codec can't encode character '✓'` — after the commit had landed. That is the bad failure mode: the work is done, the receipt says traceback, and the obvious next move is to redo something that already happened. No existing test could see it, because they call `commit.main()` in-process where pytest's capture is already UTF-8; it surfaced only once the op was driven as a real subprocess. `diff.py` had carried this guard inline since [#308](https://github.com/Digital-Process-Tools/claude-supertool/issues/308) — it now lives in `_git_common.use_utf8_stdout()` and `commit.py` calls it, so the remaining git presets printing the same glyphs (`push.py`, `resolve.py`, `checkout.py`, `merge.py`) have one call to adopt rather than a copy to paste. The regression pin forces `PYTHONIOENCODING=cp1252`, which reproduces the Windows failure on any OS.
- **An op's receipt then rendered as mojibake on that same console.** The other half of the same journey, and only visible once the crash above was fixed: `commit.py` correctly wrote `✓` as UTF-8, and supertool read it back through `subprocess.run(..., text=True)` with no explicit encoding — which decodes using `locale.getpreferredencoding()`. On a cp1252 console the three UTF-8 bytes `E2 9C 93` came back as the three characters `âœ“`, so `HEAD after: bc63422 âœ“` was the receipt for a commit that had worked perfectly. Nothing about this is specific to `git-commit`: it is the one call every preset and custom op returns through, so any op printing a glyph was affected. The decode is pinned to UTF-8 with `errors="replace"`, so a command emitting genuinely undecodable bytes degrades to a replacement character rather than taking the run down with it. The regression pin deliberately does not use the git preset — it declares a one-line custom op in an ASCII-only config and forces a C locale, which turns the mis-decode into a hard error and so goes red on Linux and macOS instead of relying on the Windows jobs to notice.

- **A validator that declined to analyse a path reported it as one new error.** Every edit under a DVSI `tests/` directory came back `phpstan-mcp : 0 → 1 (+1) ✗` with `phpstan.exit analyse: path is outside the configured --paths allowlist.` — which is not a finding about the file, it is phpstan declining to look at it. `format_response` in the phpstan-mcp adapter had one fallback for a non-zero exit with no findings, and it manufactured a single synthetic error out of whatever the daemon said, refusals included. The rendering is the smaller half of the harm. `ok` has two values and the world has three — clean, broken, and never looked at — so folding a refusal into "broken" makes an unmeasured file indistinguishable from a measured one that is genuinely wrong, and the delta arithmetic then inherits a `+1` that no edit caused. - **`gl-job:ID:fail` no longer guts a PHPUnit failure and hides that it did.** The failure view keeps every line matching an `error_patterns` entry plus `error_context` lines around it, which is the right shape for a stack trace — the middle frames are noise — and exactly the wrong shape for an assertion failure, where the middle *is* the evidence and the head and tail are boilerplate. On a real DVSI job the only matches inside a 33-line block were `Failed asserting` at its top and `FAILURES!` below its bottom, so the two ±8 windows never met: the op returned the opening `<tr …>` and the closing `' [ASCII](length: 2170) does not contain "5</"` with a bare `...` between them. A view whose job is to carry evidence must not decide the evidence is context. A PHPUnit failure is now an atomic unit: `_phpunit_blocks` bounds it from its `N) Class::method` header to the last non-blank line before the next header or the run summary (the trailing `/path/File.php:LINE` frames), and a match landing anywhere inside pulls in the whole block. Expansion is a union with what the pattern windows already selected, so no call returns less than it did before. - **`radar` — a reconcile that makes "nothing is wrong" distinguishable from "nothing is watching".** `watches` reports which pollers are alive; it cannot report what is true, and the two diverge routinely. Observed live on !33173: `last_event: pipeline_failed on pipeline 154177` against `source_state: running on pipeline 154180` — a board built on the event calls that MR broken while it is mid-retry on a newer pipeline. **`source_state` is truth; `last_event` is history**, and the divergence is surfaced as an explicit `[drift: 154177→154180]` mark rather than silently resolved in favour of one of them. The deeper problem is that events cannot survive a session boundary at all: the transport is fire-and-forget, so an event emitted while no channel consumer is bound is gone permanently; pollers are processes and die with the machine or a cleared `/tmp`; and pollers stop themselves on terminal state by design. At the start of a session an event-driven view therefore knows *nothing* — and "knows nothing" renders identically to "everything is green", which is the failure that makes a monitoring tool untrustworthy, because it is quiet either way and the user cannot tell which. So `radar` is an idempotent reconcile rather than a printer, safe to run on every session start: **one** `gl-mrs` query for open MRs is the authoritative input (state files are cache and may be absent or hours stale, so they never decide what is open or what is red), terminal state files are pruned, drift is flagged, and — the step that makes coverage survivable — a watcher is respawned for every open MR that has no live poller, covering reboot, crash, a cleared `/tmp`, and MRs that were green when watchers were last spawned, in one action. Rows render through the same `_row` helper as `gl-mrs` so there is one definition of the board format, with `[healed]` and `[unwatched]` marks appended for the two signals only radar can report. Output is the full board on cold start and delta-only afterwards, where *nothing moved* means the set of open MRs is unchanged, no MR changed pipeline status, pipeline id, draft or conflict flag, and radar itself pruned, healed and drifted nothing. Two deliberate exceptions to delta suppression: a standing failure or conflict is re-printed even when unchanged, because an unfixed red is a current fact rather than history; and a run where nothing moved still prints one summary line (`radar: no change | 7 open | 7 watched`) instead of nothing, because total silence is indistinguishable from a radar that failed to run — the exact defect the op exists to remove. For the same reason an unreachable or unauthenticated GitLab is a hard error with no board printed and nothing pruned or healed, never an empty green board. Part of [#417](https://github.com/Digital-Process-Tools/claude-supertool/issues/417).

- **A `\\` at the end of a line in a shell script is flagged.** The trap is that getting the escaping wrong does not always fail to match — sometimes it writes. In bash, `FOO=$(cmd \\` followed by a newline is an escaped backslash and then a new command, not a line continuation: it is syntactically valid, passes `bash -n`, passes the `bash-check` validator, and does something entirely different from what was meant. No syntax validator can see it; only the byte pattern can. The check runs at `_atomic_write`, the one place every mutating op passes through, and is scoped to `.sh`/`.bash`/`.zsh`/`.ksh` — a trailing `\\` is ordinary in Python, C or JSON. Bash consumes trailing backslashes pairwise from the left, so **parity** decides: an even run ends the line, while an odd run leaves one over to continue it. Only even runs are flagged, which means a single trailing backslash *and* a run of three — one escaped backslash plus a genuine continuation — both stay quiet. A backslash followed by trailing spaces or tabs gets its own warning at any parity: the escape applies to the space, so the line ends there whatever was intended, and the difference is invisible in a diff. The queue is keyed by path, so a validator rollback retracts the warning for the content it just reverted — a warning about bytes no longer on disk would be worse than none — and it un-counts the write with it, since a change that did not stick leaves no diff to read the arguments from. In practice it fires on the `@payload` route, where TOML literal strings preserve backslashes verbatim; the colon CLI decodes escapes before the write, so the pattern never reaches the file. Part of [#380](https://github.com/Digital-Process-Tools/claude-supertool/issues/380).

## [0.21.0] - 2026-07-25

### Fixed

- **Validator cache replayed results from a tool that had since been fixed.** The key was `sha256(file_content) + name + cmd` — it described *what was analysed*, never *what did the analysing*, so a fixed analyser and the buggy one it replaced produced identical keys. Upgrading `mcp-phpstan-warm` 0.6.0 → 0.7.0 (two reflection-staleness fixes) and re-running the exact repro still served 0.6.0's wrong answers, in 0.2s, without launching a worker at all; the 24h TTL meant that persisted for a day per affected file. The key now includes a **tool fingerprint**: `size` + `mtime_ns` of every `cmd` token that resolves to a real file, plus `fingerprint_paths` (per validator) and `validator_fingerprint_paths` (project-wide — this is where a lockfile belongs, since composer bin proxies and similar wrapper launchers are byte-identical across versions). Missing paths weaken the fingerprint rather than disabling the cache; fingerprints are memoised per process, so the cost is a handful of `stat` calls per run. Token extraction unions a naive whitespace split with `shlex` (POSIX mode off on Windows): `shlex` treats `\\` as an escape, so a Windows path shredded into a token matching no file — every cmd token contributed nothing and the fingerprint silently degraded to a constant on Windows, which is the exact failure this change exists to prevent. A backslash is a legal POSIX filename character, so the regression test reproduces it on every platform.
- **`between:SYMBOL` now accepts a symbol written the way it reads in source.** `between:async function fillAndSubmit` and `between:function getReorderEntityHasFileComponent` both returned `symbol not found`, even though both definitions exist — the tree-sitter matcher compares against the bare node name, so any leading keyword (`async`, `function`, `def`, `class`, `public static function`, …) or trailing `(params)` made the lookup miss. Since the natural thing to paste is the signature as it appears in the file, the op's own success path was the one you had to know not to use; both misses fell back to grep+read. The query is now normalized (modifier keywords stripped, everything from the first `(` dropped) and retried — **after** the exact match, so a symbol that genuinely is a keyword (`between:function`) still resolves literally. A miss now reports both forms tried. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).
- **`grep` no longer dumps a pathological single line in full.** One hit inside a 7KB one-line `@extends CommandGetAssetLoansBase<array{…}>` PHPDoc emitted the whole line — a screenful of context for a single match, in the op called most per turn. Match and context lines are now capped at `grep.max_line_chars` (default 500, or `SUPERTOOL_GREP_MAX_LINE_CHARS`) and the remainder is reported as `… (+N chars)` so the reader can widen deliberately instead of paying for it by accident. Normal-width lines are untouched. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).
- **`glob` retries a mid-path segment before reporting zero.** `grep` accepts `SiBrief/…` for a directory nested under `Dvsi/dvsi-private/src2/`, but `glob:SiBrief/**/*.class.php` resolved relative to the repo root and returned `(0 files)` — the same mental model, two different answers, and the zero reads as "nothing there" rather than "wrong anchor". A pattern that contains `/`, isn't already anchored (`/`, `~`, `**`, `./`, `../`) and matches nothing is now retried once as `**/PATTERN`; a hit prints a `[mid-path retry: …]` line naming the pattern that actually ran, so the rewrite is never silent. A genuine zero stays zero. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).
- **cwd drift recovers instead of dying.** After a `cd` into a subdirectory (a Playwright run, a package build), the next call with a repo-root-relative path failed with `path not found: X (cwd: Y) — wrong CWD?` and cost two round-trips: read the error, retry with `cwd:`. `main()` now probes for the drift in the same pre-pass that handles `cwd:` and chdir's to the project root, printing `[cwd auto-resolved to project root: …]`. The trigger is deliberately narrow — an ancestor directory must carry a `.supertool.json` (explicit project marker), **no** path-shaped arg may resolve against the current cwd, and at least one must resolve against that root — so a subdirectory-relative call is never hijacked. An explicit `cwd:` op still wins; `@` payloads, flags, absolute paths and wildcards are ignored when probing. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).

- **`gl-pipeline` now parses glab's `--paginate` concatenated multi-document JSON** — a pipeline with enough jobs to paginate made `glab api --paginate` emit one JSON array *per page* back-to-back with no separator (`[{job1}][{job2},{job3}]`), and the single `json.loads` on that stream choked on the second `[`, so `gl-pipeline` failed with `invalid JSON from glab` on exactly the large, slow pipelines you most want to inspect. A new `_parse_paginated_json` walks the string with `JSONDecoder.raw_decode`, consuming one document at a time and flattening every page's array into a single job list — robust to the common single-page case, to inter-document whitespace, and to empty `[]` pages. The detector now special-cases a leading `[[` as TOML before the generic `{`/`[` → JSON rule, so batch payloads written in TOML's `[[ops]]` form parse correctly. A single-object `[` (a real JSON array) is unaffected. Note the one narrowing: a JSON payload whose first two characters are `[[` (an array whose first element is an array) is now read as TOML — not a shape any op payload takes, since ops are objects. Detection alone was only half the fix: `tomllib` is stdlib from 3.11, and below that the bundled fallback parser explicitly supported no tables, so a correctly-detected `[[ops]]` payload then died in it with `bad key at offset 0` on Python 3.9/3.10. The fallback now parses `[[table]]` array-of-tables headers, and rejects a single `[table]` with a message that says so instead of complaining about a bad key. Closes [#357](https://github.com/Digital-Process-Tools/claude-supertool/issues/357).
- **`git-push`'s non-fast-forward recovery now rebases onto `FETCH_HEAD`, not `origin/<branch>`** — when the remote had moved ahead, the auto-rebase recovery ran `git rebase origin/<branch>`, but the recovery's own one-shot `git fetch origin <branch>` only populates `FETCH_HEAD` — it updates the remote-tracking ref `refs/remotes/origin/<branch>` *only* when a fetch refspec is configured. A fresh worktree or a refspec-less clone (exactly where you hit a first-push non-fast-forward) has no such ref, so the rebase aborted with `fatal: invalid upstream 'origin/<branch>'` and left the push stuck with no recovery. It now rebases onto `FETCH_HEAD`, which the fetch guarantees is present and points at the same commit — so recovery works in a plain clone and a fresh worktree alike. The incoming-commits preview reads from the same `FETCH_HEAD` ref for consistency. Closes [#354](https://github.com/Digital-Process-Tools/claude-supertool/issues/354).
- **Two `@-` (stdin) ops in one call now error clearly instead of an opaque parse failure** — `./supertool 'edit:@-' 'edit:@-'` made both ops call `sys.stdin.read()`; the first drained the single stream, so the second read empty and died with `@file ... parse error (<stdin>): Expecting value: line 1 column 1`, naming neither the real cause (the stream was already consumed) nor the fix. main() now detects more than one `op:@-` in a pre-pass — sibling to the existing `cwd:` pre-pass, before any dispatch — and exits with `stdin: only one '@-' op is allowed per call (got N: ...)`, listing the offending ops and pointing at the two escape hatches: give all but one a real `@file` path, or fold them into a single `batch:@-` ops array. A lone `@-` (the common case) is unchanged; a bare `@-` arg with no `op:` prefix isn't counted. Closes [#341](https://github.com/Digital-Process-Tools/claude-supertool/issues/341).
- **An MCP server's own timeout no longer surfaces as a phantom `+1` diagnostic** — after an edit, `lsp-diag` reported a `0 → 1` count where the single "diag" was actually `orchestrator timeout after 3s`, an infrastructure condition, not a code finding (phpstan had already covered the same file clean). The cause: cclsp swallows its *internal* LSP-orchestrator timeout and returns it as normal MCP text content with the `isError` flag unset — so it flowed through the shared dispatch as a real result and the lsp-diag adapter counted it as an advisory, reading like the edit introduced a regression. Detection now lives in the shared `_mcp_call_or_message` (so every MCP-backed op — `diag`/`hover`/`rename` — benefits, not just lsp-diag) with two signals: the structural MCP `isError` flag (spec-standard, any server) and a configurable per-server `infra_patterns` substring list (default `["orchestrator timeout", "timed out after"]`) for servers that report timeouts as plain text. A matched result is returned prefixed `op: …` — the same shape as supertool's own MCP errors — so the adapter's existing `op:`-prefix guard drops it instead of counting it. No count delta, no false regression, and the timeout value itself stays per-server configurable via `mcp.<name>.timeout`. Closes [#346](https://github.com/Digital-Process-Tools/claude-supertool/issues/346).
- **`rector-mcp` engine-glitch suppression is config-driven and now catches `toMutatingScope() on null`** — the warm rector daemon intermittently trips a PHP fatal inside rector's own engine (`Call to a member function toMutatingScope() on null`), a non-deterministic glitch a cold `rector` CLI does not reproduce. Like the June `System error: ClassReflection` case it surfaced as a false red *and* — because the validator cache keys on file content — froze into the cache and replayed on every later run until the file changed (the 2100-poisoned-entries failure mode, new signature). The fix moves glitch knowledge out of the core and into the adapter: the core had been string-matching `System error:` in `_validator_result_is_cacheable`, violating `SCHEMA.md`'s "validator core never parses tool-specific output". That branch is removed — the core cache filter is now fully generic, keying only off non-deterministic error *codes*. Tradeoff: the core no longer has a message-level backstop, so a brand-new, uncatalogued glitch signature can still reach the cache as a `rector.error` until it is added to the config list — the same failure mode, now bounded to *unknown* signatures and fixed by a one-line config edit rather than a code change. Signatures live as a config prop, `validators.rector.engine_glitches` in `.supertool.json` (a JSON list of case-sensitive substrings the adapter reads straight from `.supertool.json` — no env, the same file `daemon.py` already reads from cwd), defaulting to `["System error:", "toMutatingScope() on null"]` when absent. The adapter drops a matching error at the source, so a glitch never surfaces or reaches the cache; a new signature is a one-line config edit, not a code change. Part of [#345](https://github.com/Digital-Process-Tools/claude-supertool/issues/345).
- **`git-diff:PATH` no longer reports a missing/untracked path as "No changes."** — a path absent or untracked in the current repo produced an empty diff that printed `No changes.`, indistinguishable from a clean tracked file. Combined with a stale CWD (e.g. a `cd` into another repo) this is a silent false-negative: the op reads as "nothing changed" when it actually looked in the wrong place. Path mode now checks `git ls-files` first — a missing path warns `not found under <cwd> — wrong CWD?` and exits 1, an untracked on-disk path warns `untracked (not in git)`, and only a genuinely clean tracked file still says `No changes.`. Every mode also stamps a `Repo: <toplevel>` header so a wrong-repo invocation is visible at a glance (the trigger: `git-diff:.supertool.json` silently returned "No changes" while anchored to the wrong clone). Closes [#336](https://github.com/Digital-Process-Tools/claude-supertool/issues/336).
- **`grep` path-not-found error now includes the CWD** — `ERROR: path not found: <path> (cwd: <cwd>) — wrong CWD?` instead of the bare path, so the recurring "stale cwd makes a relative path silently miss" trap is diagnosable from the message alone. Part of [#336](https://github.com/Digital-Process-Tools/claude-supertool/issues/336).
- **`git-commit` no longer aborts on an already-staged deletion** — listing a `git rm`'d path (gone from disk) alongside present files made the op's `git add` step fail with `pathspec did not match any files`, killing the whole commit. The op now drops paths that are already staged as deletions from the `git add` step (their deletion is already staged and gets committed), so a mixed changeset of modifications + new files + deletions lands in one commit. Genuinely-unknown paths still error as before. Closes [#324](https://github.com/Digital-Process-Tools/claude-supertool/issues/324).

## [0.18.0] - 2026-06-23

### Fixed

- **`git-push` no longer misreports a pre-push hook's amend-and-push as `PUSH REJECTED`.** A pre-push hook that auto-formats commonly amends HEAD, pushes the corrected commit itself, then exits non-zero so git won't also push the stale pre-amend ref — that non-zero is *success*, not failure. `git-push` now trusts the live remote SHA (`ls-remote`) over the exit code: when the remote already matches local HEAD it reports `PUSHED (pre-push hook amended HEAD)` with the rewritten SHA, instead of `REJECTED`. And `_first_error_line` no longer picks a green `✅ … 0 errors` / `pushed successfully` line as the "first error" (the substring `errors` was matching the error scan). Closes [#297](https://github.com/Digital-Process-Tools/claude-supertool/issues/297).

### Added

- **`git-push` embeds non-fast-forward recovery.** When the remote has moved ahead, `git-push` now fetches, surfaces the **incoming remote commits** (short SHA, author, subject — the signal for force-vs-integrate, since forcing over a teammate's commit destroys it) with the ahead/behind counts, then rebases your work onto the remote and re-pushes in the same call — no manual `pull --rebase` → `git-push` round-trip. Computing is cheap; LLM round-trips are not. On conflict it leaves the rebase **paused** (never silently aborted or force-pushed), lists the conflicting files, warns to check the incoming authors before forcing, and points at `git-conflicts` to inspect plus the exact keep-both / cancel (`git rebase --abort`) / force paths — the resolution stays the caller's decision.
- **`git-push` post-push receipt surfaces the next decision.** A push isn't the end of an action, it's the start of "get this MR merged" — so the receipt now carries the signals you'd otherwise spend round-trips discovering, all riding calls already made: **mergeability** (warns loudly if the MR now `cannot_be_merged` with its target — caught at push time, not 20 min later at merge), **stale base** (`N commit(s) behind origin/<target>`), **uncommitted leftovers** (`git status --porcelain` — the "I fixed two things, committed one, pushed" catch), the **pipeline id + url** on the MR line, and a ready **`watch:gitlab-mr:<iid>`** command to hand the pipeline to a background poller. `:force-with-lease` additionally reports **what it discarded** (author + subject of the overwritten remote commits — the receipt for "did I just nuke a teammate's work"). Watching stays opt-in: the receipt recommends the command by default; `git-push:watch` spawns the poller for the push you're actually iterating on (no stray daemons on WIP pushes).
- **`git-push:force-with-lease` and `git-push:no-verify` variants.** `:force-with-lease` is the safe force (overwrite only if the remote hasn't moved since you fetched) and suppresses the auto-rebase, since the force is your explicit decision; `:no-verify` skips the local pre-push hook, the documented escape when a local formatter legitimately diverges from CI. The op cmd switched from `{arg}` to `{args}` so the flag tokens reach the script. Part of [#297](https://github.com/Digital-Process-Tools/claude-supertool/issues/297).

### Fixed

- **Test suite no longer mutates the repo it runs in (corrupted working trees under the pre-push hook).** `TestGitcliFlagSmuggling::test_checkout_allows_dash_alone` ran `checkout.py -` via a `subprocess.run` with no `cwd=`, so it executed a real `git checkout -` (switch to previous branch) against whatever directory pytest was launched from. - **Validator cache no longer freezes transient engine failures.** `rector-mcp`'s warm daemon intermittently trips rector's own `System error: "ClassReflection must be resolved for class X"` reflection bug on test classes — warm-process-state dependent, not file dependent (a clean re-run and plain `rector` CLI pass the same file). Offline / fetch-fail / no-upstream cases warn and fall back to the local ref (no hard failure). Remote-tracking refs like `origin/master` are refreshed directly.

### Changed

- **`rector-mcp`'s `System error:` suppression is now defense-in-depth, not load-bearing.** The root cause behind the warm `ClassReflection must be resolved for class X` failures ([#273](https://github.com/Digital-Process-Tools/claude-supertool/issues/273)) is fixed upstream in `dpt/mcp-rector-warm` 0.4.0: the warm daemon reused one Rector container and never reset Rector's `DynamicSourceLocatorProvider`, which caches its source locator for every non-PHPUnit run — so the second file in a warm session was analysed with a locator that only knew the *first* file. The daemon now resets reflection state per call (matching `AbstractRectorTestCase`), so this branch should no longer fire. The adapter comment was updated to reflect that it remains only to absorb any future non-deterministic engine glitch. **Requires `dpt/mcp-rector-warm` ≥ 0.4.0** (`composer global update dpt/mcp-rector-warm`).

## [0.14.0] — 2026-05-23

### Added

- **`validators/pyright/`** — Python type-check via `pyright --outputjson`. Sits next to `py-compile` (syntax-only). Hooks into `edit/replace/replace_lines/paste/vim` for `*.py`. Graceful skip when `pyright` not on PATH; pyright JSON 0-indexed `range.start` is converted to supertool's 1-indexed `line/col`. Configure via `.supertool.example.json`. README validator count bumped to 18.

### Security

- **`op_paste` containment ordering.** Previously `op_paste` called `os.makedirs(parent)` BEFORE `_atomic_write`'s `_safe_path` check, so a traversal path like `../../tmp/evil/foo` would create directories outside cwd before the write itself was rejected — leaving empty-dir pollution. `op_paste` now runs `_safe_path` at entry. Side benefit: closes the NUL-byte-in-path xfail (`_safe_path` rejects NUL before `os.replace` can leak a `ValueError`).

### Security

- **Hardening bundle.** Smaller defence-in-depth items from the audit (closes [#150](https://github.com/Digital-Process-Tools/claude-supertool/issues/150)):
  - **Gitcli flag smuggling**: `git-checkout REF`, `git-merge REF`, `git-blame PATH` reject refs/paths starting with `-` (e.g. `--orphan=evil`, `--abort`, `-X theirs`). `git-blame` uses `--` separator to keep a path-with-dash from being parsed as a flag.
  - **Regex ReDoS guards** on `grep`: pattern length capped at 1000 chars; nested unbounded quantifiers (`(a+)+`, `(.+)*`) rejected before they touch file content.
  - **`validate_staged` / `format_staged`** use `git diff -z --diff-filter=ACMR` (filenames with newlines/quotes survive) and reject symlinks — a staged symlink to `/etc/hosts` would otherwise be REWRITTEN by formatters.
  - **`xmllint` validator** runs with `--nonet --noent` so libxml2 can't fetch external entities or follow URI references during validation (XXE defence-in-depth).
  - **Validator cache HMAC** at `~/.cache/supertool/.cache_key` (mode 0600, 32 random bytes, generated on first use). Each cache entry wrapped with HMAC-SHA256 of its body. Attacker with write access to `~/.cache/supertool/validators/` cannot forge a passing `ok: true` entry without also reading the secret. Legacy unwrapped entries treated as miss.
- **Social publishing safety.** Three guards for the dev.to / bluesky publish + comment ops (closes [#149](https://github.com/Digital-Process-Tools/claude-supertool/issues/149)):
  - `file://` body must resolve under `.max/`, `drafts/`, `posts/`, or `blog/` (relative to cwd). Closes the credential-exfil vector: `bluesky_publish:file:///Users/.../app_password` now rejected before the file is read. Extend additively via `$SUPERTOOL_PUBLISH_BODY_ALLOWLIST=path1:path2` or `"publish_body_allowlist": [...]` in `.supertool.json`.
  - Confirm-default — `bluesky_publish` / `devto_publish` refuse to run without `|force`, `SUPERTOOL_NO_PUBLISH_CONFIRM=1` env, or `"no_publish_confirm": true` in `.supertool.json`. Blocks single-shot publish from a prompt-injected op.
  - Token-file mode check — `check_token_file_mode` refuses to load tokens at mode 0644+ (group/world-readable). Mirrors `ssh`'s SSH-key check.
- **MCP daemon UDS hardened.** Socket + pidfile + log moved from `/tmp/supertool-mcp-<hash>.{sock,pid,log,stderr}` (world-writable parent dir, predictable hash) to per-user runtime dir (`$XDG_RUNTIME_DIR/supertool/mcp/` on Linux, `~/Library/Caches/supertool/mcp/` on macOS, `~/.cache/supertool/mcp/` fallback). Dir created mode `0700`, ownership-checked at startup. Pidfile + log files open with `O_NOFOLLOW|O_CREAT|O_EXCL` so symlink-squatting attacks no longer overwrite victim files. Peer-uid check on every accept (defence in depth on top of parent-dir perms). Server names validated against `[A-Za-z0-9_-]{1,64}`. `os.umask(0o077)` reset in detach. Override via `$SUPERTOOL_RUNTIME_DIR`. Closes [#148](https://github.com/Digital-Process-Tools/claude-supertool/issues/148).
- **Vim shell verbs gated.** `:!cmd`, `:%!cmd`, `:N,M!cmd`, `:r !cmd` are disabled by default. A prompt-injected vim payload like `:!rm -rf ~` is rejected with a clean error. Editor verbs (i/a/o/d/s/etc.) are unaffected. Opt-in via `SUPERTOOL_ALLOW_VIM_SHELL=1` (env) **or** `"allow_vim_shell": true` in `.supertool.json`. Closes [#147](https://github.com/Digital-Process-Tools/claude-supertool/issues/147).
- **`:r FILE` honours cwd containment.** Vim's `:r FILE` (without `!`) now routes through `_safe_path` — reading `/etc/passwd` or `~/.ssh/id_rsa` into the buffer is rejected. Opt-out is the same `SUPERTOOL_ALLOW_OUTSIDE_CWD=1` as the rest of #146.
- **Path containment (`_safe_path`).** Every op path arg now resolves under cwd. A malicious `.supertool.json` or prompt-injected op like `paste:~/.ssh/authorized_keys:::pwned` or `read:/etc/passwd` is rejected with a clean error. Symlinks crossing the boundary are caught (realpath follows them). NUL bytes rejected early. Closes [#146](https://github.com/Digital-Process-Tools/claude-supertool/issues/146).
- **Opt-out**: set `SUPERTOOL_ALLOW_OUTSIDE_CWD=1` (env, one-off) **or** `"allow_outside_cwd": true` in `.supertool.json` (project-pinned, no env var dance). Env takes precedence.
- **Default excludes extended**: `.env`, `.env.*`, `.max/`, `.ssh/`, `.aws/`, `.gnupg/`, `.kube/`, `.docker/`, `.terraform/`, `.chef/`, `.npm/`, `secrets/`, `credentials/` are now pruned by `grep`/`glob`/`tree`/`map` so tokens don't surface into an LLM's context.
- Windows-compat: `os.path.normcase` handles case-insensitive drive letters (`c:\Users` == `C:\users`) and separator normalization.
