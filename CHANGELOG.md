## [Unreleased]

### Fixed

- **The post-edit syntax guarantee is now a guarantee for Python, instead of a description of a validator someone might have configured.** `edit`/`replace_lines`/`paste`/`vim`/`append` are documented — and recommended over an ordinary editor — on the strength of one sentence: *validators run post-edit and roll back on a syntax failure*. Twice in one evening, on two `.py` files in two different worktrees, a `replace_lines:@payload.toml` whose TOML content ended in a backslash-quote wrote an unterminated string literal into the file and the receipt said `lsp-diag : ok (no new errors)`. Nothing rolled back; `pytest` was what caught both, turns later. Closes [#477](https://github.com/Digital-Process-Tools/claude-supertool/issues/477).

  **The mechanism was not a miss, it was an absence.** `lsp-diag` ran, succeeded, and honestly reported what it knows — which is nothing about parsing. It is a *semantic* diagnostics adapter over a warm Pyright daemon, and it carries `rollback_on_fail: false`, so even a correct detection could not have reverted the edit. Instrumenting it showed a second layer: a `.py` file Pyright had never opened gets its syntax error reported immediately, while a file already in the daemon's document set comes back clean with diagnostics from the *pre-edit* content — and the framework's own before/after baseline pass is what opens it. So the check was strongest on files it had never seen and blind on the ones it had just been asked about. Nowhere in this repository's validator chain did anything ask "does this parse?": `py-compile` ships in `validators/` and was never registered.

  **The fix is a check the tool owns rather than one the config supplies.** `py-syntax` is built into supertool: it runs `compile()` in-process on every mutating op against a `.py` file, needs no configuration, no toolchain and no daemon, costs microseconds, and cannot be stale because there is no cache and no second process. It reverts **regressions only** — a file that already did not parse can still be edited, a broken file can be repaired, and it stands down entirely when the repo declares its own validator with `"syntax": true` for the same path. Anything it cannot answer (unreadable file, unknown builtin kind) returns `skipped`, which the framework already refuses to count as clean and refuses to roll back on ([#406](https://github.com/Digital-Process-Tools/claude-supertool/issues/406)).

  **The framework-level fix the issue proposed was already in place, and would not have caught this.** `_validator_regressed` has distinguished *clean* from *could not check* since #406 — three states, not two. That is why the defect survived: `lsp-diag` never claimed it could not check. It returned a verdict, and the verdict was wrong. A tool that can only tell you when a checker declined to run cannot help you when the checker answers confidently about the wrong version of the file, which is the failure mode that actually occurs. Distinguishing skip from clean is necessary and was not sufficient; something in the chain has to be able to answer the question.

  **Scope, stated plainly: this covers Python and nothing else.** The interpreter running supertool parses Python for free and parses nothing else without a toolchain that may not be installed, so `.php`, `.ts`, `.json` and the rest still roll back only where `.supertool.json` declares a matching validator with `rollback_on_fail: true` — unchanged behaviour, now documented as the opt-in it always was rather than implied to be universal. `README.md`, `docs/operations/edits.md` and `docs/validators.md` all stated the guarantee without that qualification and have been corrected, because that wording is what gets pasted into agent briefs. `.supertool.example.json`'s `py-compile` entry gains `"syntax": true` so the backstop defers to it. The `lsp-diag` staleness is real and is left alone here: it is a document-sync bug in the MCP/LSP layer, it is advisory-only by config, and the parse check no longer depends on it being right.

### Added

- **`gc`: supertool prunes its own caches, and the preview is the default.** On a daily-driver machine `~/.cache/supertool` reached **1.0 GB across 242,000 files in about two weeks** — `vim-cursor` 499 M / 125,953 entries, `vim-undo` 471 M / 116,201, `validators` 73 M / 18,555 — and `grep -rn` over the tree found writers for every one of them and a reaper for none. The file *count* is its own defect: both `vim-*` directories exceeded the 65535-dirent listing cap, which makes an ordinary `ls` on them visibly slow. Pruning by hand took the tree to 83 M. Every write path there is supertool's, so the retention policy is too — a user should not discover this by opening Activity Monitor.

  **The trigger is a stamp file, not a dice roll, and that is a deliberate departure from the issue's proposal.** [#474](https://github.com/Digital-Process-Tools/claude-supertool/issues/474) proposed a probabilistic sweep — roughly one write in N — for the amortised cost and the absence of a daemon. It buys both, and pays for them in the two currencies this repository has been most careful with: a probabilistic trigger is **non-deterministic to test** (every test either monkeypatches `random` or asserts on a distribution) and **non-deterministic to explain** — "why did that one call take 400ms?" has no answer a user can check. `_maybe_auto_gc` gates on the mtime of `~/.cache/supertool/.gc-stamp` instead: one `stat` per invocation, at most one sweep per `interval_seconds` (default 3600), same amortisation, and the answer to the 400ms question is a file the user can look at. The stamp is written **before** the sweep rather than after, so a sweep that dies does not re-arm itself on every subsequent invocation for the rest of the day, and the whole function is wrapped so that nothing it does can propagate — **a cache prune that raises during someone's edit is a worse bug than the disk usage it was cleaning up.**

  **Retention is per cache kind, because the measurement per kind differs.** `vim-cursor` and `vim-undo` default to **7 days**: 99% of both populations was older than that, and that is where the gigabyte lives. `validators` defaults to **30 days**, and the reason is the whole argument for not picking one number — it was measured with **zero** entries older than 7 days, it is invalidated by a content hash plus a tool fingerprint rather than by age, and it is correctly sized at 73 M. A single 7-day default would have evicted a hot cache to reclaim nothing, which is a real cost (every evicted entry is a re-run analyser) paid for no benefit. 30 days is therefore a deliberate no-op against the measured population: it exists to bound unbounded growth, not to reclaim anything today. All four windows are configurable per kind under a `gc` block in `.supertool.json`; `0` or negative means **never prune this kind**, because a window of zero would delete a cache wholesale and that is never what someone typing `0` means.

  **An entry whose age cannot be determined is kept, and counted.** A failed `stat`, a dangling symlink, an mtime in the future from clock skew or a restored backup — none of them are evidence of staleness, so none of them are deleted. They land in a `skipped` column that is printed on every run rather than swallowed, since the alternative is a cache that quietly accumulates entries GC has silently decided it cannot reason about. Directories and non-regular files are skipped the same way, and the sweep never recurses: `gc` opens the four kind directories by name and nothing else, so subdirectories, the `.cache_key` HMAC secret that #150 put there, and any directory supertool does not own are structurally out of reach rather than excluded by a filter someone could widen.

  **The unlink is `os.unlink` over `os.scandir`, and the issue is right that this needs saying.** BSD `find -delete` and `find -exec rm {} +` both silently no-opped on macOS in the reporter's environment while a plain `rm` on the same path succeeded — **269 files that `find` had just listed as matching were left untouched, with no error and a zero exit.** A deletion tool that reports success without deleting is the worst possible shape for this feature, so there is no shell-out at all, and a test asserts it by making `subprocess.run` and `subprocess.Popen` raise and requiring the deletion to still happen.

  **`gc` and `gc:dry` preview; only `gc:run` deletes.** Deleting 244,000 files is not reversible, so the bare op is the safe one: it reports per-kind counts and bytes plus a total, names the retention window it used (so "nothing was removed" is explainable rather than mysterious), and prints the exact command that would delete. `gc:run:KIND` scopes a real sweep to one cache; an unknown kind is an error that lists the kinds that exist. **The retention boundary was pinned with a test written before the implementation**, per the issue: a file at `now - retention - 1s` is removed and one at `now - retention + 1s` is kept, with a third asserting the entry exactly *at* the boundary is kept — off-by-one on a retention window is how a hot cache gets wiped. 26 tests total.

  Two seams were tidied to land it. `~/.cache/supertool` had been spelled four times in three shapes — two XDG-aware, two `Path.home()`-based — which meant `XDG_CACHE_HOME` moved the vim caches and not the validator cache; all four now resolve through one `_cache_root()`, without which a GC scanning "the" cache directory would have been scanning a different one from the writers. And the suite sets `SUPERTOOL_GC_DISABLE=1`, because a feature armed on every invocation would otherwise reap the developer's real cache as a side effect of running the tests. Closes [#474](https://github.com/Digital-Process-Tools/claude-supertool/issues/474).

- **`first_tick` on the watch event record: a watcher's bootstrap emission no longer arrives shaped exactly like news.** Widening the `radar` filter to a second author spawned watchers that immediately emitted `pipeline_succeeded` for pipelines #153311 and #153163 — six and seven days old — plus a `conflicts_appeared` for a conflict nobody had touched. Nothing was wrong with emitting them; **emitting on first tick is the feature**, it is how a new watcher reports an already-red MR and it is what [#430](https://github.com/Digital-Process-Tools/claude-supertool/issues/430) and [#434](https://github.com/Digital-Process-Tools/claude-supertool/issues/434) are built on. The defect was that the `<channel>` record carried nothing separating "this is what I found when I started" from "this just happened", so a session reported week-old outcomes as current and the first minute after any filter change was pure noise — which is a live disincentive to widen the filter, and widening it is what surfaced a week-old conflicted dependency bump on a payment path nobody was chasing. Every record now carries `first_tick: true|false`, set by the dispatcher and keyed on **state rather than process age**: a poller restarted with its state file intact is resuming, not bootstrapping, and marks nothing.

  **The locked payload was the constraint, and it did not move.** `docs/presets/watch.md` documents the event record as a locked contract and #434 was careful to state its change left the wire shape untouched — no field added, removed or retyped. Adding a marker breaks that claim unless the addition is made deliberately and in writing, so `first_tick` sits **beside** `ts`/`source`/`id`/`event` and not inside `payload`: it describes the emission the way `ts` does, not the thing that happened, which keeps every source's payload and every key in every `events.json` meaning exactly what they did. The bar for the addition was that **a consumer ignoring the new field must not be made wrong by it, only uninformed** — same event key, same payload, same `ts`, nothing dropped, delayed or deduplicated, so the old firehose is available verbatim by ignoring one key.

  **A separate event key for bootstrap state was the obvious alternative and is the reason this is a field.** `only=` filters name real event keys, so routing first-tick state to `pipeline_succeeded_initial` would have silently withheld it from every consumer already filtering — turning a cosmetic gap into the silent-omission class this repository has spent the week removing, and breaking the #430/#434 bootstrap they depend on. Carrying it in an existing field was rejected for the mirror reason: overloading a field's meaning makes the ignoring consumer *wrong* rather than uninformed. It is emitted as `true`/`false` on **every** record so no consumer has to decide what an absent key meant — with one deliberate exception at the `claude-channel` bridge, where the attribute is omitted when the poller did not send one, because an old poller has not told us the event was live and that is unknown, not false. The bridge also gives Claude the distinction in prose (`first_tick="true"` → report as context, not as news), since a marker the consumer drops is a marker that does not exist. Closes [#464](https://github.com/Digital-Process-Tools/claude-supertool/issues/464).

- **`radar` standing exclusions: a permanently-red row you can stop rendering without stopping counting.** `!19509` (`feature/max-blog`) is permanently conflicted against `master` and its pipeline fails on a MySQL service TLS issue rather than on anything in the MR. It appeared on every `radar` render and every session-start board for four hours, suppressed only because the operating instructions said "always ignore !19509" — the suppression lived in the reader's memory. That is the wrong place for it, and not because it is inconvenient: **a permanently-red row that must be mentally filtered is precisely what trains someone to skim the board, and skimming is how a real red gets missed.** `ops.radar.radar_exclusions` in `.supertool.json` (`{iid: reason}` or `{iid: {reason, until}}`, merged into the op the same way `ops.gl-job.job_patterns` is, arriving as `SUPERTOOL_RADAR_EXCLUSIONS`) moves the rule into the tool.

  **The whole design problem is that an exclusion is itself a way to hide a real failure**, and this repository has spent the week removing exactly that shape: `## No error patterns matched` on a crashed job ([#445](https://github.com/Digital-Process-Tools/claude-supertool/issues/445)), a check tally that dropped cancelled legs ([#454](https://github.com/Digital-Process-Tools/claude-supertool/issues/454)), a delegated grep reporting a truncated count as exhaustive ([#414](https://github.com/Digital-Process-Tools/claude-supertool/issues/414)). An excluded MR that simply vanished would be a better-engineered version of the same defect, and worse than all three, because it would be deliberate and configured — so nobody would go looking for it. **The row goes; the MR does not.** The footer carries an `N excluded` token and one line names each suppressed MR, its *current* status (`failed` / `conflict` / `failed+conflict`, so a suppressed MR picking up a second problem changes what the board says without un-suppressing it) and its configured reason — printed on every run, including a delta-suppressed one, since making the suppression itself invisible would rebuild the original problem one level up. The issue asked for excluded MRs to leave the summary counts too, and that half is honoured for a reason of its own: `3 open | 1 failing` above a board with two rows and no red is a dangling reference that sends the reader hunting for something deliberately removed. So the tallies describe the board that was printed and `N excluded` restores the total, which is arithmetic a reader can check rather than a number they must trust.

  **An exclusion cannot outlive its reason, and that is enforced rather than documented.** It only ever suppresses a *standing problem*: the moment the MR is green and unconflicted the suppression lifts by itself and the board prints `NOT applied — the reason is spent`, so the mechanism is structurally incapable of hiding an MR that is fine or a transition back to green. The same line appears for an expired optional `until` date and for an iid that has left the population — dead config is the quiet half of staleness, suppressing nothing today and something real the day that iid returns. `reason` is **mandatory**, because the field that makes an exclusion auditable is the same field that makes it work; an unreasoned entry is refused and its row renders. Every unanswerable case — unparseable JSON, a non-iid key, an unknown value shape — resolves to *show the row* and say why, the same bias `presets/_proc.py` encodes when an unanswerable liveness question resolves to *not alive*.

  **An exclusion is board-only, deliberately breaking [#430](https://github.com/Digital-Process-Tools/claude-supertool/issues/430)'s one-filter symmetry.** The filter says what radar is *responsible for*; radar does not stop being responsible for an MR because its row is noisy. So an excluded MR is still healed into the watcher fleet, still covered by the feed, still written to the snapshot (otherwise lifting the exclusion reports a months-old MR as new), and its watcher still emits the full `DEFAULT_ONLY` event set with notifications intact. The issue asked for events on excluded ids to be dropped and that half is **rejected on the merits**: a `pipeline_failed` event on an excluded MR means somebody pushed and a new pipeline ran, which is the one signal that can report an exclusion going stale while its row is suppressed — and since watcher events fire on transitions only, a genuinely dormant branch emits nothing anyway. Dropping them would buy no quiet and cost the staleness check. `unwatch` remains the separate, visible way to leave the fleet, and an excluded MR without a live poller has its exclusion line read `UNWATCHED` rather than `still watched`, so the feature never claims a coverage it does not have. **Automatic infra-failure classification was considered and rejected** as the alternative: a classifier deciding "this red is not your fault" is wrong in the confident direction, silently, for every MR, with no audit trail — #445 with more reach — and half of !19509's red is a merge conflict against `master`, which no trace-scanner can classify because it is a decision not to fix, not a detectable cause. Eighteen tests, every one asserting on emitted text rather than an internal count, since a footer that knows about an exclusion the board never mentions is the bug this feature was built to avoid becoming. `docs/presets/watch.md` documents the interaction with the one-filter invariant and the locked event payload, not just the config key. Closes [#447](https://github.com/Digital-Process-Tools/claude-supertool/issues/447).

### Changed

- **The encoding scan now covers `tests/` — for reads, and with no attempt to tell a repo path from a `tmp_path` fixture.** [#418](https://github.com/Digital-Process-Tools/claude-supertool/issues/418) fixed 69 locale-dependent reads and left a static scan behind, deliberately excluding `tests/` because the suite holds ~1670 `write_text()` fixture calls emitting ASCII and enforcing there would bury the signal. That reasoning covers fixture writes and not much else: a test that reads a **real repository file as data** — source, docs, a manifest — decodes whatever non-ASCII the project has accumulated with `locale.getpreferredencoding()`, so it is green on the author's machine and dead on the Windows leg. It went that way twice in one day, in tests written *after* #418 landed — [#431](https://github.com/Digital-Process-Tools/claude-supertool/pull/431) scanning preset source, [#460](https://github.com/Digital-Process-Tools/claude-supertool/pull/460) reading `docs/presets/watch.md`, both `UnicodeDecodeError: 'charmap' codec` on all four Windows legs, each costing a full CI round. The second is self-inflicted in a specific way: `watch.md` only holds the byte that broke it because the output work this week put a `⚠` in it, so the better the docs get the more reliably it trips.

  **The narrowing the issue proposed is the version that would have missed #431, and that is why it is not here.** Scoping the scan to reads whose target resolves inside the repository sounds like it keeps the 2300 fixture calls out while catching the handful that matter, and it is decidable for #460 — `(Path(__file__).parent.parent / "docs" / "presets" / "watch.md").read_text()` is rooted in `__file__` right there in the expression. It is not decidable for #431, whose read was `path.read_text()` on a **function parameter**, fed from `PRESETS_DIR.rglob()` at a call site in a different function. Any target-based rule is therefore interprocedural or it is silently incomplete, and an incomplete scan that reports clean is worse than no scan — it is the `## No error patterns matched` shape ([#445](https://github.com/Digital-Process-Tools/claude-supertool/issues/445)) relocated into the guard. So the distinction is dropped entirely: **every** read in `tests/` names its codec, including reads of files the test itself just wrote, which costs nothing and removes the whole class of question. **669 call sites in 76 files** were fixed to land it green — 553 `read_text()`, 116 `open()` — and the count is the guard's own red output, not an estimate.

  **Writes stay excluded on the merits, not for convenience.** That is where the ~1670 live, and a bare `write_text()` of an ASCII fixture cannot fail; the split is read/write rather than repo/tmp because that is the one boundary that is both decidable and load-bearing. Exactly one fixture in the suite writes non-ASCII, and it now names its codec, so read-side `utf-8` cannot mismatch a locale-written file on a cp1252 runner.

  **The runtime alternative was measured rather than estimated, and it is not viable here.** The issue's fallback — run the suite under `-X warn_default_encoding` with `EncodingWarning` promoted to an error, #418's own harness — catches every locale-dependent read at execution time regardless of where it lives, including the interprocedural one. Two findings. First, `-X` does **not** reach `pytest-xdist` workers, so the naive invocation reports a clean 4186-passed run that has tested nothing; only `PYTHONWARNDEFAULTENCODING=1`, which children inherit, actually arms it. Second, once armed it errors **4192 of 4224 tests** — and the cause is not the fixture reads. `subprocess.run(..., text=True)` calls `subprocess._text_encoding()` and warns on exactly the same seam, `tests/conftest.py`'s autouse `_guard_repo_git_state` fixture does one, and there are ~270 subprocess call sites in this repository. So the runtime route is not "noisy pending a cleanup", it is a different and much larger defect class wearing the same warning, and it deserves its own issue rather than a suppression here. `docs/contributing.md` records both the negative result and the invocation that produces it, since the next person to reach for that harness will otherwise reach for the version that silently passes.

  **What this does not catch, stated plainly.** It is a static scan, so it enumerates call sites and not executed lines — which is the half that keeps working for code written later, but it says nothing about `subprocess(text=True)`, nothing about a bare read that arrives via a helper in a non-test module, and nothing about `write_text()` of non-ASCII. It does meet the bar the issue set: a test added tomorrow that reads a repo file without `encoding=` fails on the author's machine, on Linux, and on Python 3.9 where `EncodingWarning` does not exist at all — no Windows runner required. Closes [#461](https://github.com/Digital-Process-Tools/claude-supertool/issues/461).

- **The test suite runs in parallel by default: 4m22s to 1m08s, a 3.9× cut.** `pytest-xdist` had been sitting in `[project.optional-dependencies].dev` unused, and the reason was not that nobody tried it — the suite did not survive `-n auto`, so the speedup was there and unreachable. It is a good fit for this suite specifically: 269 `subprocess.run`/`Popen` call sites across 60 test files put ~30% of the wall clock in the kernel, which is time the workers overlap rather than contend for. `-n auto` now lives in `addopts` rather than in CI's invocation, so the local inner loop, the pre-push hook and all twelve CI legs get it from one place and cannot drift apart — the thing worth avoiding is a suite that is green in parallel on CI and only ever run serially by contributors, since that is how the isolation bugs come back unnoticed. Three questions were checked rather than assumed. **Coverage still measures the whole suite**: pytest-cov combines the per-worker data files, and the parallel and serial runs report byte-identical output — 8302 statements, 957 missed, 88.47%, the same missing-line list — so the 86% gate is not passing on a fraction of the run. **CI is not an 11-core laptop**, and `-n auto` there resolves to the runner's 3-4 cores; the win is smaller but does not invert, because the constraint being relieved is process spawning rather than CPU, and even two workers overlap one test's `git init` with another's assertions. **Debuggability is the real cost**, and it is paid by contributors rather than by CI: xdist interleaves output and disables `--pdb`, so `docs/contributing.md` now documents `-n0` as the way back to a serial run, along with the rule that a test failing only under `-n auto` is a bug in the test and not a reason to reach for `xdist_group` or `--dist loadfile`. The `_guard_repo_git_state` fan-out — one violating test makes its concurrent neighbours report the same change as theirs — was left in place deliberately and documented at the fixture; both fixes for it (skip on every worker but `gw0`, or fingerprint once per session) hand back exactly the per-test attribution [#428](https://github.com/Digital-Process-Tools/claude-supertool/issues/428)/[#432](https://github.com/Digital-Process-Tools/claude-supertool/pull/432) was written to buy, to remove noise from a run that is already red. Closes [#433](https://github.com/Digital-Process-Tools/claude-supertool/issues/433).

### Fixed

- **`conflicts_appeared` fired on an MR with no commits and no diff, where nothing could conflict.** !33223 emitted one second after it was opened: zero commits, `changes: 0`, `sha: null`, `diff_refs` with a null base and head — and `has_conflicts: true`. The event was then reported to the human as a real conflict and a plausible, entirely false explanation was built on top of it (a bot filing a duplicate MR that conflicted with its own earlier one, since another open MR shared the title). That is the specific hazard and it is worse than noise: **a false `conflicts_appeared` does not read as noise, it reads as a fact**, and an agent consuming it reasons forward from it. Distinct from [#463](https://github.com/Digital-Process-Tools/claude-supertool/issues/463), where a genuine conflict re-fired; here the conflict never existed.

  **`has_conflicts` is not a conflict field, and GitLab says so in its own source.** The API entity exposes it as a straight alias for `cannot_be_merged?`, annotated: *"#cannot_be_merged? is generally indicative of conflicts … However, it can also indicate that either #has_no_commits? or #branch_missing? are true."* So the field lies in exactly one direction — an MR with no diff — and that narrows the fix considerably. It is **not** "true whenever the merge is blocked for any reason", which a survey of 19 open MRs confirms: two drafts read `can_be_merged` / `has_conflicts: false`, so being a draft does not set it. !33223 was not flagged because it was a draft, it was flagged because it had no commits.

  **`detailed_merge_status == "conflict"` was the proposed gate and it is unsafe.** It reports only the *first* failing mergeability check, and in `MergeRequest.all_mergeability_checks` the draft check runs second (trivial tier) while the conflict check runs **dead last**, after rebase, in `mergeable_git_state_checks`. A genuinely conflicted draft therefore reports `draft_status`, not `conflict` — which is already in the observed data, as the `cannot_be_merged_recheck` / `draft_status` row from #463's survey was a real conflict. Gating on `conflict` would have silently stopped reporting conflicts on drafts, on MRs with unresolved threads, and on unrebased branches: the omission class, strictly worse than the false positive being fixed. An allow-list of "block reasons that are not conflicts" fails identically, because it would have to contain `draft_status` and `draft_status` precludes nothing.

  **The discriminator is the diff, not the reason.** A conflict requires two sets of changes to overlap, so an MR with no diff cannot have one regardless of what any status field claims. The poller now clears `has_conflicts` on positive evidence of an empty diff: `detailed_merge_status: commits_status` (GitLab's own identifier for "source branch exists and contains commits" — observed live on !33194, a **non-draft** empty MR, which is what rules out the draft-keyed allow-list), a null `sha`, or a `diff_refs` whose `head_sha` is null or equal to `base_sha` (the source tip *is* the merge base). **Absent fields are never evidence** — a payload without `sha`/`diff_refs` leaves `has_conflicts` trusted, so the guard can never talk itself into silence about a conflict it merely could not see. Pinned in both directions: the two empty-MR shapes must not emit and must not latch into state, an empty MR that later receives commits and genuinely conflicts must still emit exactly once, and a real conflict must still emit when GitLab names the block `draft_status` or `discussions_not_resolved` — that last test is the one the proposed gate would have failed. `radar` and `gl-mrs` render a `[conflict]` flag from the same field and have the same false positive on a lower-stakes surface; not touched here. Closes [#465](https://github.com/Digital-Process-Tools/claude-supertool/issues/465).
- **An `[[ops]]` array handed to a single-op `@file` route (`edit:@file`, `replace:@file`, ...) reported "missing required field 'old'" instead of naming the route that would have worked.** The message was literally true — the ops-array document has no top-level `old` key, the fields live one level down inside `ops` — but it pointed the reader at editing a payload that was already correct. The routing mistake is cheap and unambiguous to detect: a single-op `@file` payload whose only meaningful top-level key is `ops` (dict form) or which is a bare array (list form) is never a valid single-op document, so `_at_file_to_parts` now raises `"this payload is an ops array — use 'batch:@file' instead of '{op}:@file'"` before it ever gets to field-checking. Checked the mirror case too — a flat single-op document (e.g. `{old, new, path}`, no `ops` key) handed to `batch:@file` — which was worse: it silently ran zero ops with no error at all. `batch:@file` now detects a dict with no `ops` key and at least one other field, and names the single-op route instead. [#468](https://github.com/Digital-Process-Tools/claude-supertool/issues/468)

- **`gh-pr:N` prints `Checks:`/`Mergeable:`, `gh-pr:N:status` prints `checks:`/`mergeable:` — same fields, two casings, and a grep for one against the other's output returns nothing, which reads as "no checks" rather than "wrong case".** Checked: both modes are already internally consistent — full mode's label set is Title Case throughout (`State:`, `Branch:`, `Checks:`, `Mergeable:`, `Merge commit:`), `:status`'s is lowercase snake_case throughout (`state:`, `checks:`, `mergeable:`, `merge_commit:`), and this holds for `gl-mr`/`gl-mr:status` too. - **`conflicts_appeared` announced one untouched conflict four times in an hour, and the rising-edge guard meant to prevent that was already there.** !33217 emitted at 16:04, 16:22, 16:58 and 17:11 with nothing resolved and nothing re-pushed — while `pipeline_failed`, four lines up in the same poller and written the same way, fires once per pipeline and a pipeline that stays failed never re-announces. So one event key looked level-triggered and its sibling edge-triggered inside a single file, and the name claiming edge semantics delivered level. The consumer cannot tell a re-announcement from a new event, so it either repeats the same conflict to the human every fifteen minutes or hand-rolls suppression — and the reporter did the latter, which meant it also stopped reporting genuine changes to that MR. Same failure as a permanently-red row: it trains the reader to skim, and skimming is how a real signal gets missed.

  **The bug was not in the guard, it was in trusting `has_conflicts` unconditionally.** GitLab computes mergeability asynchronously, and `has_conflicts` is only an answer once `merge_status` has settled to `can_be_merged` or `cannot_be_merged`. In `unchecked`, `checking`, and the `cannot_be_merged_recheck` that **every push to the target branch** puts every open MR into, the field reads `false` on an MR whose conflict was never touched — confirmed against live data, where a survey of open MRs returned `cannot_be_merged_recheck` / `has_conflicts: false` alongside `cannot_be_merged` / `has_conflicts: true` for the same population. So the poller read "no conflicts", dropped its latch, and re-armed the edge for the next settled poll: four pushes to `master`, four `appeared`, and an irregular cadence that matches pushes rather than the 30s poll interval. The poller now believes `has_conflicts` only on a settled `merge_status` and carries the last known answer forward otherwise.

  **Suppressing repeats outright would have been the opposite defect and is what the tests pin against.** A conflict that is genuinely resolved and later returns *must* fire again — a "fix" that never re-armed would convert a noisy report into an unreported conflict, which is strictly worse and is the exact class #445/#454/#414 were about. Only a settled **clean** check releases the latch, so the re-arm survives any number of recheck cycles in between; a response carrying no `merge_status` field at all is not evidence of an unsettled check, so `has_conflicts` is still taken at face value there rather than being distrusted into permanent silence. Pinned by a five-poll replay of the reported sequence asserting exactly one emission, a resolve-and-return replay asserting two, an assertion on the *state* (a poller that records "clean" mid-recheck has already forgotten the conflict whatever it emitted), and two control tests on `pipeline_failed` — conflicts were made to match its edge behaviour, not both changed together. `github-pr`'s `conflicts_appeared` reads GitHub's `mergeable`, which has its own unknown-while-computing state and is **not** touched here; it is a separate source with a separate signal and deserves its own issue rather than a speculative twin fix. Closes [#463](https://github.com/Digital-Process-Tools/claude-supertool/issues/463).

- **A result count equal to the limit read as exhaustive, and it was how a coverage audit reported a class as untested when its test file was one match past the cap.** `grep:class ServiceUpdateUserFullDelegate:Dvsi/dvsi-private:1` printed `(1 results in 1 files, scanned 118353 files, limit 1)` — truthful in every term and unreadable as truncation, since nothing distinguishes "1 match found" from "1 match shown". The reported case ran with `:3`, saw three incidental references from an EventsManager test, and concluded there was no dedicated test; `ServiceUpdateUserFullDelegateTest` — three tests, thorough — was sitting just past the limit. This is the [#407](https://github.com/Digital-Process-Tools/claude-supertool/issues/407)/[#414](https://github.com/Digital-Process-Tools/claude-supertool/issues/414) family again: output whose *shape* implies a completeness it does not have, and against which the caller has no defence except re-running with a bigger limit, which defeats the cap.

  **The marker is earned rather than inferred, and that is the whole design.** Stopping *at* N is not evidence that an N+1th match exists, so `count == limit` cannot be the trigger — a marker fired on that condition would appear on every full result and be a lie in the other direction: smaller than the original, still a lie, and equally unusable. Instead the walk fetches `limit + 1` and discards the extra, which makes the marker's **absence** a positive claim: `limit N` with nothing after it now means the search looked for an N+1th match and did not find one. The cost is bounded by something already being paid — `_grep_candidates` traverses the entire tree up front to produce #407's `scanned N` denominator regardless of the limit, so the over-fetch adds no traversal at all, only reading file *contents* until one more match turns up. On an exact result that reads to the end of the candidate list, which is simply what proving exactness costs. Context mode over-fetches the same way and trims *inside* the group rather than dropping whole groups, because matches within `2*context+1` lines merge into one window and dropping the window would take the limit-th match with it; it also fixes an overshoot nobody had noticed, where `limit 2` could emit three matches. The delegated path asks rtk for `-m limit+1` and trims identically, so #414's report line gains the disclosure rather than diverging from the walker again.

  **`glob` shared the defect and `count` mode did not**, both checked rather than assumed. `(N files)` implies completeness exactly as grep's header did and has a cap of its own (`glob.max_results`), so it now reads `(200 files — TRUNCATED, more files match)` on the same over-fetch-by-one basis. `grep:…:count` has no cap — it counts every match in every file and its header never claims a limit — so there is nothing there to disclose. Closes [#448](https://github.com/Digital-Process-Tools/claude-supertool/issues/448).

- **`glob` and `grep` walked gitignored directories, and this repository's own workflow made that compound: one agent worktree per parallel agent, so every search got worse the more work was in flight.** With six worktrees under a gitignored `.claude/worktrees/`, `glob:**/ServiceUpdateUserFullDelegate.class.php` returned seven results of which six were noise — and the noise **sorted first**, as stale checkouts of other branches, so the natural read-the-first-hit reflex operated on another branch's code with nothing on screen to say so. It also quietly corrupted the number #407 and #414 exist to make meaningful: `118,353 files scanned` against 44,183 for the same tree reached by a path that missed the worktrees, i.e. a denominator that was largely one tree counted repeatedly.

  **Git is asked; `.gitignore` is not parsed.** One `git ls-files --others --ignored --exclude-standard --directory` per search root returns the ignored directories with full semantics — negations, nested ignore files, `.git/info/exclude`, global excludes — and `--directory` collapses an ignored tree to its top entry instead of descending into it, so the answer costs a single subprocess and never walks what it is telling us to skip. The three alternatives were weighed and rejected in order: reimplementing the pattern language (negations and directory-vs-file semantics are real work, and every rule we get wrong *hides files*, which is the failure direction this whole week has been about); a targeted `.claude/worktrees/` default exclude (cheap, fixes the report, and leaves `vendor/`, `.venv/` and every other ignored tree walked — usually the larger ones); and per-path `git check-ignore` (accurate but one subprocess per candidate). Pruning happens at the walk boundary, so it shrinks `scanned N` rather than filtering results after the fact — the denominator stays honest instead of describing a walk that no longer happened.

  **An ignored path named explicitly is still searched, and that is a hard guarantee rather than a flag.** The prune is disabled outright when the search root is itself ignored, so `grep:needle:.claude/worktrees/agent-a29f` and `glob:.claude/worktrees/agent-a29f/**/*.php` both work: only a walk that would have *descended into* an ignored tree is pruned, never a deliberate entry into one. Silence there would have been a fresh instance of the exact defect class being removed. Three escape hatches otherwise, in descending scope — `"gitignore": false` in `.supertool.json`, `SUPERTOOL_NO_GITIGNORE=1` for one invocation, `:no-exclude` on one call — and outside a repo, without `git`, or on timeout nothing is pruned at all, because an unanswerable question must yield "no opinion" and never "skip it".

  **Two narrowings are deliberate.** Only ignored *directories* are pruned: the win is at the walk boundary, per-file filtering buys little, and `_DEFAULT_EXCLUDE_PATHS` already covers the secret-file case ([#146](https://github.com/Digital-Process-Tools/claude-supertool/issues/146)). And **rtk delegation is skipped when git ignores a directory the exclude list would still walk** — rtk shells out to the system `grep`, whose `--exclude-dir` takes bare names and cannot express a nested path, so a delegated grep would return precisely the copies the walker prunes, and which backend ran must never change the answer. That gate is *residual*, not "is anything ignored": a repo whose ignore set is `node_modules/` alone is already fully covered by the built-in excludes and keeps its delegation.

  **`replace` inherits the prune, which is worth stating because it is a write path.** It shares `_grep_candidates` with `grep`, so `replace:::OLD:::NEW:::.` no longer rewrites files inside gitignored trees — previously a project-wide rename would edit six worktrees' worth of another branch's code as a side effect, with the receipt counting those files as successes. The same escape hatches apply if that is genuinely wanted. Closes [#449](https://github.com/Digital-Process-Tools/claude-supertool/issues/449).

- **Warm MCP daemons accumulated instead of being reused: four `phpstan-warm` alive at once, the oldest thirteen hours old.** Ten daemons where four would do (`phpmd` 2, `phpunit` 2, `rector` 2), and the spread of uptimes — 13:19, 13:14, 07:14, 01:43 — is generational accumulation rather than one unlucky race: each is a spawn that did not find, or did not wait for, the daemon already starting, and nothing retired the predecessor. The memory (~20MB each) is the least of it. **A warm daemon is valuable precisely because it holds loaded config and analysis cache across calls, which is the same sentence as "an old daemon holds old config"** — a thirteen-hour-old `phpstan-warm` answers from the `phpstan.neon` of thirteen hours ago, and on a working day that file has changed. The answer is silent, plausible, and computed against a configuration that no longer exists on disk, which is the defect class this repo has spent the week clearing ([#444](https://github.com/Digital-Process-Tools/claude-supertool/issues/444)/[#445](https://github.com/Digital-Process-Tools/claude-supertool/issues/445), [#454](https://github.com/Digital-Process-Tools/claude-supertool/issues/454)). It was also unbounded — four in thirteen hours, with no ceiling anywhere in the mechanism.

  **What actually allowed the duplicate is the startup window, and it was wide.** Each of the four validator adapters carried its own copy of `if os.path.exists(sock) and is_alive(pid): return sock`, and both of those facts are published *late*: `daemon.py --detach` has to start an interpreter, double-fork, bind the socket and write the pidfile before either is true. Every caller that looked inside that window saw nothing and started its own daemon — the check was advisory, nothing serialised it with the spawn that followed. **`daemon.py`'s own `O_EXCL` pidfile claim, which is the one authoritative gate, ran fourth.** It came *after* the daemon had unlinked the incumbent's socket path and bound its own over it, and *after* it had `Popen`ed the MCP server subprocess — so the daemon that lost the race had already made the winner unreachable (its bound path unlinked) and already spawned a heavy PHP child, which it then orphaned by `sys.exit`ing on the pidfile collision. Losing the race was expensive, destructive and invisible; that is the engine of the accumulation. The adapters' `is_alive()` was also a fourth local copy of the `os.kill(pid, 0)` idiom that [#429](https://github.com/Digital-Process-Tools/claude-supertool/issues/429)/[#431](https://github.com/Digital-Process-Tools/claude-supertool/issues/431) consolidated into `presets/_proc.py`, and it resolved every unanswerable case to *not running* — the safe direction for a killer, the wrong one for a spawner, where "I cannot tell" becoming "spawn another" is precisely how you get four.

  **The invariant now pinned: at most one live warm daemon per (kind, config fingerprint), and no request is served by a daemon whose config has since changed.** The second clause matters as much as the first — deduplicating to a single daemon that still holds stale config only makes the wrong answer more consistent. `presets/mcp/_spawn.py` is the one spawn path for all four adapters: discovery is socket-exists **and** pid-alive (via the shared `_proc` probe, no fifth copy) **and** fingerprint-matches, all three or the daemon is not usable; the check-and-spawn re-runs under an exclusive `flock` on `<base>.lock`, so the caller that loses the race waits for the winner's daemon instead of launching a second one. `flock` and not `lockf` deliberately: POSIX record locks are per-process, so two threads of one adapter would both "acquire" them and race anyway. `daemon.py` now claims the pidfile **first**, before it unlinks a socket or spawns anything, which makes losing the race free — notice, say so, touch nothing — and a stale pidfile whose owner is dead is still cleared under `O_EXCL`, because a crashed daemon wedging every future start is a worse failure than a duplicate: it leaves the project with no daemon at all.

  **Config identity is the content of the config, not its mtime.** The fingerprint is the resolved mcp spec (json, key-sorted) plus a sha256 of every existing file named in its `cmd`/`args`/`env` — so `phpstan.neon`, `rector.php`, and the `mcp-*-warm` binary whenever the spec names it by path, meaning a server upgrade retires the daemon running the old one. `touch` is not a change, a re-save with identical bytes is not a change, and reformatting `.supertool.json` is not a change, which matters because the alternative churns a cold start onto every editor autosave. The daemon writes its fingerprint beside its socket at boot (atomically, via `os.replace`, so a reader never sees half of one) and a live daemon whose fingerprint no longer matches is **reaped and respawned**, not refused: refusing would leave the elder running, which is the accumulation. Reaping is `SIGTERM` then `SIGKILL`, never a bare kill — `SIGTERM` is what lets the daemon tear down its own MCP server child, and skipping it is how the heavy PHP process outlives its parent and becomes one of the strays this issue is about. Two limits are documented rather than papered over: a bare `$PATH` command name is not resolved and so not hashed (the shipped `.supertool.json` wiring names the binary by path, which is), and only files named *directly* in the spec are hashed — a `phpstan.neon` that `includes:` another file re-fingerprints when the top-level file changes, not when the include does. The tests simulate the startup window rather than two sequential calls — a fake spawner that publishes the pidfile and socket 400ms after `Popen` returns, with concurrent callers racing inside that delay — since two sequential calls only prove the easy half, and the easy half already worked or there would have been far more than four. Both opposite failures are pinned too: a dead daemon's leftover pidfile must not block a fresh spawn, and an in-date daemon must be reused rather than churned. Closes [#451](https://github.com/Digital-Process-Tools/claude-supertool/issues/451).

The invariant is pinned parametrically over every state either platform emits plus one that does not exist yet, so `SOME_STATE_GITHUB_ADDS_IN_2027` fails the suite rather than vanishing from the output — which is the whole point, since the bug was never about `cancelled` specifically. `TIMED_OUT` and `ACTION_REQUIRED` are red, not leftovers: a job that ran out of wall clock produced no verdict, and one blocked on a human is blocking. `SKIPPED`, `NEUTRAL` and `MANUAL` are the only non-success states treated as benign, and everything unrecognised is red on the triage boards, because "I do not know this state" must never resolve to "fine".

  **Two adjacent readings were tightened with it.** `Mergeable: yes` is GitHub's *merge conflict* state and nothing to do with CI, but printed bare beneath a check tally it reads as a verdict on the whole PR — half of what made the misread possible — so it now names what it measures (`Mergeable: yes (no merge conflicts)`) and appends `— checks ⚠ NOT ALL GREEN, see Checks above` whenever the run is not unanimously green. Closes [#454](https://github.com/Digital-Process-Tools/claude-supertool/issues/454).

- **A failed job could report `## No error patterns matched` — a crashed job rendering as green.** [#445](https://github.com/Digital-Process-Tools/claude-supertool/issues/445) and [#444](https://github.com/Digital-Process-Tools/claude-supertool/issues/444) are two readings of one defect: `gl-job:<id>:fail` reported the wreckage and not the reason. In #445 a `test_unit_dpt` job whose paratest worker took a SIGSEGV printed *nothing at all* under a header saying `Status: failed`, and was triaged as "no information, retry" rather than "a worker segfaulted in `UserModularForm02Test`" — the cause was sitting at line 1616 of the log, simply unmatched. In #444 the window did match, but anchored on the stack trace, and a stack trace is the *consequence*: the `Caused by` / `PDOException: SQLSTATE[23000] … foreign key constraint fails` that explained it was 23 lines above the first frame and never shown, so recovering it meant falling back to `:raw` with guessed line ranges — 8 extra round-trips across one session, one of which overshot a 3674-line log and had to be guessed again. The invariant the fix is written against: **a failed job must never produce output a reader can mistake for "nothing wrong", and where a cause exists in the log the output must contain the line that states it, not merely the wreckage around it.**

  **The unmatched case is where the real fix lives, and it is not a pattern.** Adding a `WorkerCrashedException` pattern closes #445 and leaves the defect: the next unmatched exception class produces the same silent green, and the set of things that can kill a CI job is not enumerable. So zero matches on a job GitLab calls `failed` now prints `## FAILED — no error pattern matched`, says in words that supertool could not classify it and that this is a missing pattern here rather than a clean log, lists the patterns it tried, names the last `section_start:` the runner entered (the failing step), dumps the last 40 lines, and points at `:raw`/`:grep`. `## No error patterns matched` survives **only** for jobs that did not fail, where it is true; a green job with a quiet log is not accused of anything. The same banner replaced the *default* view's silent fallback, which was worse than #445's: it printed a bare tail with no statement at all, so the reader had to notice the status line six lines up and infer the rest. The pre-existing `test_errors_mode_no_matches` pinned the old wording on a fixture whose status is `failed` — it was pinning the lie, and now pins the banner.

  **Anchoring moved onto the cause rather than widening the window.** More lines is not more signal, and this op exists so nobody has to read a raw trace. Instead a small set of always-on `_CAUSE_MARKERS` matches lines that *state a reason* — `Caused by`, an FQCN-shaped `…Exception: `/`…Error: ` message, `SQLSTATE[`, symfony's `In <File>.php line N:`, `Exit Code: N`, `Fatal error:`, `Segmentation fault/violation`, `Allowed memory size … exhausted`, `…CrashedException` — with context leaning *downward* (2 lines above, `error_context` below), because a cause is followed by its message body and preceded by whatever happened to run before it. A blind lookback above matched stack frames was considered and rejected: it adds lines in proportion to the surrounding noise without knowing whether any of them explain anything, whereas a marker is a positive assertion that this line is a reason. The cost is that an exception shape nobody has a marker for still needs one added — a one-line, testable change, and the unmatched banner catches the case where it matches nothing at all.

- **`radar` — a reconcile that makes "nothing is wrong" distinguishable from "nothing is watching".** `watches` reports which pollers are alive; it cannot report what is true, and the two diverge routinely. Observed live on !33173: `last_event: pipeline_failed on pipeline 154177` against `source_state: running on pipeline 154180` — a board built on the event calls that MR broken while it is mid-retry on a newer pipeline. **`source_state` is truth; `last_event` is history**, and the divergence is surfaced as an explicit `[drift: 154177→154180]` mark rather than silently resolved in favour of one of them. The deeper problem is that events cannot survive a session boundary at all: the transport is fire-and-forget, so an event emitted while no channel consumer is bound is gone permanently; pollers are processes and die with the machine or a cleared `/tmp`; and pollers stop themselves on terminal state by design. At the start of a session an event-driven view therefore knows *nothing* — and "knows nothing" renders identically to "everything is green", which is the failure that makes a monitoring tool untrustworthy, because it is quiet either way and the user cannot tell which. So `radar` is an idempotent reconcile rather than a printer, safe to run on every session start: **one** `gl-mrs` query for open MRs is the authoritative input (state files are cache and may be absent or hours stale, so they never decide what is open or what is red), terminal state files are pruned, drift is flagged, and — the step that makes coverage survivable — a watcher is respawned for every open MR that has no live poller, covering reboot, crash, a cleared `/tmp`, and MRs that were green when watchers were last spawned, in one action. Rows render through the same `_row` helper as `gl-mrs` so there is one definition of the board format, with `[healed]` and `[unwatched]` marks appended for the two signals only radar can report. Two deliberate exceptions to delta suppression: a standing failure or conflict is re-printed even when unchanged, because an unfixed red is a current fact rather than history; and a run where nothing moved still prints one summary line (`radar: no change | 7 open | 7 watched`) instead of nothing, because total silence is indistinguishable from a radar that failed to run — the exact defect the op exists to remove. For the same reason an unreachable or unauthenticated GitLab is a hard error with no board printed and nothing pruned or healed, never an empty green board. - **A `\\` at the end of a line in a shell script is flagged.** The trap is that getting the escaping wrong does not always fail to match — sometimes it writes. In bash, `FOO=$(cmd \\` followed by a newline is an escaped backslash and then a new command, not a line continuation: it is syntactically valid, passes `bash -n`, passes the `bash-check` validator, and does something entirely different from what was meant. No syntax validator can see it; only the byte pattern can. The check runs at `_atomic_write`, the one place every mutating op passes through, and is scoped to `.sh`/`.bash`/`.zsh`/`.ksh` — a trailing `\\` is ordinary in Python, C or JSON. Bash consumes trailing backslashes pairwise from the left, so **parity** decides: an even run ends the line, while an odd run leaves one over to continue it. Only even runs are flagged, which means a single trailing backslash *and* a run of three — one escaped backslash plus a genuine continuation — both stay quiet. A backslash followed by trailing spaces or tabs gets its own warning at any parity: the escape applies to the space, so the line ends there whatever was intended, and the difference is invisible in a diff. ## [0.21.0] - 2026-07-25

### Fixed

- **Validator cache replayed results from a tool that had since been fixed.** The key was `sha256(file_content) + name + cmd` — it described *what was analysed*, never *what did the analysing*, so a fixed analyser and the buggy one it replaced produced identical keys. Upgrading `mcp-phpstan-warm` 0.6.0 → 0.7.0 (two reflection-staleness fixes) and re-running the exact repro still served 0.6.0's wrong answers, in 0.2s, without launching a worker at all; the 24h TTL meant that persisted for a day per affected file. The key now includes a **tool fingerprint**: `size` + `mtime_ns` of every `cmd` token that resolves to a real file, plus `fingerprint_paths` (per validator) and `validator_fingerprint_paths` (project-wide — this is where a lockfile belongs, since composer bin proxies and similar wrapper launchers are byte-identical across versions). Missing paths weaken the fingerprint rather than disabling the cache; fingerprints are memoised per process, so the cost is a handful of `stat` calls per run. Token extraction unions a naive whitespace split with `shlex` (POSIX mode off on Windows): `shlex` treats `\\` as an escape, so a Windows path shredded into a token matching no file — every cmd token contributed nothing and the fingerprint silently degraded to a constant on Windows, which is the exact failure this change exists to prevent. A backslash is a legal POSIX filename character, so the regression test reproduces it on every platform.
- **`between:SYMBOL` now accepts a symbol written the way it reads in source.** `between:async function fillAndSubmit` and `between:function getReorderEntityHasFileComponent` both returned `symbol not found`, even though both definitions exist — the tree-sitter matcher compares against the bare node name, so any leading keyword (`async`, `function`, `def`, `class`, `public static function`, …) or trailing `(params)` made the lookup miss. Since the natural thing to paste is the signature as it appears in the file, the op's own success path was the one you had to know not to use; both misses fell back to grep+read. The query is now normalized (modifier keywords stripped, everything from the first `(` dropped) and retried — **after** the exact match, so a symbol that genuinely is a keyword (`between:function`) still resolves literally. A miss now reports both forms tried. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).
- **`grep` no longer dumps a pathological single line in full.** One hit inside a 7KB one-line `@extends CommandGetAssetLoansBase<array{…}>` PHPDoc emitted the whole line — a screenful of context for a single match, in the op called most per turn. Match and context lines are now capped at `grep.max_line_chars` (default 500, or `SUPERTOOL_GREP_MAX_LINE_CHARS`) and the remainder is reported as `… (+N chars)` so the reader can widen deliberately instead of paying for it by accident. Normal-width lines are untouched. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).
- **`glob` retries a mid-path segment before reporting zero.** `grep` accepts `SiBrief/…` for a directory nested under `Dvsi/dvsi-private/src2/`, but `glob:SiBrief/**/*.class.php` resolved relative to the repo root and returned `(0 files)` — the same mental model, two different answers, and the zero reads as "nothing there" rather than "wrong anchor". A pattern that contains `/`, isn't already anchored (`/`, `~`, `**`, `./`, `../`) and matches nothing is now retried once as `**/PATTERN`; a hit prints a `[mid-path retry: …]` line naming the pattern that actually ran, so the rewrite is never silent. A genuine zero stays zero. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).
- **cwd drift recovers instead of dying.** After a `cd` into a subdirectory (a Playwright run, a package build), the next call with a repo-root-relative path failed with `path not found: X (cwd: Y) — wrong CWD?` and cost two round-trips: read the error, retry with `cwd:`. `main()` now probes for the drift in the same pre-pass that handles `cwd:` and chdir's to the project root, printing `[cwd auto-resolved to project root: …]`. The trigger is deliberately narrow — an ancestor directory must carry a `.supertool.json` (explicit project marker), **no** path-shaped arg may resolve against the current cwd, and at least one must resolve against that root — so a subdirectory-relative call is never hijacked. An explicit `cwd:` op still wins; `@` payloads, flags, absolute paths and wildcards are ignored when probing. Closes [#363](https://github.com/Digital-Process-Tools/claude-supertool/issues/363).

Because it reads the single-object pipeline endpoint, not the paginated `/jobs` list, it sidesteps the concatenated multi-doc JSON parse bug (#352/#359). Closes [#353](https://github.com/Digital-Process-Tools/claude-supertool/issues/353). See [docs/presets/watch.md](docs/presets/watch.md).
- **`git-diff` gained a trailing `:full` mode that appends the real diff hunks** — `git-diff:full` (and `git-diff:PATH:full` / `git-diff:staged:full` / `git-diff:branch:BASE:full`) prints the raw `+/-` hunks under a `## Patch` section below the review summary. The default `git-diff` is a *review* view — classified files, shortstat, red-flag scan, forbidden-path guard, test-pairing, hints — deliberately hunk-free so it stays a cheap overview. But writing an honest commit message or actually reading a change needs the hunks, which previously forced a drop back to raw `git diff` (losing the op's repo header and CWD-safety). `full` is a trailing flag (stripped from the positional args before staged/branch/PATH dispatch, like `read:PATH:full`), so it composes with every existing mode as the last token and never collides with mode selection. Omitted by default; only the summary prints unless asked. Closes [#358](https://github.com/Digital-Process-Tools/claude-supertool/issues/358).
- **`help:OP` op prints the full reference for a single op** — `help:vim` emits that op's syntax, uncompacted description, and example, read straight from `.supertool.json` (builtin-ops → custom ops → aliases). The motivation: op hints and the `vim` example line told the reader to "see `./supertool help vim`", but no `help` op existed — `./supertool help vim` returned `unknown operation: help`, a dead front door, so discovering a non-obvious payload shape (vim's macro grammar, the `@file` field names) meant grepping source. `help` reuses the existing config as the single source of truth — the same metadata `ops` lists, but scoped to one op and never compacted, so a long description (vim's is ~1.5KB) prints in full instead of being dropped by `ops-compact`'s self-explanatory filter. An unknown op errors with a pointer to `ops`; a real built-in with no config entry says "has no documented help" rather than "unknown operation", distinguishing the two. Read-only and parallel-safe. Use `help:OP` when you know the op but not its payload; use `ops` when you don't yet know the op. Closes [#341](https://github.com/Digital-Process-Tools/claude-supertool/issues/341).
- **`cwd:PATH` op sets the working directory for a whole call** — `cwd:~/repo` as the *first* op chdir's once before any dispatch, so every following op resolves against `PATH`, then it's stripped (it never reaches the dispatch loop). Mirrors `cd PATH && ./supertool …` without the `cd`: a line starting with `cd` trips the `use-supertool` hook, and a forgotten/stale `cd` silently poisons relative path resolution (the exact trap that made `git-diff:.supertool.json` report "No changes" against the wrong clone in #336). Cross-repo sessions — a product repo plus the supertool clone — otherwise needed a `cd <repo> &&` prefix on every other call. It's an op, not a `--flag`, to keep supertool's single grammar; handled in the pre-pass (like `--plain`) so it can't race the parallel read path or force a batch sequential. Required-first on purpose: an op after it would have already resolved against the old dir, so a mid-call `cwd:` is rejected (`must be the first op`) rather than silently half-applied. `~`/`$VAR` are expanded; a non-directory target errors before any op runs. Closes [#339](https://github.com/Digital-Process-Tools/claude-supertool/issues/339).
- **Validators/formatters gained a per-spec `exclude` glob** — a validator or formatter spec may now set `"exclude": "*tests/*"` (or a list of globs, skip-if-any-matches) to skip files even when its `match` glob hits. The motivating case: editing a PHPUnit test file fired the `phpmd` validator, which reported `TooManyPublicMethods` (every `testXxx()` is public) — pure noise, since no real gate scans tests (CI mess-detection scans the source dir only; the pre-push git-hook skips any `/tests/` path). Validators were gated by a single positive `match` glob with no exclude, so there was no config-only fix. `exclude` is per-spec on purpose: a blanket "skip tests" would break `phpunit`, which *must* run on test files. Generalizes the prior `PSR_EXCLUDE` env hack into a first-class config key. Closes [#335](https://github.com/Digital-Process-Tools/claude-supertool/issues/335).
- **`gl-mr` now lists the per-file name-status by default** — the MR dashboard prints a `## Files (N)` block with one `A`/`D`/`R`/`M` line per changed path, sourced from the paginated `merge_requests/:iid/diffs` endpoint (so the change type comes straight from GitLab's `new_file`/`deleted_file`/`renamed_file` flags, no git shellout). "What got removed?" is the high-signal question when reviewing an MR, and previously `gl-mr` gave only a file *count* — forcing a separate `git diff --name-status master...branch` round-trip, exactly the borrowed round-trip the variants exist to kill (the concrete trigger was auditing a deleted-migration concern on a real MR). The list is capped at 50 files with a `… +N more` marker so large MRs don't blow context; `gl-mr:N:full` uncaps it (paginating up to 500 files) alongside the existing comment uncap. Any API/parse failure silently omits the block. Closes [#332](https://github.com/Digital-Process-Tools/claude-supertool/issues/332).
- **`git-status` gained a `:full` mode** — `git-status:full` (alias `:porcelain`) uncaps every list in the dashboard (staged/unstaged/untracked files, other branches, stashes), printing the complete untruncated set instead of the default `... (N more)` markers. The default view stays capped (20 staged/unstaged, 10 untracked/branches, 5 stashes) — a cheap overview that answers ahead/behind + dirty + MR. The bug wasn't the truncation (correct for the common case) but the lack of an escape hatch: driving precise staging — e.g. excluding a few pre-existing untracked items from a large commit — needs the full machine-readable list, which previously forced a drop back to raw `git status --porcelain`. Closes [#330](https://github.com/Digital-Process-Tools/claude-supertool/issues/330).
- **`gl-job` / `gh-job` gained a `:fail` suffix** — `gl-job:ID:fail` (alias `:errors`) prints only the matched failure blocks with no tail, the tight triage view. It applies the same per-job pattern table as the default mode (rector → diff lines, phpstan → 🪪/type markers, unit → `FAILURES!`/`Failed asserting`), so a red job shows just its actionable failures instead of the default's blocks-plus-80-line-tail. This names the discoverable front door for a behavior that previously only existed as the undocumented `:errors` mode on `gl-job` (and was entirely absent on `gh-job`); `:errors` stays as a back-compat alias. The default (no suffix), `:grep:PATTERN`, and `:raw` are unchanged. Closes [#326](https://github.com/Digital-Process-Tools/claude-supertool/issues/326).
- **`grep` gained a `:no-auto-read` flag** — `grep:PATTERN:PATH:no-auto-read` suppresses the single-small-file auto-read so only the matching line(s) are emitted, mirroring `glob`'s existing flag. Default behavior (auto-read a concrete file < 20KB on a match) is unchanged. The flag is order-independent with `:count` and any `LIMIT`/`CONTEXT` args. Avoids silently dumping 10-18KB of unrequested file content when the caller only wants the hit. Closes [#320](https://github.com/Digital-Process-Tools/claude-supertool/issues/320).
- **`git-commit` gained an `@file` payload route for multi-line messages** — `git-commit:@-` (stdin) or `git-commit:@msg.toml` reads a `message` field (subject + blank line + body) and an optional `paths` list, so a real subject+body commit no longer forces a drop to raw `git commit -F file` — which skipped the op's auto `Co-Authored-By` trailer and needed a follow-up `--amend`. The trailer is still appended on the payload route. The colon-CLI one-liner (`git-commit:::MESSAGE`) is unchanged. Mechanically this generalizes the `@file` field parser: a syntax token in a trailing `[...]` group is now optional, and a `...` token is variadic (a payload list expands into multiple positional args) — previously the parser leaked the `[`/`...]` brackets into the field names (`msg[`, `path...]`), so the route 404'd with `missing required field 'msg['`. Closes [#340](https://github.com/Digital-Process-Tools/claude-supertool/issues/340).
- **Generalized the new-class-without-test advisory into a config-driven `advice` block** — the hardcoded `adviseForNewTest` bool is replaced by a top-level `advice` map of named rules, each gated (all optional) by `hooks_into` (ops, default all mutating), `match` (path glob), `when` (`new-file`|`existing-file`|`always`), `contains` (regex over the content the op *added* — lines present after but not before, so it fires only when the op introduces the pattern), and `resolve`/`resolveFromValidator` (a subprocess emitting a would-be target via the same exit-3 + stderr contract). `message` is the rendered line, with `{target}`/`{path}`/`{op}` interpolation. The old single-purpose advisory was a dead end the moment a second nudge was wanted (e.g. "regenerate the XSD/cache after adding a component class or public attribute" — exactly the easy-to-forget step the XML editor depends on); the generic block lets a project add that as data instead of code. **Breaking:** the `adviseForNewTest: true` bool is removed — express it as an `advice.newTest` rule (`{"hooks_into": ["paste"], "match": "*.php", "when": "new-file", "resolveFromValidator": true, "message": "new class without test"}`); see `.supertool.example.json`. Closes [#347](https://github.com/Digital-Process-Tools/claude-supertool/issues/347).

### Fixed

- **`gl-pipeline` now parses glab's `--paginate` concatenated multi-document JSON** — a pipeline with enough jobs to paginate made `glab api --paginate` emit one JSON array *per page* back-to-back with no separator (`[{job1}][{job2},{job3}]`), and the single `json.loads` on that stream choked on the second `[`, so `gl-pipeline` failed with `invalid JSON from glab` on exactly the large, slow pipelines you most want to inspect. A new `_parse_paginated_json` walks the string with `JSONDecoder.raw_decode`, consuming one document at a time and flattening every page's array into a single job list — robust to the common single-page case, to inter-document whitespace, and to empty `[]` pages. The parser still enforces that every page is a JSON array — a non-array top-level document (e.g. a bare error object) raises the explicit `unexpected response format` error instead of being rendered as a garbage job row. Closes [#352](https://github.com/Digital-Process-Tools/claude-supertool/issues/352). Closes [#359](https://github.com/Digital-Process-Tools/claude-supertool/issues/359).
- **`batch` write sub-ops no longer corrupt content that contains `:::`** — a batch item's structured fields (`old`/`new`/`content`/…) were parsed from the JSON payload correctly, then re-serialized back into a `:::`-joined arg string and handed to `dispatch`, which re-tokenized on `:::` — so any sub-op whose content itself contained `:::` (or backslashes the escape-decoder would mangle) got split at the wrong boundaries and silently corrupted, even though the same edit as a standalone `edit:@file` call worked fine. `dispatch` now accepts a `pre_parsed` `(parts, replace_all)` tuple — the exact shape `_at_file_to_parts` already produces — and batch routes the already-structured parts straight through it, skipping both the `:::` split and the shell-escape decode. A readable colon-joined string is still built, but only for the batch header summary, never for parsing. Content is now taken literally, matching standalone `@file` semantics. Closes [#252](https://github.com/Digital-Process-Tools/claude-supertool/issues/252).
- **`glob`/`grep` single-file auto-read is now capped by line count, not just bytes** — the auto-read that saves a follow-up round-trip (a `grep` that matches one small file, or a `glob` that returns exactly one) gated only on byte size (< 20KB), so a file under the byte cap but with hundreds of short lines — a long config, a wide data file, a generated stub — was still dumped in full and blew a chunk of context the caller never asked for. Auto-read now also checks a line count via a cheap streaming counter and skips when a file exceeds `MAX_AUTOREAD_LINES` (default 60, tunable as `read.max_autoread_lines`), printing a `[auto-read skipped: > N lines — read:PATH:full to see it]` pointer instead of the file body. Both dimensions must pass to auto-read; a file we can't measure is treated as over-cap and skipped. The `:no-auto-read` flag and the byte cap are unchanged. Closes [#362](https://github.com/Digital-Process-Tools/claude-supertool/issues/362).
- **A leading `[[` in an `@file` payload is now detected as TOML, not JSON** — the payload format sniffer returned `json` on any first non-whitespace `{` or `[`, so a TOML table-array header (`[[ops]]` — the shape a `batch:@-` ops array takes) was misread as the start of a JSON array and died in the JSON parser, even though `[[` is never valid JSON. The detector now special-cases a leading `[[` as TOML before the generic `{`/`[` → JSON rule, so batch payloads written in TOML's `[[ops]]` form parse correctly. A single-object `[` (a real JSON array) is unaffected. Note the one narrowing: a JSON payload whose first two characters are `[[` (an array whose first element is an array) is now read as TOML — not a shape any op payload takes, since ops are objects. Detection alone was only half the fix: `tomllib` is stdlib from 3.11, and below that the bundled fallback parser explicitly supported no tables, so a correctly-detected `[[ops]]` payload then died in it with `bad key at offset 0` on Python 3.9/3.10. The fallback now parses `[[table]]` array-of-tables headers, and rejects a single `[table]` with a message that says so instead of complaining about a bad key. Closes [#357](https://github.com/Digital-Process-Tools/claude-supertool/issues/357).
- **`git-push`'s non-fast-forward recovery now rebases onto `FETCH_HEAD`, not `origin/<branch>`** — when the remote had moved ahead, the auto-rebase recovery ran `git rebase origin/<branch>`, but the recovery's own one-shot `git fetch origin <branch>` only populates `FETCH_HEAD` — it updates the remote-tracking ref `refs/remotes/origin/<branch>` *only* when a fetch refspec is configured. A fresh worktree or a refspec-less clone (exactly where you hit a first-push non-fast-forward) has no such ref, so the rebase aborted with `fatal: invalid upstream 'origin/<branch>'` and left the push stuck with no recovery. It now rebases onto `FETCH_HEAD`, which the fetch guarantees is present and points at the same commit — so recovery works in a plain clone and a fresh worktree alike. The incoming-commits preview reads from the same `FETCH_HEAD` ref for consistency. Closes [#354](https://github.com/Digital-Process-Tools/claude-supertool/issues/354).
- **Two `@-` (stdin) ops in one call now error clearly instead of an opaque parse failure** — `./supertool 'edit:@-' 'edit:@-'` made both ops call `sys.stdin.read()`; the first drained the single stream, so the second read empty and died with `@file ... parse error (<stdin>): Expecting value: line 1 column 1`, naming neither the real cause (the stream was already consumed) nor the fix. main() now detects more than one `op:@-` in a pre-pass — sibling to the existing `cwd:` pre-pass, before any dispatch — and exits with `stdin: only one '@-' op is allowed per call (got N: ...)`, listing the offending ops and pointing at the two escape hatches: give all but one a real `@file` path, or fold them into a single `batch:@-` ops array. A lone `@-` (the common case) is unchanged; a bare `@-` arg with no `op:` prefix isn't counted. Closes [#341](https://github.com/Digital-Process-Tools/claude-supertool/issues/341).
- **An MCP server's own timeout no longer surfaces as a phantom `+1` diagnostic** — after an edit, `lsp-diag` reported a `0 → 1` count where the single "diag" was actually `orchestrator timeout after 3s`, an infrastructure condition, not a code finding (phpstan had already covered the same file clean). The cause: cclsp swallows its *internal* LSP-orchestrator timeout and returns it as normal MCP text content with the `isError` flag unset — so it flowed through the shared dispatch as a real result and the lsp-diag adapter counted it as an advisory, reading like the edit introduced a regression. Detection now lives in the shared `_mcp_call_or_message` (so every MCP-backed op — `diag`/`hover`/`rename` — benefits, not just lsp-diag) with two signals: the structural MCP `isError` flag (spec-standard, any server) and a configurable per-server `infra_patterns` substring list (default `["orchestrator timeout", "timed out after"]`) for servers that report timeouts as plain text. A matched result is returned prefixed `op: …` — the same shape as supertool's own MCP errors — so the adapter's existing `op:`-prefix guard drops it instead of counting it. No count delta, no false regression, and the timeout value itself stays per-server configurable via `mcp.<name>.timeout`. Closes [#346](https://github.com/Digital-Process-Tools/claude-supertool/issues/346).
- **`rector-mcp` engine-glitch suppression is config-driven and now catches `toMutatingScope() on null`** — the warm rector daemon intermittently trips a PHP fatal inside rector's own engine (`Call to a member function toMutatingScope() on null`), a non-deterministic glitch a cold `rector` CLI does not reproduce. Like the June `System error: ClassReflection` case it surfaced as a false red *and* — because the validator cache keys on file content — froze into the cache and replayed on every later run until the file changed (the 2100-poisoned-entries failure mode, new signature). The fix moves glitch knowledge out of the core and into the adapter: the core had been string-matching `System error:` in `_validator_result_is_cacheable`, violating `SCHEMA.md`'s "validator core never parses tool-specific output". That branch is removed — the core cache filter is now fully generic, keying only off non-deterministic error *codes*. Tradeoff: the core no longer has a message-level backstop, so a brand-new, uncatalogued glitch signature can still reach the cache as a `rector.error` until it is added to the config list — the same failure mode, now bounded to *unknown* signatures and fixed by a one-line config edit rather than a code change. Signatures live as a config prop, `validators.rector.engine_glitches` in `.supertool.json` (a JSON list of case-sensitive substrings the adapter reads straight from `.supertool.json` — no env, the same file `daemon.py` already reads from cwd), defaulting to `["System error:", "toMutatingScope() on null"]` when absent. The adapter drops a matching error at the source, so a glitch never surfaces or reaches the cache; a new signature is a one-line config edit, not a code change. Part of [#345](https://github.com/Digital-Process-Tools/claude-supertool/issues/345).
- **`git-diff:PATH` no longer reports a missing/untracked path as "No changes."** — a path absent or untracked in the current repo produced an empty diff that printed `No changes.`, indistinguishable from a clean tracked file. Combined with a stale CWD (e.g. a `cd` into another repo) this is a silent false-negative: the op reads as "nothing changed" when it actually looked in the wrong place. Path mode now checks `git ls-files` first — a missing path warns `not found under <cwd> — wrong CWD?` and exits 1, an untracked on-disk path warns `untracked (not in git)`, and only a genuinely clean tracked file still says `No changes.`. Every mode also stamps a `Repo: <toplevel>` header so a wrong-repo invocation is visible at a glance (the trigger: `git-diff:.supertool.json` silently returned "No changes" while anchored to the wrong clone). Closes [#336](https://github.com/Digital-Process-Tools/claude-supertool/issues/336).
- **`grep` path-not-found error now includes the CWD** — `ERROR: path not found: <path> (cwd: <cwd>) — wrong CWD?` instead of the bare path, so the recurring "stale cwd makes a relative path silently miss" trap is diagnosable from the message alone. Part of [#336](https://github.com/Digital-Process-Tools/claude-supertool/issues/336).
- **`git-commit` no longer aborts on an already-staged deletion** — listing a `git rm`'d path (gone from disk) alongside present files made the op's `git add` step fail with `pathspec did not match any files`, killing the whole commit. The op now drops paths that are already staged as deletions from the `git add` step (their deletion is already staged and gets committed), so a mixed changeset of modifications + new files + deletions lands in one commit. Genuinely-unknown paths still error as before. Closes [#324](https://github.com/Digital-Process-Tools/claude-supertool/issues/324).

## [0.18.0] - 2026-06-23

### Fixed

- **`git-push` no longer misreports a pre-push hook's amend-and-push as `PUSH REJECTED`.** A pre-push hook that auto-formats commonly amends HEAD, pushes the corrected commit itself, then exits non-zero so git won't also push the stale pre-amend ref — that non-zero is *success*, not failure. `git-push` now trusts the live remote SHA (`ls-remote`) over the exit code: when the remote already matches local HEAD it reports `PUSHED (pre-push hook amended HEAD)` with the rewritten SHA, instead of `REJECTED`. And `_first_error_line` no longer picks a green `✅ … 0 errors` / `pushed successfully` line as the "first error" (the substring `errors` was matching the error scan). Closes [#297](https://github.com/Digital-Process-Tools/claude-supertool/issues/297).

### Added

- **`git-push` embeds non-fast-forward recovery.** When the remote has moved ahead, `git-push` now fetches, surfaces the **incoming remote commits** (short SHA, author, subject — the signal for force-vs-integrate, since forcing over a teammate's commit destroys it) with the ahead/behind counts, then rebases your work onto the remote and re-pushes in the same call — no manual `pull --rebase` → `git-push` round-trip. Computing is cheap; LLM round-trips are not. On conflict it leaves the rebase **paused** (never silently aborted or force-pushed), lists the conflicting files, warns to check the incoming authors before forcing, and points at `git-conflicts` to inspect plus the exact keep-both / cancel (`git rebase --abort`) / force paths — the resolution stays the caller's decision.
- **`git-push` post-push receipt surfaces the next decision.** A push isn't the end of an action, it's the start of "get this MR merged" — so the receipt now carries the signals you'd otherwise spend round-trips discovering, all riding calls already made: **mergeability** (warns loudly if the MR now `cannot_be_merged` with its target — caught at push time, not 20 min later at merge), **stale base** (`N commit(s) behind origin/<target>`), **uncommitted leftovers** (`git status --porcelain` — the "I fixed two things, committed one, pushed" catch), the **pipeline id + url** on the MR line, and a ready **`watch:gitlab-mr:<iid>`** command to hand the pipeline to a background poller. `:force-with-lease` additionally reports **what it discarded** (author + subject of the overwritten remote commits — the receipt for "did I just nuke a teammate's work"). Watching stays opt-in: the receipt recommends the command by default; `git-push:watch` spawns the poller for the push you're actually iterating on (no stray daemons on WIP pushes).
- **`git-push:force-with-lease` and `git-push:no-verify` variants.** `:force-with-lease` is the safe force (overwrite only if the remote hasn't moved since you fetched) and suppresses the auto-rebase, since the force is your explicit decision; `:no-verify` skips the local pre-push hook, the documented escape when a local formatter legitimately diverges from CI. The op cmd switched from `{arg}` to `{args}` so the flag tokens reach the script. Part of [#297](https://github.com/Digital-Process-Tools/claude-supertool/issues/297).

- **`gl-pipeline` filter modes — `:active` and `:failed`.** Polling a running pipeline across turns re-paid ~90 lines of `manual`/`created` bulk every call. Two filter modes cover the only questions you ask mid-pipeline: `gl-pipeline:ID:active` shows just running/pending jobs ("what's still going"), `gl-pipeline:ID:failed` shows just the failed jobs plus their job IDs/URLs ("what broke"). ## [0.16.0] - 2026-06-22

### Added

- **`git-push` op — update the branch behind an already-open MR.** The `mr` op covers push **and** create; there was no op for the common follow-up — pushing a fix to an MR that already exists — so it dropped to raw `git push -u origin HEAD`. `git-push` pushes the current branch (setting upstream on first push), then prints a verifiable receipt: remote SHA before/after with commits pushed (or "already up to date" / "branch created"), ahead/behind vs upstream, and the open MR/PR for the branch with its pipeline status (the push triggers a run). ## [0.15.0] - 2026-06-22

### Added

- **`gl-job` / `gh-job` `:grep:PATTERN` + per-job failure patterns with resolution ops.** `gl-job:ID:grep:PATTERN` (and the `gh-job` twin) runs an ad-hoc regex over the job trace — context window, gap markers, regex with literal fallback on `re.error`, and never silent-empty (no match names the pattern and shows a tail). Complements the existing `:raw` slice when you don't yet know the line numbers. Plus an optional per-job-name table in `.supertool.json`: `ops.gl-job.job_patterns` maps a job-name regex to tighter `patterns` and a `resolution` op — a failed `rector` job ends with `Resolve: ./supertool 'rector_ci_apply:<id>'` (`{id}` interpolated). No match falls back to the flat `error_patterns`. Two enablers: non-scalar custom-op config values are now JSON-encoded into their `SUPERTOOL_*` env var (so presets can `json.loads` structured config), and project-level `ops` overrides **deep-merge** into preset op-defs key-by-key (add `job_patterns` without restating the preset `cmd`). Closes [#289](https://github.com/Digital-Process-Tools/claude-supertool/issues/289). See [docs/presets/gitlab.md](docs/presets/gitlab.md).
- **`restartMcp` key on custom ops.** A custom op that invalidates state the warm MCP daemons cache (autoload map, PHPStan/PHPUnit result caches, …) can declare `"restartMcp": true` (every server in the `mcp` block) or `"restartMcp": ["name", …]` (a subset). After the op's `cmd` **succeeds**, supertool SIGTERMs those daemons via the same `stop.py` path the new-file invalidation uses; each cold-starts on its next call with a fresh index. Skipped when the cmd fails. Lets a single cache-clearing op (e.g. `dvsi_clearcache`) also reset the warm LSP layer in one round-trip, instead of leaving daemons serving stale analysis until the idle timeout.
- **`gl-mrs` — MR triage board.** Lists MRs (default `author=@me`), sorted failing-first then stalest, each enriched in parallel with everything you'd otherwise round-trip for: pipeline status (a failure shows the failed **job name** — `phpstan2`, `test_unit_dpt` — i.e. the failure class, pre-empting a `gl-job` call), approval state, age, diff size, watch-state cross-reference (which MRs already have a live `watch` poller), and `conflict`/`draft`/`threads` flags. Footer points at the first failing-and-unwatched MR. Filters: `author`/`reviewer`/`assignee`/`label`/`milestone`/`state`/`per`. Flags: `nopipe`, `iids` (bare id list), `failed` (only failing). Tunable via `enrich_workers`/`enrich_cap`/`per_page`. "Mine" is just the default filter, not a special op — enumeration is a platform concern, kept out of the generic `watch` preset. See [docs/presets/gitlab.md](docs/presets/gitlab.md).
- **`gh-prs` — PR triage board (the `gl-mrs` twin).** Lists GitHub PRs (default `author=@me`), sorted failing-first then stalest. Per PR: check rollup (a failure shows the failing **check name** — the failure class, pre-empting a `gh-job` call), approval state (`reviewDecision`), age, diff size, watch-state cross-reference, and `draft`/`conflict`/`threads` flags. Footer points at the first failing-and-unwatched PR. Unlike GitLab, `gh pr list --json` returns checks + approval in **one** call, so the core board costs a single request; only unresolved review-thread counts enrich in a second parallel wave (skip with `nopipe`). Filters: `author`/`reviewer`/`assignee`/`label`/`state`/`per`. Flags: `nopipe`, `iids` (bare number list), `failed`. Closes [#274](https://github.com/Digital-Process-Tools/claude-supertool/issues/274). See [docs/presets/github.md](docs/presets/github.md).
- **`presets/watch/watch-mine.sh` — watch-a-whole-query supervisor.** Glue between a "list mine" op (`gl-mrs`/`gh-prs`) and the `watch` preset: runs the feed op, extracts ids, spawns one watcher each. Idempotent, so it's safe on `/loop`. `gl-mrs:failed,iids | watch` turns "ping me when any of my MRs goes red" into one looped command. See [docs/presets/watch.md](docs/presets/watch.md).
- **Configurable default `project` / `repo` for issue-create payloads.** `gl-issue-create` and `gh-issue-create` no longer require `project`/`repo` in every payload. Resolution order (most specific wins): explicit payload field → `defaults.gitlab_project` / `defaults.github_repo` in `.supertool.json` → the `origin` git remote, host-matched (`gitlab` / `github.com`). In the matching checkout the remote covers it with zero config. Closes [#270](https://github.com/Digital-Process-Tools/claude-supertool/issues/270). See [docs/presets/gitlab.md](docs/presets/gitlab.md) and [docs/presets/github.md](docs/presets/github.md).
- **`watch` preset — background event pollers with async wake into Claude Code.** New ops `watch:SOURCE:ID[:only=...]`, `unwatch:SOURCE:ID`, `watches`. Each invocation forks a detached poller that emits state-change events to a UDS socket, a status file, and macOS Notification Center. Source-plugin contract makes new sources ~50 lines. Bundled sources: `github-pr` (PR state, checks, reviews, comments, merge/close, conflicts) and `gitlab-mr` (MR state, pipeline, merge/close, conflicts). Closes [#165](https://github.com/Digital-Process-Tools/claude-supertool/issues/165). See [docs/presets/watch.md](docs/presets/watch.md).
- **`notifiers/claude-channel/` — MCP channel server for async wake.** TypeScript / Bun server that binds the watch UDS socket and pushes events into a running Claude Code session via the Channels feature (research preview, requires Claude Code v2.1.80+). Events arrive as `<channel source="claude-channel" watcher_source="<source>" id="<id>" event="<event>" ...>` tags. UDS file mode 0600 + localhost-only auth model. Launch with `claude --dangerously-load-development-channels server:claude-channel`. See [notifiers/claude-channel/README.md](notifiers/claude-channel/README.md).
- **`glob` brace expansion.** `glob:src/**/*.{json,xml}` now fans out into `*.json` + `*.xml` (shell/fd/ripgrep semantics) and dedupes results, instead of silently returning 0 files. Supports multiple groups (`{a,b}.{x,y}` → 4) and nesting (`{a,b{1,2}}` → 3). Patterns without braces are unchanged. Closes [#161](https://github.com/Digital-Process-Tools/claude-supertool/issues/161).
- **`validator_cache_ttl_hours` config** (default `24`, `0` disables). Validator cache entries expire this long after being written. The cache key only hashes file content, so without a TTL an entry outlives changes it can't see — an updated adapter/`rector.php`, or a transient engine failure. Expiry is on access (stale → miss → re-run → rewrite); no cron needed.

### Fixed

- **Test suite no longer mutates the repo it runs in (corrupted working trees under the pre-push hook).** `TestGitcliFlagSmuggling::test_checkout_allows_dash_alone` ran `checkout.py -` via a `subprocess.run` with no `cwd=`, so it executed a real `git checkout -` (switch to previous branch) against whatever directory pytest was launched from. Harmless under a normal `pytest` invocation from a stable branch — but `.githooks/pre-push` runs the **full suite** on every push, so each `git push` from a feature branch silently switched the live repo to its previous branch mid-push, moving `HEAD` and reverting the working tree. Combined with a git wrapper that reports `ok` regardless of the push result, this presented as "force-push silently failed" / "HEAD reset to master" and corrupted in-flight work twice in one session before being traced. Fix: `_run_git_preset` gained a `cwd` parameter and the test now builds an isolated throwaway repo (with a real previous-branch reflog) and asserts `-` switches to it — verified by re-running the full suite from a clone and confirming `HEAD` is unchanged.
- **`claude-channel` MCP server now loads from any project directory.** The bundled `.mcp.json` launched `bun` with a cwd-relative script path (`./notifiers/claude-channel/channel.ts`). Claude Code spawns plugin MCP servers with the working directory set to the *active project*, not the plugin root, so the path resolved against the wrong directory and the server failed to connect everywhere except the plugin dir itself (`Module not found` → `-32000 Connection closed`). Switched to the `${CLAUDE_PLUGIN_ROOT}/…` variable Claude Code expands in plugin `.mcp.json` files, matching what `notifiers/claude-channel/install.sh` already wrote with an absolute path. Also aligned the version mismatch the reporter flagged: `plugin.json` (`0.13.1`) vs `supertool.py` `VERSION` (`0.14.0`) → both now `0.14.1`, with a test asserting they stay in sync. Closes [#279](https://github.com/Digital-Process-Tools/claude-supertool/issues/279). Thanks [@riccardoshrives](https://github.com/riccardoshrives) for the detailed report and verified fix.
- **Validator cache no longer freezes transient engine failures.** `rector-mcp`'s warm daemon intermittently trips rector's own `System error: "ClassReflection must be resolved for class X"` reflection bug on test classes — warm-process-state dependent, not file dependent (a clean re-run and plain `rector` CLI pass the same file). That failure was cached keyed on file content and replayed on every later run, including its frozen `duration_ms`; 2100 entries were poisoned this way across a test suite. Two-layer fix: (1) `validators/rector-mcp/rector-mcp.py` drops `System error:` results at the source — an engine glitch is not a code finding; (2) the validator cache now excludes non-deterministic engine failures (MCP transport errors, non-zero exits, `System error:` messages) from being written. Real findings (PHPStan types, `rector.refactor`) stay cached.
- **`git-merge` now fetches before merging a local branch — no more silent stale merges.** The docstring promised "fetch + merge" but there was no fetch: `git-merge master` merged the *local* `master` ref, which is stale the moment origin moves ahead. Real-world bite: a fix landed on origin/master, but merging `master` into a feature branch silently used the lagging local ref and the fix "wasn't there" — the failing job kept failing. Now `_fresh_merge_ref()` resolves the ref's upstream, fetches it, and if the local branch is behind, redirects the merge to the upstream (e.g. `origin/master`) with a loud note: `local master was N behind origin/master — merging origin/master (latest) instead`. Offline / fetch-fail / no-upstream cases warn and fall back to the local ref (no hard failure). Remote-tracking refs like `origin/master` are refreshed directly.

### Changed

- **`rector-mcp`'s `System error:` suppression is now defense-in-depth, not load-bearing.** The root cause behind the warm `ClassReflection must be resolved for class X` failures ([#273](https://github.com/Digital-Process-Tools/claude-supertool/issues/273)) is fixed upstream in `dpt/mcp-rector-warm` 0.4.0: the warm daemon reused one Rector container and never reset Rector's `DynamicSourceLocatorProvider`, which caches its source locator for every non-PHPUnit run — so the second file in a warm session was analysed with a locator that only knew the *first* file. The daemon now resets reflection state per call (matching `AbstractRectorTestCase`), so this branch should no longer fire. The adapter comment was updated to reflect that it remains only to absorb any future non-deterministic engine glitch. **Requires `dpt/mcp-rector-warm` ≥ 0.4.0** (`composer global update dpt/mcp-rector-warm`).

### Added

### Security

- **`op_paste` containment ordering.** Previously `op_paste` called `os.makedirs(parent)` BEFORE `_atomic_write`'s `_safe_path` check, so a traversal path like `../../tmp/evil/foo` would create directories outside cwd before the write itself was rejected — leaving empty-dir pollution. `op_paste` now runs `_safe_path` at entry. Side benefit: closes the NUL-byte-in-path xfail (`_safe_path` rejects NUL before `os.replace` can leak a `ValueError`).

### Security

- **Hardening bundle.** Smaller defence-in-depth items from the audit (closes [#150](https://github.com/Digital-Process-Tools/claude-supertool/issues/150)):
  - **Gitcli flag smuggling**: `git-checkout REF`, `git-merge REF`, `git-blame PATH` reject refs/paths starting with `-` (e.g. `--orphan=evil`, `--abort`, `-X theirs`). `git-blame` uses `--` separator to keep a path-with-dash from being parsed as a flag.
  - **Regex ReDoS guards** on `grep`: pattern length capped at 1000 chars; nested unbounded quantifiers (`(a+)+`, `(.+)*`) rejected before they touch file content.
  - **`validate_staged` / `format_staged`** use `git diff -z --diff-filter=ACMR` (filenames with newlines/quotes survive) and reject symlinks — a staged symlink to `/etc/hosts` would otherwise be REWRITTEN by formatters.
  - **`xmllint` validator** runs with `--nonet --noent` so libxml2 can't fetch external entities or follow URI references during validation (XXE defence-in-depth).
  - **Validator cache HMAC** at `~/.cache/supertool/.cache_key` (mode 0600, 32 random bytes, generated on first use). Each cache entry wrapped with HMAC-SHA256 of its body. Attacker with write access to `~/.cache/supertool/validators/` cannot forge a passing `ok: true` entry without also reading the secret. Legacy unwrapped entries treated as miss.
- **Social publishing safety.** Three guards for the dev.to / bluesky publish + comment ops (closes [#149](https://github.com/Digital-Process-Tools/claude-supertool/issues/149)):
  - `file://` body must resolve under `.max/`, `drafts/`, `posts/`, or `blog/` (relative to cwd). Closes the credential-exfil vector: `bluesky_publish:file:///Users/.../app_password` now rejected before the file is read. Extend additively via `$SUPERTOOL_PUBLISH_BODY_ALLOWLIST=path1:path2` or `"publish_body_allowlist": [...]` in `.supertool.json`.
  - Confirm-default — `bluesky_publish` / `devto_publish` refuse to run without `|force`, `SUPERTOOL_NO_PUBLISH_CONFIRM=1` env, or `"no_publish_confirm": true` in `.supertool.json`. Blocks single-shot publish from a prompt-injected op.
  - Token-file mode check — `check_token_file_mode` refuses to load tokens at mode 0644+ (group/world-readable). Mirrors `ssh`'s SSH-key check.
- **MCP daemon UDS hardened.** Socket + pidfile + log moved from `/tmp/supertool-mcp-<hash>.{sock,pid,log,stderr}` (world-writable parent dir, predictable hash) to per-user runtime dir (`$XDG_RUNTIME_DIR/supertool/mcp/` on Linux, `~/Library/Caches/supertool/mcp/` on macOS, `~/.cache/supertool/mcp/` fallback). Dir created mode `0700`, ownership-checked at startup. Pidfile + log files open with `O_NOFOLLOW|O_CREAT|O_EXCL` so symlink-squatting attacks no longer overwrite victim files. Peer-uid check on every accept (defence in depth on top of parent-dir perms). Server names validated against `[A-Za-z0-9_-]{1,64}`. `os.umask(0o077)` reset in detach. Override via `$SUPERTOOL_RUNTIME_DIR`. Closes [#148](https://github.com/Digital-Process-Tools/claude-supertool/issues/148).
- **Vim shell verbs gated.** `:!cmd`, `:%!cmd`, `:N,M!cmd`, `:r !cmd` are disabled by default. A prompt-injected vim payload like `:!rm -rf ~` is rejected with a clean error. Editor verbs (i/a/o/d/s/etc.) are unaffected. Opt-in via `SUPERTOOL_ALLOW_VIM_SHELL=1` (env) **or** `"allow_vim_shell": true` in `.supertool.json`. Closes [#147](https://github.com/Digital-Process-Tools/claude-supertool/issues/147).
- **`:r FILE` honours cwd containment.** Vim's `:r FILE` (without `!`) now routes through `_safe_path` — reading `/etc/passwd` or `~/.ssh/id_rsa` into the buffer is rejected. Opt-out is the same `SUPERTOOL_ALLOW_OUTSIDE_CWD=1` as the rest of #146.
- **Path containment (`_safe_path`).** Every op path arg now resolves under cwd. A malicious `.supertool.json` or prompt-injected op like `paste:~/.ssh/authorized_keys:::pwned` or `read:/etc/passwd` is rejected with a clean error. Symlinks crossing the boundary are caught (realpath follows them). NUL bytes rejected early. Closes [#146](https://github.com/Digital-Process-Tools/claude-supertool/issues/146).
- **Opt-out**: set `SUPERTOOL_ALLOW_OUTSIDE_CWD=1` (env, one-off) **or** `"allow_outside_cwd": true` in `.supertool.json` (project-pinned, no env var dance). Env takes precedence.
- **Default excludes extended**: `.env`, `.env.*`, `.max/`, `.ssh/`, `.aws/`, `.gnupg/`, `.kube/`, `.docker/`, `.terraform/`, `.chef/`, `.npm/`, `secrets/`, `credentials/` are now pruned by `grep`/`glob`/`tree`/`map` so tokens don't surface into an LLM's context.
- Windows-compat: `os.path.normcase` handles case-insensitive drive letters (`c:\Users` == `C:\users`) and separator normalization.
