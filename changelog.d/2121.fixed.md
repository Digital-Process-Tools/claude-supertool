- **`doctor` warned about a possible stale symlink for the exact launcher script that is this project's own documented remedy for #2071's dangling-symlink trap** ([#2121](https://github.com/Digital-Process-Tools/claude-supertool/issues/2121)). `_doctor_symlink`'s `path_resolves_to_running_module` check compared PATHS, not versions -- a `~/.local/bin/supertool` launcher that resolves the newest installed build at run time and `exec`s it necessarily fails a path comparison against `_supertool.py` under a version directory while being exactly as current as the module answering the call, so the person who applied #2071's fix was the one warned about it, on every run, forever, with both offered explanations (a worktree, a stale symlink) false. `_doctor_symlink` now asks the cheaper question directly for a PATH entry that differs by path and is not dangling: it runs `<path> version` and compares what it answers against `VERSION`. Three states, not two -- `current` (agrees, no note), `stale` (disagrees, the note now names the version it actually answered as), and `unknown` (could not run or parse, reported as such rather than folded into either). A dangling symlink, where the version check is deliberately never attempted, no longer draws the `unknown` note either: it would have claimed `version` was run and did not answer about a subprocess that was never spawned, hedging under a `DANGLING` line one row above that is a stronger and already-correct diagnosis.
