- **`grep` and `grep:@payload` take a `:full` flag / `full` field that suppresses the 500-char per-line cap for one call** ([#1712](https://github.com/Digital-Process-Tools/claude-supertool/issues/1712)). A pathological single line (e.g. one giant `.json` description or a minified bundle) was always cut with an honest, actionable note -- the exact `read:PATH:LINE-LINE` remedy -- but confirming a matched line's real contents cost a second round-trip through that remedy every time. `grep:PATTERN:PATH:LIMIT:CONTEXT:full` (order-independent with `count`/`no-auto-read`, and the same shape composes with `grep_around`'s context rendering) now returns every matched and context line uncut in the same call, with a disclosure note naming how many lines the cap would otherwise have cut rather than silently rendering identically to a call where nothing was long enough to matter. The default is unchanged for calls that do not ask -- the cap in `_cap_grep_line` still protects a batched multi-op call from one enormous line -- and `full` does not raise `grep_around`'s separate ~16KB whole-response budget (#241), which is a different protection against a different failure.
