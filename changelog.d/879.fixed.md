- **`git-push` declined an inherited-wrong upstream and then prescribed the one command the project's own hook forbids** ([#879](https://github.com/Digital-Process-Tools/claude-supertool/issues/879)). The refusal itself was right and is unchanged: an `@{upstream}` resolving to a different branch is genuinely ambiguous, and [#787](https://github.com/Digital-Process-Tools/claude-supertool/issues/787) taught the op to detect that before invoking `git push` rather than render git's own rejection as a remote one. What it handed back was the problem. Both remedies it printed were raw `git push`, and raw `git push` is hook-blocked in the repo this op was built to serve — by a hook that exists precisely *because* `git-push` is better than raw git. Two correct rules composed into a dead end.

  The state is not exotic. `git worktree add -b <new> <base>` leaves the new branch tracking `<base>` (`branch.autoSetupMerge` tracks the *start point*), which is the documented way every worktree branch in this repo starts — so every one of them arrives here on its first push. The way out that actually got used was `git branch --unset-upstream`, then re-run the op: git trivia that works, and a successful workaround is how a defect stays unfiled for weeks.

  Both ways out are now flags on the op — see the Added entry. The receipt no longer prints a command the caller cannot run, and the test that guards it does not stop at asserting the printed text: it parses each remedy back out of the op's own output, executes it, and reads the remote afterwards to see where the commits landed. A prescribed remedy nobody ran is a claim, not a receipt.
