- **`.supertool.json`'s trust model is now documented, and the config walk-up no longer reaches past the repo it started in or accepts a config another local account can rewrite** ([#695](https://github.com/Digital-Process-Tools/claude-supertool/issues/695)). The rule -- opening a project and running an op already executes that project's configuration, since `ops.<name>.cmd` runs a shell command the moment the op is invoked -- previously lived only in `_safe_path`'s docstring; `SECURITY.md` said nothing about it and `docs/configuration.md` presented `.supertool.json` as pure ergonomics. Both now say it in plain language. `_load_config()`'s walk-up now stops at the first ancestor containing `.git` rather than continuing to `/`, so a config sitting in a shared parent directory (a `/tmp` extraction, a CI checkout root) above the repo can no longer be picked up silently; a caller not inside a git repo at all keeps the old to-`/` behaviour, since there is no repo boundary to stop at. A new `_config_trust_violation` check refuses a candidate that is group/world-writable or not owned by the caller (root excepted) -- the same rule `ssh` applies to `~/.ssh/config` and git applies via `safe.directory` -- POSIX-only, since `st_uid` and the write bits are meaningless on Windows. `allow_outside_cwd` is deliberately left honourable from repo-local config: the docstring's own existing trust-model note already holds -- an attacker able to write a hostile `.supertool.json` can already declare an arbitrary `ops.*.cmd`, so restricting one knob among many adds no real containment and risks breaking a repo relying on the setting today.
