- **A truncated delegated `grep` said how truncated it was not, and now says how many matches there are** ([#1771](https://github.com/Digital-Process-Tools/claude-supertool/issues/1771)). `(10 results in 1 files, scanned ? files — delegated to rtk, limit 10 — TRUNCATED, more matches exist (total not counted))` told the caller the answer was partial and not *how* partial, over a denominator that was unknown too — an unquantified numerator over an unquantified denominator, which is this repo's own defect class with both halves missing at once. It matters more on this op than on an ordinary grep: a rule shipped in `claude-jit-context` refuses the harness `Grep` tool and names `grep` as the replacement, so every completeness sweep an agent runs lands on this path, including the ones whose whole purpose is completeness.

  **The count was obtainable, and cheaply.** #414 declined it on the grounds that computing the denominator meant walking the tree in Python, which is what delegation exists to avoid — true, and it hid a third option. `grep -rc` is not that walk: same C engine, same tree, and `-rc` names *every* file it scanned, zero-match ones included, so one extra call answers the numerator and the denominator together. A truncated delegated grep now reads `(10 results in 3 files, scanned 1154 files — delegated to rtk, limit 10 — TRUNCATED, 47 matches total)`, in the native walker's own vocabulary. The total is **exact** rather than the walker's `N+ … (count capped at N)`: that spelling exists because a Python walk has to stop counting somewhere, and this one does not.

  **The second pass is bought only where it buys something.** It runs on truncation and never on a complete result, which needs no total and keeps the single call it has always had. Measured on this repository (1,159 files, dense pattern): 0.47s for the `-m`-capped match pass, 0.65s for the census. `builtin-ops.grep.count_truncated: 0` (or `SUPERTOOL_GREP_COUNT_TRUNCATED=0`) declines it for a tree where that trade is wrong.

  **The uncounted state survives, named rather than filed as an aside.** rtk absent, failing or timing out; `-rc` output that is not `path:N`; a total at or below the number of rows printed under it, because the two passes are separate reads of a tree that can change between them; or the switch above turned off — any of those and the report says `— TRUNCATED, more matches exist, total unknown (the delegated count pass did not run)` and prints no number at all. A guessed total is worse than an admitted gap, because nothing downstream knows to distrust it.

  **Excluded files are subtracted from both numbers.** The default exclude list carries negations, which system grep cannot express, so `_grep_exclude_flags` withholds every wildcard entry and a `server.pem` really is read by the census pass — counting it would have put matches in the total that the caller was told were not there, and a file in the denominator that nobody searched. The census applies the same `_is_excluded` the native walker does.

  **Two of the issue's four questions are deliberately left open**, and both need a decision this change was not the place to make. Whether the default limit of 10 should still cap a sweep is a repo-wide default with `all` and an explicit `LIMIT` already answering it. Whether a truncated result should exit non-zero is a change to `main()`, which returns one batch-level `1 if any_failure else 0` — a per-op truncation code needs a composition rule for a batch where one op truncates and another fails, and that belongs in the dispatcher rather than in `grep`. The `?` denominator on a *complete* delegated result also stays: with no `TRUNCATED` marker every match is on the screen, which is the only thing a breadth question needed the denominator for.
