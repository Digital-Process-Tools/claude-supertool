- **`read` and `replace_lines` disagreed about what a line is, so editing line N could edit a different line** ([#1060](https://github.com/Digital-Process-Tools/claude-supertool/issues/1060)). `render_file` split the file's bytes; `op_replace_lines` split the decoded string, and `str.splitlines()` additionally breaks on U+000B, U+000C, U+001C, U+001D, U+001E, U+0085, U+2028 and U+2029. A file holding any of those had two line numberings, with the ops that read on one side and the ops that write on the other: you read your target at line N, asked for line N, and the write landed elsewhere. The edit succeeded, the receipt named line N, and the content at line N was not what the reader saw there. The overwritten content is gone.

  **One function owns the definition and every line-numbering op uses it.** Two independent splits is how this happened; fixing one side to match the other by hand would have left the next author free to reintroduce it. `read`, `replace_lines`, and the receipt line-lists of `edit` and `append` all route through it.

  **The definition chosen is the conservative one — LF, CR and CRLF only.** That is what a caller counting lines in an editor, in `wc -l`, or in any line-oriented CLI will have counted; `str.splitlines()` is arguably more correct about Unicode and is definitely more surprising. This is a contract change for `replace_lines` on files containing those eight characters, stated here rather than picked by whichever function was easier to edit.

  **Where the two definitions differ, the read discloses it** instead of silently picking one: a file holding any of the eight gets a `note:` line under its header naming which, and saying that other tools will number it differently while supertool's own reads and line-addressed edits agree with each other. An ordinary file says nothing. The disclosure also survives delegation to `rtk`, which renders the body but knows nothing about supertool's contract.
