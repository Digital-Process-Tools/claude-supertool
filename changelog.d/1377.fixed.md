- **A dying interpreter had the fragment of its verdict forwarded as the verdict** ([#1377](https://github.com/Digital-Process-Tools/claude-supertool/issues/1377)). #1377 removed the guard wrapper's separate probe spawn, so an envelope on stdout became both the proof that a candidate is a Python 3 and the answer itself, matched as a prefix. The exit code stopped being consulted. An interpreter killed part-way through `sys.stdout.write` — OOM, a signal, a launcher wrapping the child — leaves a *prefix* of that envelope, which is exactly what the prefix test accepts: `hooks/pre-bash-guard.sh` printed the fragment verbatim and exited 0. Claude Code cannot parse it, so there was no decision and no `additionalContext` at all — the silent fail-open the wrapper's own header exists to refuse, in the shape [#1347](https://github.com/Digital-Process-Tools/claude-supertool/issues/1347) opens with.
- An envelope is now forwarded only from a rung that also exited 0, which every path through `hooks/pre_bash_guard.py` does by construction. This is not the pre-#1377 shape returning: a rung that fails is still only recorded and the walk still continues to the next name, so a host with a broken `python3.14` and a working `python3.12` keeps its guard. What it costs is a whole envelope followed by a non-zero exit for an unrelated reason, whose answer is dropped — bash cannot tell that from a fragment, and dropping it buys a disclosed decline where forwarding it buys silence (#1377).
- The decline now distinguishes the two failures, because they send a reader to different places: a rung that "began writing a verdict and then exited N" is a dying interpreter, where "exited N without writing a verdict" is one that never answered. **The first of those is sticky**, reported in preference to the last rung's generic failure — the walk continues past a dying rung, so a message built from whichever rung was tried last named one that was never going to answer and buried the one that crashed mid-write (#1377).
