- **An `eslint` validator — JavaScript semantics were entirely unchecked** ([#667](https://github.com/Digital-Process-Tools/claude-supertool/issues/667)). `eslint -f json`, global binary or `npx --no-install`, `rollback_on_fail: false`. Before this, a plain `.js` file got syntax (`node-check`), formatting (`prettier-check`) and nothing else: no unused variables, no `==` versus `===`, no unreachable code, no shadowed declarations.

  **Three ways eslint says nothing, and all three used to read as a clean file.** The tool not installed; the tool installed with no resolvable config, which exits 2 with an *empty stdout* and the explanation on stderr; and — the one the issue does not mention, verified against eslint 10.8.0 — a file matching an ignore pattern, which exits **zero** and returns a single `ruleId: null` message saying it was ignored. All three now report `skipped` with the reason.

  **No fallback configuration is shipped, and that is the decision rather than an omission.** Inventing one would have the validator enforce rules the project never adopted, and the first thing anyone does about findings they did not opt into is switch the validator off. It would also be misleading for the case that motivated the issue: the "never `var`" rule mostly governs JavaScript inside XML templates and inline handlers, which eslint cannot reach at all, so a fallback would produce a green that says nothing about the rule it was configured for. A repository that wants JavaScript linted adds `eslint.config.js`; until then the row states on every edit that nobody checked.
