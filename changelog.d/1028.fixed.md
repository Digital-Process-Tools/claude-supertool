- **`git-status` reported a cleanly rebased branch as `ahead 5, behind 1`, which reads as lost work** ([#1028](https://github.com/Digital-Process-Tools/claude-supertool/issues/1028)). The count is arithmetically true and its ordinary meaning is the opposite of what happened: `ahead N, behind M` is the render for two histories that have genuinely diverged, while after a rebase nothing was lost and the remote merely holds the pre-rebase originals of commits the branch already carries. Two agents stopped mid-task on separate lanes the same night to work out which of the two they were in. Class: a reader acting reasonably concludes "I have diverged and may lose commits" where the truth is "I am ahead cleanly and the remote is behind".

  The count is **not** suppressed — that would trade a confusing render for a quiet one, and lose the fact that the remote differs at all. A two-sided count now carries a `Diverged:` line saying which kind it is, decided by `git rev-list --count --right-only --cherry-pick HEAD...@{upstream}`: `--cherry-pick` drops every upstream commit whose patch already exists on this side, so what remains is exactly the commits the remote has and this branch does not. Zero is a rebase or any other replay (`REBASED — … nothing is lost and the remote is stale`, with the force-with-lease push); non-zero names how many remote commits are genuinely absent from this history and says a force push would discard them. A check that did not answer renders as neither verdict, in the `UNKNOWN — … did not answer` vocabulary [#1002](https://github.com/Digital-Process-Tools/claude-supertool/issues/1002) established for this file. The extra call is made only when both sides are non-zero, which is the only ambiguous render.

  An unrecognised mode is now reported instead of silently rendering the default ([#647](https://github.com/Digital-Process-Tools/claude-supertool/issues/647)'s class): `git-status:breif` used to look exactly like the render you asked for.
