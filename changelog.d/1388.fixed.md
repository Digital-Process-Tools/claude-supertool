- **27 preset scripts died mid-render on a Windows console, not 2** ([#1388](https://github.com/Digital-Process-Tools/claude-supertool/issues/1388)). `gh-starred` printed `→` and `gh-find-starable` printed `★` straight to stdout. Run straight from a shell — no supertool in front to pin `PYTHONIOENCODING=utf-8` — a console codec with no mapping for the character raises `UnicodeEncodeError` partway through the output, so the work lands and the receipt says it crashed. Every preset entry point that prints a non-ASCII literal of its own now calls `use_utf8_stdout()` as the first statement of `main()`, from the new `presets/_console.py`.

  The issue named two instances; the census says 27, and which ones die depends on the codepage rather than on the file. cp1252 encodes `—`, `…`, `•` and `·`, so only `→` (`starred.py`), `★` (`find_starable.py`) and `↳` (`mcp/status.py`) raise there. cp437 and cp850 — the actual default of a US Windows console — encode none of the em dashes, so all 27 raise. Observed on macOS against a real cp1252 stream, not reasoned: `PYTHONIOENCODING=cp1252 python3 presets/github/starred.py 5` printed two lines and then died on U+2192, while the same call through `supertool gh-starred:5` under the same environment completed.

  **No exemption route, deliberately.** The issue asked for a per-literal rule — a glyph goes through a degrading writer or declares an exemption — and worried that a loose exemption makes the scan's zero meaningless. The per-literal framing is what does not survive: there are 325 non-ASCII print literals in shipped code, `_untrusted` exposes no writer for a glyph the *tool* wrote, and the property that decides whether a `print` survives is `sys.stdout.encoding` — settled once per process, not per literal. At that granularity nothing an entry point could state would make a raising `print()` acceptable, and the precondition costs one line.

  `tests/test_encoding_seam.py` enumerates it in three states rather than two: pinned, unpinned, and **unreadable** — an entry point printing a glyph whose `main()` the rule cannot find. The `presets/git/` scan it generalises has two states and silently `continue`s past that third, so such a file has always read as compliant; ten preset entry points are in that shape today and pass only because none of them prints a glyph. Both floors are asserted too, so a zero means the scan looked rather than that it stopped looking.

It has held `tests/` to the same rule as shipped code since #862, and the paragraph still described the pre-#862 exclusion and cited 125 violations that are not there.
