- **`channel:health` guards the watcher state files the way it already guarded the health file** ([#1191](https://github.com/Digital-Process-Tools/claude-supertool/issues/1191)). The `NOT DELIVERING` report lists every watcher whose own last emit found nobody home, built by globbing `/tmp/supertool-watch-*.state.json` — and that read had neither of the two guards [#1184](https://github.com/Digital-Process-Tools/claude-supertool/issues/1184) and [#1187](https://github.com/Digital-Process-Tools/claude-supertool/issues/1187) had just put on the health file thirty lines above it in the same file. A plain `open()` on a predictable name in a world-writable directory meant a symlink there had whatever it pointed at opened and parsed, and `last_emit.ts` was interpolated raw into the render, so the closing channel tag and the column-0 directive demonstrated on #1187 applied here verbatim. Worse than the health file on both counts: this name is not derived from a socket path at all, so the glob accepts any file a co-tenant chooses to create — including the `source` and watcher id, which are parsed out of the *filename*, and a POSIX filename carries any byte but `/` and NUL.

  The open is now `O_RDONLY | O_NOFOLLOW` with the descriptor closed on every path out, and the row text — `ts`, `source` and the id — goes through `presets/_untrusted.py`, with the one-line provenance note above the rows on any report that prints one. On Windows there is no `O_NOFOLLOW` and the open carries no guard; the tests measure `os.symlink` and `os.O_NOFOLLOW` rather than reading `os.name`, and skip instead of passing vacuously.

- **A state file that cannot be read is a row, not a gap** ([#1191](https://github.com/Digital-Process-Tools/claude-supertool/issues/1191)). Every unreadable file was previously `continue`d past, so a listing whose whole job is completeness silently dropped exactly the entries somebody had tampered with. Each one now renders on its own line saying why — a refused symlink and an unparseable file are named apart, because they send an operator to different places — and the report never says `none recorded an emit into this socket` when files were present and unread. Declining the whole listing was the alternative and is the worse trade: one `ln -s` in `/tmp` would then erase every other watcher from the report. An unread row is not claimed for this socket either — `sock_path` is inside the file, and `STATE_DIR` is shared across sessions even when the socket paths are not, so the line declines that attribution out loud rather than guessing it in either direction.
- **Invalid UTF-8 in either `/tmp` file no longer answers with a traceback** ([#1191](https://github.com/Digital-Process-Tools/claude-supertool/issues/1191)). `json.load` decodes the stream before it parses it, so two bytes a same-uid writer chooses raise `UnicodeDecodeError` — a `ValueError`, and neither the `OSError` nor the `json.JSONDecodeError` that `read_health` and the state-file read both named. It escaped as an unhandled traceback from the one op whose subject is that declining beats guessing, where the answer is `CANNOT DETERMINE` for the health file and an unread row for a state file. Pre-existing on the health read, and [#1184](https://github.com/Digital-Process-Tools/claude-supertool/issues/1184)'s fix rewrote that exact `except` into three arms without widening it. Both arms now catch `ValueError`, deliberately the base rather than the two leaves: a third decode failure must decline too, not crash the report that says a fleet is down.
