- **`hooks/session-start.sh` now recognises its own stale symlink from an earlier plugin release, instead of calling it a stranger's file** ([#2071](https://github.com/Digital-Process-Tools/claude-supertool/issues/2071)). `$BIN` carries the *currently running* version's path, so the hook compared the existing `./supertool` symlink's target against it for exact equality -- and a plugin update alone made the previous session's own symlink fail that check, falling into the branch written for a file the hook has never seen: `./supertool already exists here and is not the plugin symlink -- leaving it untouched.` Both halves were false in the sense a reader took them: it was the plugin symlink, just a stale one, and nothing was deciding to leave it alone -- nothing ever looked at it again. Reported cost: a shipped fix sat unused in the plugin cache for ten days while every session kept answering from the older version, with nothing on any surface saying so. The hook now recognises a symlink whose target sits inside a *sibling version directory of this same plugin's own cache* -- same cache root, same binary name, only the version segment differs -- as its own artifact rather than a stranger's, names both versions, and repoints it. This is not the trust decision #711/#737 refuse: nothing local is read or executed, only two path strings are compared, so a checkout-owned `supertool.py` still gets no wrapper and a genuine stranger's file at `./supertool` is still left untouched.
