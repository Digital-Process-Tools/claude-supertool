- The repository now runs the raw-command guard it ships. `.claude/settings.json` wires `hooks/pre-bash-guard.sh` as a third `PreToolUse` hook on `Bash`, alongside the two jit-context hooks rather than inside them, so a failure in one is not the other's silence ([#1376](https://github.com/Digital-Process-Tools/claude-supertool/issues/1376)). Until now the guard reached this checkout only through a plugin release: the install these sessions run is v0.25.0, whose `hooks/` holds `session-start.sh` and no `pre-bash-guard.sh` at all.
- Three hand-written `block` rules under `.claude/jit-context/tools/00-manual/` are retired, markdown and index row together, in the same commit that wires the guard — so nothing is uncovered in between and no command is ever refused twice with two different messages. `gh-pr-view-merge-have-ops.md`, `gh-list-limit.md` and `git-push-has-an-op.md` go; the guard blocks every command each of them forbade, verified per command through `guard:` rather than read off the registry.
- Five rules stay, each because `replaces` cannot reach what it forbids: `supertool-no-cut.md` is about piping an *op's own* output, `harness-tools-blocked.md` fires on non-Bash tools, `op-defaults-that-narrow.md` on an op string rather than a raw command, `merged-is-not-ancestry.md` on `git branch --merged`, which `git-worktrees` answers for a different population, and `git-C-has-cwd.md` on `git -C <path> <sub>`, which no mapping can reach until [#1421](https://github.com/Digital-Process-Tools/claude-supertool/issues/1421). Each keeper's command is asserted `clean` against the guard, so the day a mapping starts covering one the test goes red and names the rule.
