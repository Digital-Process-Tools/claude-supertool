- **`gl-runners` — a failed running-jobs read is no longer an idle fleet** ([#1112](https://github.com/Digital-Process-Tools/claude-supertool/issues/1112)). `hercule` was executing `test_unit_dv` and `test_unit_mathematic` on a live merge-request pipeline. The watcher emitted `runner_liveness_unknown runner_id=25 last_seen=30m running_on_it="0"`, and `gl-runners:queue` read seconds later showed both jobs on it. The event retracted itself 69 seconds later with `running_on_it="2"` and nothing about the fleet having changed — which is the trap, not the exoneration: an operator acting inside that window drains a runner mid-job, and one who waits concludes the alerting is fine.

  **One read answered both the verdict and the count.** `_fetch_fleet` coerced an API error on the running-jobs list to `[]`, and `annotate_live_jobs` stamped its "evidence gathered" mark on every runner regardless. That mark exists to keep `UnannotatedFleetError` firing when nobody looked, so stamping it on an unread list bypassed the guard at the one caller most able to trip it: liveness fell through past both throughput tests onto `contacted_at`, the field GitLab throttles and this module's own docstring puts last, and `running_on_it` reported zero running jobs on a runner running two.

  **This is a bad read, not a bad disclosure policy.** [#750](https://github.com/Digital-Process-Tools/claude-supertool/issues/750) decided the unproven queue keeps being reported with only the certainty claim withdrawn, because "it said nothing while I was blocked" is this repo's most-filed defect; that stands untouched, and `tests/test_gl_runners_false_liveness_unknown_1112.py` fences it — a stale heartbeat over a running list that was genuinely read and genuinely empty still fires `runner_liveness_unknown`. What changed is that an unread list is now distinguishable from an empty one. `annotate_live_jobs(runners, None)` annotates nothing, so any later liveness question raises rather than guessing, and all three callers stopped coercing: the watcher fails the whole tick and retries in a minute (the sibling handling the pending list already did this), radar returns `WARNING — the running-jobs list is unreadable` instead of blaming runners for a read that failed on our side, and `gl-runners` refuses rather than printing a table whose every liveness marker is derived from a list it does not have.

  **A second liveness read was forging the opposite verdict, found by auditing this one for timing dependencies.** Every age in the module is GitLab's clock subtracted from ours and nothing measures the gap. When ours runs behind, `_age_seconds` returns a negative number, and both temporal rungs of `_is_responsive` are a `<=` against a ceiling — which a negative satisfies. A heartbeat two hours in the future read as *fresh*, a job history dated in the future counted as work finished just now, and the queue-age floor in both `classify_queue` and `stranded_split_for` dropped every pending job as "queued too recently", so the board came back empty. Four sites, and the floor is the one worth remembering: skew belongs to the host, so a job's `created_at` goes ahead exactly when `contacted_at` does, and guarding only the liveness rungs yields an honest UNKNOWN about a queue that has silently disappeared from the same render. That direction is worse than the one filed: a false `runner_liveness_unknown` is a loud alarm about a healthy runner, a false *alive* is a silent all-clear over a wedged one, and it lands on the whole fleet at once because skew belongs to the host rather than to any runner. Ages beyond `_CLOCK_SKEW_TOLERANCE_SECONDS` in the future are no longer evidence of anything, so the runner lands in the existing UNKNOWN state; the tolerance is deliberate, because two NTP-synced hosts disagree by milliseconds and refusing every negative age would withdraw the evidence from an entire healthy fleet on ordinary jitter. `_human_age` says `ahead of our clock` instead of rendering `-3600s` as though it were a measurement. This is not what produced the filed event — that was the coerced read above — and it is not reachable from it; it is a second live path to a false liveness verdict in the same function.

  **Runner tags now reach the channel.** Every runner event carried `unsendable="1 payload key refused — tags (array)"`. The transport is right to refuse arrays and right to say so, but tags are exactly the field naming which jobs a runner can take, so they are joined at the emit site in `classify_queue`'s key format — a runner event and a queue event now name the same tag set the same way.
