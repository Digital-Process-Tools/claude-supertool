- **`test_parallel`'s three sequential-vs-parallel comparisons asserted an environment condition as if it were a product verdict** ([#1364](https://github.com/Digital-Process-Tools/claude-supertool/issues/1364)). They compared two independent subprocess runs of the same `read` byte-for-byte, and a `read` receipt's meta line can carry `git?` — the disclosure from [#705](https://github.com/Digital-Process-Tools/claude-supertool/issues/705) that the working-tree lookup declined, state unknown rather than clean. One run can trip that while the other does not, and the parallel one spawns four `git status` at once against a 2s timeout, so it is the likelier side. One `pytest (windows-latest, 3.10)` leg went red on a docs-only diff, expecting `crlf git?` and getting `crlf`.

  **The product is right in both forms, and that was checked before the test was touched.** Outside a repository the steady-state answer is no token: git exits non-zero with "not a git repository", `_path_meta_suffix` recognises that and stays silent. The token needs the git call to fail some other way. Both such failures were reproduced against the product on macOS by putting a shim `git` on `PATH` — a `sleep 4` and an `exit 128` with a dubious-ownership message each turn `(1 lines, 10 bytes) crlf` into `(1 lines, 10 bytes) crlf git?`, and an end-to-end run of the test's own five reads with that shim on one side reproduces the CI diff exactly. So neither reading of the receipt is a dropped disclosure; the comparison was over-specific.

  **The token is normalised out of both sides and nothing else is.** Order, headers and content stay byte-exact, which is what those tests exist to check. The Windows trigger itself is not reproducible on macOS and is not claimed to be: what is observed is the mechanism, not the runner condition that fires it.
