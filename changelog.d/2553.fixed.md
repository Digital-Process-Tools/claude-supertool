- **`serialize_once`'s absence recheck no longer gives up after one beat** ([#2553](https://github.com/Digital-Process-Tools/claude-supertool/issues/2553)). The #2552 fix for #2551 disambiguated an `OSError` from `os.open()` by rechecking whether the lock file exists -- but trusted a single 0.05s recheck to tell "the `lock_dir` is genuinely unusable" from "the holder just unlinked the lock file on release, and the lock is actually free": if that one recheck still read absent, it ran `fn()` immediately. A third caller can win the now-free lock at any point during, or after, that one recheck window, not only inside its first 0.05s -- under CI scheduling jitter, a waiter that gave up on the stale reading ran `fn()` concurrently with that third caller, caught by `tests/test_go_warmup_lock_2331.py::test_two_racing_calls_still_serialize_when_contention_raises_permission_error` (`max concurrently active: 2`) on `macos-latest, 3.9`. The fix retries the create itself, bounded by the same `deadline` every other wait on this path already uses, instead of trusting one more snapshot read of `exists()`: it only falls back to running `fn()` directly once the create keeps failing with no lock file ever appearing for the whole retry window. A new test, `test_the_absence_recheck_keeps_waiting_past_one_beat_before_giving_up`, pins this by holding the "still gone" reading past the old single-recheck window before a lock file appears, asserting the caller keeps waiting rather than bailing out immediately.
