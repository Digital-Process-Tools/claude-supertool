- **`between:PATH:1-30` — the range spelling `read:` accepts — answered `ERROR: file not found: 1-30`** ([#1234](https://github.com/Digital-Process-Tools/claude-supertool/issues/1234)). `read:` takes both `PATH:OFFSET:LIMIT` and `PATH:START-END`, and both spellings reach `between` from the same muscle memory. Only the colon one was caught by the [#983](https://github.com/Digital-Process-Tools/claude-supertool/issues/983) hint; the dash one fell through to a filesystem complaint about a line range, which is the tool's own mis-split wearing the shape of an absence on disk. Both now redirect to `read:PATH:START-END`, and the [#1142](https://github.com/Digital-Process-Tools/claude-supertool/issues/1142) containment guard covers the new spelling — the hint stats a slot `_PATH_ARG_POSITIONS` does not, so without it the pair of answers is an existence oracle.
- **A batch where one op is refused now says how many ops ran.** Filed as a refusal *suppressing* the other ops' output. Reproduced at 0.32.0 it does not: every op runs and every op renders. What was missing is the reconciliation — the exit code is one bit for a call that ran N ops, and a shell `&&`, a pre-commit hook or an agent harness that reframes any non-zero command as an error block had nothing in the output to tell it that most of the answers were complete.
- The disclosure is a line, not a change of behaviour: a batch was never all-or-nothing and must not start being one.

  ```
  [batch] 3 ops ran — 2 ok, 1 refused. Exit 1 flags the refusal; the other 2 answers above are complete.
  ```

- Only on a multi-op call, and only when the exit code is about to be 1. `[batch] N ops ran — all N refused.` when nothing survived, since "the other answers are complete" would then be a claim about nothing. And when `any_failure` came from a skipped write, a rolled-back edit or a validator that could not run, the line says so instead of printing `0 refused` beside an exit 1 and sending the reader hunting for an op that did not fail.
- **When both kinds of failure land in one call the completeness claim is withheld entirely.** The refusal count reads first-line `ERROR`/`FAIL` markers, so it does not see the failures that render as ordinary prose — `replace`'s `(0 occurrences of 'x' found)`, an edit a validator reverted — which reach the exit code through `_SKIP_COUNT` and `_ROLLBACK_COUNT` instead. An op can therefore sit outside the refusal count and still not have landed, and a two-branch tally called one such op `1 ok` and asserted "the other 1 answers above are complete" directly under that op's own `1 skipped — nothing changed on disk`. Found reviewing this change: the disclosure line had acquired the defect it was written to fix.
