- **`no-changelog` can now clear the run that asked for it** ([#1722](https://github.com/Digital-Process-Tools/claude-supertool/issues/1722)). The changelog check prints `label the PR 'no-changelog' if it genuinely announces nothing`, and taking that branch could not clear the PR. Labelling starts a fresh run which passes, but nothing removes the run that failed before the label existed, and the merge gate is conjunctive over every run on the head sha — correctly so. Re-running did not help either: a re-run replays the event payload the run was created with, so `github.event.pull_request.labels` was the set as it stood *before* the label. The documented remedy therefore ended where it started, and the only route out was an empty commit whose message existed to explain CI mechanics (measured on #1721, twice). The check now reads `repos/{repo}/issues/{pr}/labels` **live**, so label-then-re-run works, and the workflow declares the `pull-requests: read` scope that needs. Two costs, both stated rather than hidden: the verdict is no longer reproducible from the run's own payload, and a label *removed* after the run started now reddens it — which it must, or the escape hatch outlives the decision to use it. If the live read fails, the job falls back to the run's payload, prints `note (live label read failed …)` instead of answering as though it had read something, and switches its remedy line from "re-run this check" to "push a commit" — that arm behaves exactly as this job did before, so it can turn a finding into a skip and never the reverse, and an outage cannot redden the board.
