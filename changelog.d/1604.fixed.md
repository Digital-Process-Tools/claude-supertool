- **A loaded CI runner's timeout is no longer published as a verdict about your file** ([#1604](https://github.com/Digital-Process-Tools/claude-supertool/issues/1604)). Fifth instance of one defect after [#1296](https://github.com/Digital-Process-Tools/claude-supertool/issues/1296), [#1360](https://github.com/Digital-Process-Tools/claude-supertool/issues/1360), [#1461](https://github.com/Digital-Process-Tools/claude-supertool/issues/1461) and [#1501](https://github.com/Digital-Process-Tools/claude-supertool/issues/1501), each fixed one adapter at a time: `cargo check` blew its 120s wall on a `windows-latest` leg and the assertion read `timeout (cargo check exceeded 120s)` as a statement about `sibling.rs`, on two pull requests whose diffs went nowhere near cargo. Both cleared on a plain re-run, so the price was never the re-run — it was that every Windows red on this repo had to be read before it could be dismissed.

  **The product half is `ruby-check`, and it is why the class kept needing a new issue.** It was the only adapter that gave its tool a `timeout=` and had no `except subprocess.TimeoutExpired` arm, so the wall escaped into the module-level `except Exception`, whose payload hardcodes `duration_ms: 0`. `after 0ms` beside "timed out after 30 seconds" reads as a rendering nit; it was load-bearing. The suite tells a real wall from an adapter whose error routing is broken by whether the elapsed time reaches the budget, so a 30-second stall reporting zero was unclassifiable and got published as a finding about a Ruby file with nothing wrong with it. It now reports the time it actually spent, names the budget it blew, and `TIMEOUT_S` is hoisted so the test budget derived from it tracks automatically.

  **The class is now checked rather than remembered.** [#1464](https://github.com/Digital-Process-Tools/claude-supertool/issues/1464)'s sweep reads every adapter's timeout arm and refuses any error code but `adapter` — so an adapter with no arm at all had nothing to inspect and passed it vacuously, which is this repo's own defect class sitting inside the guard written against it. A second sweep now asks the complementary question: every adapter that grants itself a wall must have somewhere for that wall to land.
