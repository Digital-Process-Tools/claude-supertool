- **An op whose exit code is its answer is no longer counted as a refusal — three correct `git-worktrees` answers rendered `FAIL` under a footer saying `all 3 refused`** ([#1672](https://github.com/Digital-Process-Tools/claude-supertool/issues/1672)). `git-worktrees` deliberately compresses its occupancy verdict into the process exit status — `0 = idle, 1 = occupied, 2 = cannot tell` — and documents it in the line immediately above the footer. The dispatcher reads any non-zero child exit as a refusal, so the composition asserted, in words, in the one line a reader keeps, that a scan which had answered three times had not run. This is not [#1291](https://github.com/Digital-Process-Tools/claude-supertool/issues/1291): [#1297](https://github.com/Digital-Process-Tools/claude-supertool/issues/1297)'s structural dispatch is correct that the exit was non-zero, and could not know that for this op non-zero is not failure — which is a property of the op, so it is now declared where the op's other properties are.

  **A registry entry may declare which exit codes are values.** `"exitStatus": {"values": [0, 1, 2]}`, beside `paths` and `safety`. Every listed integer is read as an answer; a code outside the list is still a refusal, so a crash exiting 127 is still a crash. The verdict line discloses it rather than leaving `PASS` to be reconciled against the op's own exit note two lines down: `PASS (7.79s) [exit 1 is this op's answer, not a verdict — its registry entry declares the exit code a value]`.

  **Declaring it spends a channel, so the failure has to arrive on another one.** For a listed non-zero code the verdict is taken from a line at column 0 beginning `ERROR: ` anywhere in the op's output, or anything on stderr. Both matter for this op specifically: `git-worktrees` returns 2 for `cannot tell` **and** for `git worktree list` failing outright, and a traceback exits 1, which is a listed value. Exit 0 is unchanged — it has always been a pass whatever the op printed.

  **The third direction in the issue — stop overloading the exit code — was priced before being declined, and the price is that it buys nothing.** `main` collapses every failing op to exit 1 and always has, so `supertool 'git-worktrees:PATH'` returned 1 to the shell for both `occupied` and `cannot tell` and never 2: measured on a `cannot tell` path, the preset exited 2 and the shell saw 1. Nothing can be branching on the integer through supertool, so removing it would break nothing and fix nothing; what crossed the boundary was only the false `refused`. The op's registry description said the caller saw those integers and no longer does.

  `docs/configuration.md`'s copy of the reserved-key list was three keys behind before this change (`restartMcp`, `replaces`, `paths`) and is now current — a config key wrongly believed reserved is one the author expects in the subprocess environment and does not get.
