- **`gh-branch` printed `concluded success` for a workflow the same render had just refused to clear** ([#1408](https://github.com/Digital-Process-Tools/claude-supertool/issues/1408)). GitHub closes a run object as `completed / success` while one of its own jobs is still `in_progress` — twice on 2026-08-11, 25 minutes apart, on `pytest (windows-latest, 3.11)` and `pytest (macos-latest, 3.12)`, and neither leg would ever have reported because the run that would have carried its result was already closed. The op read both fields honestly and printed both, so the workflow table said `concluded  success` three lines under a verdict saying that workflow had not concluded, and the natural resolution of that is *the verdict is being pedantic, merge it*. The `Outcome` cell now carries a `⚠` and a sentence under the table names which two sources disagree and which one the verdict acted on. Marked rather than rewritten: `success` is what the run object says, and printing something else would trade a loud disagreement for a quiet one. A run still **running** is untouched — a pending leg under an open run is an ordinary wait — and the leg arithmetic is unchanged, so the tally still sums and no consumer of `summarize()` gains a fifth bucket.
