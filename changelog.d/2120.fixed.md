- **Every read op's "to modify" footer suggested `./supertool`, which does not resolve in a `git worktree`** ([#2120](https://github.com/Digital-Process-Tools/claude-supertool/issues/2120)). `./supertool` is a gitignored symlink present in the main clone but never carried across by `git worktree`, so a dispatched agent -- exactly where this footer is read most -- got `No such file or directory` and reasonably read it as "the tool is not installed" rather than "the prefix was wrong". `_read_edit_hint`'s footer now goes through a new `_modify_hint`, which applies the same three-state check `presets/_st_hint.py`'s `st_hint` already uses for every other printed remedy in this repo (#905/#1012): `./supertool` only when a runnable wrapper genuinely sits on disk beside the running core, `sys.executable supertool.py` when only the entry point is there (the worktree case), and an explicit "no runnable supertool found" rather than either literal when neither is. Duplicated into `_supertool.py` rather than imported from `presets/`, which ships no `__init__.py` and is a tree of subprocess-invoked scripts, not a package core reaches into.
