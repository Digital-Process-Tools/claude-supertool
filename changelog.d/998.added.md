- **`gh-labels` — the repo's label vocabulary, with usage** ([#998](https://github.com/Digital-Process-Tools/claude-supertool/issues/998)). Before applying a label you have to know which labels exist, and `gh issue edit --add-label` offers nothing useful when you guess wrong. With no op for it the answer came from a hand-rolled `gh label list --json name -q '.[].name' | grep` pipeline — the surface [#454](https://github.com/Digital-Process-Tools/claude-supertool/issues/454) exists because of — paid on the *first* call of every triage or release-planning run, by every fresh agent, forever. The spelling is not portable either: this repo uses `priority-high`, `claude-remember` uses `priority:high` and has no `lane-*` family at all, so an agent carrying one repo's spelling into the other mislabels or silently no-ops.

  The op prints names, descriptions and how many **open** issues carry each, grouped by name prefix. The grouping is declared as inferred, because a prefix is a convention of whoever created the labels rather than a GitHub field, and a family of one is not rendered as a family.

  A count has three states and never two: exact when every open issue was read — pull requests are not counted, since `gh issue list` excludes them, so `0` means "on no open issue" rather than "unused" and a label carried only by open PRs reads zero; a floor rendered `>=N` when the read hit `GH_LABELS_ISSUE_CAP` (default 400), naming the cap and the knob, because a label used only by the four-hundred-and-first issue would otherwise read as unused and "unused" is the input to deleting it; and `?` when the issue list could not be read at all — never `0`, since "I did not look" and "nobody uses it" are opposite facts that print as the same character. An unreadable label list is an error and a nonzero exit rather than an empty list, while a repo with genuinely no labels says that in its own words. The read paginates, so a repo past a hundred labels is not silently truncated into a vocabulary an agent then invents around.
