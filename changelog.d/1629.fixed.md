- **`lint-new` reported the number of files it checked as the number carrying findings; it now reports both, as `N of M`** ([#1629](https://github.com/Digital-Process-Tools/claude-supertool/issues/1629)). The finding arm formatted `len(files)` — the set handed to ruff — into the sentence `N file(s) this PR adds, copies or renames carry lint findings`. Measured on a 40-commit range with one dirty path, it printed `46 file(s) … carry lint findings` above a single listed line. The two counts coincide whenever every checked file is dirty, which is the single-file diff that ships most often, so the wrong one read correctly nearly every time.

  **Files scanned, files with findings, and findings total are three different questions**, and a bare count answers whichever one the reader arrived with. On PR [#1622](https://github.com/Digital-Process-Tools/claude-supertool/pull/1622) a `1 file(s) … carry lint findings` line was read as "one of several shown" and became a brief sending an agent to look for findings that did not exist. The headline is now `1 of 2 file(s) this PR adds, copies or renames carry lint findings`, which cannot be read as either of the other two.

  **A finding line the parser cannot attribute to a path leaves the count unstated** rather than lowering it. ruff's `concise` output has always carried `path:line:col:`, so the arm should never fire — which is why it is pinned: a gate that silently under-counts its own findings is the same defect with a smaller number on it.
