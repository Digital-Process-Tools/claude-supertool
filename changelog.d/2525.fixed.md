- **`watches`' GitHub API budget line flags a DISAGREEMENT when a healthy-looking core reading contradicts a poller that is presently being throttled, and reports separately when a poller's own state could not be checked at all** ([#2525](https://github.com/Digital-Process-Tools/claude-supertool/issues/2525)). Five exhaustions on one token in nine hours turned up `gh api rate_limit` reporting `5000/5000` (or close to it) within minutes of a `*_unreachable` event on the same token -- GitHub's *secondary* rate limit (abuse-detection throttling on request burst/concurrency, undocumented thresholds) is enforced entirely separately from the primary per-hour budget, and GitHub's own docs say a secondary-limit rejection is not reflected in `/rate_limit` or in any response header at all. A full-looking core reading was never proof the fleet was not being throttled.

  `watches` now reads every `GH_SOURCES` poller's own current state and, when at least one is failing with a rate-limit-shaped error while the core reading shows real headroom (never when `remaining == 0`, which the core budget already explains), prints both instruments side by side with a `DISAGREEMENT` line naming the example poller and error -- flattened through this preset's own `_untrusted.flat()` convention, since a poller's id and error text are argv/state-derived. A poller whose state file could not be read at all (a symlink refusal, a corrupt or mid-write JSON file) is now reported as its own caveat rather than silently counted as "no active error" -- a self-review finding on the first draft, which read the mutator-half state accessor instead of the report-half one every other report call site in this preset already uses.

  Separately, `ratelimit.workflow_file_count`/`gh_branch_calls_per_tick` measure `gh-branch`'s real per-tick API cost (the flat `CALLS_PER_TICK["gh-branch"] = 3` this preset's own comment already admitted undercounts, missing one `_jobs_for` call per concurrently-selected workflow run) against a repo's `.github/workflows/` file count. A first attempt wired this fleet-wide off `watches`' own cwd; self-review found that unsound -- a poller's watched repo can differ from the rendering process's cwd (`SUPERTOOL_REPO`, or the *spawning* process's cwd, either possibly stale or foreign-channel) -- so it is shipped as tested, unwired building blocks rather than a silently-wrong fleet-wide number.

  Scoped down from the same issue's third finding (foreign pollers on another channel running a stale plugin fork with no restart mechanism): naming each foreign poller's version safely requires reading another channel's own state directory, a new cross-channel read this preset does not yet have, and was left for a follow-up rather than rushed into this fix.
