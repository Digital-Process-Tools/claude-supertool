- **`watches`' GitHub API budget line flags a DISAGREEMENT when a healthy-looking core reading contradicts a poller that is presently being throttled, and its `gh-branch` projection is measured against the watched repo's own workflow count instead of a flat guess** ([#2525](https://github.com/Digital-Process-Tools/claude-supertool/issues/2525)). Five exhaustions on one token in nine hours turned up `gh api rate_limit` reporting `5000/5000` (or close to it) within minutes of a `*_unreachable` event on the same token -- GitHub's *secondary* rate limit (abuse-detection throttling on request burst/concurrency, undocumented thresholds) is enforced entirely separately from the primary per-hour budget, and GitHub's own docs say a secondary-limit rejection is not reflected in `/rate_limit` or in any response header at all. A full-looking core reading was never proof the fleet was not being throttled.

  `watches` now reads every `GH_SOURCES` poller's own current state and, when at least one is failing with a rate-limit-shaped error while the core reading shows real headroom (never when `remaining == 0`, which the core budget already explains), prints both instruments side by side with a `DISAGREEMENT` line naming the example poller and error. Separately, `ratelimit.CALLS_PER_TICK["gh-branch"]`'s flat `3` -- which this preset's own comment already admitted undercounts by one `_jobs_for` call per concurrently-selected workflow run -- is now measured against the watched repo's own `.github/workflows/` file count (`ratelimit.gh_branch_calls_per_tick`) rather than left as a fixed guess, falling back to the flat table entry only when that directory cannot be read.

  Scoped down from the same issue's third finding (foreign pollers on another channel running a stale plugin fork with no restart mechanism): naming each foreign poller's version safely requires reading another channel's own state directory, a new cross-channel read this preset does not yet have, and was left for a follow-up rather than rushed into this fix.
