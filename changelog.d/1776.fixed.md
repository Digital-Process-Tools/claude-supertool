- **`@-` in a value field is refused instead of written to the file** ([#1776](https://github.com/Digital-Process-Tools/claude-supertool/issues/1776)). `paste:victim.txt:@-` did not read stdin. The @payload route is gated on the argument right after the op name, so a `@-` anywhere later fell through to the handler as ordinary content: two characters written over the file, under `rewrote victim.txt (1 lines, 39 → 3 bytes)`. Nothing in that receipt is false and nothing in it says the body written is not the body that was piped in — the byte count was the only tell, and a three-byte intended body would have left none.

  **Five ops that write had it, not two.** The reported case was `paste` and `append`; `edit`, `replace` and `replace_lines` reach the same handler position the same way, each of them measured writing the literal `@-` over a known fixture (`replace_dry` parses it identically and writes nothing). `vim` refused it by accident — its script parser has no verb `@` — which is loud but does not name the route that works. The guard sits once in dispatch, ahead of every handler, scoped to ops that have a payload route: that is what makes it a refusal rather than a dead end, since the message names `OP:@-` and the keys its payload wants.

  **Both colon forms, read ops out, and the reasons for each.** `paste:::PATH:::@-` is refused too — `:::` never routed a payload from a later field either, so it is not where the ambiguity lives, but it is the separator this repository tells agents to reach for first and the two characters land on disk identically. The read ops (`grep`, `around`, `grep_around`, `between`, `read`, `validate`) are deliberately out: a `@-` in one of their value fields is a path, so it already fails by name with nothing written, and the payload hint is built from the mutating registry and would print a remedy with no keys in it.

  **The payload route is untouched, and is the escape hatch.** Fields that arrived through a payload or a batch sub-op are not scanned — there the caller has already said "these bytes, exactly", nothing was tokenized, and that is how to write a literal `@-` to a file. The test asserts the file's bytes rather than the receipt text, and pairs every refusal with a write that must still happen, because a refusal test that also passes when the op stops writing altogether is not a test.

  **The gap the issue names as underlying is not one.** `paste:@-` with a TOML `content` block and `paste:::PATH:::CONTENT` both take a multi-line body today, both measured on 0.47.0, so "no write op takes a multi-line body at all" was wrong when it was written and the refusal leaves no caller stranded. What was missing was discoverability, and `help:paste` / `help:append` — reported as answering `no documented help` on 0.46.0 — have printed the colon form, an example and the payload route since [#1773](https://github.com/Digital-Process-Tools/claude-supertool/issues/1773).
