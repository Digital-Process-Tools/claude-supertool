- **`html-check`'s `</script>` end tag is walked, not matched to the next `>`** ([#1182](https://github.com/Digital-Process-Tools/claude-supertool/issues/1182)). #1176 replaced the start tag with a walker because `>` can hide inside a quoted attribute value; the end tag kept `[^>]*>`, which stops at the first `>` in the source. Both tags now use the same walker, because after `</script` plus whitespace the HTML tokenizer is in before-attribute-name state — the same state a start tag reaches — so a quoted value hides a `>` from one exactly as it does from the other.

  The issue classed this `misreports` and verdict-neutral. Measured against `html.parser`, two forms are not. `</script data-t="x > <script>const q = ;</script">` had its close cut inside the value, the value's remaining text was then read as markup, and the `<script>` standing in that string became a block whose own `</script"` is not a close — so the adapter refused the whole file, `NO inline <script> block in this file was checked`, about a page the tokenizer reads as one clean script followed by text. `</script data-t="oops>` failed the other way and is the worse half: that is EOF-in-tag, where the tokenizer emits no end tag at all and #1185's rule applies, and `[^>]*>` instead invented a close at the `>` inside the unterminated value and reported `ok: true`. The two forms the issue was filed about, `</script foo=">">` and `</script data-t="a > b">`, were verdict-neutral and remain so.

  A refusal now names which tag it met. `</script data-t` at EOF used to report "the element has no closing tag anywhere after it" against the *opening* tag's line — there is a closing tag, it is truncated, and "finish this tag" and "add one" send the reader to different places.

  The test that pins this asserts against **frozen** expectations taken from the WHATWG tokenizer states, not against whatever `html.parser` the runner ships ([#1236](https://github.com/Digital-Process-Tools/claude-supertool/issues/1236)). Reading the stdlib live made the assertion a function of the runner image: five of seven forms went red on 8 of 20 legs — every macOS leg and windows 3.9 — while ubuntu stayed green, because CPython rewrote `HTMLParser.parse_endtag` to follow the spec and backported it into later patch releases. Ubuntu's 3.9.25 has the rewrite; the macOS image's 3.9.13 does not. Measured locally: 3.11.11 and 3.13.2 do not close `</script bar>` at all and silently drop the script body, 3.14.6 closes it.

  **The old stdlib was wrong, and the walker was right**, so the test was not relaxed. Per 13.2.5.17 an end tag closes on whitespace, on `/` and on `>`, and the whitespace case enters before-attribute-name state where quoted values live — which is the whole of #1182. Restricting the corpus to forms every stdlib agrees on would have left the two the pre-#1182 regex already handled; skipping the five on old interpreters would have deleted the coverage on 8 legs. The live parser is retained as a cross-check gated on a behaviour probe rather than a version number, so a frozen constant cannot drift from a conformant stdlib, and where the stdlib is too old that check declines with a stated reason instead of passing.

  Stated because it is easy to over-read: re-run against the old `[^>]*>` close, six of the seven frozen rows still pass and only `script-tag-inside-a-value` fails. The corpus is a breadth check on where the boundary lands; the pin against a revert is that one row plus the three verdict tests.
