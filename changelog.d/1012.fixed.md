- **Printed remedies prescribed `./supertool`, which does not resolve where they are printed** ([#1012](https://github.com/Digital-Process-Tools/claude-supertool/issues/1012)). `./supertool` is a gitignored symlink: absent in a linked worktree, and inside a `claude-supertool` worktree actively wrong, because the global `supertool` on `PATH` then resolves to a different checkout and runs *that* tree's core against *this* tree's presets — the mixed tree [#678](https://github.com/Digital-Process-Tools/claude-supertool/issues/678) discloses after the fact. `git-conflicts` closed its output with `Resolve: ./supertool 'git-resolve:::ours:::PATH'` and `git-push`'s watch advisory with `Run it yourself: ./supertool 'watch:…'`, both at the moment the reader is mid-conflict or mid-recovery and least likely to second-guess a copy-pasteable command. A rule in a docs page is consulted; a command in an error is pasted.

  `push.py` already carried the answer for one line of its own output, from [#879](https://github.com/Digital-Process-Tools/claude-supertool/issues/879). It is now shared as `_git_common.st_hint` and applied to every printed follow-up in `git-conflicts` and `git-push`: `./supertool 'op'` where the wrapper exists and is executable, `python3 supertool.py 'op'` where only the entry point does, and a stated `(no runnable supertool found in <dir> …)` where neither does — a hint invented for an install nobody found is a remedy that cannot be run, which is the same defect one layer down.

  Printed `./supertool` follow-ups remain in `git-merge`, `git-resolve`, `git-diverge`, `git-commit` and in the `gitlab/`, `github/` and `watch/` presets. They are the same class and the helper is now in place for them, but they are outside what this issue names.
