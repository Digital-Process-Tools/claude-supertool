- **`gh-issue-create`, `gh-pr-create`, `gh-pr-edit` and `gl-issue-create` now say in their signatures that they read stdin** ([#2115](https://github.com/Digital-Process-Tools/claude-supertool/issues/2115)): all four already accepted `@-` -- the reference is resolved by the core payload loader, before any preset script runs -- but each advertised only `@FILE`, so a caller followed the signature, wrote a temp file, and paid a second round-trip for a payload that could have arrived on the same call. Measured over 42h of session transcripts: `gh-pr-create` ran 104 times from a file against twice from stdin, and `gh-issue-create` 98 against 8, while every op whose signature already named `@-` -- `edit`, `paste`, `git-commit`, `batch`, `append` -- ran through stdin more than 95% of the time. The split tracks the documentation op by op, not habit. No behaviour changed: the `syntax` strings, the `replaces` hints the raw-command guard prints, the four scripts' own missing-payload errors and the preset docs now name the route the code has always had. `tests/test_payload_ops_document_stdin_2115.py` pins the general rule -- any preset op whose `syntax` names `@FILE` must also name `@-` -- rather than the four instances, so a fifth payload op cannot ship with the same gap, and carries a second test asserting the three github ops still declare a syntax, because a sweep over a renamed-away set passes vacuously.
