- **A write-class built-in op (`paste`, `edit`, `append`, `replace`, `replace_lines`, `vim`, `format`, `format_staged`, `gc`, `rename`, `batch`) run under a mixed core/tree pair now declines outright, the same as a preset or custom op already did** ([#1942](https://github.com/Digital-Process-Tools/claude-supertool/issues/1942)). #678's guard was reached only from `_resolve_custom_op` (the route preset ops and `.supertool.json`-defined custom ops spawn a subprocess through), so `git-commit` refused with `SKIPPED: … comes from a different supertool tree …` while `paste`/`edit` and the rest of `_OP_SAFETY_BUILTIN`'s `"writes"` class ran to completion with only the stderr-only warning `main()` already prints once per call — a warning nothing downstream reads, on a receipt that read exactly like a correct one. Investigation traced the target path itself: `_safe_path` resolves every write against `os.getcwd()` regardless of which core answered, so a write-class builtin never lands in the wrong directory under a mix — what was silent instead was that the *code* answering (its validators, formatters and hooks) came from a different build, with no signal in the receipt saying so. The gate now sits at the one chokepoint every path argument already passes through in `_dispatch_impl`, keyed off the same `_OP_SAFETY_BUILTIN[op] == "writes"` table `ops` already renders from, rather than a second list that could drift from the first. `SUPERTOOL_ALLOW_MIXED_TREE=1` still overrides it, exactly as it already did for preset/custom ops.
