- **`vim`'s listing entry moved into a `vim` preset** ([#2026](https://github.com/Digital-Process-Tools/claude-supertool/issues/2026)). It sits under `presets/vim.json`'s `builtin-ops` section, the doc-only shape [#2025](https://github.com/Digital-Process-Tools/claude-supertool/issues/2025) added. The op is untouched: it dispatches from core, and `vim:@-` derives `path` and `script` from `_AT_FILE_BUILTIN_DEFAULTS`, so the payload route works with no config at all — pinned against an empty config rather than against this repo's, because a route deleted by an edit to `syntax` is silent ([#770](https://github.com/Digital-Process-Tools/claude-supertool/issues/770)). Measured here, leaving the preset unlisted takes 1,478 bytes off `ops-compact` and `ops:full` and 19 off the default `ops` listing, which has been signatures-only since [#1774](https://github.com/Digital-Process-Tools/claude-supertool/issues/1774). This repository lists it; the trade elsewhere is 1,478 bytes against a `help:vim` round-trip.
- **`help:OP` reaches a built-in documented by a shipped preset, wherever the caller is standing** ([#2026](https://github.com/Digital-Process-Tools/claude-supertool/issues/2026)). `_shipped_config()` reads the `.supertool.json` beside the module, so moving `vim`'s entry out of it made `help:vim` answer "no documented help" in every repo that does not list the preset — [#1773](https://github.com/Digital-Process-Tools/claude-supertool/issues/1773)'s exact failure, one file over, and caught by that issue's own test. The shipped reference now folds in the shipped presets' `builtin-ops` as well: where a built-in's documentation lives in an install is a property of the binary, not a fact about the caller's tree. An entry in `.supertool.json` still wins, and the fold reaches the `help:OP` fallback only — `ops` renders the project's merged config, so the listing bytes above are still saved.
