- `gh-run` renders each job's id beside its name, not only for the legs that failed ([#1482](https://github.com/Digital-Process-Tools/claude-supertool/issues/1482)). The `## Failed jobs` section was the one place an id appeared, so reading the log of a leg that **passed** meant leaving supertool for a raw `gh api` call — the same seam #1409 closed in `gh-branch`. A `Job id` column plus a `gh-job:<id>` pointer under the table closes it here.
- Every id `gh-run` prints is labelled `job #`, and that is established by the endpoint rather than inferred per row: `gh run view --json jobs` reads a run's Actions jobs, and a check run is in no run's job list. `gh-job` answers for both of GitHub's overlapping id namespaces, so an id offered without its namespace is one that can resolve in the wrong one.
- An unreadable job id renders `id unread` rather than `job #None`. `.get("databaseId", "?")` returned `None` for a key present with a null value, and the failed-jobs section printed it in the shape of an id.
