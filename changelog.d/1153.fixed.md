- **`html-check` read a `<script>` start tag with a regex, and a `>` inside an attribute value ended it early** ([#1153](https://github.com/Digital-Process-Tools/claude-supertool/issues/1153)). `<script data-tpl="a > b">` stops the old `<script\b([^>]*)>` at the first `>`, which is not the end of the tag — the same class CodeQL flagged on the *closing* tag in [#1140](https://github.com/Digital-Process-Tools/claude-supertool/pull/1140), on the half that was never flagged. Cutting there does not merely shorten the attribute string, it stops *inside* a quoted value, so the value's own text is then read as attribute syntax and the adapter fails in both directions: a block carrying `type="application/json"` or `src=` past the cut is checked as JavaScript and node reports a syntax error about markup, while a value reading `foo src=1 > b` makes the block look external, so it is dropped and the file reports `ok` with broken inline JS still in it.

    The start tag is now walked rather than matched. This is not a wider regex: the start-tag grammar is a small state machine, `>` can only hide inside a quoted value, and a quote only opens such a value directly after `=` — anywhere else it is an ordinary character, so `<script data-x=a"b>` still ends at its `>` rather than running to the next quote in the file. Checked against `html.parser` over 20,000 generated well-formed tags, attribute for attribute. Over a further ~60,000 *malformed* ones the two can disagree about what an attribute is named — where `html.parser` itself also parts company with the spec — so what is measured there is the property the adapter actually rests on: wherever `html.parser` parses the tag at all, this never answers differently about whether `src` is present or what `type` holds. It only declines.

    **A `<script` start tag that cannot be delimited is `skipped`, not guessed at.** A quoted value whose quote never closes, and a file that stops mid-tag, are both EOF-in-tag, where the tokenizer drops the tag outright; there is no smarter parse available, so the adapter declines the file and says which line it could not read and which of the two it met, rather than cutting the tag at a `>` that is inside a string. The third state, per `docs/validators.md` §"Declining instead of guessing".

    The refusal is per file and outranks a finding already in hand: a page with a broken block at line 3 and an undelimitable tag at line 40 reports `skipped`, because `ok: false, count: 1` would be a verdict about a file that was never read past line 40. Nothing is lost — the reason names the line to fix first, and the finding is still there on the next run.

    **`src` and `type` are read off parsed attributes now, which closes a second silent skip reachable without any `>`.** Both were matched against the tag's raw text, anchored on whitespace so that `data-src=` / `data-type=` — the names OneTrust and Cookiebot use to stash the real values — were not mistaken for the real thing. But an anchor tells one attribute name from another; it cannot tell an attribute from a *string*, and `<script data-tpl="foo src=1 bar">` has no `src` attribute, no stray `>`, a tag that delimits perfectly, and was still dropped as external with its broken JS unchecked. Parsing removes the class rather than the instance.

    Also: a tag name ends at whitespace, `/` or `>`, and the old word boundary also ended one at a hyphen — so `<script-foo>` was extracted as a script block and its children handed to node, a syntax error reported against markup on a page whose JavaScript is fine.
