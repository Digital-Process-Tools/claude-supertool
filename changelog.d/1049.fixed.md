- **`edit`, `replace` and `replace_lines` rewrote every line ending in a CRLF file to LF** ([#1049](https://github.com/Digital-Process-Tools/claude-supertool/issues/1049)). All three opened the target without `newline=""`, so Python's universal-newline translation flattened every `\r\n` to `\n` in memory and `_atomic_write` put those bytes back. A one-line edit produced a whole-file diff, under a receipt that named a single line — true about intent, false about effect. `op_append` has opened with `newline=""` since it was written, with a comment stating the contract; the other three never adopted it. Nothing on POSIX authors a CRLF file in the ordinary course of work, so no local run and no macOS or ubuntu CI leg ever exercised it.

  **The obvious fix on its own would have swapped one bug for another.** A caller composing a payload types LF, so an `old` string describing lines of a CRLF file arrives LF-terminated and, once the read stops flattening the file, matches nothing. Preserving endings alone would turn a silently damaging edit into a hard `old string not found`. The literal text is therefore matched first — a file that matches exactly is never reinterpreted — and only on a miss are the re-terminated forms tried, with the replacement re-terminated to match. The receipt says which convention was used.

  **Mixed-ending files have no single right answer, so `replace_lines` does not invent one.** Lines the op did not name come back out byte for byte, each keeping its own ending. The block it writes takes the ending of the line it replaces, or for an insert the line above it — not a file-wide majority vote, because on a mixed file a majority rewrites the caller's own line to the other convention, which is the same silent normalisation one line wide. Whenever the file is not plain LF the receipt says so, including the census: `line endings: file is mixed (2 CRLF / 2 LF / 0 CR) — every line this op did not touch kept its own`.

  Every test in the new suite asserts **bytes**. A text post-condition decodes `\r\n` to `\n` and would call a CRLF file equal to an LF one, so the same green would sit over a write of the wrong bytes.

  **Not fixed here, and deliberately: `vim`.** It reads with the same gap, but it is a line-oriented editor whose every motion, `o`/`O` and `dd` assumes `\n`; adding `newline=""` under that without reworking the model would trade whole-file normalisation for scattered mixed endings, which is harder to see and harder to review. Filed rather than half-done.
