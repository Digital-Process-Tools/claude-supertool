- **The suite forked a child from a multi-threaded worker and then waited for it with no deadline, so a deadlocked child stopped the whole run and named nothing** ([#914](https://github.com/Digital-Process-Tools/claude-supertool/issues/914)). `coverage (floors + disclosure)` was cancelled at its `timeout-minutes: 20` ceiling on three unrelated branches on 2026-08-07 — `8b14b9be`, `0c08cd10`, `f693c776` — against 3m07s-3m32s on the seven runs of that job that finished. Bimodal, never anything in between: a hang, not a slow job. Every cancelled log ends the same way — the progress bar reaches 95-96%, then twelve to seventeen minutes of complete silence, then `The operation was canceled.`, then six `Terminate orphan process: pid (N) (python)` lines, one per surviving process of the run.

  `tests/test_watch_dispatcher.py::_run_loop_in_child` calls `os.fork()` and then `os.waitpid(pid, 0)`. Nine tests go through it. Under `-n auto` that fork happens inside an xdist worker, which is a multi-threaded process — execnet's receiver thread, coverage's, and whatever the tests before it left running. A fork copies the memory of the calling thread alone, so every lock another thread held at that instant is inherited **locked, by an owner the child does not have**, and nothing can ever release it. CPython says so out loud on every one of those nine tests: `DeprecationWarning: This process (pid=N) is multi-threaded, use of fork() may lead to deadlocks in the child`.

  **The cost is not one failed test.** The wedged child holds every descriptor it inherited from the worker, including the execnet channel back to the xdist controller. The controller therefore never sees that worker close, waits for it forever, and stops printing — which is why the log ends mid-progress-bar with no test named, and why all six processes were still alive to be reaped. The position is not a coincidence either: `test_watch_dispatcher.py` sorts near the end of collection, so the fork lands in the last few percent, which is exactly where every cancelled run stopped.

  **Why `--timeout` did not save it, and why that was the confusing part.** pytest-timeout was installed and armed at `--timeout=300` on the run that hung, and eleven minutes passed between when it should have fired and when GitHub cancelled the job. It fires per test *item*; by the time the controller is the thing that is stuck, there is no item left to fail. Reproduced here directly: with the deadlock forced deterministically, a `pytest` carrying `@pytest.mark.timeout(60)` ran for **thirty minutes**, ignored the marker, and survived an external `timeout 180` SIGTERM. A guard outside the fork cannot reach this; the deadline has to sit next to the `waitpid` that lacks one.

  **`_reap` bounds the wait at `_CHILD_BUDGET_S` (30s), SIGKILLs the child, and fails the test by name** — naming the fork hazard as the likely cause, because "the child did not exit" on its own sends the reader looking for a slow poll. Killing it is what releases the inherited descriptors, so the controller finishes and the leg writes its log: a red row instead of a cancellation, which is the whole ask of #914. The budget is a parameter, not a literal, so the test that induces a real deadlock can wait out a 3-second one through the same helper every other test uses rather than supplying its own guard.

  **Still true, and deliberately left: the fork itself.** These nine tests should not be forking a multi-threaded interpreter at all — a spawned child would have none of this hazard. That is a larger change to how the poller and its monkeypatched modules reach the child, and it is not what this fix was verified against. The deadline makes the failure survivable and legible today; the migration is the follow-up.
