- **Re-running an applied payload now says the replacement is already in the file, instead of printing what a broken anchor prints** ([#984](https://github.com/Digital-Process-Tools/claude-supertool/issues/984)). Two states a caller most needs to tell apart — "this already applied" and "this anchor never matched" — shared one message, `ERROR: old string not found`, and the reader could not recover which from it. The remedies are opposite: one means stop, the other means find a new anchor.

  `edit` now checks whether the text it was going to write is present, and says where:

  ```text
  ERROR: old string not found in a.py
    ↳ the replacement text is ALREADY present at line 12 — this looks like a re-run of an edit that already applied, not a broken anchor
  ```

  A located fact, not a verdict. The `ERROR` stands, the op is still counted in `K skipped`, and the call still exits non-zero — downgrading a failure because it is probably benign is how a loud bug becomes a quiet one.

  This is the half of the re-run problem that `re-applied` (#701) does not reach. That signal fires when `new` contains `old`, so the anchor survives its own edit and the payload applies a second time. When `new` does not contain `old`, the second run matches nothing and there was no signal at all. The other two halves the issue reported had already shipped and were verified against the tracker before this was written: the batch footer has carried `K skipped` at the very bottom, below the validators and surviving `| tail -1`, since #680, and the re-apply disclosure since #701.
