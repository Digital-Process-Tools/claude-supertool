Every regenerated row is well-formed, so `jit-index` reports `ok` on the weaker file.
- The three that were data now live in the frontmatter the generator already reads: `require:` on `merged-is-not-ancestry.md` and `git-C-has-cwd.md` (`build_tool_tsv` has read that field all along — the issue's "no frontmatter field expresses those columns" was wrong for the tools family), and `pyproject.toml` folded into `version-sites.md`'s own `match:` as an alternation, since the paths column is handed to awk `match()` and one entry file yields exactly one row. Verified through the real hook: both paths still reach the rule, both blocks still fire, and `git status` and `git -c user.name=x commit` still do not (#1579).
- **No rule is broader than it was.** The paths row loss was the only change in coverage — a `require` on a `mode: block` rule cannot alter the verdict, because the block is unconditional either way; it decides the refusal text, and on a `remind` rule it would be the verdict. Both columns are pinned by name so a future "just regenerate it" cannot satisfy the round-trip by deleting them (#1579).
- `tests/test_jit_index_round_trips_1579.py` re-derives both indexes from the frontmatter in Python and diffs them. Deliberately a reimplementation rather than a call to the script: the script is in another repository, and a test that skips when a neighbour is not cloned is a test that never runs in CI — which is how this drifted unseen. `CLAUDE.md` and the `jit-context` note also had the tools row as `tool⇥match⇥file⇥mode⇥keyword`; there is no `keyword` column, and calling `require` and `forbid` something else is part of why nobody put them in the frontmatter (#1579).
