- **`gh-pr` printed a GraphQL page cap as if it were the pull request's total** ([#1491](https://github.com/Digital-Process-Tools/claude-supertool/issues/1491)). `reviewThreads(first: 100)` requests no `pageInfo`, so the reply cannot say whether it saw everything — and both renders divided by what it got: `Unresolved threads: N / 100` in the default dashboard and `Threads: N unresolved of 100` in `gh-pr:N:threads`. A fetch limit stated as a fact about the PR, one line under `Unresolved threads: 0 / 0 — read, not assumed.`

  A reply holding exactly the cap and a PR holding exactly the cap are the same bytes, so at the cap every number taken off the fetched set is printed as a floor — the unresolved tally too, since it is counted over the same truncated list. `… N more not indexed here` was computed off that set and under-reported by the same amount; it is a floor there as well. Below the cap the total *is* established and prints bare, unchanged: qualifying a number that is known would be the same defect pointed the other way.

  The comment list inside one thread was capped at 50 and said nothing at all, so a thread cut mid-way read as a thread that ended. `gh-pr:N:threads` now closes such a thread by naming the cut. Both caps are named constants used to build the query itself — the render infers truncation from the length it got against the cap, which is sound only while the two agree, and the number used to be a literal in the query string plus a hand-copy of it in a comment.
