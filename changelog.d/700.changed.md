- **Documented why `batch:` stays best-effort by default rather than gaining a rollback mode** ([#700](https://github.com/Digital-Process-Tools/claude-supertool/issues/700)). Split from #680, which fixed the *reporting* half (a declined op names itself in the footer and the call exits non-zero); this was the *policy* half, deliberately left open. Closed without new code: a `batch` entry is not necessarily a file write — `git-commit`, any `gh-*` op, or another network-side-effecting preset can sit in the same list as `edit`/`paste`, and a git commit or a posted comment cannot be snapshotted and restored the way a file can. A rollback that only ever covered the file-writing entries would report a batch as "rolled back" while an earlier, irreversible entry had already landed — a quieter, wronger answer than the honest partial-application `batch:` already reports. `continue_on_error: false` already stops a batch at the first failure, and #680 already made that failure visible; `docs/operations/edits.md` now says so in one place instead of leaving the gap for #700 to re-ask.
