- **A test can now ask for the whole shipped registry, not just one route of it** ([#1829](https://github.com/Digital-Process-Tools/claude-supertool/issues/1829)). `with_preset_op` ([#1812](https://github.com/Digital-Process-Tools/claude-supertool/issues/1812)) installs a **subset**, deliberately: a test asking for `git-commit` must not silently acquire `gh-pr` as well, or every other op's presence in that test becomes an accident of the fixture. Eight test files wanted the other thing — this repo's own `.supertool.json` with every preset resolved, because the thing they assert about *is* the whole registry — and each of the eight had rediscovered `_merge_presets` from scratch. Six of them already spelled it `shipped_config`.

  `shipped_config` is that second fixture. It reads the tracked manifests through the real loader, installs the result as `_CONFIG` for one test, and hands back a private deep copy so a consumer that mutates what it was given cannot poison the process-wide cache for the next test. The two fixtures share the loader and nothing else — `with_preset_op` still installs only the entries it was asked for, and that is pinned as a behaviour rather than left to a comment.

  **It fails rather than skips**, on the same argument: `presets/*.json` are tracked files one directory from `conftest.py`, so a checkout that cannot read them is broken rather than under-provisioned, and a skip would report an environment quirk for a suite that had quietly stopped exercising the shipped registry.

  The guard for that is not the one the obvious implementation writes, and this is the part worth knowing. `.supertool.json` declares eight ops **directly**, so `assert config["ops"]` stays true with every single preset manifest deleted — a guard reporting a healthy registry for a checkout that resolved none of it, which is this repository's own defect class sitting inside the guard against it. It refuses on three separate conditions instead: a `_preset_warnings` entry, an empty `ops`, and a declared preset that contributed no op to the registry. That last one is asked per preset against the provenance the loader stamps as it merges (`_op_sources`), not by counting the op names the merge added — counting names cannot see a preset whose whole contribution collides by key with an op the project also declares, and this repo's eight direct `ops` entries are exactly the keys `git`, `watch` and `dashboard` ship. Each condition was checked by neutering it on its own; each reddens exactly one test and no other.

  One conversion changed behaviour rather than only shape. `test_ops_underreports_dispatchable_ops_1124.py`'s hand-rolled fixture loaded `.supertool.json` and **never called `_merge_presets`**, so a file about what the tool can do had been asserting against a config with no preset-derived op in it at all. It now sees the resolved registry, and its assertions hold.
