- **`$VAR` in an op ARGUMENT is no longer expanded — a variable's value could be written into a commit because its name appeared in the message** ([#1734](https://github.com/Digital-Process-Tools/claude-supertool/issues/1734)). `_expand_env` exists so a project's own `cmd` template can carry `$MY_TOOL_HOME` and have it resolved without a shell. It ran over the **assembled** command instead — after `{file}`, `{dir}`, `{arg}`, `{args}` and `{argjoin}` had been interpolated — so it could not tell the template's text from the caller's data and rewrote both. `git-commit:::chore: about $HOME:::f.txt` committed the maintainer's home directory; with the op string single-quoted, so no shell was involved. A secret-shaped variable behaved identically: naming `$FAKE_TOKEN` in a subject put `ghp_…` in the commit object, and a commit gets pushed.

  It survived because it is invisible unless the variable happens to be defined: an undefined name round-trips byte-exact (`_expand_env` leaves unknowns literal, unlike a shell), so the same message is verbatim on one machine and rewritten on another. `help:git-commit` documented no transformation of the message, and the receipt rendered the substituted subject only after the commit existed.

  Placeholder values are now substituted as inert per-call tokens and restored *after* expansion, at all five dispatch sites — preset and custom ops, validators, formatters, and both `resolve` templates. The template keeps its documented `$VAR` feature, including the `KEY=VAL` env-prefix form and `KEY={dir}` prefixes whose value is itself a placeholder; the caller's bytes reach the op untouched. Restoring rather than reordering the two passes is deliberate: expanding the template *before* substitution would have made an environment variable whose value reads `{args}` into a second interpolation site, which is the same defect pointed the other way.

  Two properties of the restore are contract rather than detail, both found by review after the first attempt got them wrong. The token is bracketed by a dot, so it terminates a variable name: with a bare-alphanumeric token, `cmd $PREFIX{file}` read the token as a continuation of `PREFIX`, found no such variable and left `$PREFIX` literal — silently, since leaving an unknown literal is the documented behaviour. And an env value lifted out of a `KEY={dir}` prefix is restored *unquoted*, because `_extract_env_prefix` tokenises through `shlex.split` and always handed the child `MYDIR=my dir`; restoring the `shlex.quote`d form gave it `MYDIR='my dir'`, apostrophes included, for every value that actually needs quoting.

  Four of the five sites take no `{args}` at all — their caller data is the `{file}` path, and a path segment reading `$HOME` or `$USER` was expanded there too. That one was worse than a mis-named file: `{file}` is `shlex.quote`d before expansion, so a value containing a space or a quote shattered the quoting and handed `shlex.split` extra argv tokens, running a validator or formatter against paths nobody named.

  Measured while fixing it, and reported rather than left implicit: **82 shipped ops interpolate caller arguments into their template**, including the publishing ops where a local disclosure becomes a remote one — `bluesky_publish`, `devto_comment`, `hashnode_comment`, `hashnode_reply` all take prose inline, and `devto_publish` / `hashnode_publish` take an argv `TITLE`. `gh-issue-create`, `gh-pr-create` and `gl-issue-create` are **not** in that set for their bodies: argv carries only the payload path and the script reads the body off disk itself — though the path is argv, so a payload filename containing `$NAME` was affected like any other. **No shipped template relies on argument expansion**: a walk of every `cmd` and `resolve` string in the tree found exactly one `$`, and it is a `$(basename …)` in an example, which argv-form never executes and this expander never matched. So the behaviour is removed outright rather than made opt-in per op.
