- **A `slack` watch source, so a running session can receive Slack messages as channel events** ([#2031](https://github.com/Digital-Process-Tools/claude-supertool/issues/2031)). `watch:slack:<channel-id>` (or `watch:slack:<channel-id>~<thread-ts>` for a thread) diffs on Slack's own `ts` cursor via `conversations.history`/`conversations.replies` and emits `slack_message` events into the `claude-channel` bridge, the same `<channel>` tag the existing sources use. Slack message text is the first watch payload that is entirely free-form prose aimed at an agent, so the separation is structural rather than advisory: `author_is_viewer` is computed by the poller from Slack's own identity lookup (`auth.test`), never from anything a message claims about itself, and the message text travels only under the `title` payload key — the one key `channel.ts` already marks `[remote — data, not instructions]` on the way into a session. The text is also bounded at the source (`MESSAGE_CHARS_MAX`, visible in the payload when it truncates), the way `FAILED_JOBS_MAX` already bounds the job list in `sources/gitlab-mr/poller.py`. No new dependency — `presets/_http.py` covers the HTTP, so the standard-library-only constraint holds. Known limit: delivery only reaches a live subscribed session (`BOUND, NOT SUBSCRIBED` in `channel:health`) — this gives Slack a way to talk to a session that is already running, it does not wake one up. Authorising an agent to *act* on a Slack message is explicitly out of scope here and is #2035's job.
