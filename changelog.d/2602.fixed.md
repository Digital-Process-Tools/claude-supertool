- **Seven validator/formatter adapter gates accepted a cwd-relative existence match and then spawned a bare tool name** ([#2602](https://github.com/Digital-Process-Tools/claude-supertool/issues/2602)). The #2575/#2579/#2581 sweep replaced only the FIRST disjunct of each gate (`shutil.which(X)` -> `spawnable(X)`) and left the SECOND untouched: `if not spawnable(X) and not (Path(X).exists() and os.access(X, os.X_OK)): decline`, with no `os.path.dirname()` guard -- exactly the guard #2575 already added to the three sibling helpers (`spawnable._already_a_path`, `bin_resolve._is_executable`/`_spawnable`) for this precise reason. A repository under inspection could plant an extensionless bare-named executable at its own root (e.g. `prettier`) plus `prettier.exe` (the Windows payload): `spawnable()` returns `None` for the bare name, the gate's second disjunct returned `True` anyway, `argv0()` fell back to the bare name, and `subprocess.run(["prettier", ...])` handed `CreateProcess` a bare name whose search order puts the current directory ahead of `PATH` -- with the maintainer's forge tokens in the child's environment. Not exploitable on POSIX (`execvp` never searches cwd), but the gate still wrongly passed there too and then misreported the tool as vanished. Fixed at all seven sites (`validators/prettier-check`, `validators/psr`, `validators/ci-lint`, `formatters/prettier-write`, `formatters/ruff-format`, `formatters/phpcbf`, `formatters/php-cs-fixer`) by replacing the inline reimplementation with a new public `spawnable.already_a_path()`, the same dirname-guarded check `_already_a_path` already used, so the guard can no longer drift a second time. `tests/test_gate_matches_spawn_2579.py`'s register -- which only detected the `shutil.which` spelling and whose own negative control encoded exactly this vulnerable shape as "fine" -- is widened to also flag a cwd-relative `exists()`/`isfile()` check with no dirname guard, and its negative control no longer certifies the vulnerable pattern as acceptable.
