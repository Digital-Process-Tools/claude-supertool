- **An int-backed setting could not be switched off, and the substitution was silent** ([#1332](https://github.com/Digital-Process-Tools/claude-supertool/issues/1332)). `_get_op_int` ended in `val if isinstance(val, int) and val > 0 else default`, so a configured `0` in `.supertool.json` was indistinguishable from an absent key and the helper's own default won. `read.elide: 0` shipped documented in three places and inert — a switch that reports back the state it was asked for and does not enter it.

  **A switch now has its own reader.** `_get_op_bool` takes `0`/`1`, `true`/`false` and `yes`/`no`/`on`/`off`, from config or from `SUPERTOOL_<OP>_<KEY>`, and `0` means off whichever way the default points. `read.elide`, `read.abstract` and `read.php_abstract` are read through it; `read.elide`'s inline workaround is gone.

  **The threshold reader still refuses a `0`, but says so.** Honouring `"max_lines": 0` would trade a loud misconfiguration for a silently empty read, which is the worse of the two failures — so `_get_op_int` keeps refusing, and now names the key, the value it discarded and the limit actually in force, the way it has named a bad env value since [#654](https://github.com/Digital-Process-Tools/claude-supertool/issues/654). It said nothing at all about a bad *config* value, which is why nobody writing a deliberate `0` could tell it had been ignored.

  **A JSON `true` in a threshold was reading as `1`.** `isinstance(True, int)` is true in Python, so `"max_lines": true` gave a one-line `read` without a word. It is now refused and announced with the rest.
