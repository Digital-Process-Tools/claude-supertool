- **`git-status` omitted its working-tree and stash sections entirely when git did not answer** ([#1002](https://github.com/Digital-Process-Tools/claude-supertool/issues/1002)). Both sections were guarded by `returncode == 0` with no other arm, so a held index lock, a corrupt index or a `git status` that outran its 5s budget produced a report with nothing at all where the working tree belongs. The only disclosure was the `git-status INCOMPLETE` footer at the very bottom, which says that *some* section is missing without saying which — and it arrives after the reader has already scrolled past an empty space that is byte-for-byte the render of a clean tree. Each section now has three states rather than two: `## Working tree: clean`, `## Working tree (N changes)`, and `## Working tree: UNKNOWN — …` quoting git's own words at the place the section belongs. The footer is kept as well: the marker is where the eye is, the footer is what survives a `| tail` and what a script greps. A run in which every call answered gains neither.

  **The issue as filed does not reproduce, and that is on the record in the tests.** It reported the section vanishing in a linked worktree with six dirty files. It does not: with a `git status` that answers, the files are listed — in a linked worktree, on a branch with no commits of its own, in a repository with fifty-nine other branches, all of which were tried. `test_a_dirty_tree_still_lists_its_files` pins that render so the report is not re-filed a third time. What is real is the half the issue's own "fix shape" paragraph asked for, and that half was reachable and silent.
