- **`git-commit`'s receipt no longer replays the whole message once the commit has landed** ([#946](https://github.com/Digital-Process-Tools/claude-supertool/issues/946), [#1235](https://github.com/Digital-Process-Tools/claude-supertool/issues/1235)). The op header is `--- <the argument you sent> ---`, and for this op the argument is the commit message — so a twelve-line message was printed in full above a nine-line receipt, once to send and once to read back. On success the header is now `git-commit: "<subject>" +N more message lines → M path(s): …`, because `git log -1` already holds the message and the receipt underneath is what proves the commit landed.

  **On a refusal it stays verbatim, and that is the point.** Nothing was committed, so the header is the only surviving copy of a message the caller composed; eliding it there would cause the loss #1235 was filed about rather than fix it. The summary is gated on the op having succeeded, and arguments under 160 characters keep their verbatim header either way.

  The second half of #946 — `git-status` opening with a preceding command's output — was **not** reproducible: every op's output opens with its own `--- <op> ---` header, which is the unambiguous delimiter the issue asks for, and anything printed by an earlier process lands above it.
