- **A second op that declares a project-config key already claimed by another op now refuses at the point it would run, instead of silently sharing one env var with it** ([#1009](https://github.com/Digital-Process-Tools/claude-supertool/issues/1009)). `ops.<op>.<key>` in `.supertool.json` has always reached that op's own subprocess as `SUPERTOOL_<KEY>` -- the key alone, never namespaced by the op that declared it. Nothing stopped a second op from picking the same key name for something unrelated; a live instance shipped as `hashnode_react.auto_force` / `hashnode_comment.auto_force`, two separately documented opt-ins, both landing on `SUPERTOOL_AUTO_FORCE`.

  Refusal, not renaming: `SUPERTOOL_<OP>_<KEY>` would break every project's `.supertool.json` and every preset reading the existing flat names, for a defect that -- measured against this repository's own config -- costs nothing to catch instead. The check is scoped to a project's own `ops` section and to genuinely *differing* values; a preset's shipped vocabulary shared across many ops on purpose (`REPO_TARGET`, `DEFAULT_LIMIT`, this repository's own `watch_name` repeated across the whole `watch` family) is untouched, because flagging it would have refused this repository's own config the moment the fix landed.
