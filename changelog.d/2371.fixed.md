- **`worktree:teardown` could no longer silently no-op when git itself was unreliable, instead of only when a worktree genuinely had nothing set up** ([#2371](https://github.com/Digital-Process-Tools/claude-supertool/issues/2371)). `presets/worktree/_common.py::read_manifest` resolved the provisioning manifest's path through `git rev-parse --git-path` and caught any failure (including `_run_git`'s own 15-second timeout/`OSError` guard) as `TargetError`, then collapsed it into the exact same `ConfigResult({"linked": [], "copied": [], "excluded": []})` as a worktree where `setup` had genuinely never run -- even though `--git-path` does not look at whether the manifest file exists, only at where it would be, so that failure can never mean "no manifest was ever written". `teardown_op.py` read that empty result and reported exit 0 with "nothing recorded as setup's own, nothing removed", identical to a truly clean worktree, while a live symlink into the primary checkout could still be sitting there untouched. `read_manifest` now reports a nonzero `--git-path` resolution through `ConfigResult(None, error=...)` -- the same "could not determine" path `teardown_op.py` already takes for a manifest that exists but fails to parse -- so teardown declines and says why, rather than silently no-op'ing. A genuine absence (the path resolves fine and the file simply is not there) still returns the plain empty manifest, unchanged.
