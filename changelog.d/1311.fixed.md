- **`grep`'s catastrophic-backtracking guard no longer refuses a bounded `(...+)?`, correctly still catches a `+`/`*` wrapped around one, and `help:OP` now names `literal_backslashes` wherever it can actually fire** ([#1311](https://github.com/Digital-Process-Tools/claude-supertool/issues/1311)). The guard used to refuse any group carrying an unbounded `+`/`*` followed by ANY quantifier, `?` included — but `?` bounds a group to at most one repetition, so it has no outer loop left to re-partition the same input across and cannot backtrack catastrophically; only an outer `+`/`*` can. `[0-9]+.(added|fixed)(.[a-z-]+)?.md`, a legitimate pattern, was refused this way.

  A first pass narrowed the check to a single-level regex that only flags an outer `+`/`*` directly against the group holding the unbounded content — which turned out to reopen a real hole for the outer quantifier sitting one level further out, e.g. `((a+)?)+` (confirmed catastrophic: several seconds against 25 characters), because a single-level regex can only ever see the FIRST close-paren it reaches and the old, over-eager regex had only ever caught that shape by accident, via its own unrelated over-refusal of the inner `(a+)?`. Caught in self-review before merge. The guard is now a small bracket-depth-aware scan: for every `(...)` group it finds the TRUE matching `)` by tracking nesting depth, and refuses only when an unbounded `+`/`*` appears anywhere inside that group (at any depth) AND the character immediately after the group's real closing paren is itself `+` or `*`. `(a+)?b(c+)?` — two independently-bounded groups, neither's risk depending on what quantifier the other carries — still passes.

  `help:paste`, `help:edit`, `help:git-commit` and every other op whose payload route carries a write-bound field (`new`, `content`, `message`) now print the `literal_backslashes` escape hatch (#1096) in that same block, alongside the field names #1400 already added — previously discoverable only by tripping the doubled-backslash write refusal once.

  Two related items from the same report did not reproduce against current `master` and are not touched here: the doubled-backslash write refusal already names every offending field and every occurrence within it, capped and disclosed (#1808/#1814/#1819/#1839) rather than showing only the first; and `git-commit:::MESSAGE` with a multi-line message and no PATHS correctly reports `no PATHS were given` (the same claim `tests/test_git_commit_cause_and_all_1155_1137.py` already pins as refuted for #1155) — every reproduction tried (multi-line message with a path, with an embedded quote, alone) staged and committed correctly, or refused for the actual reason.
