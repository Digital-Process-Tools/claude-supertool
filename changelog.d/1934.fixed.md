- **Anchored five adapters' line-parsing regex on the invoked path, tolerant of the spellings a real tool's own platform can introduce** ([#1934](https://github.com/Digital-Process-Tools/claude-supertool/issues/1934)). `actionlint`, `xmllint`, `ruby-check`, `hadolint` and `gofmt-check` located a tool's own `path:line[:col]: message` diagnostic with a non-greedy wildcard standing in for the path, so the regex bound to the *earliest* colon-digit run in the line rather than the one the tool actually wrote. A workflow, XML, Ruby, Dockerfile or Go file whose name embedded its own `:N:M: ` sequence supplied the reported line, column and message of the filename author's choosing, discarding the tool's real diagnostic. Each adapter now anchors on `re.escape()` of the path it actually invoked — `actionlint` additionally relativises against its own working directory first, matching a relativisation actionlint itself performs on the path it prints. An exact-match anchor alone turned out to cost more than it protected: on Windows CI, real ruby's own diagnostic did not echo the exact invoked path byte-for-byte, so the anchor matched nothing and a real, located diagnostic silently lost its line and column. `validators/common/path_anchor.py` widens every adapter's anchor to a small, fixed set of equivalent spellings (separator direction, drive-letter case) rather than one exact string, never a wildcard — a forged filename still cannot use it to impersonate a different path.
