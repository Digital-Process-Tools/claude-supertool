- **Anchored five adapters' line-parsing regex on the invoked path, tolerant of the spellings a real tool's own platform can introduce** ([#1934](https://github.com/Digital-Process-Tools/claude-supertool/issues/1934)). `actionlint`, `xmllint`, `ruby-check`, `hadolint` and `gofmt-check` located a tool's own `path:line[:col]: message` diagnostic with a non-greedy wildcard standing in for the path, so the regex bound to the *earliest* colon-digit run in the line rather than the one the tool actually wrote. A workflow, XML, Ruby, Dockerfile or Go file whose name embedded its own `:N:M: ` sequence supplied the reported line, column and message of the filename author's choosing, discarding the tool's real diagnostic. Each adapter now anchors on `re.escape()` of the path it actually invoked — `actionlint` additionally relativises against its own working directory first, matching a relativisation actionlint itself performs on the path it prints. An exact-match anchor alone turned out to cost more than it protected: on Windows CI, real ruby's own diagnostic did not echo the exact invoked path byte-for-byte, so the anchor matched nothing and a real, located diagnostic silently lost its line and column. `validators/common/path_anchor.py` widens every adapter's anchor to a small, fixed set of equivalent spellings (separator direction, drive-letter case) rather than one exact string, never a wildcard — a forged filename still cannot use it to impersonate a different path. That widening is gated to Windows specifically: on POSIX, `\` and a leading drive-letter-shaped prefix are ordinary filename content rather than a separator or a drive letter, and the first cut of this module treated them as the latter unconditionally — which let the anchor accept a genuinely different file's diagnostic as this one's, found by this branch's own self-review before it shipped. A second, ungated widening covers a different mismatch found once the Windows-only fix reached CI on Linux: the invoked path can traverse a symlink (a symlinked temp directory is the common case) that a tool's own diagnostic resolves before printing, so the anchor now also accepts `os.path.realpath()` of the invoked path as a candidate — safe on every platform, since two files that are not symlink-equivalent always have different realpaths. When the anchor still matches nothing, the adapter's non-verdict message now names both the invoked path and whatever path-looking prefix the tool's own output appears to use, so a future CI red prints the two strings that differ instead of asking a maintainer to guess the transform from an assertion failure alone — which is exactly what surfaced the real, final cause: real `ruby -c`, on some CI runners, prints the invoked path *twice* before its own diagnostic (a bare `<file>: ` prefix with no line number, then the genuine `<file>:<line>: `), so the anchor's own message quoted its output back verbatim, byte-identical to the invoked path both times — no spelling difference, no symlink, ever. The adapter's own fallback text had already said as much ("ruby -c exited 1 without reporting anything about the file") while the located diagnostic sat unread a few characters further into the very same string it was quoting — the silent-zero shape this repository names as its own defect class, one layer up from the anchor itself. Fixed by matching the invoked path at a `:<digits>:` boundary *anywhere* in the line rather than only at column 0, applied to all five adapters; the search target stays the same small, fixed set of literal spellings `path_anchor.py` already produces, never a wildcard, so a forged filename still cannot fabricate a location. That widening needed a left boundary too, found by this branch's own self-review before it shipped: a bare search-anywhere matched a genuinely different, longer real path that merely *ends with* the invoked one (a diagnostic naming `vendor/a.rb` misattributed to an invoked `a.rb`) — no forged filename involved, just an ordinary tool mentioning a sibling path. Fixed by requiring the match be preceded by start-of-line or whitespace, which every observed doubled-prefix case already is, while a path preceded by `/` or a letter no longer matches.
