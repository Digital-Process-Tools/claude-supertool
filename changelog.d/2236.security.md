- **`new-file-lint` and `changelog-fragment` no longer auto-execute a sibling or fully-disjoint checkout's own conventionally-named script** ([#2236](https://github.com/Digital-Process-Tools/claude-supertool/issues/2236), follow-up to [#2228](https://github.com/Digital-Process-Tools/claude-supertool/issues/2228)). `_config_dir_is_untrusted_ancestor` refused only the case where `SUPERTOOL_CONFIG_DIR` sits strictly ABOVE the edited file's own git root; a sibling checkout (config in one project, root in another with no ancestry either direction) or a fully disjoint one was still TRUSTED, and `_load` imports what it finds — running that checkout's own `.github/scripts/lint_new_files.py` / `assemble_changelog.py` with the operator's privileges, before either adapter's own checks ever ran. A new `_config_dir_may_authorize_execution` gate now authorizes automatic execution only when `SUPERTOOL_CONFIG_DIR` is the edited file's own repo root, or nested inside it; every other relationship — including the disjoint case — now reads `skipped`, unless `SUPERTOOL_NEW_FILE_LINT_SCRIPT` / `SUPERTOOL_CHANGELOG_ASSEMBLER` names the exact script explicitly. `_config_dir_is_untrusted_ancestor` itself is unchanged: whether a path may be *substituted* across that boundary (ordinary usage) is a separate question from whether a script found there may be *executed*, and only the second one was the vulnerability. This narrows one pre-existing convention-based write shape: pasting or editing into a disjoint project's `changelog.d/` fragment from a different project's own `.supertool.json` scope now needs an explicit `SUPERTOOL_CHANGELOG_ASSEMBLER` pin to keep validating against that project's own rules.
