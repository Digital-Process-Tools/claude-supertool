- **`radar` and `radar:--state` accept `tiers=NAME[,NAME...]` to render a named subset of the registered tiers** ([#2446](https://github.com/Digital-Process-Tools/claude-supertool/issues/2446)). Every registered tier used to render on every run, so a project holding both a CI board (`gl-mrs`, `gl-runners`) and a fleet board (`server-diag`) in one `.supertool.json` had no way to point one session at either without a second config. `radar:tiers=gl-mrs,gl-runners` now filters an already-registered set in render order, touching no poller for any tier not named; `radar:--state:tiers=...` honours the same selection, so the read-only view can never describe a different run than the one `radar` would make. A name in `tiers=` absent from the registry is refused and named on the board rather than silently rendering as if that tier simply had nothing to report -- the same reasoning the `milestne=v19` typo refusal already gives one level up -- and the board names the selection it was built from, the way it already names its `gl-mrs` scope. `tiers=` is read as the whole argument and is not combined with a further per-tier filter on the same comma line; not persisted, for the same reason the `gl-mrs` filter is not.
