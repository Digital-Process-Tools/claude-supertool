- **`tsc-check` trusted the target on the way out and `tsc`'s path on the way back** ([#1519](https://github.com/Digital-Process-Tools/claude-supertool/issues/1519)). Two instances of one defect, both from the v0.38.0 release audits.

  The target went into argv with nothing separating it from `tsc`'s own option grammar. `tsc` reads a leading `@` as a **response file** — its command line comes from that file instead — so `--noEmit` did not survive it. Measured on tsc 6.0.3 with `@r.ts` on disk beside an `r.ts` holding `--noEmit false --outDir out`: the receipt read `ok: true, count: 0` for a file whose one line is a type error, and `out/a.js` and `out/b.js` were written, against this page's own "`--noEmit` — no output files written". A leading `-` is the same class one character over. Escaping is not the fix — this is `tsc`'s grammar, not the shell's — and neither is `--`, which `tsc` rejects outright (`error TS5023`). A relative target now carries a `./` prefix, spelled with the platform's separator; `tsc` normalises it back, so the diagnostic it prints is unchanged.

  And `tsc --noEmit FILE` type-checks the whole import graph, so a diagnostic about an **imported** file is the common case rather than an edge one. The parse threw the reported path away, so an imported file's error was published as a located finding in the target, with `context_fields` printing *this* file's source at *that* file's line as the evidence. The recommended `.ts` registration is `rollback_on_fail: true`, which made that arithmetic capable of reverting a correct edit over a defect in a file the edit never touched. The path is now compared through `validators/common/pkg_paths.attribute` against the directory the adapter ran `tsc` in, and a foreign or unplaceable diagnostic keeps `ok: false` with `line`/`col` null, `code: "adapter"` and no `source_context` — `validators/SCHEMA.md` §"A located diagnostic still has to be about *this* file (#754)". It is kept, not filtered: the program genuinely does not type-check.
