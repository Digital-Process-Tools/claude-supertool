- **`git-resolve` with `both` reported `markers: clean` over a duplicated heading** ([#911](https://github.com/Digital-Process-Tools/claude-supertool/issues/911)). The guard added in [#839](https://github.com/Digital-Process-Tools/claude-supertool/issues/839) asked whether one conflict hunk carried the same heading on *both* of its sides. A rebase produced the asymmetric arrangement instead — `### Fixed` inside the hunk on one side, its twin in the surrounding context git had already merged — so the union emitted two `### Fixed` under one `## [Unreleased]`, the hunk still looked internally clean, and the receipt said the resolution held.

  The check now reads the document the union would produce rather than the shape of the hunks. Headings are counted by their ancestor path, so `### Fixed` under `## [Unreleased]` is a different thing from `### Fixed` under a tagged release and an ordinary changelog is never refused; the count is compared against the surrounding context alone, so a file that already repeated a heading is not charged to this resolve. Fenced blocks are skipped — a `# run it` line inside a quoted shell snippet is a comment, not structure.
