- **Every regex rule in `.claude/jit-context/tools/00-manual/` is pinned to command position, and the anchor now admits a tab** ([#1415](https://github.com/Digital-Process-Tools/claude-supertool/issues/1415)). Two `mode: block` rules were tested as a bare substring over the whole command text, with no notion of where a shell would find a command word, so they refused **eleven commands on 2026-08-11** that cut nothing and listed nothing — this repository's own directory name inside a `cd` path, a shell variable, a bar inside an op's own argument, and a quoted payload body seven times, including the filing of the issue, the writing of its test file, a commit message and the verification harness itself. The other six rules were already anchored, but as `(^|[;&|\n] *)`, which admits only spaces: a **tab**-indented continuation line walked through all of them. All eight now open `(^|[;&|\n])[[:space:]]*`.

  **Two defects in opposite directions, and the second one was silent.** A wrong block announces itself; a missed block looks exactly like nothing happening, which is why four `block` rules could fail on tab-indented commands without anyone noticing. Measured against `pre-tool-hook.sh` itself, 23 cases: four rules gain the tab-indented true positive, `op-defaults-that-narrow` stops firing on a mere mention of an op name in prose, `supertool-no-cut` stops firing on the directory name, and every case that must stay allowed — an ordinary `git branch -d`, a `--limit`ed list, a `git -c` carrying no path — is unchanged.

  **Three narrowings on `supertool-no-cut` besides the anchor.** The cutting utility must be a command word after the bar, which stops a bar inside an op's own `grep:` argument; the scan is confined to one line, which stops a payload body joining an earlier invocation; and the tool name must end at whitespace, which stops `supertoolkit` and `supertool-benchmark.sh`. One true positive is newly caught in exchange: a cut behind a second pipe.

  **Narrower is not precise, and the residue is named rather than left to be discovered.** A payload line that *begins* with a command-shaped string still matches: only a tokeniser can tell a body from a command, and the jit matcher lives in `claude-jit-context`, a separate repository. `supertool-no-cut.md`, `CLAUDE.md` and `jit-context.md` all say so.

  Also fixes `git-C-has-cwd.md`, whose frontmatter `match:` had lost the leading `~` its index row carries — inert where it sat, but the `.md` is what a reader copies, and copied as-is it becomes a literal substring rule that can never match.

  `tests/test_jit_block_match_anchored_1415.py` hands each live pattern to `awk` the way the hook does and asserts both directions per rule, plus that no regex row in the index is left unanchored.
