- **`git-push` no longer reports a tracker it could not reach as a branch with no MR** ([#948](https://github.com/Digital-Process-Tools/claude-supertool/issues/948)). The shared branch→MR lookup returned `None` for *there is no open MR/PR* and for *the lookup did not happen*, and swallowed every exception on the way — on the op a person reads immediately before and after the one irreversible thing supertool does. It now returns an `MrLookup`: a fact, or the reason there is no fact.

  Three consumers read that `None` and all three took it as an absence. The MR line went missing, which reads as "no MR yet, open one". The mergeability warning and the stale-base check were skipped silently, so a conflicting MR raised nothing. And `:watch` printed *"there is no open MR/PR for this branch yet — nothing to watch. Open one"* about a request that may well exist. That last one is a positive claim about the world, manufactured out of a lookup that timed out.

  The push is never blocked. This runs after the ref has moved, and a tracker that cannot be reached is not a reason to withhold work already on the remote — refusing there would trade a quiet wrong answer for a loud one that is worse. The receipt degrades to a stated unknown naming the CLI and its own words.

  The healthy path is byte-identical: a lookup that answered prints what it always printed, and a branch that genuinely has no MR still says nothing. Three cases are answers rather than failures, two of them on the reading `git-status` already used — a CLI saying *no open merge request* / *no pull request*, and the other host's CLI saying *none of the git remotes … point to a known GitHub host*. The second is structural and permanent, so declining on it would put a warning on every push in every GitLab repo with `gh` installed. An answer already given is never downgraded by the fallback: `glab` reporting "no MR" on a GitLab repo stands, whatever `gh` does a moment later.

  The phrase list `git-status` used to keep privately now lives beside the lookup and is imported, split into "this host has no such request" and "this is not this host's repo" — the two need different treatment and one copy.

  Reading those phrases is not enough on its own, because both CLIs check their own credentials **before** they look at the repository. An unauthenticated `gh` exits `4` saying so and never reaches *none of the git remotes … point to a known GitHub host*, so a repo with no forge remote at all — a sandbox whose `origin` is a path under `/tmp`, a clone from a colleague's disk — was reported as an unknown rather than as the plain absence it is. That fact was local the whole time, so the lookup now asks `git remote -v` first: if git answers and no remote names a host, there is no tracker for a request to be open on, and no CLI is consulted. A repo whose remote *is* on a forge is unchanged — it still probes, and still declines out loud when the probe cannot answer. Only a positively-local remote counts as local; a shape the check does not recognise is probed rather than assumed, because a wrong "no MR" is the expensive direction.

  Two things about that local check are worth stating, because both were got wrong once. A Windows checkout puts its remote at `C:/Users/…/remote.git`, which has a colon before its first slash — the scp-style shape — so a drive letter reads as a hostname and a temp directory reads as a forge; one character before the colon is what tells them apart. And `git` itself may not be on PATH, in which case `_git` raises rather than returning: that is the "git did not answer" state, so it is caught and degrades to `unknown` instead of taking the receipt of an already-successful push down with it. The reason then names git rather than the CLI, so the reader is not sent to fix the wrong tool.

  The reason attached to an unauthenticated CLI is now legible. `gh` says what it needs across four lines, none of which contains an error keyword, so the salient-line picker fell through to the *last* one — and inside GitHub Actions that is `GH_TOKEN: ${{ github.token }}`, a fragment of an example block offered to the reader as the reason their lookup did not run. The disclosure was correct and unreadable, which is half a disclosure.

  **The disclosure found a second defect on its first run, which is the argument for having built it.** `glab mr list --state opened` is rejected by glab 1.86 — `Unknown flag: --state.`, exit 1 — so the GitLab arm has been failing at argument parsing on every call for as long as the flag has been there, falling through to `gh`, which cannot answer on a GitLab repo either. Nobody found out, because both failures were swallowed. Open is `mr list`'s default (`--closed` is the opt-out), so the flag was unnecessary as well as wrong; it is gone, and the argv is pinned by a test.

  `git-status` was **not** affected, contrary to the issue: it has had its own three-state `_hosted_request` since #705 and never called this function. The consumers were `git-push` and `git-commit`'s post-commit hint.
