- **`gh-issue-create` falls back to REST when the GraphQL mutation transport is down, and names which transport answered** ([#1790](https://github.com/Digital-Process-Tools/claude-supertool/issues/1790)). Observed 2026-08-17: `gh issue create` 503'd six times in ten minutes on `https://api.github.com/graphql` while `gh api rate_limit` and a raw `gh api -X POST repos/OWNER/REPO/issues` both worked throughout -- the outage was specific to the mutation path, and a REST POST is a real alternative route to the same write. This is the same call `gh-pr-edit` already made for editing a published pull request (#195, #1739): write through REST, read back what landed, and never hide which transport ran. On a detected transport failure, `gh-issue-create` now (1) looks for an open issue with the exact title it is about to create, so a mutation that actually landed despite the 503 is reported rather than duplicated, (2) resolves a milestone name to the REST number it needs and names it NOT APPLIED if no such milestone is found rather than dropping it silently, and (3) prints `transport=graphql` or `transport=rest (fallback ...)` in every receipt. Detection is deliberately narrow -- only "no server is currently available" or "503" alongside "graphql" -- so an ordinary refusal (bad milestone, no write access, an unauthenticated `gh`) never triggers a second write attempt. Checked and declined as an alternative: whether `gh` itself already intends a REST fallback the way #195's `cli/cli#13069` reasoning suggested a version floor might be the fix here too -- `cli/cli#13069` turned out to be an unrelated stale-package deprecation error, and no evidence of an intended fallback in `gh` itself was found, so there is no version to pin to instead.
