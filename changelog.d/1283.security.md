- **`claims:PATH` read any path on the machine, and the core refused the same path in the same call** ([#1283](https://github.com/Digital-Process-Tools/claude-supertool/issues/1283)). `presets/claims/check.py` resolved an absolute argument directly and a relative one against the git toplevel with no containment check of any kind, so `supertool 'read:/etc/hosts' 'claims:/etc/hosts'` returned `ERROR: path escapes cwd` and `PASS` — one call, one path, opposite answers about whether it may be read. Not only an existence oracle: reference-shaped substrings of the out-of-boundary file come back in the render, and the read has already happened by the time anything prints. `claims` now enforces its own boundary, the **repository root** — resolved, not spelled, so a symlink inside the repo pointing out is refused too — before the file is opened and before existence is tested, so an out-of-boundary path that exists and one that does not get the same refusal. Exit 2 and one `ERROR:` line; a rendered document with zero findings is what an unread file must never look like. Root rather than the core's cwd because `claims` resolves relative arguments against the toplevel and its own path lens has always answered `path leaves the repository root` for a document *citing* `/etc/hosts` — the op owned that boundary for the paths it reads about and never applied it to the path it reads from. Both of the core's opt-outs are honoured (`SUPERTOOL_ALLOW_OUTSIDE_CWD=1`, `allow_outside_cwd` in `.supertool.json`), and an unparseable config is not an opt-out. `docs/presets/claims.md` claimed "the op never reaches outside the repository root" from the day it shipped; that sentence is now true and says which root. **Still open:** preset ops remain absent from the core's `_PATH_ARG_POSITIONS`, so this is the instance and not the class — any other preset op with a path argument is still outside the chokepoint.
