- **`gh-issue-create` and `gl-issue-create` silently discarded any payload key they did not read, and it bit in both directions on the same day** ([#2123](https://github.com/Digital-Process-Tools/claude-supertool/issues/2123)). A `body` key on `gl-issue-create` (which wants `description`) created a GitLab issue with no description at all -- GitLab filled it with the project's default template, and the call still returned `PASS` with an `iid` and a URL. Filing that issue then reproduced it the other way: a `description` key on `gh-issue-create` (which wants `body`) created an empty GitHub issue the same way, minutes later. A payload key that goes nowhere is indistinguishable from a payload key that worked, and create-wrong is the worst of the three outcomes a payload key can produce (create-correct, refuse, create-wrong), because only a human noticing recovers it.

  `gh-issue-create`, `gl-issue-create`, `gh-pr-create` and `gh-pr-edit` -- every `@payload` write op this maintainer loop's own tracker calls go through -- now refuse a payload carrying a key they do not consume, before `gh`/`glab` is ever invoked, naming the offending key(s) and the op's full accepted set. `gh-issue-create` also accepts `description`/`description_file` as aliases for its native `body`/`body_file`, and `gl-issue-create` accepts `body`/`body_file` as aliases for its native `description`/`description_file`, so a payload written for one forge and pointed at the other now lands rather than silently losing the text. New shared helper: `presets/_payload_keys.py`.

  No shared payload loader exists across these four ops today -- each already carries its own private `_load_payload` -- so building one to learn every op's key set would be a larger change than this issue warrants; the wider question, one core loader for every `@payload` op, is filed rather than answered here.
