- **The guard rules `replaces` cannot express now ship to every repo, and the four that do not are named** ([#1698](https://github.com/Digital-Process-Tools/claude-supertool/issues/1698)). `.claude/jit-context/tools/00-manual/` holds five hand-written rules, each there because no `replaces` entry can reach what it forbids. `claude-jit-context`'s hooks read them out of `$CLAUDE_PROJECT_DIR`, so they guarded sessions run inside this checkout and no other repository — measured in `Digital-Process-Tools/claude-oss`, whose whole workflow is ops, `./supertool 'git-push' 2>&1 | tail -6` ran unblocked and the cut removed the `Repo:` and `Upstream:` lines, the two that say which repository was written to. `hooks/shipped_rules.py` is read by the PreToolUse hook `hooks/hooks.json` already registers, so it reaches every plugin user; it reads the same markdown and the same `00-index.tsv` out of `$CLAUDE_PLUGIN_ROOT` rather than copying them, translating the index's awk pattern into Python `re` and declining a POSIX class it does not know instead of approximating it into a different pattern.

- **One of the five travels, and the other four are a recorded absence with the reason** ([#1698](https://github.com/Digital-Process-Tools/claude-supertool/issues/1698)). `supertool-no-cut` is a claim about supertool's own output format, so it is true wherever supertool is installed. `merged-is-not-ancestry` encodes a squash-merge workflow and would be a wrong block in a repo that merges with a merge commit; `git-C-has-cwd` names ops that exist only where the `git` preset is loaded; `harness-tools-blocked` fires on `Edit|Write|Read|Grep|Glob`, which no shipped matcher covers and which `plugin.json` already calls the operator's setting; `op-defaults-that-narrow` wants `once,remind`, and once-per-session needs state a PreToolUse hook does not carry. A wrong block in someone else's repository has no escape short of `raw_command_guard: false`, so the bar for travelling is that the rule is about supertool rather than about this repository. `tests/test_shipped_guard_rules_1698.py` partitions every `.md` into the two lists and goes red when a sixth belongs to neither.

- **A repo that does not get a rule is told which and why, rather than left silent** ([#1698](https://github.com/Digital-Process-Tools/claude-supertool/issues/1698)). `hooks/guard-selftest.py` prints every shipped rule with its state — enforcing, stood down because the project owns its own copy, or skipped with the reason — and then every rule that stays local with its reason. That is the property `.claude/settings.json`'s own registration already keeps when its script is absent (`the command was allowed - this is a statement about the guard, not about the command`): a guard that is quietly not there is worse than one that is loudly missing. Two ordering rules keep the layer honest: a shipped rule is consulted only where the registry returned no block, because a regex cannot express `unless_flag`; and a project carrying its own copy of a rule file owns that rule, per rule, so no supertool worktree refuses one command twice with two different messages ([#1376](https://github.com/Digital-Process-Tools/claude-supertool/issues/1376)'s option 3).
