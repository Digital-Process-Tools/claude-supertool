- `channel:health` can reach `FORWARDING` again when supertool is installed as a plugin (#2182).
  Both of `subscription()`'s collision gates answered "will a second channel-capable server bind
  this socket?" from the filesystem, and both were wrong in the ordinary supported configuration.
  `_dual_declaration_objection` walks `_mcp_roots()`, whose first entry is derived from `__file__`
  and therefore resolves to whichever copy of supertool is executing -- a development clone, or the
  marketplace cache directory -- and both ship a `.mcp.json` declaring `claude-channel`, so the
  objection fired in every session regardless of the user's own config. `read_refusal` was worse:
  `channel:health` writes the marker it then reads, because `_configured` runs `claude mcp get`,
  which spawns a fresh instance of the configured channel server, which loses the bind to the live
  consumer and marks on its way out -- measured by deleting the marker, running `channel:health`
  alone, and watching it come back inside that run's own 1.26s. Both gates now ask the harness
  whether `claude-channel` is actually configured, via the `_configured` call this file already
  has: `False` opens them, `True` keeps #2051's and #2133's findings exactly as they were, and an
  unanswerable lookup keeps declining rather than being read as "no rival".
- Two tests in `test_watch_channel_dual_declaration_2051.py` resolved their socket from the bare
  name `oss-supertool`, which is a live channel on a developer machine rather than a fixture, so a
  real `.refused.json` left beside that real socket by an unrelated process decided the verdict.
  One of them failed for that reason alone, independently of any product change. They now use the
  `st2051-` prefix the same file already reserves for its own paths (#2182).
