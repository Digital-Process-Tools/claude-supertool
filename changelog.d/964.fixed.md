- **A board op's filter split by the `:` tokenizer was dropped, and the board printed as the answer** ([#964](https://github.com/Digital-Process-Tools/claude-supertool/issues/964)). `gh-issues`, `gh-prs` and `gl-mrs` take their filters as one comma-separated segment, and supertool hands every `:`-segment to the preset as its own argv entry — but each `main()` read `sys.argv[1]` and nothing else. So `gh-issues:state=open:oops` reached the op as `['state=open', 'oops']`, the second half was discarded in silence, and the board rendered from a partly-applied filter at exit 0 with no warning. All three now refuse, naming the segments that were never applied and the single-segment form that survives the tokenizer.
- **This is [#864](https://github.com/Digital-Process-Tools/claude-supertool/issues/864) one layer up, and the layer is why it survived it.** #864 taught the *tokenizer* in `presets/_filter_tokens.py` to refuse a token it could not place, and #939 put all three boards behind that one refusal. Nothing guarded the argv the tokenizer is handed. So the refusal was not bypassed by a token mangled into something that looks valid — it was bypassed by never being shown the token at all, which is why every value-level check kept passing. The new guard is in the same module for the same reason: two independently written refusal paths in one preset family is how they disagree again in three months.
- **The colon-in-a-value case, which has no fix and now says so.** `label=lane:tracker-ops` splits into a perfectly valid `label=lane` plus an orphan, so the key is known, the value is a string the backend might match, and nothing anywhere objects — `gh issue list --label lane` is queried instead. There is no escape: `label=lane\:x` splits identically, and [#806](https://github.com/Digital-Process-Tools/claude-supertool/issues/806) declined to promote `\:` into a supported contract. Rather than invent a grammar, the refusal states that such a value cannot be expressed to a board op at all, so a reader stops looking. A payload route (`gh-issues:@file`) remains open to be designed later; GitLab's scoped `scope::value` labels are the real candidate for it, not GitHub's.
- **The issue's own premise did not survive checking, and the finding is larger than it.** It was filed reporting that this repo's labels are namespaced with a colon — `lane:tracker-ops`, `priority:medium` — and that every lane query was therefore returning a silently empty board hiding fifty issues. Verified live against the tracker on 2026-08-07: `gh label list` returns `lane-tracker-ops`, `lane-validators`, `priority-medium` — every one spelled with a **hyphen**, and no label containing a colon has ever existed here. `gh-issues:label=lane-tracker-ops,state=open` returned its sixteen rows before this change and returns them after. No lane query anyone could actually run was ever empty. What *is* real is the general case the colon example is one instance of: any trailing segment, on any of the three boards, was discarded without a word, and `gh-issues:state=open:COMPLETEGARBAGE` returned the entire open board as a filtered one.
- Ops whose grammar is genuinely positional — `gh-job:ID:raw:START:END`, `gh-job:ID:grep:PATTERN` — are deliberately not covered, and the helper's docstring says so.
