- Eleven of the twenty-one GitHub ops now declare what raw `gh` invocation they supersede, up from four, so the shipped `PreToolUse` guard covers the whole `gh` family rather than `gh pr` alone ([#1384](https://github.com/Digital-Process-Tools/claude-supertool/issues/1384)). `gh issue view` names `gh-issue` (`--comments` / `-c` selects `:full`), `gh issue create` names `gh-issue-create`, `gh pr list` names `gh-prs`, `gh pr checks` names `gh-pr:NUMBER:status`, `gh run view` names `gh-run`, `gh run view --log` / `--log-failed` name `gh-job`, and `gh label list` names `gh-labels`.
- `gh run list --branch` and `gh run list --commit` name `gh-branch`. That pair is the whole `gh run list` mapping: those are the two questions `gh-branch` answers, and `gh run list --branch <default> --limit 1` is the exact command whose wrong answer it exists for — it returns whichever workflow started last, routinely CodeQL, and reports that conclusion as the commit's. A bare `gh run list` is an enumeration no op produces and is left running.
- `gh pr list --json` is excluded too, and asymmetrically: `gh-prs` renders a board with no field-selection vocabulary, and the maintainer skill's branch reap uses `--json headRefName -q` to enumerate merged head branches, which no op produces. `gh issue list --json` stays claimed, because `gh-issues` carries `search=` and `iids` and no documented use of the raw shape survives them. A missed block is the direction this guard may safely be wrong in; a dead end has no per-command way past.
- `--web` and `-w` are excluded from every `gh` mapping that has them, including the four that shipped in v0.34.0. No op opens a browser, so `gh pr view 1 --web`, `gh issue create --web` and their siblings were dead ends with no per-command way past — `raw_command_guard: false` is repo-global. This widens what stays usable; nothing new blocks because of it.
