- **The `gh-branch` poller's #2333 direction guard now covers a missing job list, not only a raw-empty run list** ([#2537](https://github.com/Digital-Process-Tools/claude-supertool/issues/2537)). `branch._jobs_for()` failing one `gh run view --json jobs` reached `branch.verdict()` straight through as UNKNOWN -- never as `NO_RUN` -- so it never entered the #2333 guard, which only ever widened `NO_RUN`/`NO_RUN_STALE`, and fired a transition on the very first miss: a concluded, already-green commit flapped `went_green` -> `unknown` -> `went_green` three times in one afternoon, each dip lasting exactly one 30s poll. `_snapshot` now also reports `has_unread_jobs`, structural rather than text-derived (mirroring `has_failed_leg` from #2355), so `poll()` can tell "a job list did not come back" apart from the *other* way `verdict()` reaches UNKNOWN -- an unreconciled tally, where every job list did come back and there is nothing to ride out. Only the job-list-miss UNKNOWN now feeds the same `no_run_streak` grace window the raw-empty case already used: a single miss on an otherwise-confirmed commit is discarded, and a persistent one still surfaces `unknown` once it reaches the threshold. `tests/test_watch_gh_branch_unread_jobs_2537.py` is the fixture, with both must-fire positive controls the issue named -- a fresh sha's first miss, and a miss that persists past the confirm streak.
