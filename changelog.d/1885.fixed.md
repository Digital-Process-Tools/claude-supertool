- **The `git-status` validator's no-argument arm answered `ok: true, state: "clean"` for a working tree nothing had measured** ([#1885](https://github.com/Digital-Process-Tools/claude-supertool/issues/1885)). A missing or empty file argument is an adapter fault, not a measurement — every sibling adapter that takes a single file argument (`ruff`, `eslint`, `tsc-check`, `phpstan`, `xmllint`, `yaml-check`, and more) already routes it to `code: "adapter"`; this one adapter alone answered a fabricated `clean`. It now matches the convention.
- **The `rev-parse` arm stays as it is, and that is a finding rather than a punt** ([#1885](https://github.com/Digital-Process-Tools/claude-supertool/issues/1885)). The question this issue asked: can a genuine "not inside a repository" (endorsed as clean by this adapter's own README) be told apart from a real repository whose `rev-parse` faulted — a corrupt `.git`, a permissions problem? Measured rather than assumed: `git rev-parse --is-inside-work-tree` answers both a directory with no repository above it and a repository whose `.git/HEAD` is corrupted with the byte-identical signal — exit 128, empty stdout, "fatal: not a git repository" on stderr. Git itself does not expose the distinction, so the adapter cannot manufacture one without also misrouting the endorsed case, which is the regression [#1883](https://github.com/Digital-Process-Tools/claude-supertool/pull/1883) declined to introduce. `test_rev_parse_cannot_tell_outside_a_repo_from_a_faulted_one` pins this so a future git version that starts telling the two apart is a signal to revisit, not a silent gap.
