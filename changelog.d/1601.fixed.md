- **Three validator adapters read an empty run as a clean verdict about a file the linter may never have opened** ([#1601](https://github.com/Digital-Process-Tools/claude-supertool/issues/1601)). `prettier-check`, `markdownlint` and `stylelint` each published `ok: true, count: 0` on a zero exit with no output, which is what an *ignored* file produces too. They do not share a probe, so they do not share a fix — the precedent is `ruff` after [#1587](https://github.com/Digital-Process-Tools/claude-supertool/issues/1587): ask on the zero-finding arm only, and let the question have three answers.

  **`prettier-check` asks `prettier --file-info`**, which resolves the same ignore files and answers `{"ignored": true|false}`. It is handed the same `--config`/`--ignore-path` flags as the check, because a probe reading a different ignore set answers about a different run; a probe that cannot answer — non-zero, unparseable, no `ignored` key, gone, hung — is `skipped` with its own reason and never falls back to `ok`.

  **`markdownlint` needs no second spawn, because the first one already says so.** markdownlint-cli honours `.markdownlintignore` while resolving its arguments to a file list, and when nothing survives — an ignore match, or a path that is not there — it prints its usage banner on stdout and exits 0 (measured, markdownlint-cli 0.49.1). A file it genuinely linted clean prints nothing on either stream, so any output on a zero exit is the tell, and the skip quotes the first line of it. A missing `.md` was `ok: true` until now.

  **`stylelint` was worse than the issue said, and reading one stream was why.** It writes its `--formatter json` report to **stderr** — `process.stderr.write(report)` in its own `cli.mjs`, stdout being reserved for `--fix` output — and older releases wrote it to stdout. The adapter read stdout and called emptiness clean, so against stylelint 16+ every CSS file came back clean including one holding a `CssSyntaxError`: not the ignore case at all, but every run. Both streams are now offered to the JSON reader, since the stream is not the question and the report is. No report on either is a `NOT CHECKED` fault, except the one case stylelint names itself (`AllFilesIgnoredError`), which is a scope decline and is `skipped`; no probe was invented for it, because it has none and needs none.

  Two adjacent arms in the same class, fixed with it: `stylelint` absent was an `adapter` error, so a repo registering it on a machine without it failed every CSS edit — it is `refusal.absent()` now, quiet unless named in `$SUPERTOOL_REQUIRE_VALIDATORS`, like every other adapter since [#1202](https://github.com/Digital-Process-Tools/claude-supertool/issues/1202). And `pyright` with nothing on either stream reported `ok: true`; it declines instead. A third, found by running the fixed `markdownlint` against the real CLI: its row parser predates the severity word markdownlint-cli now prints between the position and the rule (`b.md:1:1 error MD018/...`), so every located finding missed the pattern and fell through to the whole-output catch-all — four findings arriving as one `lint` error with `line: null`, no source context and a count of 1.
