- **`gh-job` split a CI job log with `str.splitlines()`, so the log's author chose where its lines began** ([#1105](https://github.com/Digital-Process-Tools/claude-supertool/issues/1105)). The same forged-boundary class as [#1081](https://github.com/Digital-Process-Tools/claude-supertool/issues/1081), one preset over, with a worse reader. Python splits on eight separators no CI log defines — VT, FF, FS, GS, RS, NEL, U+2028, U+2029 — and everything `gh-job` does afterwards anchors at column 0. `_SUITE_SUMMARY_RE` does so **on purpose**, to keep a nested run's summary reprinted under `-s` from replacing the job's own. On a pull request the code writing that log is the pull request's code, so a `print` carrying U+2028 opened a column-0 line mid-sentence and authored the `Suite:` line — the one number in the whole render claiming to count TESTS — on a job whose log states no test count at all. The split is now LF / CR / CRLF only, via the `_untrusted.split_lines` #1081 added.

    **Narrowing alone would have been the same bug pointed at the terminal.** The separator would have survived into `  1234 | …`, breaking the row on every terminal in normal use and putting the half below it at column 0 with no gutter — a line the reader attributes to supertool ([#851](https://github.com/Digital-Process-Tools/claude-supertool/issues/851), one surface over). So the separators the split no longer honours are disclosed as pictures on the way through. Tabs are kept: a log line is a block and its indentation is the author's content.

    **Eleven other `str.splitlines()` calls in `presets/github/` were checked, not swept.** The count in the issue title was right — twelve, verified. One more changed and ten did not, because the fix is only correct where the format recognises fewer separators than Python does, and a sweep that touches twelve files and explains none of them makes the next reader believe the question was answered everywhere.
