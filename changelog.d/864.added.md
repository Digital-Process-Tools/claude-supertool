- **`gh-issues` carries the milestone, and can ask for its absence** ([#864](https://github.com/Digital-Process-Tools/claude-supertool/issues/864)). Every release tick starts with a milestone query, and the board could answer neither half of it — so each one paid for a raw `gh issue list --json … --jq` fallback plus a second call to re-acquire the labels the op gives for free.

  **The milestone is a flag, not a column.** A column costs its width on every row of every board, and most issues on most repos carry no milestone, so a reserved cell would be mostly blank space taken from the title. It rides in the flags slot beside `[stale]` instead — `[m:v0.26.0]` when there is one, nothing at all when there is not. `[m:?]` is the third state and is load-bearing rather than decorative: `gh issue list --json milestone` returns an explicit null for an unmilestoned issue, so a missing key means the field did not come back, and rendering that as blank would assert "unscheduled" about an issue nobody asked GitHub about.

  **`nomilestone` is the gap query, and it declines rather than guessing.** `gh issue list` can name a milestone; it cannot ask for the absence of one, so the filter runs client-side over the fetched rows. That makes a row whose milestone did not come back unplaceable — keeping it reports a scheduled issue as unscheduled, dropping it hides exactly the kind of gap the query exists to find — so the op declines and names the field, the way `external` and `stale` already do.
