- **`watch:github-issue-feed:<scope>` — GitHub issues, watched as a population rather than one at a time** ([#525](https://github.com/Digital-Process-Tools/claude-supertool/issues/525)). Labels land, assignees change, someone answers a question you asked days ago, and until now nothing in `watch` noticed. Six bundled sources covered pipelines and merge requests; none covered the thing that *starts* the work. The scope is a filter string — `@open`, or `state=open,label=lane-watch` for exactly the label-triggered handoff the issue was filed about — and every poll is one `GET /repos/{owner}/{repo}/issues` call whatever the population size. Eleven events: `issue_opened`, `issue_reopened`, `issue_entered_feed`, `issue_labeled`, `issue_unlabeled`, `issue_assigned`, `issue_unassigned`, `issue_comment_added`, `issue_closed`, `issue_left_feed`, `issues_unreachable`.

  **It is a feed and there is deliberately no per-id companion, which is the opposite of what #525's body asked for.** The body specified `watch:github-issue:<n>`; the issue's own comment then argued that shape cannot serve the case that motivated it, and the comment is right — a label-triggered workflow fires on issues no poller was spawned for, and *was an issue created* is unanswerable by construction from a watcher over a number that already exists. The reason no per-id tier is needed on top is specific rather than a preference: `gitlab-mr-feed` has to spawn per-MR pollers because pipelines, conflicts and approvals are absent from its list payload, whereas every fact #525 named — `labels`, `assignees`, `comments`, `state_reason`, `created_at` — is carried by the population rows themselves. So this source has one tier, no fan-out, and none of the cross-tier duplicate suppression ([#434](https://github.com/Digital-Process-Tools/claude-supertool/issues/434)) that a second tier would require.

  **An arrival gets three answers, not one.** `issue_opened` is claimed only when the row was created after the previous poll's own recorded instant; a number this feed watched close and then saw return is `issue_reopened`, observed rather than inferred; everything else is `issue_entered_feed`, which reports the arrival and carries `created_at` and `state_reason` without asserting a cause the population query cannot establish. GitHub leaves `state_reason: reopened` on an issue permanently, so reading it as an edge would announce a reopen that happened months ago as one that happened now.

  **A population that could not be established is never a short one.** A gh failure, junk JSON, a scope carrying a filter token this source cannot apply, or more rows than the five-page cap all return no population at all and emit one `issues_unreachable` per outage — not once per poll. Returning the prefix that fit would fire a departure event for every issue past it, which is this repository's house defect wearing a page cursor. `known`, `observed_at` and `closed_recent` survive the outage untouched, so recovery re-announces nothing.

  **Pull requests are dropped, and that is load-bearing.** `GET /repos/{owner}/{repo}/issues` serves issues and pull requests from one array and distinguishes them only by a `pull_request` key — 2 of the 79 rows on this repository at the time of writing. Without the drop, every PR anyone opens arrives as `issue_opened`.

- **Two claims in [#525](https://github.com/Digital-Process-Tools/claude-supertool/issues/525)'s design notes were already false when it was filed, and both were re-derived rather than carried forward.** It states that the `gitlab-mr` source excludes `comment_added` from `DEFAULT_ONLY` because `user_notes_count` counts system notes. `presets/watch/defaults.py` has carried `comment_added` in `DEFAULT_ONLY` since [#519](https://github.com/Digital-Process-Tools/claude-supertool/issues/519), and the belief it was held out for was itself disproved there against a live instance over twelve merge requests. The GitHub analogue is sound for the same reason: REST `comments` is a count of issue comments, so a label edit does not move it and `issue_comment_added` cannot fire with nothing to read.
