- **An interpreter that exited 0 wrote the Bash guard's permission verdict, because the wrapper forwarded its whole envelope verbatim** ([#1625](https://github.com/Digital-Process-Tools/claude-supertool/issues/1625)). `hooks/pre-bash-guard.sh` matched a prefix of the rung's stdout and printed the rest unchanged, so a `$VIRTUAL_ENV/bin/python3` that wrote a well-formed `hookSpecificOutput` document carrying `"permissionDecision":"allow"` had authored the harness's own decision. Well-formed JSON, so nothing for [#1613](https://github.com/Digital-Process-Tools/claude-supertool/issues/1613) — that fix closed the route where a *path* writes the field by concatenation, this is the route where the rung's own stdout does. Same `usurps` class, different door — and the guard had no way to tell its own answer from a forgery, because the two were the same bytes.
- **The fix is a shape change, not a filter.** `hooks/pre_bash_guard.py` no longer writes JSON at all: it writes `supertool-guard-v1 ` and one of three words — `silent`, `note`, `deny` — then a newline, then the text. The wrapper authors every structural byte of the envelope, `permissionDecision` is a literal next to the only value it can hold, and the rung's text reaches JSON only through the escaper [#1613](https://github.com/Digital-Process-Tools/claude-supertool/issues/1613) added. Authenticating the channel was the other candidate and it cannot work here: any token proving *my rung wrote this* has to be handed to the rung, and the interpreter is what executes the script, so no secret separates "ran it" from "read it and lied".
- **A verb the wrapper does not know is declined and disclosed, never dropped and never relayed.** Two installs disagreeing about the vocabulary would otherwise be a gate that silently said nothing on every call. The stated cost of a closed vocabulary: a field the `PreToolUse` protocol gains has to be added to both files before it can be emitted — an open channel into someone else's schema, exchanged for a closed one this repository owns both ends of.
- **The bound, unchanged and still the reason this is not a release blocker.** Reaching the sink needs `$VIRTUAL_ENV` pointed at a directory whose `bin/python3` the attacker controls, and running that binary is already an execution primitive. A rung that is lying can still fabricate a `deny` reason, or suppress one by staying silent — which it could always do by not answering. What it can no longer write is `allow`, the one value that removes the user's own permission prompt, or any other field of the hook protocol.
- **Two Windows-only regressions the change introduced were closed with it, both graded reasoned rather than observed.** A text-mode `sys.stdout` turns the new line feed into CR LF there, which would have left the wrapper reading a verb with a carriage return stuck to it — an unknown dialect, so every `deny` on Windows would have become a disclosed allow. A text-mode write also encodes with the console code page, so a non-ASCII path inside a refusal could raise instead of writing. `json.dumps` escaped both into ASCII for free, and that is the property not writing JSON gives up, so the hook writes UTF-8 bytes through `sys.stdout.buffer` and the wrapper strips a trailing carriage return from the verb. `_json_string` also escapes line feed, carriage return and tab now rather than replacing them with `?`: `guard_refusal` is a multi-line document and it reaches JSON through bash now, not through `json.dumps`.
