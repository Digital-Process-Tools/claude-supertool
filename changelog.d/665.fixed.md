- **`SUPERTOOL_REQUIRE_VALIDATORS` produced its loud error and then exited 0, reporting it as somebody else's problem** ([#665](https://github.com/Digital-Process-Tools/claude-supertool/issues/665)). The escalation is the one knob that exists to stop "the gate is not running" from reading as a pass, and it read as a pass. Found in the v0.26.0 audit, in code from this release, guarding among other things a secret scanner.

  **The mechanism is the before/after delta, and the fix is that an adapter error was never a finding.** The `[validators]` block subtracts the pre-edit count from the post-edit one. `refusal.required()` emits its `adapter` error on *both* passes when the tool is absent, so the counts cancel and the row was labelled `pre-existing — not from this edit` — a sentence asserting that a real finding predated the edit, printed about a file nothing had opened. Meanwhile `[result]`, the line documented to survive `| tail -1`, said `1 op run, 1 write` and the process exited 0. A result whose errors are all `code: "adapter"` is now its own state: never diffed, rendered `NOT CHECKED (no verdict about this file)` with the adapter's full reason under it, named on the `[result]` line as `1 validator NOT RUN (shellcheck)`, and exit 1.

  ```text
  shellcheck  : NOT CHECKED  (no verdict about this file)   0.2s
       adapter  shellcheck is named in $SUPERTOOL_REQUIRE_VALIDATORS but could not run, so this file was NOT checked: shellcheck not found on PATH
  [result] 1 op run, 1 write, 1 validator NOT RUN (shellcheck) — those validators returned no verdict, so the file was NOT checked
  ```

  **The judgment call: naming a validator in the variable is a statement that it must be present *here*, so a missing one is a configuration fault and not a CI-only escalation.** There is no CI auto-detection and deliberately none — a tool that decided for you which absences are fatal would be guessing at the one thing only the operator knows. Unset, nothing above is reachable and an absent tool is the honest `skipped` it always was, exit 0. And it is an exit code, **not a refusal**: the edit still lands and still rolls back on exactly the conditions it did before. Converting "we could not check" into "we will not work" would trade the quiet failure for a louder one rather than removing it. All of an adapter's errors must be `adapter`-coded for the state to apply — four real findings alongside one adapter row is still a measurement of the file, and suppressing that would be this same defect pointing the other way.

  **Method.** TDD, end-to-end through `main()` rather than through the adapter. RED: 9 failing, including the auditor's reproduction driven by the real `shellcheck` adapter with an empty `PATH`, asserting the exit code and the content of the `[result]` line specifically. That distinction is the reason this shipped: all three adapter suites assert the escalated message and all three were green, because the defect is entirely in what the core does with a correct result. Three of the new tests passed from the start and pin what must not move — the write still happens, a genuine pre-existing finding still reads as pre-existing, and an unset variable still yields `skipped` and exit 0. GREEN: full suite 7597 passed, 72 skipped.

- **`eslint` reported an absent eslint as a failed one, on the machine it actually happens on** ([#667](https://github.com/Digital-Process-Tools/claude-supertool/issues/667)). Case one of that adapter's documented three — *"eslint not installed → `skipped`, with the install hint"* — was unreachable on any laptop with node. `eslint` is not on `PATH`, `npx` is, so `_resolve_cmd` returns the documented `npx --no-install eslint` fallback and the install-hint branch is never taken. npx then exits 1 with empty stdout and `Unknown command: "eslint"` (npm 11) or `could not determine executable to run` (npm 8-10) on stderr, neither of which matches the no-config signature, so it landed on an `adapter` error and the reader was told eslint had failed. Those two messages, only those two, and only on the npx route, are now the same `skipped` with the same `npm install --save-dev eslint` hint; every other npx failure stays loud.
