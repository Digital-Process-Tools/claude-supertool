- **Every invocation was recompiling 17,380 lines; the entry point is a shim now** ([#931](https://github.com/Digital-Process-Tools/claude-supertool/issues/931)). CPython writes and reuses `__pycache__/*.pyc` for modules it *imports*, and never for the script named on the command line — `__main__` is compiled from source on every run, by design. The whole tool *was* that script, so every call re-parsed and re-compiled all of it. `supertool.py` is now ~80 lines that import `_supertool.py`, which is the same file under a new name.

  Measured with the harness from the issue, macOS/py3.14, 15 samples, `min`: `python3 supertool.py version` went from 199.4ms to 89.0ms, and the recompile term specifically from 109.2ms to 1.3ms. On GitHub runners the term was 143.0ms (ubuntu), 144.8ms (windows) and 100.0ms (macOS), so this is not the Windows-specific cost the issue was originally filed as — it is paid on every platform, by every user, on every call, and roughly 900 times per CI leg.

  Nothing about the invocation contract moves. `python3 supertool.py 'op'`, `python3 -m supertool`, the `supertool` console script and the `~/.local/bin/supertool` / `dvsi/supertool` symlinks all behave exactly as before, and `import supertool` still yields the module that holds the code — the shim rebinds its own `sys.modules` entry rather than re-exporting, so a name patched on `supertool` is the same object the implementation reads.

  An install that copies `supertool.py` alone now refuses with exit 2, naming the missing file and the directory it looked in, instead of raising `ModuleNotFoundError: No module named '_supertool'` at whoever inherited it. That verdict is taken from what is on disk beside the shim and never from whether `import _supertool` succeeds — wherever the tool is installed as a package the name resolves from anywhere, so the naive version ran a *different* tree and printed a convincing version banner. For the same reason the shim checks which file actually loaded, since `sys.path` does not outrank the `sys.meta_path` finder an editable install puts there, and warns on stderr if it was not the one beside it. And `_supertool.py` is still runnable as a script — anything spawning `[sys.executable, supertool.__file__, ...]` lands there, and without that it would have printed nothing and exited 0.

  Three things quietly stopped looking at the code when it changed name, and all three moved with it rather than being discovered later: the coverage floor (a 89% floor over 17k lines would have become a 89% floor over an 80-line shim, still green), the `changelog.yml` path filter that decides whether a PR owes a fragment, and the mixed-tree guard, which compared the invoked file against the project's `supertool.py` by identity and now compares install directories — file identity could never hold again and it would have warned on every invocation made from inside a checkout.
