- **`SUPERTOOL_READ_ONLY=1` — a caller declares itself read-only, and any op `ops:roster` does not class `read-only` refuses instead of running** ([#1787](https://github.com/Digital-Process-Tools/claude-supertool/issues/1787)). `ops:roster` has always classed every op unmarked/`*`/`!`; until now that classification was descriptive only. The concrete incident, `claude-oss#251`: a review agent ran `radar` (classed `!`) against the live watch fleet it was auditing, mid-audit of that fleet's own healing logic -- nothing stopped it, and it was knowable only because the agent reported itself. The refusal names the op and its class rather than a bare "denied" (`SKIPPED: 'paste' is class \`*\` (writes) ...`) and points at `ops:roster`. Fires at the earliest point the op name is known, ahead of every other check, so a batch sub-op is caught the same way. Deliberately an env var, not a `.supertool.json` key -- the flag is one caller's intent for one call, and a project-level toggle would gate every caller sharing the tree or none. And deliberately shipped despite constraining only a cooperative caller: the raw-command guard hooks `Bash` only, so a determined writer can always not call the op -- this is a guardrail against a mistake, the same shape as a shell `readonly` variable, not a security boundary. `docs/configuration.md#caller-declared-read-only-mode` has the full writeup.
