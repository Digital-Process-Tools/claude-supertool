- **`SUPERTOOL_READ_ONLY=1` — a caller declares itself read-only, and any op `ops:roster` does not class `read-only` refuses instead of running** ([#1787](https://github.com/Digital-Process-Tools/claude-supertool/issues/1787)). `ops:roster` has always classed every op unmarked/`*`/`!`; until now that classification was descriptive only. The concrete incident, `claude-oss#251`: a review agent ran `radar` (classed `!`) against the live watch fleet it was auditing, mid-audit of that fleet's own healing logic -- nothing stopped it, and it was knowable only because the agent reported itself. The refusal names the op and its class rather than a bare "denied" (`SKIPPED: 'paste' is class \`*\` (writes) ...`) and points at `ops:roster`. Fires at the earliest point a *recognised* op name is known, ahead of every other check -- an unrecognised/typo'd name is explicitly carved out (self-review, mirroring the mixed-tree gate's own #1878 carve-out) so it still falls through to "unknown operation" instead of a manufactured, unfixable-sounding decline. A batch sub-op re-entering `dispatch` recursively is caught the same way; the six `_READ_OP_AT_FIELDS` read ops (`grep`, `read`, `between`, ...) route around that recursion and are pinned read-only by a census test instead, since they never re-enter the gate at all. Deliberately an env var, not a `.supertool.json` key -- the flag is one caller's intent for one call, and a project-level toggle would gate every caller sharing the tree or none. And deliberately shipped despite constraining only a cooperative caller: the raw-command guard hooks `Bash` only, so a determined writer can always not call the op -- this is a guardrail against a mistake, the same shape as a shell `readonly` variable, not a security boundary. `docs/configuration.md#caller-declared-read-only-mode` has the full writeup.
