- The validator cache was a second way into #1036. `_validator_run_one` returns
  a cache hit before it reaches the point where an adapter's payload is stripped
  of the keys the core owns, so an entry written by any build from before that
  fix carried the adapter's `"timeout": true` verbatim. Nothing retired those
  entries: the cache is signed with this machine's own secret, so a stale entry
  verifies, and its key is `content ‖ name ‖ cmd ‖ tool-fingerprint` with no
  supertool version in it, so upgrading does not miss it. Inside
  `validator_cache_ttl_hours` (default 24, `0` meaning forever) a real finding
  came back out of the cache wearing a timeout the core never observed, the row
  read `NOT CHECKED`, `rollback_on_fail` did not run and the bad edit stood. The
  cache read now strips the same keys the fresh path does, and re-stamps the two
  the core owns for the run in hand — `elapsed_s` is the lookup that just
  happened, `resolved_to` is the target just resolved — rather than replaying a
  cached copy of either.
