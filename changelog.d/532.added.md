- **`worktree:setup[:PATH]` / `worktree:teardown[:PATH]`** — a fresh `git worktree add` never brings gitignored local state along (vendored binaries, machine-specific DB config, a generated asset cache), so a project's test suite fails there in whatever misleading way each missing piece produces ([#532](https://github.com/Digital-Process-Tools/claude-supertool/issues/532)). Driven entirely by a project's own `ops.worktree.setup` in `.supertool.json` — nothing project-specific lives in the op itself: `link` (symlinked — large, immutable, shared artefacts only), `copy` (copied, never linked — machine-specific or mutable state; `shutil.copytree(..., symlinks=False)`/`copy2` under every code path, never `os.symlink`, since getting `link`/`copy` backwards corrupts the primary checkout from a worktree), `exclude` (appended to a worktree-PRIVATE exclude file — not `.git/info/exclude`, which git shares across every worktree of a repo — so a symlinked artefact can never be swept into a commit by `git add -A`/`git add .`). No config declared is a clean no-op naming where to declare one. Every entry reports one of three outcomes — acted-on, already-there (idempotent), or a WARNING (never a failure) for a source missing from the primary checkout. `teardown` undoes exactly what `setup` recorded creating, in a manifest kept in the worktree's own private git dir (covering `link`, `copy` and `exclude` alike, and refused rather than trusted as empty if it exists but cannot be parsed), and leaves everything else — including a file the user happens to have at the same path — untouched. Every entry is validated before anything touches disk: config is read from the worktree being provisioned, so an entry carrying a newline, an absolute path, or a `..` segment is refused as untrusted text, and a real filesystem failure warns rather than aborting the run.
