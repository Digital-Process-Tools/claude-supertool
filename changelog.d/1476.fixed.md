- **`channel:health` names the process holding the socket in the two arms that used to decline without asking** ([#1476](https://github.com/Digital-Process-Tools/claude-supertool/issues/1476)). *nothing is consuming this socket* and *another session is consuming it* call for opposite actions — launch a consumer, or accept that delivery works and this session is simply not the listener — and both printed the same two lines under `CANNOT DETERMINE`.

  `peer_pid()` shipped with #1192 and had exactly one caller: the point past `read_health()` where a record already exists. The arms that return before it — no readable health file, and a health file the op objects to — never asked a question the platform can answer. The first is the arm that fires when the consumer is a Claude session launched with the channel flag, because it publishes no health file at all.

  Three states, and the third is the one that used to be everything: `socket-holder: pid N — not this process (this process is pid M)`; `socket-holder: pid N — this process`; or `socket-holder NOT resolved — <the refusal the probe returned>`, which is where Windows and FreeBSD land, by name. The verdict does not move — naming the holder is not evidence of delivery, so both arms stay `CANNOT DETERMINE` and the ceiling is still printed. What changes is that a reader can tell *no listener* from *not my listener*.
