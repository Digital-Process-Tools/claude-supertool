- **A runner description or a job ref can no longer become a line `gl-runners` appears to have written.** Same mechanism as #965 — an API-supplied string reaching `print()` without `_untrusted.flat`, and `str.splitlines()` breaking on one of the ten separators #886 widened `flat()` to cover — on the three hand-padded blocks this op renders: the fleet table (`{description[:22]:<22}`, `{tags[:34]}`), the queue view (`{name:<44} {ref:<24} on {runner}`), and the STARVED / UNKNOWN diagnosis, where a description is interpolated into the sentence naming which hosts a reader should go and check. A GitLab runner description is set by whoever registered the runner and a job's `ref` and `tag_list` by whoever can push a branch, so all three are a stranger's text. Twenty renders across `_print_fleet`, `_owner_names`, `_print_diagnosis`, `_print_queue`, `_print_full` and `radar_report` now flatten.
- **What the payload could forge here is a row, not just a line.** None of these blocks goes through `_board.render_row`, which flattens every cell it is handed — they pad with f-string field widths, which is why the defect exists at all. The text after the separator is unconstrained, so it can be spaced to the widths of the block it lands in and read as something the tool emitted: a runner that is not in the fleet, a `3 live runner(s)` verdict against a tag that has none, or — the case in the test — the `Queue: 1 pending, all have a responsive runner` all-clear rendered underneath a queue the op had just reported `## STARVED`. Nothing in this op feeds a merge decision, which is why #968 left it out of a release blocker; it feeds an operational one, and this tracker already records a misleading process view getting two live watchers killed, one of them the one that was needed.
- **Flatten, then truncate — the order is the fix, not an implementation detail.** The fleet table slices its cells to the column width. `flat()` can *widen* a field, because a stream that cannot carry U+2028 spells it `[U+2028]`, eight characters for one (#863), so flattening a cell already cut to 22 trades a row that splits for a row that overflows into the next column. Slicing last keeps `:<22` a width rather than a floor. The queue view has no such slice and is deliberately not given one: cutting a job name to 44 characters to protect an alignment shows the reader a different job's name while they are deciding which job is stuck, which is a visibly ragged row traded for a quietly wrong one. A long job name already pushes that column with no hostile input involved, and the rows around it are independent `print()` calls that are unaffected.
- **The #965 scanner now answers for `ref`, and still for nothing that is not a refname.** `presets/gitlab/runners.py` was already inside `test_no_preset_prints_a_refname_raw`'s three scanned trees; what it was outside of was the key set, so the build was green. `ref` was added on the test the set was built to pass rather than on it sounding like a refname: it names exactly the two `gl-runners:queue` sites and nothing else in those trees, so the set still needs no exemption. `name` was not added and the `title`/`name`/`login` widening **rejected** in #968 stays rejected — `name` alone adds an `mr.py` hit that is a CI job name, and keeping the scan green past it would take the per-field allowlist that is the failure mode the scanner exists to avoid. The remaining fields here are pinned by `tests/test_forged_runner_line_970.py`, which asserts the post-condition per mode: no forged line, and the render is the same height as the same fleet with the separator replaced by a space.
