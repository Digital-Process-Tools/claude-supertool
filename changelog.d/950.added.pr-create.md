- **`gh-pr-create:@FILE` — open a PR from a payload, and never guess the base** ([#950](https://github.com/Digital-Process-Tools/claude-supertool/issues/950)). The payload route, for the same reason `gh-issue-create` has one: a PR body is long markdown with colons, fences and quotes, and none of that survives `:`-tokenisation.

  `repo` defaults to the origin remote and `head` to the current branch, because both are unambiguous facts about where you are standing — a detached HEAD is refused rather than substituted. `base` is required and is never defaulted: `master` and a release branch are equally plausible from one cwd, and a wrong base does not fail, it opens a PR that reviews clean, merges clean, and lands the change where nobody was reviewing. The refusal names the repository's default branch without using it. Both refs are echoed back with the source each came from, so a wrong one is visible at creation instead of after the merge.

  The receipt answers what the second call always was. **Zero checks is not "pending"** — an empty rollup renders identically to one nobody has filled in yet, so the receipt states which of the two it is, with GitHub's own ~15min run-creation window as the boundary and a stated `UNKNOWN` past it; waiting for a run that will never exist is what cost a PR its first life. The body's closing references are parsed with the same reader `gh-pr` uses and echoed back, so a malformed `Closes` line is caught here rather than discovered after the merge. Ends on a one-line `[result]` verdict that survives a pipe.
