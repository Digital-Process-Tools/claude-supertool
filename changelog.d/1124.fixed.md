- **`ops` listed 80 operations and the dispatcher accepted 86** — `batch`, `check`, `introduction`, `ops`, `ops-compact` and `output-format` dispatched fine and appeared in no listing, so the tool's own answer to "what can you do?" read as complete while omitting them ([#1124](https://github.com/Digital-Process-Tools/claude-supertool/issues/1124)). The load-bearing omission was `batch`: the only op that puts several mutations in one call, since a call carries just one `@-` payload ([#341](https://github.com/Digital-Process-Tools/claude-supertool/issues/341)). Measured across 232 agent transcripts from one evening on this repo, 70% of supertool calls carried a single op against a documented 6-7, and every agent that did reach for `batch` had learned it from an out-of-band brief rather than from the tool. `batch` now has a reference in `.supertool.json`, and any op the dispatcher accepts that no config section describes is named on one derived line at the head of the listing — above the SessionStart truncation point, and derived from the same sets `_valid_op_names` uses so the next undocumented op discloses itself. An op a project hides with `status: 0` stays hidden: the disclosure names what the tool omitted, never what the project chose to omit.

  `help:OP` gated its "valid built-in" arm on `_BUILTIN_OPS`, which is a shadowing blocklist rather than a capability list, so `help:batch` answered `no help for op: batch` — denying an op that dispatches, then pointing at a listing that omitted it. It now gates on the dispatcher's own set, the same fix [#614](https://github.com/Digital-Process-Tools/claude-supertool/issues/614) applied to the unknown-op error one layer out.
