- **The four remaining files carrying a stale render size corrected, and every one of them pinned to the render it describes** ([#1877](https://github.com/Digital-Process-Tools/claude-supertool/issues/1877)). `README.md`, `docs/operations/index.md`, `docs/contributing.md` and `hooks/session-start.sh` stated `ops:full` at 74,838 bytes when it renders ~72.7KB, `ops:roster` at ~1.7KB and ~1.4KB when it renders ~2.0KB, and the SessionStart payload at ~2.7KB when it is ~2.9KB. `tests/test_render_size_claims_1877.py` now grades all thirteen figures against the live render, so the next one to drift reds in the pull request that drifts it rather than in an audit six weeks later.

  **Two figures were older than the issue and describe a tree that has not existed since #1774.** `hooks/session-start.sh` and `docs/operations/index.md` still said `ops` is 47,254 bytes and `ops-compact` 9,067 — figures from before the descriptions moved out of `ops` into `ops:full`. `ops` is now ~3.7KB and fits the 7,168-byte cap on its own; `ops-compact` is ~14.7KB and is now *larger* than `ops`, which is why index.md's row calling it "`ops` with the per-op detail trimmed" was wrong about the direction and not only about the number. `docs/contributing.md` attributed `ops:full`'s size to `ops` for the same reason.

  **The figures were reworded from exact byte counts into the KB form, because an exact count cannot be pinned.** Every one of these renders carries `_preset_disclosure()`, which names the absolute path of the config it read, so its byte count is a function of where the checkout sits on disk — measured at 3,721/3,727 for `ops` and 72,709/72,715 for `ops:full` at a 40- and a 46-character path. `tests/test_ops_roster_1231.py` already stated that as policy for the roster. A tolerance of 0.1KB is 100 bytes, an order above that variance and two orders below the 2,129-byte drift this issue is about.

  **A registry, not a walker, and the reason is measured.** The issue asked for a single test walking every file that states a size for a named render. A deliberately narrow regex — a render name in backticks, a size within 80 characters of it on the same sentence — finds 40 hits in 11 files here, and they are at least five kinds nothing in the text separates: a live claim, a historical record in `CHANGELOG.md` and `changelog.d/`, a past-tense sentence, a SessionStart cap that is not a render size at all, and figures already pinned by `tests/test_meta_doc_figures_1783.py`. A dated measurement is a record and stays; an undated present-tense one is a claim and gets graded. So membership is explicit and a record is simply absent from the list. The half a walker was wanted for is kept: a figure written into a file *already* in the registry and graded by no row is a red test naming it, and `CHANGELOG.md` is never opened.

  **Three states in the grader, because two would have hidden the next rewording.** A row whose pattern finds nothing fails as "this test stopped being able to see the claim" rather than passing as clean — the alternative is a figure going stale again behind a green tick, which is the defect this whole class is. Two disagreeing figures for one render fail rather than being graded at random, which is #1783 item 5. The exemption list carrying the one cap figure the harvester reaches is itself guarded: an entry that matches nothing is reported, because a dead exemption is a blind spot that looks exactly like a working one.

  **Three sites remain, in files this change was scoped out of.** `_supertool.py:2575` (`ops` 47,254, `ops-compact` 9,067) and `_supertool.py:17101` (74,838) were held by another lane, and `tests/test_ops_roster_1231.py:3,181,292` carries the same pre-#1774 pair in an undated docstring. Recorded rather than fixed, and the registry is one line per site when they land.
