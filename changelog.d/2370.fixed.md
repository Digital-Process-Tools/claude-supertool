- **`worktree:setup`'s config walk now carries the same trust boundary the core loader and `gl-runners` maintenance-window reader already carry, instead of being a third walker nobody hardened** ([#2370](https://github.com/Digital-Process-Tools/claude-supertool/issues/2370)). `presets/worktree/_common.py::load_config` walked from the target worktree up to the filesystem root looking for `.supertool.json`, with no ownership/permission check and no stop at the nearest `.git` ancestor -- the exact class of bug #695 closed for `_supertool._load_config` and #2365 closed for `presets/gitlab/_maintenance.py::load_config`, both of which had to re-implement the same two limits because a preset cannot import the core module. The section this file reads (`ops.worktree.setup`) drives real filesystem effects once found -- `os.symlink`, `shutil.copytree`/`copy2`, and appended lines to a worktree-private `core.excludesFile` -- so a `.supertool.json` sitting in an ancestor directory owned by another local account, or group/world-writable, or above the repository root, could silently supply the `link`/`copy`/`exclude` lists that drive them. `load_config` now stops at the nearest `.git` ancestor and skips a candidate that fails `_config_trust_violation` (POSIX-only; trusted unconditionally on Windows, root treated as trusted) exactly like an absent one -- not routed through `ConfigResult.error` -- so the walk can still find a further, trusted config higher up rather than refusing outright in a case the core loader would have resolved.
