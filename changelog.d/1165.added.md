- **Preset ops gain a `@file`/`@-` payload route, via a reserved `args` list field, so a colon-bearing argument the colon CLI cannot express has an escape** ([#1165](https://github.com/Digital-Process-Tools/claude-supertool/issues/1165)). Core ops have had `@payload` since #625 (`grep:@-`, `edit:@FILE`), but a preset op (`gh-job`, `gl-job`, every entry under `.supertool.json`'s `"ops"`) took `{args}` only, substituted from parts the colon tokenizer had already split on `:` — the one character with no other escape (everything else an argument might contain, `$;&` backtick `*` spaces/quotes/backslashes, already survives `shlex.quote`). `gh-job:ID:grep:PATTERN` rejoins everything after the mode (#1145) and covers the ordinary case, but a pattern that must genuinely *end* in `:`, or one whose intended reading disagrees with the rejoin, had no explicit form to fall back to. Every preset op with no already-registered `:::` named-field route now accepts `op:@file` / `op:@-` with `{args = [...]}` — each element becomes one positional argument, sent verbatim: no colon split, no rejoin heuristic, nothing re-tokenized. Generic rather than per-op (an author cannot forget to opt in, the same reasoning behind #625's own registry), additive (the colon CLI and its rejoin heuristic are entirely unchanged — `args` is only reached from an explicit `op:@...` call), and reuses `_resolve_custom_op`'s existing `{args}` substitution, which already `shlex.quote`s every entry, so the route needed no quoting logic of its own. `docs/input-forms.md#file-for-preset-ops--the-args-escape-hatch` has the full writeup.
