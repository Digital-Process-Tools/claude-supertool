- **`_configured` no longer reads a `plugin:`-qualified server's own harness blind spot as a clean "not configured"** ([#2361](https://github.com/Digital-Process-Tools/claude-supertool/issues/2361)). On Claude Code 2.1.261, `claude mcp list`/`get` stopped reporting a plugin-provided MCP server at all -- a reporter measured a `plugin:supertool:claude-channel` consumer that was demonstrably loaded and holding its socket (`lsof`/`ps` on the pid), while `claude mcp get -- plugin:supertool:claude-channel` exited 1 with the same `No MCP server named ...` text a genuinely absent server produces. `_configured` read that as its strongest answer, `False`, which is exactly the finding [#2182](https://github.com/Digital-Process-Tools/claude-supertool/issues/2182) built both of `subscription()`'s collision gates on: "`claude mcp get` is the authority on whether the harness loaded a server not on disk." That premise does not hold for this population on this harness version. A `plugin:`-qualified name that comes back "not found" now yields the admission, `None`, instead of `False` -- neither gate treats `None` as "no collision" (both already guard `is not False` / `is None`, #2182's own tests pin it), so a lookup this file cannot settle no longer silently opens a gate [#2133](https://github.com/Digital-Process-Tools/claude-supertool/issues/2133) was filed about.

  Scoped narrowly on purpose: `.mcp.json` declaring the standing `claude-channel` consumer was tried as a second signal for the *bare*-named standing-server lookup and rejected -- #2182's own regression test (`test_watch_channel_census_2182.py`) shows that declaration is present in every install regardless of whether the harness ever loaded it, so it corroborates nothing and would have reopened exactly the false-positive collision #2182 fixed. No general replacement signal is known for a bare (non-`plugin:`-qualified) name whose harness lookup goes unreported; that gap is unresolved and left open rather than guessed at.
