- **The cwd-exclusion chokepoint #2579/#2581 added for `validators/`/`formatters/` left the same gate-then-bare-spawn shape open in the core and in `presets/`** ([#2596](https://github.com/Digital-Process-Tools/claude-supertool/issues/2596)). `_supertool.py`'s post-edit lint gated `php` and `xmllint` with raw `shutil.which()` and spawned the bare literal name, not the resolved path; `presets/git/_git_common.py` and its independent copy `presets/git/conflicts.py` did the same for `glab`/`gh`; `presets/_git_run.py` and `presets/git/worktrees.py` resolved `lsof` through raw `shutil.which()` before spawning it; `presets/watch/transport.py` did the same for `osascript` (gate discarded, bare literal spawned) and `ps` (both the scan invocation and its bare-`ps` control probe). On Windows, `CreateProcess` searches the current directory ahead of `PATH` for a bare executable name, so a repository shipping `gh.exe`/`glab.exe`/`php.exe`/`lsof.exe`/`ps.exe`/`osascript.exe` at its own root would have that file resolved and executed in place of the real tool at those specific sites, with a maintainer's forge token sitting in the environment. Neither the core nor `presets/` can import `validators/common/spawnable.py` (a preset runs with `presets/` on `sys.path`, not the repo root; the core has the same documented boundary), so the fix follows this repo's own duplicate-and-pin convention already used for `_LINE_BREAK_RE`/`RESOLVE_ERROR_PREFIX`: a third stated copy of `which_excluding_cwd()`, one in the new `presets/_spawnable.py` (shared by all five preset call sites) and one in `_supertool.py` itself, each pinned equal to the producer by `tests/test_bare_spawn_cwd_gate_2596.py`, which also registers all six call sites so a future bare `shutil.which()` reintroduced for any of the eight tool names goes red rather than unnoticed.
