- **#1417's refusal stated a cause that is false when the caller typed `.`** ([#1417](https://github.com/Digital-Process-Tools/claude-supertool/issues/1417)). `_parse_grep_args` produces `path == "."` from an empty PATH slot *and* from a literal one, and the refusal explained itself with "an empty slot defaults to it" in both — untrue for the second caller, in the one place they go to find out what they typed wrong. It now names the slot and both readings of it. The parser is deliberately not widened to carry the origin: its 6-tuple is unpacked at eleven sites, and the two inputs earn the same refusal for the same reason. `.supertool.json` and `docs/operations/search.md` carried the same half-claim and now say the same thing.
- **A `read` window said which lines came back, never which grammar it took, and the hint that would have caught the commonest mistake was gated behind one that was silent** ([#1417](https://github.com/Digital-Process-Tools/claude-supertool/issues/1417), folding in #1414 and #1138). `read:PATH:A:B` and `read:PATH:A-B` are one character apart and return different windows; the window line described both in OFFSET/LIMIT terms, so a range call was reported in the vocabulary of the form it did not use. It now names `(OFFSET:LIMIT form)` or `(START-END form)`. The skip-count correction fired only when `LIMIT <= OFFSET`, deferring the rest to the misread-range note, which is itself gated on overshoot-or-`LIMIT < 2*OFFSET` — so `read:PATH:1:40` on a long file tripped neither and got nothing. It now fires on every non-zero OFFSET and names the window that came back — clamped end included, so a call cut short by EOF or the byte cap is not handed a range it never returned. The second range, the one a caller reading `:A:B` as `START:END` was after, is withheld wherever the misread-range note already proposes one, because the two derive different answers from the same numbers. The parse is deliberately unchanged: measured over 5,598 real `read:PATH:N:M` calls, the two parses #1138 proposed would refuse or silently re-aim 5,549 and 3,208 of them.
- **A nested `batch` accepted any single field name and refused the result in the wrong grammar** ([#1417](https://github.com/Digital-Process-Tools/claude-supertool/issues/1417), folding in #1407). A sub-op with no declared field order places a lone key as an unnamed positional, so `{"op": "batch", "file": "inner.toml"}` ran as `batch:inner.toml` and came back with "batch requires an @file argument, e.g. `batch:@ops.json`" — a command-line example for a caller writing TOML, naming no field. `batch` now declares its one field, so a wrong key is refused by name against `accepted: path`, and the missing-`@` refusal states both spellings including `path = "@ops.toml"`.
- **The editor was told to highlight a `read` window one line above the one that came back, and the range form got no highlight at all** ([#1417](https://github.com/Digital-Process-Tools/claude-supertool/issues/1417), found reviewing the above). `_read_target_read` returned `OFFSET .. OFFSET+LIMIT-1` for `read:PATH:OFFSET:LIMIT` — OFFSET read as a start line, the same mistake the disclosure fix is about, in the code that decides where the cursor lands. `docs/notifiers.md` documented the off-by-one faithfully, so the doc and the code agreed with each other and neither agreed with the op. `read:PATH:START-END` fell through to no range, so the form the docs tell callers to prefer was the one that never highlighted anything, and `read:PATH:10:0` computed an END before its START and handed `10 .. 9` to an editor.
