- **`test_two_racing_calls_do_not_overlap` no longer infers "did two callers' `fn` windows overlap" by comparing `time.monotonic()` readings taken on different threads** ([#2398](https://github.com/Digital-Process-Tools/claude-supertool/issues/2398)). It failed once on `windows-latest, py3.11`, printing two byte-identical windows for two distinct 0.1s-sleep calls -- a shape neither a genuine overlap nor a working clock can produce, and consistent instead with Windows' monotonic clock's documented history of skew across CPU cores under virtualization, which a cross-thread clock comparison has no way to detect or correct for. Code review of `_go_warmup_lock.serialize_once`'s `os.open(..., O_CREAT | O_EXCL | O_WRONLY)` mutual exclusion, and hundreds of local stress runs (down to a real measured 0.24ms gap between serialized calls) using an independent, clock-free ground truth (a lock-guarded active-call counter) turned up no case where the lock actually let two callers run `fn` concurrently -- the lock's own serialization guarantee holds. The test now uses that same clock-free counter as its assertion instead of comparing timestamps, which answers the actual question ("was more than one caller inside `fn` at once") directly rather than inferring it from a clock two different threads may not agree on. Confirmed the new assertion still catches a real race: deliberately dropping `O_EXCL` from the lock's `os.open` call made it fail reliably (`max concurrently active: 3`), and 30/30 repeats of the restored test passed clean.
