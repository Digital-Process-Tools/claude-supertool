- **Taught eslint's npx-absence guard npm 10.9.4's current refusal spelling, and moved the marker into a shared module** ([#1948](https://github.com/Digital-Process-Tools/claude-supertool/issues/1948)). `validators/eslint/eslint.py` already routes an eslint that is absent, on a machine with `npx` but no global install, to the `skipped` third state rather than a loud `adapter` fault — but `_NPX_ABSENT` only matched npm 8-10's `could not determine executable to run` and npm 11's `unknown command: "eslint"`. npm 10.9.4 instead refuses before ever resolving a command at all — `npm error npx canceled due to missing packages and no YES option: [...]` — reproduced directly against a real `npx --no-install eslint` on this machine, exit 1, empty stdout, matching neither marker, so the reader was told eslint *failed* on a machine where it was simply never installed. The new marker matches only the stable prefix, `npx canceled due to missing packages`, deliberately not the trailing package-list-and-YES-option clause npm has already been observed to phrase two different ways for the identical refusal — any other npx failure stays a loud fault. The three spellings now live in `validators/common/npx_absent.py`, shared with stylelint (see #1949) rather than duplicated a second time.
