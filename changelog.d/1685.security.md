- **A `paste` over a `0600` file wrote its bytes to a world-readable backup** ([#1685](https://github.com/Digital-Process-Tools/claude-supertool/issues/1685)). The snapshot #1650 shipped one release earlier was written with a bare `open(dest, "wb")`, so the copy landed at `0666 & ~umask` — `0644` on a stock box — whatever the source's mode was. A `paste` over a `0600` `.env`, `id_rsa`, `.netrc` or `.pypirc` therefore left the credentials group- and world-readable under `~/.cache/supertool/paste-backup/` for the whole seven-day retention window, unredacted and unmentioned. Reproduced end to end: `0o600` on the source, `0o644` on the copy, the `glpat-` token in it verbatim. The copy now inherits the source's own mode, and a mode that cannot be read falls back to `0600` rather than to the umask default — never wider than whatever the source turns out to have been.

  **Not fixed by refusing to snapshot a mode-restricted file.** That would close the disclosure by deleting the data-loss net #1650 exists to be, which is choosing a different failure rather than removing one. The snapshot is also still unredacted, deliberately: a redacted backup is not a backup. What has to hold instead is that reading the copy is never easier than reading the original.

  **The receipt now says which mode it used**, on the line that already names the copy: `previous contents kept at PATH (mode 0600, the file's own)`. #1275 shipped `_created_mode_note` in the same release precisely because a widening nobody is told about is the defect being removed, and it went on the **create** path while the path carrying the **displaced** bytes said nothing. The mode is read back off disk rather than quoted from the request, because the umask subtracts from what `os.open` is given; nothing is printed on Windows, where `st_mode` reads back `0o666` whatever was asked for.

  **A `paste-backup` that is a symlink is declined rather than followed.** `mkdir(exist_ok=True)` succeeds on a symlink pointing at a directory and the write went wherever it pointed, so one symlink planted under a shared cache root redirected every later snapshot — the `time_ns()` leaf is unpredictable, the directory is a fixed name. It is now refused out loud as a `no backup of the previous contents — WHY`, and the copy is opened with `O_EXCL | O_NOFOLLOW` so an existing or symlinked leaf is never written through either.

  **What this does not touch, and a reader should not assume it did:** `_cache_root()` still reads `XDG_CACHE_HOME` with no shape check, so an environment read chooses where full file contents land, and a symlink at `~/.cache/supertool` itself is the same class one level up. That is the store's location rather than this writer's mode, it changes where five other cache kinds live, and it is left to its own diff.
