- **`hashnode_comment`, `hashnode_reply` and `hashnode_publish` now route their body-file argument through `_publish_safety.safe_resolve_body_path`, the same allowlist `bluesky_publish`, `devto_comment` and `devto_publish` already enforce -- a breaking narrowing of all three documented syntaxes** ([#2082](https://github.com/Digital-Process-Tools/claude-supertool/issues/2082)). Both the bare-path and `file://` arms of `presets/hashnode/{comment,reply,publish}.py` read straight off disk with no allowlist check, unlike their bluesky and devto twins, which [#2077](https://github.com/Digital-Process-Tools/claude-supertool/issues/2077) named as the containment gap left open when [#2039](https://github.com/Digital-Process-Tools/claude-supertool/issues/2039) fixed `slack_publish`. The three hashnode files existed before `_publish_safety.py` was written (#149, closing PR #159) and were simply never wired in -- that PR's own description names the three files it touched (`bluesky/publish.py`, `devto/comment.py`, `devto/publish.py`) and the hashnode analogs are absent from that list despite already existing at the time, with no comment anywhere recording a deliberate exclusion. No route was found by which untrusted text reaches these TEXT arguments -- `presets/watch/sources/` names no hashnode source -- so the argument is maintainer-typed, same as bluesky and devto's already-guarded siblings; this closes the shape gap #2077 identified rather than a demonstrated exposure.

Extend via `SUPERTOOL_PUBLISH_BODY_ALLOWLIST` or `"publish_body_allowlist"` in `.supertool.json`, same knobs the other three presets already use.
