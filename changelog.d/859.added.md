- **radar can watch a GitHub PR board** ([#859](https://github.com/Digital-Process-Tools/claude-supertool/issues/859)). `presets/watch/tiers/` held exactly one tier and it spoke GitLab, so the board this repository is actually merged from was the one population radar could not see. Register `gh-prs` like any other tier:

  ```json
  { "ops": { "radar": { "radar_tiers": { "gh-prs": {} } } } }
  ```

  One `gh pr list` call builds the board — GitHub returns the check rollup and the review decision on the list response, so there is no per-PR enrichment wave — and the rows are `gh-prs` rows, so the board, the op and `gl-mrs` cannot drift apart.

  **The repository's default branch is a board member.** A green PR is a statement about its merge base, and nothing watches `master` after a squash lands; the row composes `gh-branch`'s own four states (`GREEN` / `NOT GREEN` / `NO RUN` / `UNKNOWN`) rather than a second, weaker verdict. `default_branch` names the ref, `""` switches the member off, and absent resolves the repo's own.

  **It is a parallel tier rather than `gl-mrs` generalised**, because three of the four things that tier does do not transfer: there is no `github-pr-feed` source, so new PRs are found on the next radar tick and the footer says `discovery: radar ticks only`; drift has no analogue, since a PR's identity under a re-push is its head SHA and not a pipeline id; and watch state is keyed by PR number with no repository. What does transfer is the snapshot, which moved to `presets/watch/tiers/_snapshot.py` and is now read by both tiers — keeping a previous board keyed by the population it describes is not a GitLab argument, and a second copy of it is how a fixed defect comes back.

  **The one-filter invariant gains a clause on GitHub.** Board and watcher fleet still come from one resolved filter, and that filter must describe one repository: under a repo target a live poller for `#12` cannot be told apart from `#12` of the clone it was started in ([#673](https://github.com/Digital-Process-Tools/claude-supertool/issues/673)), so coverage renders as `watch coverage UNKNOWN` and nothing is healed. Zero watched would be a number a reader acts on, and healing on it would be an action taken on a misidentification.

  **Every route by which the board could narrow itself says so.** A filter token the tier cannot honour is refused before any call, because `gh pr list` silently ignores an unrecognised key and would otherwise return the whole unfiltered board reading as "everything matched". An auth failure or rate limit raises, exits non-zero and snapshots nothing. A filter that matched nothing is reported with its scope rather than as "no open PRs". A PR with an empty check rollup is counted `unchecked`, never green. And a PR the board calls green — the only claim that can be wrong in the expensive direction — is reconciled against the legs its runs declare through `gh-pr`'s own machinery ([#724](https://github.com/Digital-Process-Tools/claude-supertool/issues/724), [#804](https://github.com/Digital-Process-Tools/claude-supertool/issues/804), [#837](https://github.com/Digital-Process-Tools/claude-supertool/issues/837)), consumed and never re-implemented; a shortfall marks the row `[legs UNVERIFIED]` and counts as unchecked. The tier prints no leg count of its own.

- **`radar:--state` looks at the tiers without spawning anything** ([#859](https://github.com/Digital-Process-Tools/claude-supertool/issues/859)). `radar` heals, and healing forks pollers, so inspecting this subsystem used to cost the same as acting on it — and the result was hours of not inspecting it. The read-only view reports which module each registered name resolved to, the options it accepted, the ones it did not recognise, and, for a tier exposing the new optional `radar_state(options)` hook, its resolved scope, its snapshot file and its live pollers. Both shipped tiers implement it; everything comes from files already on disk and no API is called.

  It is an argument rather than its own op deliberately: `ops.radar.radar_tiers` merges into the op it is keyed by, so a second op name would need a second copy of the tier list — and a read-only view describing a different tier set from the one radar runs is precisely the defect it exists to remove. A tier with no `radar_state()` says so, rather than rendering as an empty block that reads as healthy.

- **`gh-prs` now fetches `headRefOid`** ([#859](https://github.com/Digital-Process-Tools/claude-supertool/issues/859)). Not rendered; it is what the radar tier keys its delta on. A push that lands a new head commit re-runs everything, and without the SHA a `failed → failed` transition across two different commits reads as "no change" — a missed event on a board a maintainer merges from. One extra field on a response already being fetched.
