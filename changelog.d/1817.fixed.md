- **The release gate now names every workflow a release can never be gated by** ([#1817](https://github.com/Digital-Process-Tools/claude-supertool/issues/1817)). `gh-branch` already disclosed which declared workflows produced no run on a commit, but that disclosure sat on a different op, read by a human deciding whether to tag -- nothing in `presets/github/_release_gate.py` (what `gh-prs:merged-since=TAG` calls to build the release gate's own report) said that `slow tests` (`schedule`/`workflow_dispatch`-only, #891) structurally never runs on a release candidate's own commit, so a `slow`-marked regression anywhere in the delta was unmeasured with nothing saying so. `not_gated_by_push_workflows` answers this locally, off the `.github/workflows/*.yml` trigger declarations on disk rather than a per-commit API query, reusing `_declared_workflows.parse_triggers`/`.is_push_triggered` so a fix to the trigger grammar reaches both disclosures together; a workflow whose `on:` block cannot be parsed is left out rather than claimed as provably excluded, the same "I could not tell" versus "this cannot happen" distinction `_declared_workflows` already draws. The report distinguishes the two workflows this decision actually found: `changelog` is `pull_request`-only and already checked every PR in the delta before it merged, so it is unrepeated at the tag rather than unchecked; `slow tests` is genuinely unmeasured at release time and is caught, if at all, by its own schedule rather than by this gate. The unmeasured premise the issue flagged -- whether any `slow`-marked test would actually catch something the per-push matrix misses -- was not taken; this ships the cheaper, honest "report" option the issue named rather than building dispatch-and-wait machinery on that premise.
