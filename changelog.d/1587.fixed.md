- **A file `[tool.ruff] exclude` covers was reported `ok`, count 0, by a run in which ruff never opened it** ([#1587](https://github.com/Digital-Process-Tools/claude-supertool/issues/1587)). The adapter passes `--force-exclude`, which applies the project's `exclude` patterns to the single explicit path it names. A match makes ruff exit 0 with an empty JSON array — byte for byte a clean file — so the receipt carried a verdict nothing had earned. Inert on this repo, which sets no `exclude`; live for anyone who does.

  **The zero-finding arm now asks a second question.** `ruff check --no-cache --force-exclude --show-files <file>` resolves the same configuration and prints the paths that survive exclusion; an empty list means the file was never opened, and the result is `skipped` naming the exclusion instead of `ok`. It runs only where the answer is ambiguous — a run that reported findings has demonstrably read the file — and costs one extra spawn, ~50ms measured against ruff 0.16.1 on macOS and not measured on Windows, where process creation is dearer. It shares the lint's own 30s budget rather than carrying a tighter one, so a loaded machine cannot decline a file the lint itself had time to read. A probe that cannot answer returns `skipped` too, because a zero it could not attribute is not a pass, and the reason names no single config key — the flag enforces `exclude`, `extend-exclude` and ruff's built-in defaults at once, and `--show-files` reports the outcome rather than the cause.

  **The decision behind that shape: an `exclude` entry governs the file you just edited, so the honest answer is a decline rather than a lint.** The other coherent repair was dropping the flag, which is what the [#1481](https://github.com/Digital-Process-Tools/claude-supertool/issues/1481) release gate does — correctly, because its question is whether anything unlinted reached the tree and its file list is built by hand from a diff. A post-edit validator asks a different question, and `eslint` had already answered it the same way one adapter over: a file matching an ignore pattern is `skipped`, not `ok`. Two adapters in one directory answering it two ways is worse than either answer alone.

  Asking ruff rather than reading `pyproject.toml` is deliberate — exclusion resolution walks up for `pyproject.toml`/`ruff.toml`, honours `extend-exclude`, and carries a default list (`.venv`, `build`, `node_modules`, …) a hand-written check would drift from on every release. `respect-gitignore` is not part of it: measured on 0.16.1, a gitignored path handed over explicitly is still linted.
