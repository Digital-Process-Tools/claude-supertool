- **`st_hint`'s wrapper probe now answers something on Windows, instead of a check that could never say no there** ([#1919](https://github.com/Digital-Process-Tools/claude-supertool/issues/1919)). `os.access(wrapper, os.X_OK)` answers true for any existing file on Windows -- there is no execute bit for it to read -- so the probe degraded to "does a file named `supertool` exist", and the helper's third state ("no runnable supertool found") became unreachable on that platform: a stray, unrelated file wearing the name got printed as the runnable wrapper.

  **Both duplicated implementations, not one** -- `presets/git/_git_common.py::st_hint` (since #1061) and `presets/_st_hint.py::st_hint` (added by #1917 that same day) each grow a `_wrapper_is_runnable` helper carrying the identical check, kept as two functions rather than one shared one for the reason #905's own fragment already gives: `test_printed_invocation_worktree_1012.py` pins `conflicts.st_hint.__globals__ is vars(git_common)`, which a re-export from a different module breaks.

  **The replacement reads the first two bytes rather than trusting existence.** On `os.name == "nt"` the probe now asks whether the file opens with a shebang (`#!`), matching what this project's own install instructions (`README.md`) always produce -- a symlink to `supertool.py`, itself `#!/usr/bin/env python3`. Weighed against the other two options the issue named: a `PATHEXT`-suffix check answers nothing for this wrapper's literal, extension-less name, and a spawn attempt is the most truthful of the three but also the most expensive, on a refusal path where the caller is already stuck waiting for the remedy. What the shebang read cannot establish: that the named interpreter exists or is on `PATH`, that a POSIX-aware shell is what receives `./supertool` on the machine at all (native `cmd.exe` and PowerShell ignore shebangs entirely), or that the file is not truncated past those two bytes.

  **Grade: reasoned, not observed** -- there is no Windows host in this project. `tests/test_windows_wrapper_probe_1919.py` reproduces the actual defect on any host by faking `os.access` to the real Windows behaviour (true for any existing file, mode ignored) rather than merely setting `os.name`, since the pre-fix code never branched on `os.name` at all and a POSIX host's real permission bits would otherwise mask the bug. The control pair sits in one fixture: a stray non-executable file must report the third state, and a shebang-carrying file must still print `./supertool` -- both against an explicit `tmp_path` install root, never this checkout's own `./supertool` symlink.
