- **The exit code was decided by re-reading text formatted for a human, and it was wrong in both directions** ([#1291](https://github.com/Digital-Process-Tools/claude-supertool/issues/1291), [#1279](https://github.com/Digital-Process-Tools/claude-supertool/issues/1279)). A dispatch receipt is `--- {arg} ---` followed by the op's answer, and `{arg}` is whatever the caller typed — so locating the boundary in the rendered string made the verdict a function of the argument.

  A **successful** op could exit `1`: the failure scan searched the whole body for a `---` line followed by an error-shaped one, and an argument spanning lines supplied both. `supertool 'grep:zzz ---<newline>ERROR: nope:README.md'` found nothing, said so, and exited `1` — after which the batch tally added in v0.33.0 printed `1 refused` in words, an explicit false sentence built on a false bit.

  A **failing** op could exit `0`: the header's close was taken to be the first ` ---` in the body, which an argument can contain. A `git-commit` refusal whose message quotes an op receipt — the shape this repo's own commit convention asks for — exited `0`, which is the defect fixed in v0.33.0 returning on a different input.

  The verdict is now taken where the receipt is assembled, from the string the op returned, before a header is prepended to it. Preset ops are not a second population: their exit status is already recorded at the subprocess and the `FAIL` line is rendered from it. Twenty-one early-return gates inside dispatch now go through one assembly point rather than each building a string for something else to parse back.

  It is also no longer a function of receipt size. Measured on a diff-shaped body of 3000 `--- a/path` hunk headers: **0.15 microseconds against 0.85 milliseconds**, and unchanged at 6000 hunks where the scan doubles to 1.68 ms.
