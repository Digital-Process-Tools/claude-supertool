- **A watch poller whose `poll()` keeps raising now gives up instead of retrying until the machine reboots** ([#1852](https://github.com/Digital-Process-Tools/claude-supertool/issues/1852)). `_run_poll_loop` broke out on `is_terminal`, but the error branch could not consult it — a failed poll produces no new state — so it wrote `last_error`, slept and `continue`d, forever. An expired token, a deleted MR, a renamed project or a source module that no longer imports polled indefinitely while holding its slot. Measured on one machine: 22 live pollers, the oldest eight days into watching an MR that had stopped being interesting on day one.

  After 120 consecutive failed polls (`MAX_CONSECUTIVE_POLL_FAILURES`, overridable per source with `MAX_CONSECUTIVE_FAILURES`) the poller emits `watcher_gave_up` and leaves through the same `finally` a terminal exit takes, so the pidfile is released and `radar` can re-arm the slot. One successful poll starts the count again, so a forge that answers one poll in ten keeps its watcher. Unlike a terminal exit the state file is **kept**, carrying a new `gave_up` record beside `last_error`: a merged MR has nothing left to explain, but a give-up's reason is the only thing that turns a stopped row on the board into a re-armable one.

  `watcher_gave_up` is the dispatcher's event rather than a source's, so it is in no `events.json` and `only=` does not filter it — a watcher that filtered away its own obituary would stop, release its slot and tell nobody. Nothing here reaps a poller because nothing is bound to the socket, which #511 records as having cost two live watchers, and there is deliberately no absolute lifetime ceiling: ending a poller that is succeeding, on a timer, is the same shape as reaping on `NO LISTENER`.

  The error backoff also became interruptible. It was one `time.sleep(interval)`, and PEP 475 resumes an interrupted sleep for its remaining time, so `unwatch` was honoured within a second by a working poller and ignored for up to a full interval by a failing one.
