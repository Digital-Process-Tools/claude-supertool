- **`gh-pr:N:status` and `gl-mr:N:status` are pinned to the same fact set, and two divergences the pin caught are fixed** ([#628](https://github.com/Digital-Process-Tools/claude-supertool/issues/628)). The two ops are visibly forked from a common ancestor with nothing holding them together, so improving one side reached the other only if somebody remembered. [#620](https://github.com/Digital-Process-Tools/claude-supertool/issues/620) is what that costs: an identical `_load_payload` defect in both `issue_create.py` files, fixed on one side by hand. `tests/test_gh_gl_status_parity_628.py` renders both ops against merged and open fixtures and refuses any fact one side carries and the other does not.

  The bar is `docs/validators.md`'s three-state contract applied to output shape rather than to checks: **every fact one side reports, the other reports or explicitly declines.** "Not applicable on this platform" is an answer; silence is not. So the code stays forked — sharing a renderer fights real API differences — and the *test* is the thing that fails the day one side improves alone. Divergences are legal only with an entry carrying a reason: `mergeable:`/`merge_status:` and `checks:`/`pipeline:` are recorded as one fact under each platform's own vocabulary (`MERGEABLE`/`CONFLICTING`/`UNKNOWN` and `can_be_merged`/`cannot_be_merged`/`unchecked` do not share a domain; a flat list of check runs and a pipeline whose jobs nest in stages do not share a shape), and `review:` is the single exemption, because GitHub's `reviewDecision` rides in a call already being made while GitLab approvals cost a separate request on the poll-loop render. Three further tests stop that list decaying into a record of every divergence nobody could be bothered to fix: a paired spelling that stops being emitted fails, an exemption for a fact the exempted side now reports fails, and an entry with no stated reason fails.

  **`gh-pr:N:status` now prints `merged_at:`.** `gh pr merge` can print nothing on success, so a merge has to be read back off the remote — and this op answered only half of that, which cost four hand-rolled `gh pr view --json state,mergedAt,mergeCommit` calls in a single evening while the GitLab twin handed all three over free. `mergedAt` rides in the dashboard fetch already being made, so the line costs no extra call, and it prints unconditionally with `-` for absent the way `gl-mr` does: a key that appears only on merged PRs cannot be grepped for on an open one.

  **`gl-mr:N:status`'s `merge_status:` reads the same field `:full` does.** `:full` has always been `merge_status or detailed_merge_status or "?"`; `:status` was `.get("merge_status", "?")` — same file, same payload, strictly less, on the render read most often. A key present and empty never reaches a `.get` default, so the line rendered **blank**, which reads as a rendering bug rather than as an unanswered question; and GitLab deprecated `merge_status` in favour of `detailed_merge_status`, so an instance that has stopped populating the old key got a literal `?` printed over a value already in the fetched payload. `?` still means unknown, and now only means unknown.

  **What was deliberately not changed:** `gl-issue`'s `Related MRs:` heading, against the wording drift reported on #628. It is not drift. `gh-issue` asks GraphQL `closedByPullRequestsReferences` — "will this close it", the distinction [#780](https://github.com/Digital-Process-Tools/claude-supertool/issues/780) exists to protect — while `gl-issue` asks `related_merge_requests`, which is the broader set including MRs that merely reference the issue. Renaming it to `Linked` would make the word claim a stronger fact GitLab was never asked for. The reason is now recorded next to both the endpoint and the heading, so the next reader does not re-derive it as a bug.
