- **One git invocation chokepoint, reachable from every preset** ([#2447](https://github.com/Digital-Process-Tools/claude-supertool/issues/2447)). `presets/dashboard/dashboard.py` and `presets/github/pr_merge.py` each carried a private `_git()` over a bare `subprocess` call, so neither had `_with_lock_retry` (#2034), the `_stop()` SIGTERM grace (#2033) or `SUPERTOOL_GIT_TIMEOUT` (#650), and #1945's `--no-optional-locks` had to be propagated to all three by hand. The invocation layer moved from `presets/git/_git_common.py` to `presets/_git_run.py`, where a file outside `presets/git/` can import it without reaching into another preset's directory; `_git_common` re-exports every name by identity, so the eight git presets are unchanged.

  `pr_merge._git` is the cleanup arm of every merge the maintainer loop performs: `branch -d` and `worktree remove` against a repository that may have several worktrees live, which is what `_with_lock_retry` was written for. It now retries a lock-contention failure within `LOCK_WAIT_DEFAULT` instead of failing on the first attempt. That is a timing change on a write path, not only a refactor.

  Both call sites keep their own budgets (15 for the board, 30 for the merge) and now read them through `git_timeout()`, so `SUPERTOOL_GIT_TIMEOUT` reaches a fourth and fifth site that #1886/#1903's join could not cover.

  `tests/test_git_invocation_chokepoint_2447.py` reds on a fourth private wrapper. One census guard had to be widened rather than lowered: `tests/test_forged_child_stream_line_1475.py` scanned three preset directories, stopped being able to see two relay sites that moved out of them, and reported 142 measured against 144 published -- telling the reader that sites were fixed when nothing had been.
