- **A symlink planted on a named watch channel's state directory was adopted, and every poller write landed in it ([#1518](https://github.com/Digital-Process-Tools/claude-supertool/issues/1518)).** `SUPERTOOL_WATCH_NAME=x` derives `/tmp/supertool-watch-x`, and `naming.ensure_state_dir` created it with `os.makedirs(..., mode=0o700, exist_ok=True)`. `exist_ok=True` accepts whatever already holds the name and reaches it through `os.path.isdir`, which follows symlinks, so a link planted at the leaf was taken over in silence; `mode=0o700` applies only to directories that call creates, so it was not a defence in the pre-taken case. `transport.claim_pidfile` calls this before its `O_CREAT|O_EXCL` pidfile open — which a *new* file inside the planter's directory satisfies perfectly — and `write_state` opens `<path>.tmp` by path, so pid files and state files both landed there. `/tmp` is world-writable and the name is public rather than per-uid: this repo commits `"watch_name": "oss-supertool"` to its own `.supertool.json`. The leaf is now established by `presets/_image_root.ensure`, the boundary written for `gl-issue`'s attachment root in this same release rather than a third hand-rolled one: created non-recursively, held open `O_RDONLY | O_DIRECTORY | O_NOFOLLOW`, `fchmod`ed and then asked about ownership and mode through that one descriptor. A symlink, a reparse point, a file, another uid's directory or a mode group or other can reach is a refusal naming which, and no slot is claimed there. **Not closed:** another local uid can squat the name ahead of you, and that channel then refuses rather than writing into their directory until it is removed — the same residual `docs/presets/gitlab.md` discloses for the attachment root. On Windows there is no `O_NOFOLLOW`, so the check is `os.lstat`, and the ownership and mode arms are skipped rather than faked because `st_uid` is a constant and the permission bits are synthesized there.
