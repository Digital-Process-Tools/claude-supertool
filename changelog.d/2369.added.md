- **`radar` gained a `gh-issue` tier — the GitHub half of `gl-issue` (#898), a board scoped to one GitHub issue, not a population** ([#2369](https://github.com/Digital-Process-Tools/claude-supertool/issues/2369)). `{"radar_tiers": {"gh-issue": {}}}` plus `radar:gh-issue:2369` reports the issue's state and labels, every one of its still-`OPEN` linked PRs with a `github-pr` watcher healed onto it (the entire event set `sources/github-pr/events.json` declares — checks, review verdicts, comments, merges, closes, conflicts, unreachable), and — from the second run on — a reopen, a label change, or a linked PR that arrived or departed, each counted against `healthy`. "Linked" is GitHub's own `closedByPullRequestsReferences` — the set of PRs whose body carries a working closing reference (`Closes #2369`), reusing `presets/github/issue.py`'s existing query and parsing (#780/#782) rather than a second copy or a looser `gh pr list --search` that would also match a PR that only mentions the issue. No feed poller: `github-issue-feed` is population-first by design with no per-id companion (#525), so a reopen/label change is detected the same way `gl-issue` detects one — diffing this run's live-fetched state against the previous run's snapshot. Same deliberate non-goals as `gl-issue`: no `RADAR_POLICY` markdown, no per-category history ledger, and the pre-existing `radar:gh-issue:N` / `gh-prs` filter-parser argument collision is inherited rather than fixed here.
