- **The `unwatch` and `watches` channel-token disclosures now flatten the token they print, closing a cursor-control injection through another process's argv** ([#1925](https://github.com/Digital-Process-Tools/claude-supertool/issues/1925)). Both surfaces read `channel` out of another process's argv via `transport._labelled` and printed it straight into an f-string. `_ps_rows` splits argv on whitespace, which blocks a newline, but a CSI sequence carries no whitespace and passed through intact — `ESC[1G` then `ESC[2K` rewrote the disclosure line from column 0, on the exact surface whose job is to tell an operator that a poller survived. Five sibling fields already routed through `_untrusted.flat()`; the channel token, which comes from a less trustworthy source than any of them, was the one that skipped it.

  `presets/watch/dispatcher.py:220` (`_foreign_slot_lines`, [#1893](https://github.com/Digital-Process-Tools/claude-supertool/issues/1893)) and `:477` (`_foreign_poller_lines`, [#1890](https://github.com/Digital-Process-Tools/claude-supertool/issues/1890)) now call `_untrusted.flat(channel)` at the point they render it. No chokepoint already prepares `channel` for either render — each function reads it straight out of `census["other"]`'s own keys inside its own loop — so this is two call sites, not one shared preparation point; flattening the *key* itself at `poller_census()` was ruled out because that same value is also used as a dict lookup against `channel_dirs()`, where equality with the real hash matters. An ordinary hex channel token renders unchanged.
