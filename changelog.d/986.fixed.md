- **`git-commit`'s `nothing staged` refusal pointed only at the route the caller had already rejected** ([#986](https://github.com/Digital-Process-Tools/claude-supertool/issues/986)). A caller on `git-commit:@-` is usually there *because* their message will not survive `:`-tokenization, and being answered with `git-commit:::MESSAGE:::PATHS` reads as "you used the wrong form" when the accurate statement is "here is how this form stages". The refusal now names both routes, and spells the payload one out with its `paths` key pre-filled from the list it just printed.

- **A pathspec that failed to add never said what the separator was** ([#986](https://github.com/Digital-Process-Tools/claude-supertool/issues/986)). `git add` answering `fatal: pathspec 'a.txt,b.txt' did not match any files` tells a caller who guessed `,` only that their guess was wrong. The failure now states `Paths are separated by ':::' — not by commas, not by spaces`, and where a comma-joined token is **not** something git already knows, offers the split form as a question (`A ',' above is not a separator here. Did you mean:`). A token git recognises is never taken apart, because `a,b.txt` is a legal filename and re-splitting it would trade a loud failure for a quiet wrong one.

  **The issue's headline claim — that `git-commit:@payload` has no way to stage — is false, and this is its third airing.** The `paths` key has worked since [#340](https://github.com/Digital-Process-Tools/claude-supertool/pull/340), the field registry is derived from the op's own `syntax` string, and `tests/test_git_commit_payload_route.py` has pinned the committed bytes since [#415](https://github.com/Digital-Process-Tools/claude-supertool/pull/415). [#400](https://github.com/Digital-Process-Tools/claude-supertool/issues/400) claimed it, [#1003](https://github.com/Digital-Process-Tools/claude-supertool/issues/1003) claimed it again, and both were already refuted in the tree when they were written. A further pin asserts the staged file list rather than only the message, so "it cannot stage" is now false against a test that reads on staging specifically. What made the claim keep coming back is the `nothing staged` remedy above: two agents reached the payload route, got an error naming the *other* route, and concluded the key did not exist.
