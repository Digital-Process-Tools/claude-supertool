- **A batch containing an unknown or flag-shaped op used to run every earlier member to completion before saying so, spending the largest available cost right before refusing it** ([#2122](https://github.com/Digital-Process-Tools/claude-supertool/issues/2122)). Every positional CLI argument is its own op, so `./supertool 'read:docs/compatibility.md' --offset 900 --limit 5` ran the unbounded `read:` first -- the entire file -- before four ERROR lines named `--offset`, `900`, `--limit` and `5` as unknown operations, inverting the tool's own thesis of collapsing round trips and holding output down. A new pre-validation pass (`_batch_prevalidation_refusal`) checks every member's op NAME against the registry -- builtins, dispatch-only ops, this config's custom ops and aliases, and every shipped preset op, whichever answers "yes, this name routes somewhere" -- before any member runs, and refuses the whole call if one does not, mirroring the raw-command guard's own rule that a refusal covers the whole call rather than the part that named it. Deliberately narrower than "will succeed": a shipped preset op this config does not enable, or a real op given a bad argument, is a RUNTIME failure and still runs in place exactly as before -- only a NAME that cannot route at all (a typo, a bare flag) is knowable ahead of time. A flag-shaped member (`--offset`) is now also named as one, with a pointer at the positional form of the nearest earlier member that actually routes -- not simply the one before it, which in this issue's own headline example was the unroutable `900` and would have suggested `900:PATH:...` one line under `unknown operation: 900`. The refusal keeps the help a single-op typo already got ([#614](https://github.com/Digital-Process-Tools/claude-supertool/issues/614)'s `Did you mean:` per member, and the valid-ops roster once rather than once per bad member), and sits *after* the loader's own stderr warnings rather than before them, so a `.supertool.json` that failed to parse -- which drops every custom op it declared -- still says so instead of answering `unknown operation: mycustomop` about an op the caller really did define.
  - Note: the payload field-name mismatch between an op's string form and its `@payload` form (`read:PATH:OFFSET:LIMIT` vs. `read:@payload` wanting `offset`/`limit`, not `start`/`end`), and the ambiguous positional reading between `read:PATH:A:B` and `between:PATH:START:END`, are the same issue's second and third observations and are not addressed here -- filed separately for follow-up.
