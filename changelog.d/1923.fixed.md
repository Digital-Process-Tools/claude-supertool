- **`git-worktrees`' activity probe read the reflog file's mtime, not its newest entry, so a bare `git fetch --prune` flipped every linked worktree to `occupied` for 15 minutes** ([#1923](https://github.com/Digital-Process-Tools/claude-supertool/issues/1923)). `git gc` / `git reflog expire` -- auto-triggered by `fetch --prune` -- rewrites `.git/worktrees/<name>/logs/HEAD` for every linked worktree without appending anything: the mtime moves, the content does not. `_newest_write` compared candidate files by `os.stat().st_mtime`, so the rewrite alone read as `reflog written 0s ago`; on the tick that found this, six merged, hours-quiet worktrees all flipped `occupied` seconds after the tick's own fetch, suppressing cleanup on evidence the tick itself manufactured.

  `_newest_write` now reads the reflog's own newest **entry** timestamp for this one candidate rather than the file's mtime, and the control pair is what the fix is graded against: a tree whose reflog was genuinely appended to inside the activity window still reads `occupied`; a tree whose reflog file was only rewritten does not. An entry that cannot be parsed (an empty file, a line in an unrecognised format) deliberately falls back to the file's own mtime rather than dropping the signal -- keeping that failure mode on the side already shown safe here (a spurious `occupied`, never a spurious `idle`, which is the verdict that authorises deleting a worktree). The sweep for the same class found no other stat-based evidence line with this failure mode: `_newest_write`'s tree walk and the lock-file probe both stat real file writes, which git does not rewrite without changing.
