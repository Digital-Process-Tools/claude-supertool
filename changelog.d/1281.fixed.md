- **`gh-pr-merge`'s `cleanup` deleted the base repository's ref named after the PR head, so a fork branch called `master` deleted ours** ([#1281](https://github.com/Digital-Process-Tools/claude-supertool/issues/1281)). `headRefName` is chosen by whoever opened the PR and opening one from a fork needs no permission on the target repo, but the `DELETE` landed on `repos/{owner}/{repo}/git/refs/heads/<headRefName>` — this repository. Every existing gate passed on `master`, `main`, `develop` and `release/1.0`.
- The receipt made it worse rather than merely missing it: it read `deleted X on the remote via the API (recoverable: GitHub keeps refs/pull/N/head)`, which is false in precisely this case, because the ref deleted is not that PR's head.
- Three things are now established before anything is deleted, and none of them was. `isCrossRepository` is fetched and a head that is not in this repository — **or a field that did not come back** — refuses all three items, local ones included: the local branch delete and the worktree removal ran on the same unchecked name. The default branch is never a cleanup target whoever opened the PR. And the remote ref is read back and compared to `headRefOid` before the delete names it.
- The read-back subsumes the name-shaped version of the question. `develop`, `release/1.0` and every other ref of ours fails it because they do not point at this PR's head, so no list of protected names has to be kept anywhere. It also declines a branch somebody pushed to after the merge — the same defect one commit smaller.
- **The same guard reaches the commands the op *prints*, which are the default path.** Without `|cleanup` it hands back `gh api -X DELETE .../refs/heads/<head>` and `git branch -d <head>` to be pasted — both aimed at this repository, both naming a head the contributor chose. Refname quoting was the only thing in front of them, and quoting makes a wrong command safe to paste rather than making it right. A head that is cross-repository, unestablished, or the default branch now gets no command at all, and a line saying which of the three it was. Found by the review pass, not by the audit.
- The success line now states what was verified rather than asserting a recoverability nobody had checked: `deleted X on the remote via the API — it was read back at 0123456, this PR's own head, so it is recoverable from refs/pull/N/head`.
