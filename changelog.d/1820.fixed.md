- **A `read` window that came back whole and one that was cut short rendered the same line** ([#1820](https://github.com/Digital-Process-Tools/claude-supertool/issues/1820)). `read:PATH:40-72` on a 1,974-line file printed `stopping at line 72: the limit was reached` — the sentence a *truncated* read prints too. The clause named which bound closed the window; nothing said whether that bound had cost anything, so telling a satisfied read from a truncated one meant reading again, wider, and comparing. That is one extra read of the reporter's file spent to learn the first had already answered, and it is this repo's own defect class pointed at the op's own message.

  **A window that ended at the bound the caller set now says so**: `— the window ends here because it was asked to, nothing was cut`. The clause is absent from the other three states and each absence is a fact rather than an oversight — EOF already settles it in its own words (`nothing follows line N`, [#1342](https://github.com/Digital-Process-Tools/claude-supertool/issues/1342)) and a second verdict beside it would be two speakers on one question; a genuine cap cut is the state this distinguishes *from*; and the `read.max_lines` default was never asked for, so nothing about it ends where it was asked to.

  **"Limit" was one word for two different bounds, and they want opposite responses.** `read:PATH:10:20` ends at a window the caller closed themselves and needs no action. `read:PATH:10` ends at `read.max_lines` — the op's own cap on output, standing in for a bound nobody named, and the one that hides the rest of the file. Both said `the limit was reached`. The second now names the setting and counts what is below it: `the read.max_lines default of 300 lines was reached — you named no LIMIT, so this bound is the op's and 690 lines of the file are below it`. `op_read` resolves that default before `render_file` is called, so the fact is recorded where the two are still distinguishable and passed rather than re-derived, the same shape as the `grep=` case one argument over ([#1052](https://github.com/Digital-Process-Tools/claude-supertool/issues/1052)).

  Found building this, not by the issue: the first cut fired the satisfied verdict on the defaulted case too, so the note read `you named no LIMIT, so this bound is the op's — the window ends here because it was asked to`. Nobody asked. It is pinned by its own test.

  **The window note is emitted only for a non-zero OFFSET, and a range starting at line 1 has an offset of zero** — so the whole fix above missed `read:PATH:1-50`, which is the shape the issue is most likely to be asked about. That call and a plain `read:PATH` cut short by `read.max_lines` both closed with a bare `... (150 more lines)`, byte for byte, one having delivered exactly what was asked and the other missing 150 lines to a bound the caller never set. The footer now carries the same two verdicts the note does. Found by the audit of this change's own first commit, which is why it is a second hunk; the tests that reach the note all use a non-zero offset, so nothing in the suite would have caught it.

  Under compact mode that footer drops the `nothing was cut` half: blanks and comments really were dropped, and unlike the window note the footer has no `held` clause beside it to say so. Trading a silent truncation for a confident false claim would have been the same defect facing the other way.

- **A whole-file `read` of a large file previewed its head and named no way to narrow** ([#1811](https://github.com/Digital-Process-Tools/claude-supertool/issues/1811)). The head is the region least likely to be why the file was read, so the preview is often paid for and answers nothing — and the stop was disclosed with no remedy attached. `... (N more lines)` named none at all, and the byte-cap footer named only `read:PATH:OFFSET:LIMIT`, the one spelling this repo has three issues of evidence that callers read as START:END ([#382](https://github.com/Digital-Process-Tools/claude-supertool/issues/382), [#1417](https://github.com/Digital-Process-Tools/claude-supertool/issues/1417), [#1489](https://github.com/Digital-Process-Tools/claude-supertool/issues/1489)).

  Both footers now close with the two forms that narrow — `read:PATH:START-END` for a region, `read:PATH:::grep=PATTERN` to find one — which is what `between:`'s refusal already does: suggest its own narrowing form at the moment it declines, rather than after the reader has paid.

  **The preview is kept**, against the two alternatives the issue offered. Dropping it for a structure block loses the thing that tells the caller what kind of file this is, which is the input to writing the narrowing call. Previewing an implied region loses because `read:PATH` implies none — that is the shape the issue is about, and guessing a caller's intent is what #382 and #1417 are the record of.

  **The `rtk`-delegated branch is covered too, and it is the one that fires by default where this was reported.** That path returned rtk's render unchanged, so a fix confined to supertool's own footers would not have reached the caller who filed it. rtk owns the preview and its own footer and knows nothing about supertool's call forms — the same argument the line-numbering disclosure on that branch is already there for. The gate is supertool's own caps rather than a parse of rtk's text, which under-fires where rtk compresses a file supertool would have returned intact; a hint printed on a complete read is advice nobody reads, so that is the safe direction.

  It fires only where it is actionable: not on a read that returned the file, not when the caller already typed a window, not under `:full`.
