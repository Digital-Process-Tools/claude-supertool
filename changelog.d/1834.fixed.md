- **`gh-pr-edit` said the new body linked no issue on the same receipt that named the issue it links** ([#1834](https://github.com/Digital-Process-Tools/claude-supertool/issues/1834), [#1788](https://github.com/Digital-Process-Tools/claude-supertool/issues/1788)). Adding a `Closes` line to a published body that had none printed, in one block:

  ```
  ## Closing references
    the published body linked no issue, and neither does this one
    Issue: #321
  ```

  The first line was false and the second right — GitHub binds the reference. `closing_ref_verdict` decided its message from `old_refs` alone, so once nothing had been *lost* it described the **pre-edit** body and `main` printed `linked_issue_line(new refs)` underneath it. Observed five times across `claude-oss` #268, #273, #277, #331 and #332, the last adding two references at once, so it was never specific to a single one.

  **The gate was never wrong and has not moved.** Nothing was lost, so `ok` and the write were correct, and both writes verified byte-identical on the server. What was wrong was the sentence about the write — this repo's own defect class one line over from where it usually lands.

  **Three gate states, four messages under `ok`**, because *nothing was lost* and *nothing is linked* are different facts: `carried through: #N`, `added: #N — the published body linked none, this one does`, `carried through: #N; added: #M` when it does both, and the original `linked no issue, and neither does this one` when there genuinely is none. The `carried`/`added` split rather than a five-row transition matrix: `some → none` is already the `DROPPED` arm, which refuses and is untouched, and `some → different` refuses on the same arm before any of this is reached — so the surviving branch has exactly two independent axes and composing them beats enumerating them.

  The third row was wrong too and nobody had filed it: a second `Closes` added to a body that already had one read `carried through: #N` and never named `#M`. Pinned by its own test.

- **`help:gh-pr-create` said a malformed `Closes` line was "caught at creation", and it is reported at creation** ([#1835](https://github.com/Digital-Process-Tools/claude-supertool/issues/1835)). The pull request is opened either way, exit 0. `caught` reads as *prevented*, and that reading is what makes the linked-issues block — the one place the problem is visible — look skippable. It propagated into a consuming repository's maintainer skill as "`gh-pr-create` **refuses** a body with no `Closes #N`", which is false, and four of seven agent-written payloads across two sessions had no working closing reference.

  `help:gh-pr-create` now says the line is **reported** at creation rather than discovered after the merge, and then says what that does not mean: reported, NOT refused — the pull request is opened either way and the exit code is 0, so that block *is* the check and the caller has to read it. `gh-pr-edit` is named as the repair, and as the op in the pair that does gate. `README.md` carried the same word (`gh-pr-create` **catches** a malformed `Closes` line at creation) and is corrected with it.

  **The reader was right in both directions and is untouched**, including refusing a keyword inside a code span, which is the case a substring grep passes.

  **Making `gh-pr-create` actually refuse, with an `unlink`-style escape, was considered and deliberately not built** — handed back for the maintainer to file, not filed here. It is the wider fix — the only one that reaches a hand-written body — but it is not the same shape as `gh-pr-edit`'s refusal. `gh-pr-edit` refuses a **regression**: something was bound, and this write would unbind it, so the escape token is a statement about a change of intent and is rare by construction. Refusing at creation would refuse an **absence**, which has no prior state to regress from and is legitimate on every `Part of #N` pull request. An escape token needed by a legitimate and recurring case is one that lands in the payload template, and a gate every template disables is a gate that no longer fires — the failure mode this issue is already the record of, one layer down.
