- **`cleanup`'s worktree removal destroyed ignored files, and its refusal text claimed the opposite** ([#1280](https://github.com/Digital-Process-Tools/claude-supertool/issues/1280)). `git worktree remove` without `--force` declines a tree holding modified or untracked files — that is the whole scope of the flag. An **ignored** file is deleted either way: a local env file, a virtualenv, a scratch database. Nothing recovers one, which is what ignoring it meant.
- The tree is now read with `git status --porcelain --ignored` before it is removed, and a tree holding anything git is not tracking is `refused` with the first five paths named. A `git status` that could not be run is also a refusal — a tree whose contents were never established is not a tree to delete.
- **The false safety claim is removed, because that was the aggravating half.** The old refusal read `(no --force is ever passed here)`, so a reader auditing the line was told the case was covered and stopped looking. A wrong safety claim is worse than no claim.
- The clean case now says what it checked instead of being exactly as quiet as the dangerous one: `removed <path> — git status --ignored found nothing untracked or ignored in it first`.
