- **A hand-rolled PATH-stripping env can no longer reach a Windows leg unnoticed** ([#1151](https://github.com/Digital-Process-Tools/claude-supertool/issues/1151)). On Windows `env={"PATH": ""}` is not "this environment with PATH replaced", it is "an environment holding only PATH": SYSTEMROOT and WINDIR go with it, the child interpreter cannot resolve its system DLLs, it writes nothing, and the adapter test dies in `json.loads("")` naming neither the tool nor the adapter. `tests/_winenv.py::empty_path_env()` exists for this and ten suites import it; three times a new one did not, and each was invisible until a CI log came back, because on POSIX none of the kept names exist and the two envs are byte-identical by construction. `tests/_pathenv_scan.py` is a static guard built to the specification the first, cut, scanner failed: scope-aware, so a name bound in a sibling function is never resolved as this one (the false positive that got that scanner cut); restricted to spawns of `sys.executable`, because a bash or git child does not need SYSTEMROOT and a security test's deliberately scrubbed environment is not this guard's business; and reporting `unresolved` as its own state rather than folding "I could not tell" into "clean". It follows an `env` parameter forwarded through a module's own spawn helpers to the call sites that actually decide it, which is where the regression was written. The two expressions it still cannot read are declared in the test with the hand verdict that cleared them, so the blind spot is a list somebody signed rather than a silence.
