- **Add a verdict cache for classify's model stage** ([#2054](https://github.com/Digital-Process-Tools/claude-supertool/issues/2054)): a repeated call for identical text no longer spawns `claude -p` a second time. `check.py` is a fresh subprocess per call, so nothing in-process could ever have cached across invocations -- `presets/classify/cache.py` is a small file-backed store instead, one JSON file per key under a per-uid leaf of the platform temp directory (reusing `presets/_image_root.py`'s symlink-safe directory establishment rather than a second copy of it). Keyed on the bare text plus a version derived from `model.AXES` and `model._SYSTEM_PROMPT` -- never on the fenced prompt, which draws a fresh per-process nonce and would never repeat -- so a change to either invalidates every cached entry without a hand-bumped counter. `safe` gets a 24h TTL; `suspect` never expires, on the argument that `safe` is the verdict a caller acts on permissively. `could-not-classify` is never written: the transient bucket must not calcify into a permanent verdict for that text. `model.classify()` and `check.run()` both default to `cache=None` -- unchanged behaviour for every existing caller -- and `check.py`'s own CLI entry point (`main()`) is the one place that opts in. `presets/_classify_render.py` (#2049), the caller most likely to repeat, is outside this issue's lane and does not yet pass a cache through; wiring it in is a one-line follow-up for whoever owns that file next.
