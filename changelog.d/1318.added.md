- **`ops:grep=PATTERN` — filter the op roster by name, syntax or description instead of piping it through `grep`** ([#1318](https://github.com/Digital-Process-Tools/claude-supertool/issues/1318)). `supertool 'ops'` prints every op's signature, and finding the one op that does X meant reading all of it or piping it through `grep` — the exact motion the shipped raw-command guard (`supertool-no-cut.md`) blocks, correctly, leaving a redirect-to-a-temp-file workaround as the only route left. Three independent agents hit it in one week. `ops:grep=PATTERN` matches op name, syntax and description — including a dispatchable op with no `.supertool.json` entry, so `ops:grep=introduction` finds it rather than reporting `0 of M` for an op that plainly exists — and prints only the matching rows, always stating `N of M ops matched` — `0 of M` included — so an empty result can never be misread as a short roster. Case-sensitive, like every other pattern slot in this file. A pattern containing `:` (the shape a search for `read:PATH`-style syntax naturally has) reaches the filter whole rather than being silently cut at the first colon by the CLI tokenizer; an empty config falls back to a bare name list rather than "0 of 0". Reuses `_pattern_gate`, the single chokepoint every other pattern-taking op goes through (#2574 did the same for `between`), with `check_saturation=False` since the count line already discloses when a pattern matches everything. Scoped to bare `ops`, the same way `ops:roster`/`ops:full`/`ops:session` are — `ops-compact:grep=X` still refuses, naming the new token.
