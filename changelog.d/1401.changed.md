- **Documented how Claude Code actually resolves the shipped hook commands, and pinned both as shell form** ([#1401](https://github.com/Digital-Process-Tools/claude-supertool/issues/1401)). The concern was that `bash "${CLAUDE_PLUGIN_ROOT}/hooks/..."` is resolved by `CreateProcess` searching `PATH`, which on Windows finds System32's `bash.exe` - the WSL launcher, which is not a shell, exits 1 and writes UTF-16 without ever opening the script. That is how this repository's own pytest reached the launcher; it is not how the harness runs a hook.

  A command hook with no `args` is **shell form**: the string is handed to a shell - `sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash is not installed. A hook **with** `args` is exec form, and that is where `command` is resolved on `PATH` and spawned directly - so adding `args` would introduce the defect rather than remove it. The remaining branch, a native Windows host with no Git for Windows, is also the host with no `Bash` tool at all, so a `PreToolUse` hook matched on `Bash` never fires there.

  No behaviour changed. `tests/test_hook_interpreter_windows_1401_1402.py` now refuses `args` on either shipped hook and refuses the two entries drifting apart, so the reasoning survives the next reader not having it.
