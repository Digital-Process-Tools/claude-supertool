- **`introduction` and `output-format` no longer print a permanent "No ... configured" non-answer in every unconfigured repo's session preamble** ([#2342](https://github.com/Digital-Process-Tools/claude-supertool/issues/2342)). Both ops were a bare `config.get(KEY, "")` with no fallback, and `hooks/session-start.sh` calls both on every session, so any repo that had not hand-written the two keys opened with two dead lines — the two smallest onboarding surfaces were also the only ones with no shipped default (`help:OP`/`ops` already fall back to the built-in op reference; `git-commit`'s coauthor trailer already falls back to `_DEFAULT_COAUTHOR`). Both ops now follow that same env-over-config-over-built-in convention: `SUPERTOOL_INTRODUCTION`/`SUPERTOOL_OUTPUT_FORMAT` wins over `.supertool.json`, which wins over a shipped default, and any layer set to `""`/`"none"`/`"off"`/`"false"`/`"no"`/`"0"` disables it and reaches the old "not configured" line — for a project that has deliberately kept its session preamble bare. `introduction`'s default states mechanical, install-wide facts only (path resolution, the `@-` payload route, TOML literal-vs-basic-string escaping) and deliberately carries no batching exhortation, on the evidence of a downstream A/B test (claude-oss `scripts/batch_hint.py`, #490) that found the same prose 6% *more* expensive in single-op rate when resent every turn. `output-format`'s default is measured against a real batched call rather than written from memory, and a test asserts its described shapes (header, meta line, truncation, per-op failure isolation, the batch-exit-code-vs-op-exit-code distinction, the `↳ to modify:` footer) against a live call. `init` — the op that bootstraps `.supertool.json` — keeps emitting neither key, pinned by a new test, so the fallback is not silently duplicated into generated config bytes. `docs/operations/meta.md` also wrongly stated `output-format` carries a `---` dispatch header while `introduction` does not; both are meta-ops with no header, corrected.
