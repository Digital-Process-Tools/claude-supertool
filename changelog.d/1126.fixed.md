- **A batched `read` paid a `git status` spawn per file, so the better an agent followed the batching advice the more it paid** ([#1126](https://github.com/Digital-Process-Tools/claude-supertool/issues/1126)). The ` m`/` ?`/` !` marker beside a rendered filename came from one `git status --porcelain --ignored=matching -- <path>` per path. A `read` of one file spent 48ms of its 165ms there; a single call rendering seven files spent 355ms of 504ms — 70%, growing linearly with exactly the batching this tool asks for everywhere.

  The filed shape was a memo keyed by path, and a memo cannot help here: seven files are seven different keys and every lookup misses. What repeats is the spawn, not the question. So the query is coalesced instead — the first path in a repo is asked about directly, as before, and the second escalates to one repo-wide status that answers it and every path after it. Measured before-and-after interleaved on one machine, nine runs each: a single call rendering seven files goes from 752ms to 365ms at the median (504ms to 257ms at the minimum), and a lone `read` is unchanged, because a single-op call never reaches the escalation.

  Three things drop the snapshot, and between them they are the answer to how long it may live: any write through `_atomic_write`, any op outside the read-only set finishing dispatch (which is what catches an index move from `git-commit`, invisible to file mtimes), and a file whose own mtime is at or after the instant the snapshot was taken. A repo whose status query times out is recorded as *declined*, stays on the per-path route, and keeps that verdict across invalidations — the decline describes the repository, not the tree, so re-deriving it after every edit would have made a one-off cost a per-edit one.

  A path reached through a symlink is never answered from the snapshot. A repo-wide status keys its records by the name in the tree, so a lookup under the link's target name misses — and a miss is indistinguishable from clean, which would have rendered an untracked symlink as a tracked, unmodified file. Worse, resolving the link first picked the repository the *target* lives in: a link in one repo pointing into another was described by the other one's status. The repo root behind this marker is now walked with links intact, matching the directory the per-path query has always used as its cwd.

- **`git-commit` asked git for its git dir twice in a row and threw one answer away** ([#1126](https://github.com/Digital-Process-Tools/claude-supertool/issues/1126)). The repository check and the merge-in-progress probe ran the identical `rev-parse --git-dir` microseconds apart. One spawn now, on the `--no-edit` path where both fired.

  The same issue listed the two `rev-parse --abbrev-ref HEAD` calls in `git-checkout` as a third duplicate. They are not: one reads the branch before the checkout and one reads where it landed, and merging them would print a receipt claiming every checkout was a no-op. They are the shape the issue itself refuses a `rev-parse` cache over, and a comment now says so at the call site.
