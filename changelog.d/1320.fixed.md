- **A create a validator refused, and no validator rolled back, is now disclosed as still on disk** ([#1320](https://github.com/Digital-Process-Tools/claude-supertool/issues/1320)). `paste` of a malformed `changelog.d/` fragment printed the refusal and `[result] 1 op run, 1 write` — the same footer a fragment that passed prints — and left the artefact in the tree for `git status`, test collection and every later read to find.
  - **The issue's stated mechanism was wrong, and re-deriving it changed the fix.** It reported that a create "has no baseline, so the comparison cannot fire". #1088 already built the create arm: `_rollback_action(False, None)` is `unlink`, and a new `.json` that does not parse really is removed. `? → N ✗ (baseline not measured)` is a statement about the delta, not about whether rollback can fire. The only discriminator is per-validator `rollback_on_fail`.
  - **So the fix is not rollback, and not flipping the flags.** Four of this repo's eight validators set `rollback_on_fail: false` deliberately — `ruff` and `lsp-diag` are advisory, `git-status` is not about the file's content, and `changelog-fragment` refuses shapes an author iterates on. Unlinking there would trade a misreport for the destruction of a write the caller asked for.
  - **`[left on disk]` is the mirror of `[rolled back]`**, built the same way: it quotes the receipt's own `created …` line back, so a filter that caught the claim catches its qualification adjacent to it. It confirms rather than retracts — the path is real and the next action is to delete or fix it.
  - **The `[result]` line carries it**, because that is the part that survives a pipe: `1 op run, 1 write, 1 left on disk — 1 created file a validator refused was NOT removed and is still on disk`. `nothing changed on disk` is suppressed when it fires, so a batch that both reverted a write and kept a refused create cannot net to a footer that is false about the one path the reader must act on.
  - **The exit code does not move**, and that is the one place the mirror of `[rolled back]` stops. A rollback exits 1 because the write did not land; here it landed exactly as asked. Gating would make `rollback_on_fail: false` mean "advisory, unless you created the file" — the identical finding exits 0 on an edit — so a repo whose new file trips an advisory linter would break its `&&` chain over a checker its own config declared non-blocking.
  - **Four boundaries stay silent**: a clean create, a `skipped` (a checker that declined refused nothing), an overwrite (the `edited` line above already states it truthfully), and a create a rollback already removed or already reported on.
