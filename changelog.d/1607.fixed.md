- **`gl-mr:N:status` now sums the pipeline's legs, and the terms add back to the job count** ([#1607](https://github.com/Digital-Process-Tools/claude-supertool/issues/1607)). `pipeline: failed` was one word where `gh-pr:N:status` sums legs, so [#445](https://github.com/Digital-Process-Tools/claude-supertool/issues/445)/[#454](https://github.com/Digital-Process-Tools/claude-supertool/issues/454)'s arithmetic was simply absent on the GitLab side of the merge gate. The expensive shape is not the failed pipeline but the green one: GitLab reports `success` for a pipeline whose jobs include `skipped`, `manual` and allow-failure `canceled` legs, so a run where four legs never executed rendered byte-identically to one where every leg passed. The render now carries `legs: 12 total: 8 passed, 0 failed, 0 pending, 2 skipped, 1 manual, 1 canceled ⚠ NOT ALL GREEN` under the pipeline line.

- **The judgement is the one in `presets/_checks.py`, not a second GitLab-only copy** ([#1607](https://github.com/Digital-Process-Tools/claude-supertool/issues/1607)). [#958](https://github.com/Digital-Process-Tools/claude-supertool/issues/958)'s rule is that the render may legitimately differ per platform and the classification may not, and reusing `summarize()` is safe here precisely because that module does not enumerate states: GitLab's one-L `canceled` is in none of its four sets, so it lands in the leftover term and is **named there** rather than mapped onto GitHub's two-L `CANCELLED`. Nothing about the two vocabularies is guessed, and a status GitLab adds after this was written takes its own term for the same reason. `tests/test_gl_mr_status_leg_tally_1607.py` asserts the rendered tally is `summarize()`'s output verbatim, so a second classifier cannot be introduced quietly.

- **An element the jobs array carried and the render could not parse is counted as a leg, not dropped from the total** ([#1607](https://github.com/Digital-Process-Tools/claude-supertool/issues/1607)). [#1517](https://github.com/Digital-Process-Tools/claude-supertool/issues/1517) added the `! 2 of 3 pipeline jobs had a shape supertool could not read` note; this adds the arithmetic it belongs to. Unreadable elements normalise to `UNKNOWN` and take their own term, so the note and the count now agree instead of the note saying three while the tally said one. A page that came back exactly `per_page` long still carries the `PAGE FULL` hedge, because the tally off it is a floor.

- **Counting legs costs one `glab api` jobs request per `:status` call, on green pipelines too — stated, not smuggled** ([#1607](https://github.com/Digital-Process-Tools/claude-supertool/issues/1607)). The fetch was gated on the pipeline already being not-green, which is right for *naming* jobs and wrong for *counting* them: gating on redness cannot see the case the tally exists for. [#815](https://github.com/Digital-Process-Tools/claude-supertool/issues/815) forbids buying a per-call round trip **silently** rather than forbidding the purchase, so the cost is in the op's own `description`, the README bullet and `docs/presets/gitlab.md`. The GitHub mirror of a leg tally is not the rollup — that is free and already in the payload — it is `_declared_for_commit`, which fires 1+N requests on every `gh-pr:N:status` including the green ones, on [#804](https://github.com/Digital-Process-Tools/claude-supertool/issues/804)'s argument that a request is cheaper than a merge on four green CodeQL legs.

- **A jobs request that could not be completed says so, and never counts to zero** ([#1607](https://github.com/Digital-Process-Tools/claude-supertool/issues/1607)). `legs: UNKNOWN — <reason>` rather than a zeroed tally, because `0 failed, 0 pending` reads as "everything is accounted for and nothing is outstanding" and over a read nobody completed that is the one reading that is definitely wrong — this repo's most-filed defect class, arriving with arithmetic on top. A pipeline that genuinely carries no jobs answers in GitLab's own vocabulary instead of borrowing `_checks.NO_CHECKS`, whose words are about check runs on a commit.

- **The `:status` parity allowlist lost its stale sentence** ([#1607](https://github.com/Digital-Process-Tools/claude-supertool/issues/1607)). `_SYNONYMS["ci"]` in `tests/test_gh_gl_status_parity_628.py` said the GitHub side carried a summed leg tally and the GitLab side did not, and that the gap was tracked elsewhere. It is closed, so the reason now records what still differs — where each side prints its tally — rather than a divergence that no longer exists. The three other items #1607 files (approvals on `:status`, `gl-issue`'s `closed_by` endpoint, a `gl-issues` listing op) are untouched and the issue stays open for them.
