- **`gh-branch`'s green now states what it covers, and names the workflows it does not** ([#846](https://github.com/Digital-Process-Tools/claude-supertool/issues/846)). Every source in the leg reconciliation from [#804](https://github.com/Digital-Process-Tools/claude-supertool/issues/804)/[#837](https://github.com/Digital-Process-Tools/claude-supertool/issues/837) is read off the runs on the commit, so a workflow that produced no run appears on neither side of the arithmetic and cancels out exactly. The tally sums, every term is accounted for, and it describes a strictly smaller universe than the reader believes they are looking at. On the morning of the v0.27.0 tag `Verdict: GREEN — every workflow on dcb574e concluded and every leg passed (19 legs across 3 workflows)` was that sentence: `slow tests` was the fourth, `schedule`-triggered, declared in `.github/workflows`, never dispatched on that commit, and it started four minutes later. A release was tagged on it.

  The workflow directory is now read **at the head SHA** — not off the checkout, which is a different ref — and the names declared there are compared against the names that produced a run. The verdict state is deliberately unchanged: a `paths` filter, a `branches` filter, a job-level `if:`, a workflow disabled in repository settings and a matrix computed at runtime are each a legitimate reason for a declared workflow to produce no run, and every one is either invisible from here or costs more calls than the answer is worth, so concluding a shortfall from an absence would trade a silent miss for a false alarm on a merge gate. What changed is that the clearance states its own scope on the line people read, and the uncovered workflows are named beneath it.

  The clause names the un-covered workflows itself rather than pointing at a block below it. Every surface republishing this verdict quotes lines out of it and not the same ones — `pr_merge._default_branch_report` filtered for four prefixes, so a clause ending "named below" arrived on the merge gate with nothing below it, and #846's own reproduction was a `Verdict:` line read on its own. The names now ride on the sentence, capped with `+N more`, and the merge gate additionally carries the detail block as a blank-line-terminated region. `presets/dashboard/dashboard.py` calls the same new `scope_for` seam, because the dashboard's default-branch line is the board a human reads immediately before tagging and it was publishing the unscoped green that motivated this issue. `presets/watch/tiers/gh_prs.py` makes the same call and is deliberately not touched here.

  Two parses had to agree or the check manufactured the false alarm it exists to refuse. `parse_triggers` stripped a trailing YAML comment and `parse_name` did not, so `name: tests # the matrix` never matched GitHub's `workflowName` of `tests` and a workflow that had run and passed was reported as not covered; a comment now starts at a `#` after whitespace, so `build#3` keeps its hash and a quoted `release # 1` keeps its spaces. A flow sequence spread across lines — `on: [pull_request,` / `push]` — was truncated at the first line, which answered `is_push_triggered` as False and routed a genuinely undispatched **push** workflow into the quiet summary: the loud line this issue exists to print, silenced by the parser. It is read whole now, and an unterminated bracket declines rather than returning the part that was read.

  The enrichment is bounded by construction rather than by a projection: one directory read plus `ceil(12 / 6)` waves at a 10s per-call ceiling is a 30s absolute worst case, against `gh-branch`'s budget raised to 90s and `pr_merge`'s wrapper raised to 120s. A projected-cost refusal was tried first and rejected — it declined a ten-file repository that would in practice have answered in about three seconds, turning a working check into a permanent non-answer.

  The two absences read differently because they are different questions. A workflow with no push-family trigger producing no run on a pushed commit is expected, so those collapse into one summary line — naming them individually on every call is how a disclosure gets tuned out. One that **does** declare a push trigger and produced no run gets its own line, stating that the question is open rather than answering it, and a workflow whose `on:` block could not be parsed is in that same loud group, because "I could not tell" is not "no". The declared set itself has a third state: an unreadable `.github/workflows`, or one wider than the twelve files this op will fetch in a render, prints `UNESTABLISHED` with the reason instead of claiming complete coverage; a genuine 404 is the opposite answer and is treated as one, since a commit with no workflow directory declares nothing there and needs no caveat.
