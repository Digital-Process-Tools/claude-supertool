- **The "carries a fragment" gate was satisfied by *deleting* one** ([#925](https://github.com/Digital-Process-Tools/claude-supertool/issues/925)). `changelog.yml` read the pull request's fragment state out of `git diff --name-only`, which lists a deletion identically to an addition — so a PR that changed the core and removed somebody else's pending fragment passed green, announced nothing, and dropped an already-approved entry from the next release. The gate reported that a fragment had been touched, which was true and was not what its `ok` line meant. Additions and deletions are now read apart, by two diffs rather than by one `--diff-filter` flag: restricting the single diff would also have stopped the user-visible-paths read seeing a *deleted* preset, and a preset that goes away is as user-visible as one that arrives. A release cut deletes fragments and adds none, so that shape is a pass and now says so in its own words (`ok (release: N fragment(s) assembled into CHANGELOG.md)`) rather than passing by accident; a deletion with no `CHANGELOG.md` beside it is a finding that names the files it lost. The gate's own `run:` block is now executed against real repositories in `tests/test_changelog_fragment_deletion_925.py`, including the release shape, which the one-flag fix would have reddened on every release.
