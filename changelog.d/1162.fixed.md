- **A config found and skipped was reported as a config that was never there** ([#1162](https://github.com/Digital-Process-Tools/claude-supertool/issues/1162)). Git writes conflict markers into `.supertool.json` during a rebase; the file stops parsing, the loader skips it and keeps walking, and with nothing usable above, no preset ops load at all. The refusal then read `No .supertool.json was found from X or any parent` — one line under a stderr warning naming the file it had just skipped. Two lines of one render disagreeing about whether the config exists, and a reader who sees only the ERROR goes looking for a missing file that is present.

  The refusal and `ops`' preset-disclosure line now both name the file, say why it was unusable, and — when it holds conflict markers — say so and give the marker line numbers, which is the one fact `git-conflicts` would have supplied from the code that can still supply it. `|||||||` counts as a marker: the diff3 and zdiff3 merge styles emit it and the default `merge` style does not, so matching only the two obvious ones would classify a diff3 conflict as ordinary broken JSON.

  Neither dead remedy is offered for the conflicted case. `cwd:<other-project>` retargets the working directory, so a git op would report *that* repo's conflicts — [#678](https://github.com/Digital-Process-Tools/claude-supertool/issues/678)'s shape arriving through the remedy line — and there is no other root to move to, because the broken file is in the tree the caller is standing in.

  The issue's second option — loading the git preset from defaults when the config is unparseable — was **declined**. Running ops out of a config the user cannot see is a guess, and `docs/validators.md`'s "Declining instead of guessing" is the rule it would break. The circularity is real and stays: the message says what is true instead of inventing a way around it.
