- **`gh-pr-edit:NUMBER:@FILE` — correct a published pull request body, from the payload that wrote it** ([#1739](https://github.com/Digital-Process-Tools/claude-supertool/issues/1739)). `gh-pr-create` writes a body once and nothing updated one, which is the wrong gap for a loop that asks authors to correct their own record. The raw fallback is not one either: `gh pr edit` fetches the pull request through GraphQL before writing and the field set includes `projectCards`, which GitHub has sunset, so on a repository with Projects classic it fails outright — re-derived 2026-08-15, exit 1, nothing written. This goes through REST `PATCH`. It is a separate op rather than `gh-pr-create` taking a number because a number that went missing from the payload would then not fail: it would open a second pull request. Two things the raw `gh api -X PATCH` route cannot do. The **closing-reference gate runs again at update time**, on the difference between the published body and the new one, with the same `_checks.closing_issue_refs` reader `gh-pr` uses — a reference the new body drops, and a published body that could not be read at all, both **refuse and write nothing**, because a check that could not look is not a check that found nothing; `unlink` is the single token that permits a deliberate re-scope. And the **receipt is a byte comparison**: the PATCH response carries the stored body, so `EXACT`, line endings `NORMALISED` by the server, `MISMATCH` naming both lengths and the first differing line, or `UNKNOWN` are answered in the same call, and only the first two exit 0. The raw route printed one timestamp, which says a write happened and not which bytes are on the server. `gh pr edit --body` / `--body-file` / `--title` now name it through `replaces`.
