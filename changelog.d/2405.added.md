- **`ruff-format` now reports the before-file line span its reformat actually touched, and the caller-visible row says the same-session read of that region is stale** ([#2405](https://github.com/Digital-Process-Tools/claude-supertool/issues/2405)). Observed live: an `edit:@-` call in an `oss:developer` lane failed "old string not found" because a prior edit in the same session triggered `ruff-format`'s post-write pass, which collapsed an unrelated multi-line `isinstance(...)` condition onto one line inside a block a later, separate edit was about to touch -- the block had been read via `around_line` moments earlier and no longer matched byte-for-byte by the time the second edit ran. Not a correctness bug (the failure was loud and safe to retry), but a real, reproducible cost every multi-edit lane in a formatted file paid blind, with no way to tell *which* lines had moved. `formatters/ruff-format/ruff-format.py`'s `_line_diff` now uses `difflib.SequenceMatcher.get_opcodes()` instead of a bare unified diff, and reports `metrics.first_changed_line` / `metrics.last_changed_line` (1-indexed, `null` when nothing changed -- never a fabricated `(1, 1)`); `_formatter_render_row` appends `(lines N-M touched -- an earlier read of that region is now stale, re-read before reusing it)` to the row whenever the range is present, so the same call that ran the triggering edit already carries the warning, with no second round-trip. Scoped to `ruff-format` only, matching the issue's own repro; `php-cs-fixer`, `prettier-write` and `phpcbf` share the identical gap and were left alone as a same-shaped follow-up rather than tripling this diff's blast radius.
