- **The MCP validators now read the auto-spawn flag the core stamps for them, instead of spending their whole spawn budget disobeying it** ([#1743](https://github.com/Digital-Process-Tools/claude-supertool/issues/1743)). `SUPERTOOL_MCP_AUTOSPAWN=0` has been stamped into every validator adapter's environment since [#475](https://github.com/Digital-Process-Tools/claude-supertool/issues/475), and the only reader was the core's own MCP client — a different process, reached only when an adapter shells `supertool diag:`. The four MCP adapters go through `presets/mcp/_spawn.ensure_daemon`, which looked at the socket, the pidfile and the config fingerprint and never at the flag. Measured on a machine with `mcp-rector-warm` installed and no warm daemon: `rector-mcp` with the flag explicitly `0` spent 30194 ms raising a daemon it had been told not to create, then published the spawn timeout as an adapter error about the edited file. `ensure_daemon` now declines before the spawn lock, so the same call returns in milliseconds.

- **A suppressed spawn says so on the receipt** ([#1743](https://github.com/Digital-Process-Tools/claude-supertool/issues/1743)). A knob that works silently is indistinguishable from one still being ignored, which is how this survived two years. The adapter publishes the third state — `skipped`, verdict keys omitted — whose reason names `SUPERTOOL_MCP_AUTOSPAWN`, its value, and the two ways out: warm the daemon from a caller that can wait, or set `mcp_autospawn` on the validator. It routes through `refusal.absent()`, so a validator named in `$SUPERTOOL_REQUIRE_VALIDATORS` gets the loud arm instead: a gate that did not run is not a gate that passed. Suppression still removes *creation* and never *use* — an already-warm daemon is connected to exactly as before, which is the clause that keeps the fix from degrading into "MCP validators are inert".

- **What the old test asserted, and what joins it** ([#1743](https://github.com/Digital-Process-Tools/claude-supertool/issues/1743)). `tests/test_mcp_autospawn_provenance_475.py` pinned that the flag is *present* in the child environment — a shape check over the setter, which passes whether the flag is obeyed or ignored, a guard that checks the message was sent and never that it was received. `tests/test_mcp_autospawn_honoured_1743.py` drives the four adapters and the shared spawn path with the flag at `0` and asserts nothing was launched, in under a second of a 30s budget. Every one of those is an assertion that nothing happened, so each is paired with a must-fire control in the same fixture: unset the flag and the same call still launches `daemon.py --detach`. `presets/mcp/_spawn` and the core are pinned to the same falsey vocabulary, because two readers of one variable that disagree about `off` is this bug again at one spelling per release.
