- **A line in a file you `git-investigate` could forge the blame row that names who wrote it** ([#1693](https://github.com/Digital-Process-Tools/claude-supertool/issues/1693)). `git blame --line-porcelain` interleaves porcelain headers with the blamed file's **own lines**, and the parse split that stream with `str.splitlines()` — which folds on U+2028, U+0085 and the vertical tab, none of which git writes there. A source line spelling `<U+2028>author X<U+2028><TAB>text` therefore added a row to the blame hotspots carrying an author, a date and a line number no commit ever had, in the one section a reader consults to answer *who changed this and when*. The bar is a line in a file you blame, which is far below a commit subject.

  `_untrusted.split_lines` is not the repair and would not have closed it, because the parse was not the only line reader in the path. `_git_common._git` runs `subprocess.run(text=True)`, and text mode rewrites a lone CR **and** a CRLF into LF before any preset sees the stream — measured against real git 2.46.2, a file holding `x = 1<CR>author Mallory<CR><TAB>I did this` reached the parser as three lines, two of them reading as git's. That is the same forgery over plain ASCII, and no choice of splitter undoes it once the bytes are gone. So the blame call goes through a new `_git_verbatim` — the same budget and the same `TIMEOUT_RC` contract, with the translation off — and the parse then splits on git's own LF, which a file line cannot contain by definition. The crafted text is still shown, in the row it belongs to and with its separators disclosed; the old reader silently discarded everything past the first one.

  The log render and the two diff renders in the same function are [#1681](https://github.com/Digital-Process-Tools/claude-supertool/issues/1681)'s shape one function further on — every line rendered and counted, with the count as the product — and take `split_lines` plus `visible()`. `presets/git` is out of `NOT QUOTED, open` entries; the ground is kept with a count of 0 so the next one has a spelling, and the register is down to 23 sites / 23 functions / 8 files.

- **The ground under `git-resolve`'s five raw path renders, written down** ([#1693](https://github.com/Digital-Process-Tools/claude-supertool/issues/1693)). The `✓` / `⊘` / `✗` rows interpolate `path` with no `_untrusted.flat`, and nothing said why that was sound — not the register, not the file, not the docs — so the next auditor either repairs five provable no-ops or leaves them and cannot say why. Re-derived, the ground is stronger than the report: a caller's comma-separated `PATH` list is not a second source beside `git diff --name-only --diff-filter=U`, it is a **filter** over it, refused unless every element is already conflicted. So `core.quotePath` reaches all five. Recorded at the code, in the register and in the docs, and pinned by a test — if that refusal is ever relaxed, the ground is gone and the five need flattening the same day.
