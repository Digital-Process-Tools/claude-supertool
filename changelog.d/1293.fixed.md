- **A file outside `changelog.d/` can no longer name a fragment the next tag will delete** ([#1293](https://github.com/Digital-Process-Tools/claude-supertool/issues/1293)). The release *consumes* fragments, so any reference keyed to `changelog.d/<n>.<section>.md` is green for exactly the window between the PR that writes it and the release that consumes it, and red on that release and every one after — and the window is invisible from inside the PR that adds it, because the file is present the whole time that PR's CI runs.

  It has shipped four times. #941 took five legs on v0.26.0, #953 thirteen of twenty on v0.27.0, and #1231 thirteen of twenty-two on v0.33.0 — that last one was not an assertion at all, just a filename in a tuple of paths a test swept and resolved with a `read_text`, which the #1053 AST detector is blind to by construction. So the class was never a syntax.

  `tests/test_changelog_findable_1293.py` asks which fragments are on disk *now* and refuses any tracked text file that names one, in any language and by any shape. Keying it to the directory's contents rather than to a filename pattern is what makes it precise: a reference to an **already consumed** fragment names nothing the next tag can delete, and this repo holds 162 of those — doc examples, comments, `tmp_path` fixtures — every one correct and every one left alone. Swept for live-keyed references at the same time: **zero**, `tests/test_ops_roster_1231.py` having been the last. When nothing is pending, or when git cannot list the checkout, it skips rather than passing, because a scan that looked at nothing must not read as a clean sheet.

  The rule is now stated where fragment authors meet it — `changelog.d/README.md` and `docs/contributing.md` — with `CHANGELOG.md` and `assert_change_is_findable(<issue>)` named as the two permanent things to point at instead.
