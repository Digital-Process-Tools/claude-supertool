- **`gh-pr` writes through the opt-in mirror the same way `gh-issue` has since #1955, and `gh-mirror` grows a `pr` kind to read it back** ([#2472](https://github.com/Digital-Process-Tools/claude-supertool/issues/2472)). `gh-pr`'s dashboard fetch now stores its full, untruncated API reply under `.supertool.json`'s `gh_mirror_dir` as a side effect of every read, in its own `prs/` subdirectory with its own manifest and lock -- an issue and a PR sharing the same number can never answer for each other. `gh-mirror:pr:NUMBER` answers the same four states (`cached (AGE)`, `not-cached`, `mirror-unreadable`, `not configured`) `gh-mirror:issue:NUMBER` already did. `presets/_mirror.py`'s `write_issue`/`read_issue` are now thin wrappers over a generic `_write`/`_read` pair keyed by SUBDIR, shared with the new `write_pr`/`read_pr`. `gh-issues` and `gh-prs` (the list ops) are deliberately **not** wired -- their `--json` field sets are a partial projection of the dashboard shape (`gh-issues`'s omits `body` entirely), so write-through would either silently downgrade a full mirror entry to a partial one on the next board poll, or need a field-level merge scheme this lane did not size, and a list read returning dozens of rows per call would mean that many manifest-lock acquisitions on exactly the op (`gh-prs`) this feature's own design constraint says must stay fast and live for collision-avoidance. See `presets/_mirror.py`'s module docstring and `docs/presets/github.md`'s "The write-through mirror" section for the full reasoning.
