- **A file `paste` creates now lands at the process umask, and the receipt says which mode that is** ([#1275](https://github.com/Digital-Process-Tools/claude-supertool/issues/1275)). An agent wrote a new shell script into a directory where every sibling was `0755`. It arrived `0600`, and nothing in the receipt mentioned a mode, so the only thing that would have surfaced it was running the script — which is what the next person does after the merge rather than before it. A created file is now `0666 & ~umask` (`0644` under the common `umask 022`), the same as `>`, `tee`, `cp` and every editor produce, and the receipt carries `↳ mode 0644, from the process umask`.

  **`0600` was never a chosen default.** `_atomic_write` renames a `tempfile.mkstemp` temp file over the target, and mkstemp creates at `0600`; #259 re-applies an *existing* file's mode before the rename, so the tight bit only ever applied to files that were not there before. A property that holds for creates, not for rewrites, is undocumented and unmentioned in the receipt is not a security guarantee — it is a temp file's mode leaking through a rename. A caller who wants owner-only files sets `umask 077`, which is what the mask is for, and gets it for every op rather than for half of them.

  **Said plainly, because it is a widening:** on a default `umask 022` a created file is group- and world-*readable* where it used to be owner-only, and a payload can hold a secret. Three things bound that. The mask is the caller's own declared policy and is now honoured rather than overridden; the mode is stated in the receipt on every create, so the widening is never silent; and an overwrite is untouched, so a file that is already `0600` stays `0600` through any number of pastes.

  **`paste` does not infer the executable bit, and that is deliberate.** Not from the shebang, not from the modes of the file's neighbours, not from a flag. Each is a guess, and the neighbours-match rule is most likely to be right and most surprising when it is wrong. What it does instead is state a fact it can be certain of: content beginning `#!` that is not executable gets a second line naming `chmod +x PATH`. The mode on disk is identical either way, so a wrong reading of the content costs one line of prose rather than a permission nobody asked for.

  **Nothing is printed on Windows**, where the executable bit does not exist and `os.chmod` honours only the read-only flag — `st_mode` reads back `0o666` whatever was asked for, so a mode line would be a statement about access that is not true there. The tests gate on a probe that creates a file with an explicit `0666` and reads it back, not on a platform name, so a filesystem mounted without permission bits skips for the reason it actually has.

  **What the issue claimed and the code did not do:** git does not record a wrong mode. It stores only the executable bit, so a `0600` create and a `0644` shell redirect are byte-identical in the index — `100644` for both, which is a correct record of a file that is not executable. Verified with `git ls-files -s` over one of each. The defect was on disk and in the receipt's silence; the index was never wrong.
