- **Five more renders put a value off disk at column 0, and a sixth said in its own docstring that it did not** ([#1569](https://github.com/Digital-Process-Tools/claude-supertool/issues/1569)). Round 2 of the class [#1557](https://github.com/Digital-Process-Tools/claude-supertool/issues/1557) opened. `git-diff`'s `Repo:` line — the op you run before every commit — printed `git rev-parse --show-toplevel` raw, so a repository checked out under a name containing a newline wrote a second `Repo:` and a `Scope:` of its own choosing. `git-status` printed the whole of a failed `git branch -vv`'s stderr, which a crafted `core.abbrev` in `.git/config` is enough to fill with `Working tree: clean` and `Stashes: 0`. `git-commit`'s refused-commit transcript relayed a pre-commit hook's lines at column 0 under `--- git output ---`, so a hook could write `Status: COMMITTED` and `[result] 1 op run, 1 write` into a receipt that says the opposite. And `read`'s `↳ to modify:` footer interpolated the filename raw, two lines below a header [#1019](https://github.com/Digital-Process-Tools/claude-supertool/issues/1019) had already flattened, inside what reads as a command to run.

  **Why there were five and not one, which is the finding.** #1557 and [#1475](https://github.com/Digital-Process-Tools/claude-supertool/issues/1475) were closed by flattening the sites they named. Each shape here already had a seam and the site simply did not use it: `_git_common.repo_label()` for a repository path (`git-diff` never called it, although `repo_label`'s own docstring names `git-diff` as the op that has printed a `Repo:` line for years), and `status._reason()` for why a git call did not answer (five of its six callers went through it; the `branch -vv` sink did not). The third shape had no reachable seam at all: the relay lived in `push.py`, which a sibling preset cannot import, so `commit._failure_receipt` restated its body — and the half it dropped was the `> ` prefix, while its docstring claimed it relayed "exactly as `push._relayed_lines` does it".

  So the relay moved into `_git_common` as `relayed_block()`, which emits the `--- git output ---` header and the `> ` prefix **together**. A header is an opening delimiter with no close; on its own it never separated anyone's lines from ours. `git-push`'s three dumps were on the same footing and moved with it, so all four now carry the prefix. `tests/test_column_zero_renders_1569.py` closes the loop with an AST census: no file in `presets/git/` other than the seam may render that header at all, which is what makes the next copy fail at the moment it is written rather than one audit round later.

  **One correction, because a wrong mechanism in a comment is folklore.** `presets/git/commit.py:498` justified three of #1475's edits with "`str.split()` folds ASCII whitespace and nothing else, so a U+2028 walked through this one-line normaliser untouched". Python does not do that — `str.split(None)` uses the *Unicode* whitespace predicate, so U+2028, U+0085 and the vertical tab all fold, and the forged-line mechanism that sentence names was never reachable through those sites. The edits stay: they close **ANSI/C0** disclosure, which `split()` does not touch. `_reason()` has the identical construct and was still exposed to `ESC [2K ESC [1A`, an erase-line/cursor-up pair that deletes the receipt line above it ([#851](https://github.com/Digital-Process-Tools/claude-supertool/issues/851)) — and the false premise is exactly what made it look already covered.
