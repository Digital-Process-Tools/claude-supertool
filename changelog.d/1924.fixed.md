- **The four warm PHP MCP adapters no longer wait out their full timeout on a response they already received** ([#1924](https://github.com/Digital-Process-Tools/claude-supertool/issues/1924)). `ndjson_call` in `phpunit-mcp`, `phpstan-mcp`, `phpmd-mcp` and `rector-mcp` parsed the daemon's socket buffer one LF-delimited line at a time. When a forked PHP process fatals, the host application can render an HTML error page into the same stream, and the real JSON-RPC response then lands glued to the end of the last HTML line with no separator (`</html>{"jsonrpc":"2.0","id":2,...}`) — a line-anchored parser never sees it, so the adapter blocked on `recv()` until the full call timeout (300s for phpunit-mcp) and reported `NOT CHECKED`, indistinguishable from a genuine timeout. Measured: the answer was in the buffer 2 seconds in; the adapter gave up 5 minutes later. `validators/common/ndjson_scan.find_response` now scans the whole accumulated buffer for the response rather than requiring it to open a line, so it is found the moment its bytes arrive. The per-`recv()` socket timeout is also now tied to the call's own deadline rather than reset on every call, so a genuine no-answer still fails at the deadline instead of a further multiple of it, and the error names what was actually in the buffer — no bytes at all, or bytes with no decodable `id`-matching frame — rather than a bare "timeout" that could mean either.
