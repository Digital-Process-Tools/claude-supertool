- **`.supertool.example.json` told readers to export an environment variable nothing reads** ([#1021](https://github.com/Digital-Process-Tools/claude-supertool/issues/1021)). `ops.dashboard._doc` ended "Passes through as `SUPERTOOL_DASHBOARD_LANE_PREFIX`". The preset reads `SUPERTOOL_LANE_PREFIX`, and the runner exports `SUPERTOOL_<KEY.upper()>` for each key of the entry — the key alone, never namespaced by op name. Someone who prefers an env override to a config edit exported the documented name, got no error, and watched the lanes section correctly print `!! unread — no lane vocabulary configured`: the op was right and the reader had been told the op was broken. Misreports, on the shipped artifact rather than on the code.

  **The prose was the defect, not the runner.** The op-namespaced form is not a design nobody implemented: three other entries in the same file document the flat form and are correct, every preset reads the flat name, and `test_the_config_key_reaches_the_preset_under_the_name_it_reads` pins it. Changing the runner to match one sentence would have broken all of them.

  **The mistake is copy-paste-shaped, so the pin is the rule rather than the sentence.** The sibling `ops.radar._doc` directly below is right — but only because its key is `radar_tiers`, not because the op name is prepended, so copying it onto a key called `lane_prefix` silently changes what it claims. A new test sweeps both `.supertool.json` and `.supertool.example.json`, and refuses any `SUPERTOOL_*` name in an entry's prose that is not `SUPERTOOL_<KEY.upper()>` for a non-reserved key of that same entry, naming the entry and listing the keys that would have been right. A bare `SUPERTOOL_*` is a mention of the mechanism, not a claim about a key, and does not match. The sweep found exactly the one instance filed.
