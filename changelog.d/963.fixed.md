- **`git-commit`'s refusals listed fifteen paths and then offered a remedy naming three of them** ([#963](https://github.com/Digital-Process-Tools/claude-supertool/issues/963)). Both `ERROR: nothing staged` and the post-commit left-behind warning printed the full list of candidate files and followed it with `git-commit:::MESSAGE:::` carrying the first three. Pasted, that stages three, commits, and prints a success receipt; nothing in the line says the other twelve were dropped. A remedy that produces the wrong outcome is worse than no remedy, because it carries the authority a refusal lends the tool — it is read by someone who has just been told they were wrong, in the state of mind where they paste what they are handed. The remedy now names **every** path it listed.

  **Past the display cap it names none of them, on purpose.** A refusal that dumps 200 pathspecs into a suggestion is its own defect, and dumping the first 20 of 200 is the original one wearing a bigger number. Over 20 the line becomes a visible placeholder — `git-commit:::MESSAGE:::PATH[:::PATH...]` — with `N paths in all, 20 shown and N-20 not shown — name the ones you mean`. Three states, and the third one declines rather than guessing.

  **The left-behind hint also glued a literal `…` onto its last pathspec.** `…:::f12.txt…` is not a path, so the remedy for "you left files behind" failed on paste even when it was otherwise right.

  **The counts are measured against what was printed, not re-derived from the cap.** `ERROR: nothing staged` prints modified and untracked as two lists capped *independently*, so a tree with 15 of each shows the reader all 30 — and a remedy computing `min(cap, 15 + 15)` announced `20 shown and 10 not shown`, which is false twice over, in the one line whose whole purpose is not to be. Both remedies now take the list that was actually printed plus the true total. Found by the independent review of [#1062](https://github.com/Digital-Process-Tools/claude-supertool/pull/1062), in the first version of this fix: the defect survived inside its own repair, under a docstring asserting the guarantee it broke.

  **And a path containing a quote pastes now.** The `:::` suggestion is a single-quoted shell word, so `it's.txt` closed it early and the pasted line was a syntax error; the payload array wrapped each path in raw `"`, so a `"` or a backslash in a filename produced TOML the payload route cannot parse. Paths reach these lines unquoted on purpose — `git status -z` is read precisely so spaces and non-ASCII survive ([#1003](https://github.com/Digital-Process-Tools/claude-supertool/issues/1003)) — and quotes were the case that was not carried through. Shell-quoting is unconditional rather than `shlex.quote`, which leaves ordinary words bare and would have re-written every line that was already correct.

  **The third `_colon_remedy` call site was still uncapped, and that one had never been capped at all.** The comma-guess remedy behind `git add failed` — `A ',' above is not a separator here. Did you mean:` — builds its list by splitting the caller's own argument on `,`, which is unbounded: one argument can hold any number of commas. When the remedy grew its `shown`/`total` pair, the two sites named in the review were updated and this one kept calling it with a single argument, which defaults `total` to `len(shown)` and makes the placeholder branch unreachable there by construction. Twenty-five guessed pathspecs went into one pasteable line with nothing saying anything had been left out, three lines below the docstring asserting that cannot happen. It now takes the same cap and the same placeholder as the other two, and past the cap it lists the guesses as well, because the count line claims what the reader saw and nothing above it had shown them. Found by the second independent review of [#1062](https://github.com/Digital-Process-Tools/claude-supertool/pull/1062) — the same shape as the first finding, one call site along.

  **The `:`-split refusal quoted its own payload example by hand, and still does not.** Its `paths = [...]` array wrapped each path in a raw `"` — the exact defect fixed above for the other payload example, in a sibling function that predates it, so a path holding a `"` produced TOML the payload route cannot parse and a path holding a backslash produced TOML that parses as a *different* path. `src\new\tab.py` is the quiet half of that: both escapes are legal TOML, so the payload loads without complaint and would stage something the reader never named — which is a Windows path shape, not an exotic one. Its `./supertool '...'` line was hand-quoted too, and the subject it reconstructs is the caller's own prose, so an ordinary apostrophe closed the shell word early. Both now go through the helpers rather than through `%s`.

  **The two defects the issue actually reported do not exist and did not when it was filed.** The `:`-split refusal's `@-` example has emitted a separate `paths = [...]` key since it landed in [#751](https://github.com/Digital-Process-Tools/claude-supertool/issues/751)/#771, never a file list inside `message`; and its single-colon suggestion commits the intended subject and stages the intended path, because `:::` is the outer separator and survives the tokenizer. Both are now pinned end-to-end — the second by executing the suggested line and asserting the resulting subject — so the claim is settled by a test rather than by reading.
