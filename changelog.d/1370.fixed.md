- **`_safe_path` no longer expands `$VAR` before checking cwd containment, so the check and the use agree on `$` again** ([#1370](https://github.com/Digital-Process-Tools/claude-supertool/issues/1370)). The containment gate ran `os.path.expandvars` before comparing a path against cwd, but no op ever expands `$` when it actually opens the file -- every op opens the literal, unexpanded string. A directory literally named `$HOME` (or any `$name`) sitting *inside* cwd was refused with "path escapes cwd", which was false: the literal path never left cwd, only its expanded interpretation would have (had it existed at all). `read:$HOME/weird.txt`, `ls:$HOME` and `grep:x:$HOME/weird.txt` all answer correctly now instead of being wrongly refused. This is the twin of #1300 (fixed for `~`), applied in the opposite direction: #1300 made the *use* match the *check* by expanding `~` on write-back; here `$` is a legal filename character no op ever expands on open, so the coherent fix is to stop expanding it in the check instead -- one rule, applied uniformly, rather than a per-op special case (rejected during #1366's review on the grounds that a second copy of `_containment_error` drifts). A genuine escape via `..` or an outward-pointing symlink is still refused; that is pinned by a positive control alongside the fix. Also fixed: `tests/test_edge_cases_glob.py`'s `test_symlink_to_file_outside_cwd_included` asserted that `glob` includes a symlink pointing outside cwd, which stopped being true once #1366 shipped containment-on-by-default for `glob` -- the test only stayed green because `conftest.py` sets `SUPERTOOL_ALLOW_OUTSIDE_CWD=1` suite-wide. It is now split into two tests that each name the behaviour they actually assert: `..._included_under_explicit_opt_out` (containment explicitly off) and `..._refused_by_default` (containment on, the shipped default).
