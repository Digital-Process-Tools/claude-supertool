- **`git-resolve` can now resolve a conflicted file whose name is not ASCII, and the conflicted-path read no longer depends on a git preference** ([#1708](https://github.com/Digital-Process-Tools/claude-supertool/issues/1708)). `_list_conflicts` read `git diff --name-only --diff-filter=U`, and five `git-resolve` receipt rows were written down as resting on `core.quotePath` octal-quoting every byte above 0x7F out of it. That is a config default rather than a git guarantee, and the issue asked for `-c core.quotePath=true` to make it true by construction.

  Driving the code path first showed the setting has no correct value, measured on git 2.46.2 against a real conflicted merge. At `true` — the default, and what the pin would have frozen — git hands back the octal-escaped *spelling* of an accented name, which is not a filename: `git-resolve` fed it straight back as a pathspec and printed `did not match any file(s) known to git`, so **no conflicted path holding a byte above 0x7F could be resolved at all**. At `false` the name is usable, but one file named with a `U+2028` came back as **two** records, neither of them a file. Pinning either value picks which failure every operator gets.

  The read is `-z` now, which is the answer `git-commit` already reached for the same defect at `diff --cached --name-only -z` ([#1003](https://github.com/Digital-Process-Tools/claude-supertool/issues/1003)). Paths arrive as their real bytes and the records are NUL-separated — the one byte a pathname cannot hold on any platform — so the split cannot be forged by a filename rather than merely being unlikely to be. What that costs moved to the render: a real path can carry `LF`, `CR` or `U+2028`, so every path printed by `git-resolve`, `git-conflicts` and `git-merge` goes through `_untrusted.flat`, which discloses a separator instead of dropping the tail. The paths handed to `open()` and `git add --` stay unflattened, because the filesystem wants the name.
