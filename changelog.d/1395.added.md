- **`gh-issues` and `gl-mrs` take `search=TEXT`, and the query goes to the forge** ([#1395](https://github.com/Digital-Process-Tools/claude-supertool/issues/1395)). `gh issue list` and `glab mr list` are both refused by the shipped guard in favour of the board ops, and neither op could search — so *find the issue whose text mentions X* had no route at all, and the honest answer was `"raw_command_guard": false`, which disarms every mapping in the repo. `search=` forwards to `gh issue list --search` / `glab mr list --search`: it narrows the population, not the page. A client-side filter over one `--limit` page answers "which of the first 50 mention X" while disclosing `capped at --limit 50` about the fetch, which on any repo with more than a page of matches is a different question.

- **One key over two engines, and every render says which answered and what it read.** GitHub's issue search covers title, body **and comments**; GitLab's `search=` covers title and description only. The board prints `(search 'X' — GitHub issue search over title, body and comments)` above the rows and in the footer, and the GitLab one names the half it does not cover. A search that quietly scoped to less than the caller meant returns a zero that reads as an absence in the world. `tests/test_board_search_1395.py` asserts the two scope sentences are different and that each names comments, so the day they collapse the suite reds rather than the render going quietly wrong — which is [#628](https://github.com/Digital-Process-Tools/claude-supertool/issues/628)'s question answered for this one key rather than in general.

- **The shared spelling is honest for a mechanical reason, not an aesthetic one.** A board's whole grammar is one comma-separated segment and supertool splits an op argument on `:`, so GitHub's qualifier language (`in:title`) is refused by the tokenizer with nothing fetched — it is unreachable from either op. Stripped of qualifiers both engines answer "this text occurs in this thing", and what survives is scope, which is why the scope is printed rather than assumed.

- **Three states, not two.** Rows; an empty result that says *the search ran and matched nothing — an empty result, not a lookup that failed*; and a lookup that could not run, which keeps its non-zero exit and prints no board. `No issues match.` / `No MRs match.` on its own is never printed under a search. The disclosure rides the `iids` number stream too — a leading `#` comment on GitHub, stderr on GitLab — because that shape becomes another tool's input and a shorter list otherwise reads as a quieter tracker.

- **`search=` beside `iids=` is refused on `gh-issues`.** A named population has no listing for GitHub to search, so the query would be dropped and N rows the caller enumerated would read as N rows that matched.
