- `gh-prs`, `gh-issues` and `gl-mrs` refuse a filter key given with no value (`author=`, `label=`) instead of dropping it and answering with a wider board ([#974](https://github.com/Digital-Process-Tools/claude-supertool/issues/974)). The key is known, so [#939](https://github.com/Digital-Process-Tools/claude-supertool/issues/939)'s unrecognised-token refusal never fired; the query was then built with `if not val: continue`, so the flag vanished. On `gh-prs` that widened the board rather than merely un-narrowing it — the role-key test `any(k in filters for k in ("author", "assignee", "reviewer"))` is satisfied by an empty value, so `--author @me` was suppressed too and `gh-prs:author=` returned everyone's PRs while the scope line still named a filter. The refusal names the key, says the value is missing rather than misspelled, and states the widening.
- The `gh-prs` radar tier and the `gitlab-mr-feed` poller inherit the same refusal, because the check lives in the tokenizer they share. The poller's existing `unknown` guard returns `None` — "population not established" — so an empty scope no longer spawns a watcher per stranger's MR, and does not crash the long-lived process either.
