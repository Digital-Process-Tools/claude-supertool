- **Three `git status` gates inherited the display setting that decides whether git mentions untracked files at all** ([#1295](https://github.com/Digital-Process-Tools/claude-supertool/issues/1295)). `status.showUntrackedFiles=no` is an ordinary user or repo preference. A consumer reading `git status --porcelain` with inherited config gets an **empty list from a dirty tree** and cannot tell "nothing there" from "not looked" — the mechanism that disarmed #1290's gate. Each of these now pins `-c status.showUntrackedFiles=normal` on the command line, where it outranks config files **and** `GIT_CONFIG_*` both:

  - `git-push`'s pre-push "you forgot to commit X" catch. It had three states for a status that *failed* and none for one that succeeded after being configured not to look — which renders as silence, which reads as "nothing was left behind", on the run right after a push landed.
  - `oss_train`'s pre-rebase guard, whose own comment already read *"A status this op could not read is not a clean tree"*. That was written about a non-zero exit; a suppressed read exits **zero**, so the principle was stated and the code did not cover the case that arises. The guard opened and the op went on to fetch, rebase and force-push a worktree an agent was working in.
  - `git-commit`'s `--all` resolution. #1295 filed this one as a render; it is the strongest gate of the three. `_worktree_changes` feeds the list that gets **staged and committed**, so a suppressed untracked half does not merely print short — `--all` commits the tracked half only, under a receipt naming that subset as the answer to `--all`.

- **`normal`, not `all`.** The flag is there so the command line has the last word on whether untracked files are mentioned; `all` would additionally defeat git's own directory collapse and turn an untracked `venv/` into thousands of lines. Every gate here only needs to establish that the tree is not empty.

- **The remaining `git status` readers are deliberately left alone, and a register says so.** `git-status` and `git-checkout` render their working-tree section for a human and branch on nothing, and pinning a *render* overrides a display preference in the one place it is meant to take effect. That split is the whole judgment, so it is recorded per site in `tests/test_git_status_display_config_gates_1295.py` rather than left for the next reader to re-derive: a new `git status` under `presets/git/`, `presets/github/` or `scripts/` is a red build until someone writes down which kind it is. A shared helper was rejected for the reason it usually wins — it would make the pinning invisible at the call site, which is exactly where the decision has to be made, and it cannot express an answer that differs per site. The register also asserts that every site marked as a gate *actually carries the pin*, because a table of intentions is the inert-gate shape this repo keeps filing.

  Not swept: the three consumers in `_supertool.py`, left untouched because that file was under concurrent rewrite. They are named in the register so the zero reads as "out of scope" rather than "none exist". `git clean` has no consumers in these trees; the `git ls-files` and `git diff` readers were checked and take explicit pathspecs or plumbing flags with no equivalent display suppression.
