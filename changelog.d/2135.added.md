- **A watch source may live outside the plugin** ([#2135](https://github.com/Digital-Process-Tools/claude-supertool/issues/2135)): `SUPERTOOL_WATCH_SOURCES_PATH` is a list of extra directories, separated by the platform's path separator, each holding `<NAME>/poller.py`. `presets/watch/sources/` was hardcoded and had no override anywhere in the preset, so a source plugin could only exist inside the installed plugin directory -- which every plugin update overwrites, and which a symlink into it does not survive. The cost was not a missing convenience: `watch:my-source:scope` answered `unknown source`, and with it went the pid slots, `unwatch`, the `watches` board and radar's healing, about three thousand lines of poller runtime that exist, work, and could not be reached by anything watched privately. It is an ordinary environment variable, so a `watch_sources_path` key in an op's `.supertool.json` block reaches it with no plumbing at all (`docs/contributing.md`, "Extra config keys as environment variables") -- the same route `watch_name` takes since #1477, and `presets/watch/naming.py` is the precedent for the shape.

  All five watch ops resolve it through one function (`presets/watch/sourcepath.py::find`, reached by `dispatcher._load_source`, which is also how `radar` and the `gl-mrs` tier load a poller), because a key declared for `watch` alone gives a source `watch` can start and `radar` can neither locate nor re-spawn -- the half-configured shape of #1309 and #1732 arriving through the config door a third time. Every watch surface prints which ops declared the key and which did not. Shipped sources win: an external directory declaring `gitlab-mr` would otherwise replace a shipped poller with arbitrary Python on a path that came from a config file, and the shadowed external source is **named** on every surface rather than skipped in silence, because an operator who believes their source is loaded and is wrong is the same defect one layer down. Relative entries are refused and named -- a poller detaches, re-execs and runs for days while `radar` re-derives the path from wherever it is invoked, so the directory a relative entry resolves against is not the one it was typed in -- as are entries that are not directories and entries the `stat` could not perform, which are reported as two different facts rather than one.

  `unknown source` now names every directory it searched, with the sources each held, the reason each unsearched entry was refused, and, when nothing is configured, that `SUPERTOOL_WATCH_SOURCES_PATH` is unset. It used to print `Available: <shipped names>`, naming neither the directory those came from nor the directory the operator had just configured -- an absence that does not say where it looked, in the one message a user hits while setting the feature up.

  **This imports and executes Python from a caller-supplied path**, and `docs/presets/watch.md` says so rather than leaving it to be discovered: `poller.py` runs in the poller process with the caller's privileges, on a value that arrived from an environment variable or a JSON file in a repository, and nothing checks a signature, an owner or a mode. Nothing is pinned across the poller's re-exec and nothing needs to be: unlike the state directory and the socket (#1477/#1534) this value is not derived, and `transport.poller_env` is `dict(os.environ)` plus those two pins -- a property `tests/test_watch_sources_path_2135.py` asserts rather than assumes.
