- **Slack channel instruction-authorization: out-of-repo, default-closed, per-channel** ([#2035](https://github.com/Digital-Process-Tools/claude-supertool/issues/2035)). A message arriving through the `slack` watch source (#2031) is delivery; whether it may INSTRUCT the agent sitting in the session is a separate, security-bearing question this issue answers on purpose rather than letting it fall out of the poller by accident. `slack_authorization[:CHANNEL_ID[:USER_ID]]` resolves and prints the policy for a channel, read from `~/.config/supertool/slack_authorization.json` -- never a tracked `.supertool.json`, which can only narrow a channel's level, never widen one. Four levels: `off` (default, and the answer for any channel the config does not name -- absent means refuse), `context` (delivered, marked untrusted, nobody may instruct), `allowlist` (a pinned list of Slack `U...` user ids may instruct -- never a live Slack group lookup, per the issue's own "pin the group, then diff it" rule), and `open` (declared in the schema but refused rather than silently implemented in this build -- a level nobody built the eligibility check for fails the whole channel closed, not open). **Scoped down from the issue's full design**: this ships the authorization decision engine and its runtime-visibility op; it does not yet gate `presets/watch/sources/slack/poller.py`'s delivery path, which still delivers every message unchanged from #2031 regardless of what the config says. See `docs/configuration.md#configuration-that-grants-execution-must-not-be-repo-tracked` and `docs/presets/slack.md`.
