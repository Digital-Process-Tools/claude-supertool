- **`radar`'s `gh-prs` tier now spawns and heals a standing `gh-branch` poller for the resolved default branch** ([#2024](https://github.com/Digital-Process-Tools/claude-supertool/issues/2024)): `watch:gh-branch:<ref>` (#1953) closed the "no event when the default branch goes green" hole, but only for an operator who typed it, on one machine, until that process died -- there was no configure-once route, so the poller everyone actually wanted was the one nobody had running. The tier already resolves the ref for its own on-demand board row and already holds the `_watch` spawner it uses to keep `github-pr-feed` alive, so it now spawns the standing poller the same way, through `radar`'s own death cap and ledger. Subscribed to all five of `gh-branch`'s events, not just `went_green` -- a `gh` outage that could not even look now arrives as `branch_unreachable` rather than as silence, which is the same shape of bug this closes one layer down. `default_branch=""` still switches the row off and spawns nothing, honouring the operator's own call rather than overriding it. The poller's own health is a third, independent value alongside the board row's existing `(lines, could_tell)`, deliberately not folded into it: a red master reported by a perfectly healthy direct query stays a thing the tier could tell, regardless of whether the standing poller happens to be down. A dead, capped, unknown or blind poller is reported as a `WARNING` and costs `radar`'s own `healthy` verdict, so `quiet_when_healthy` cannot hide it. The kept-old-ref-after-a-rename hazard the issue raised explicitly -- `master` renamed to `main` with the old ref left alive, a stale poller on `master` emitting `went_green` forever, indistinguishable from a real one -- is answered by `other_branch_scopes`, which reads and names any such stray on the board as a `WARNING` (not merely a disclosed cost the way the feed's own duplicate-discovery strays are): it is loud, never suppressible by a quiet run, and names the exact scope to `unwatch`.
