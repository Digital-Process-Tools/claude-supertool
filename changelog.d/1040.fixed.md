- **`repo:OWNER/NAME` refuses a leading `-` in either half** ([#1040](https://github.com/Digital-Process-Tools/claude-supertool/issues/1040), [#1487](https://github.com/Digital-Process-Tools/claude-supertool/issues/1487)). The shape check validated only that the value held exactly one `/` with both halves non-empty, so `repo:-x/y` passed it and reached a shipped op as a POSITIONAL argv element to `gh` -- the slot where a `-`-prefixed token is read as a flag rather than a value. `gh` currently rejects the unknown flag, so this was loud and harmless, but the validator's own guarantee ("this shape is safe to use as an argv value") was borrowed from the callee's behaviour rather than checked. `_REPO_SEGMENT_RE` now requires the first character of every segment to be a letter, digit, `.` or `_`.

  Closed together with the identical leading-dash gap #1487 found independently while auditing `_repo_target_platform`: a project-defined op with a repo dimension used to resolve through `next(iter(found)) or None`, making it indistinguishable from "no repo-targetable op in this call at all". That state is now named explicitly (`"unknown"`) rather than silently collapsing into `None` -- the accepted shape for a project op is unchanged (there is no way to know which forge's stricter rule it wants), but the "could not classify" case is a checkable value instead of an accidental falsy fallthrough.
