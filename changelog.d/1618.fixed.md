- **`gh-branch` reported `did NOT run on this commit` for a workflow whose run the same listing returned three minutes later** ([#1618](https://github.com/Digital-Process-Tools/claude-supertool/issues/1618)). Hit at the v0.41.0 release gate, which is the caller this op exists for. GitHub created two runs on master's head `339d04d` at 16:19:44Z; at 16:31Z `gh run list --branch master --limit 60` returned neither, and at 16:34Z, unchanged head, it returned both. The `NO RUN` verdict itself held — it is its own state, it named the ~15min creation window and it said a run was still expected, which is why this cost nothing — but the block under it flattened the same absence into a fact: `tests — did NOT run on this commit`, with the hedge attached to the *reason* rather than to the fact. At a release gate the two readings take opposite actions: a genuine absence means the commit is uncovered, a listing that has not caught up means wait and re-ask.

  **The sentence now says what was observed.** `no run for it was RETURNED on this commit`, which is a different sentence from `ran and passed` and a different one again from `did not run`. When the listing returned no run at all on the head *and* the head is still inside the creation window, one more line says so outright and names the incident, so a reader can tell a query that has not caught up from a commit nothing covers. Past the window the extra line stops: a commit with no runs is then an ordinary, legitimate state, and a hedge printed forever is a disclosure that gets tuned out.

  **The previous head was named from list position, and that was a second defect on the same line.** `previous_head` took the first entry with a different SHA — the newest one only if GitHub hands the list back in descending order. It does not always: the incident named `d7e67ee` as master's previous head, a commit 527 commits and 17 days behind, carrying one run, which a newest-60 window on that branch cannot contain. So the flat sentence was wrong about *which* commit it was comparing against as well as about the absence. Selection is now by `createdAt`, tie-broken by run id, falling back to list position only when no entry carries a readable timestamp. `dashboard` and `watch`'s `gh-prs` tier call the same helper and get the same fix.

  **The gap is stated, because 23 seconds and 17 days are not the same news.** When the disclosure fires it also prints how far the newest run anywhere in the listing predates the head commit. A listing seconds behind has plainly not caught up yet; one 17 days behind answered about a different slice of history, and a reader shown only `zero workflow runs` cannot tell those apart.
