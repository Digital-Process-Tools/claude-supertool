- **`replace` no longer double-applies silently when its own re-run finds the anchor still there** ([#938](https://github.com/Digital-Process-Tools/claude-supertool/issues/938)). `edit` already disclosed this in #701: a payload whose `new` embeds its own `old` keeps the anchor alive, so re-running it — a plausible operator move, since the per-op result prints above a long validators block (#621) — applies the edit a second time. `batch:@payload` with an `op = "edit"` entry already inherited that fix, since it routes the sub-op through the same `op_edit`; confirmed with a regression test. `replace` did not: two runs of an identical payload printed byte-identical receipts (`(1 replacements in 1 files)`, `[result] 1 op run, 1 write`) while the file gained a second copy of the inserted text. `op_replace` now runs the same positional containment check `op_edit` uses, per file, against the pre-write content, and bumps the shared `K re-applied` counter -- the footer reads `[result] 1 op run, 1 write, 1 re-applied`, and the per-file receipt line gains a `[N re-applied]` tag plus a `re-applied:` disclosure, matching `edit`'s posture exactly: disclose, never refuse, so a genuinely-intended second application (appending a repeated element) stays expressible. `vim`'s substitutions are regex-driven rather than anchored and are not covered by this fix -- confirmed to share the same silent double-apply and filed separately, since "the old text is contained in the new" has no settled meaning once `old` is a pattern rather than literal text.
