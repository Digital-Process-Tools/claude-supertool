- **`gh-issue` wrote attachments into a fixed world-writable `/tmp` path, and joined an API-supplied number onto it with no check at all** ([#1506](https://github.com/Digital-Process-Tools/claude-supertool/issues/1506)). Two defects in one file, and they are [#1493](https://github.com/Digital-Process-Tools/claude-supertool/issues/1493) and [#1484](https://github.com/Digital-Process-Tools/claude-supertool/issues/1484) one forge over, both already fixed for `gl-issue`. `IMAGE_DIR` was the literal `/tmp/supertool-images/gh` — a fixed name any local user can take first, as a directory of their own or as a symlink pointing anywhere, and a POSIX literal that anchors to the current drive on Windows. And `os.path.join(IMAGE_DIR, issue_number)` took `number` straight out of the `gh issue view --json` reply: no numeric check, and no containment check anywhere in the module. `_local_path` sanitizes the basename, so the *directory* component was whatever the remote said. An absolute number makes `os.path.join` discard the root outright; `../x` resolved outside it. Precondition class is #1484's: a hostile or compromised host on the other end of the API call, since `number` is server-assigned.

  Three checks now, and their order is most of the fix. A non-numeric number is refused **before the root is created** — a directory created is already a write and no later guard un-creates it, so the traversing and absolute cases leave nothing on disk at all, not even the root. Then the root is established by `_image_root.ensure(default_root("-gh"))`: `gettempdir()` plus a per-uid suffix, created non-recursively at `0700`, held open `O_RDONLY | O_DIRECTORY | O_NOFOLLOW` with the `fchmod`, the ownership check and the mode check asked of that one descriptor. Then every leaf is checked against **that root**, never against the derived per-issue directory — anchoring a check to the value it is meant to constrain was #1484.

  **The root is a sibling of `gl-issue`'s, not a child.** `supertool-images-<uid>-gh` beside `supertool-images-<uid>`, so each is established in its own right and neither depends on the other having been created first.

  `_is_inside` moved to `_image_root.is_inside` rather than being copied. Two forge presets asking the same containment question against a root the same module hands out is two chances for one copy to drift; `presets/gitlab/issue.py._is_inside` keeps its name and delegates.

  **The eight `#817` cases that asserted a refused image leaves no directory now assert it leaves no *per-issue* directory, and that is a re-aiming rather than a relaxation.** The property somebody paid for is that a refused issue leaves no record it was ever read, and `_http.download` still makes the destination's parent only after the body has passed the destination policy and the byte cap — so `<root>/<number>/` is still absent. The root is not a record of anything: it is per-user, says nothing about which issue was fetched, and after any one successful call it exists for the life of the temp directory, so "the root is absent after a refusal" only ever held on the first call a machine ever made. It is also the boundary those destinations are checked *against*, and a boundary that does not exist yet cannot be proven to be ours — which is the whole of #1493.

  **The two seams the issue named were both declined.** Hoisting the destination decision out of `download` duplicates a security check. Adding a `prepare` callback to `download` puts a new refusal grade and a caller-supplied predicate into a module four other presets import, for its one caller, to buy a property that decomposes instead.

  **A destination refusal is a refusal, and it still produces one `ImageResult` per URL.** A root that cannot be established, or a leaf that does not resolve inside it, is graded `refused` with the reason — not dropped, and not shortened out of the list, because a URL that vanishes reads as an issue that did not have that image. The `## Images` footer now says whether the URL or the destination on this machine was refused, instead of advising every refusal be answered by widening the allowlist.

  A number carrying a bare CR is flattened through `_untrusted.flat` before it is printed, so the value cannot overwrite the line printed about it — the same rule the refused URLs on the lines below already followed.

  **Windows.** The old value was a POSIX literal anchored to the current drive; `gettempdir()` resolves inside the user profile there, which is not the shared directory the finding rests on. The `O_NOFOLLOW` branch is absent, so `_image_root` uses `os.lstat` and refuses a symlink or a reparse point, and the ownership and mode arms are *skipped* rather than faked. Those claims are inherited from #1493 and are **reasoned from CPython's documented behaviour, not observed on a Windows host**. The new tests carry no POSIX path literals: the traversal is built from `os.pardir`, paths are compared as `Path` objects, and the mode assertion is gated on `hasattr(os, "geteuid")` rather than passing vacuously.
