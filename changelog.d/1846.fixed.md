- **Every `gh` and `glab` error classifier now matches an auth *status* rather than the three characters `401`, so a throttle stops printing `gh auth login`** ([#1846](https://github.com/Digital-Process-Tools/claude-supertool/issues/1846)). [#1823](https://github.com/Digital-Process-Tools/claude-supertool/issues/1823) fixed two radar tiers. The identical predicate was still in **23 more call sites** — 16 under `presets/github/`, 7 under `presets/gitlab/`, one file carrying two — and five of them widened it again with a bare `"token" in s`.

  **The reported population was wrong in both directions, and the count is derived rather than quoted.** The filing listed 10 GitHub files and 7 GitLab ones. `presets/github/` actually holds 16 sites in 15 files: the five it missed are `batch_follow.py`, `batch_star.py`, `check.py`, `job.py` and `starred.py`, and the `"token"` half was 5 sites rather than 3 (`check.py` and `job.py` again). The GitLab list was exact.

  **All 23 sites were checked for reachability before being changed, and all 23 were live.** The check that settles it is the arm order, because a broad phrase fenced by an arm above it is not a defect. At every one of these sites the auth arm sits **above** the rate-limit and permission arms, so nothing fences it: `HTTP 403: API rate limit exceeded for user ID 44012345` matched `401` inside the user id and never reached the `rate limit` arm two lines down. The reproduction is the test — the negative assertion was red at 23 of 23 sites before the change and green at 23 after, with the positive control green throughout.

  **The GitLab mechanism is not a request id, it is the request URL.** go-gitlab puts the URL it called into every error string it constructs, so any project, job or pipeline id containing those three digits made a `500` or a `429` render as a missing credential — which needs no exotic input, only an id.

  **`"token" in s` becomes nothing, and that is the fix.** GitHub's own scope error is `Resource not accessible by personal access token`: a 403 about permissions that reached the credential arm and left the permission arm below it unreachable. The precise markers (`bad token`, `token expired`) already cover the credential readings, so the phrase had no work left to do; it now falls through to the arm that says "check repo access".

  **The predicate moved from `presets/watch/tiers/_auth_probe.py` to `presets/_auth_probe.py`.** None of the 23 sites can reach a module nested under `watch/`; they import `presets/_*.py` through the `sys.path` insert every preset script already does. Moving a module merged two hours earlier cost two `_load` call sites and one line of prose; the alternative was a second copy under `presets/`, which is precisely the drift the module was created to prevent, on its first day. The GitLab vocabulary (`unauthenticated`, the `authenticate` stem) is passed in as `extra` rather than folded into the shared tuple, so a GitLab phrase cannot silently widen the GitHub sites or the radar tiers — still one copy of it, where seven files previously had seven.

  **The positive controls are the test, and there is a population pin.** An assertion that a remedy is absent passes on a classifier that returns nothing, so every "must not say it" case is paired at the same site with a "must still say it" case; the pairs ran through the real functions, with `subprocess.run` faked, rather than through a re-implementation of the chain. The structural pin from #1823 now covers `GITLAB_MARKERS` too, and a new sweep test refuses any `"401" in` or `"token" in` in `presets/github/` or `presets/gitlab/` — because a seventeenth file growing its own copy is exactly how this came back the first time.
