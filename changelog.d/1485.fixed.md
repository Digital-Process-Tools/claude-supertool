- **The GitLab error relays let the server choose which line its text landed on** ([#1485](https://github.com/Digital-Process-Tools/claude-supertool/issues/1485)). `glab` echoes the GitLab API's own error body on stderr, and six renders in `presets/gitlab/` printed it into a line at column 0 with no `_untrusted.flat` — `gl-issue`, `gl-mr`, `gl-pipeline`, `gl-job`, `gl-runners` and `gl-issue-create`. `_untrusted.split_lines` cuts on LF/CR/CRLF alone by design, so a U+2028 survives *inside* what the render treats as one line and puts everything after it back at column 0 for any consumer that splits the way `str.splitlines()` does — ahead of the `[result]` a caller reads as the verdict. Same mechanism as [#1470](https://github.com/Digital-Process-Tools/claude-supertool/issues/1470), one forge over.

  `gl-api`'s `classify_error` was already correct and is the shape the six adopted rather than a seventh invention. Three more sites in the same subsystem went with them: `gl-mrs`'s list-failure relay, which reaches a receipt because the core appends a failing preset's stderr to it, and `gl-mr`'s `_glab_fail_detail` and merge-tree detail line, where `str.splitlines()` already stopped U+2028 but nothing removed an ESC — a relayed `ESC [2K ESC [1A` deletes the line above it.

  Disclosed, not stripped. Every test asserts on what a `[result]` consumer counts and on the separator having reached the render at all, never on `flat` having been called: a site can call it and print the raw value anyway, and a render that dropped the text would otherwise pass for the wrong reason.
