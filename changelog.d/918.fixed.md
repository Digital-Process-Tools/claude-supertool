- **`CHANGELOG.md`'s link refs are audited on every pull request, and the two releases that shipped without one are backfilled** ([#918](https://github.com/Digital-Process-Tools/claude-supertool/issues/918)). `## [0.24.0]` and `## [0.25.0]` had no link-reference definition, so both rendered as literal bracketed text rather than as links to the release, and `[Unreleased]` had twice been left comparing from a tag two releases behind — a link that resolves, returns a real diff, and shows shipped work as pending. The assembler has written one definition per cut since #906, which keeps the *next* release honest and says nothing about the state it inherited, so `--check-links` now reads the whole table and `.github/workflows/changelog.yml` runs it repo-wide on every PR: the run that finds the refs stale must not be the run cutting the tag.
- **A version that was never tagged is declared, not guessed at.** `0.11.0` and `0.14.0`–`0.19.0` have sections in the file and no tag anywhere, and a `releases/tag/vX.Y.Z` invented for one is a 404 that renders as a working link — `[0.11.0]` already carried exactly that and is now removed rather than left resolving to nothing. Those versions are listed in `UNTAGGED_RELEASES`, the list is audited itself (a declared version that *has* a definition, or that is not in the file at all, is a finding), and nothing from 0.20.0 on may be added to it, so the third state cannot become a place a real regression is filed away.
- **The changelog is now pinned to the version that ships.** `plugin.json` and `pyproject.toml` were already tied to `supertool.VERSION`; the newest `## [x.y.z]` section was tied to nothing, so a release could bump three of its four files and describe a different version in the one users read.
