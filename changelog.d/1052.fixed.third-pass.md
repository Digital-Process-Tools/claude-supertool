- **A filtered read that matched and then hit the byte cap never said the rest of the file was unread, and every `grep=` note arrived below the content it qualified** ([#1052](https://github.com/Digital-Process-Tools/claude-supertool/issues/1052)). Two review findings on the fix above.

  The three-state zero was guarded on the scan *not* having been truncated, so the combination that matters most — a large file, matches found, output stopped at the 20 KB cap — fell through to the older wording: `truncated at 20000 bytes — showed lines 1-92 of 400 (308 more lines)`. The byte cap breaks the scan loop, not just the emission, so those 308 lines were never looked at; `(308 more lines)` can only be read as 308 lines that did not match. That is the same absence-read-as-presence this issue was filed to remove, left standing in exactly the case where the file is big enough for it to cost something. The capped scan now names the cap, the range it did search, the count it did not, and where to resume.

  All of these notes are also now rendered directly under the count header rather than appended after the matches, which is where the same disclosure for windowed reads has been since [#955](https://github.com/Digital-Process-Tools/claude-supertool/pull/955): a correction that arrives after the reader has already paid for the wrong window is barely a correction.
