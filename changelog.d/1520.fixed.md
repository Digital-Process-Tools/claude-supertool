- **`lsp-diag` parsed a shape the server chooses, and each arm disclosed the opposite of what it did** ([#1520](https://github.com/Digital-Process-Tools/claude-supertool/issues/1520)). Three instances of one class, from the v0.38.0 release audits.

  [#1500](https://github.com/Digital-Process-Tools/claude-supertool/issues/1500) bounded the parse to the first segment of a physical line, where a segment ends at one of the five *inline* breaks. LF is not one of them by construction — it is the framing character — so a server message carrying an LF was still split into physical lines and every line after the first was read as a fresh diagnostic at a location the message chose. Where the server marks its list, an unmarked line is now a continuation of the entry above it rather than an entry of its own. The framing is decided from the *first* framed line and never from any line: a bulletless document can contain an echoed `*` in its source, and letting that flip the answer would turn every real finding into a continuation.

  A non-empty line matching neither pattern used to fall off the end of the loop body, taking its already-computed remainder with it — and the whole-text fallback runs only when *nothing* matched, so with any other line holding a record both halves left no trace anywhere in the receipt. `remainder_note`'s own docstring said "Not dropped". It is kept and labelled now, like every other fragment.

  `_REMAINDER_MAX` capped each fragment and its comment stated the invariant "a record must not grow without bound", but nothing capped how many fragments one `msg` collected. A file whose echoed source carries an inline break on hundreds of physical lines grew a single record past 100kB. The aggregate is bounded, the ceiling on any one `msg` is applied last so it is a property of the receipt, and what is over it is reported as a number rather than being silently absent.
