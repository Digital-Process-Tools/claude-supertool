- **`presets/github/job.py`'s own em-dash literals -- already covered by #1388's cross-platform stdout fix -- now carry a behavioral regression test against the codepage that actually crashes on them** ([#2256](https://github.com/Digital-Process-Tools/claude-supertool/issues/2256)). The issue named cp1252 as the crashing codepage; it is not: cp1252 has an em dash at byte `0x97` and encodes it without error. This repo's own `tests/test_encoding_seam.py` already documents the split -- cp1252 raises only on the arrow/star/hook glyphs, while cp437/cp850 (this repo's own stated "actual default of a US Windows console") have no em-dash mapping at all and raise on every one of `job.py`'s ~122 sites. `job.py`'s `main()` already calls `use_utf8_stdout()` as its first statement (added by #1388, before this issue was filed), which reconfigures the stream to UTF-8 and prevents the crash class entirely, regardless of which non-ASCII character is printed. No production code changed. `tests/test_gh_job_em_dash_cp437_2256.py` adds a real `cp437`-encoded `io.TextIOWrapper` behavioral check on the two sites #2256 named (the download-cap-exceeded `ERROR` branch and #2248's size-unknown `NOTE` branch), confirmed red with `use_utf8_stdout()` removed (`UnicodeEncodeError: 'charmap' codec can't encode character '—'`) and green with it restored -- so a future regression in that call, or a new print added ahead of it, is caught here rather than only by the structural AST scan in `test_encoding_seam.py`.
