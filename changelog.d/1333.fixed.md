- **A crashing `stop.py` reported its traceback as terminal escape sequences, and the 500-character budget was spent on them** ([#1333](https://github.com/Digital-Process-Tools/claude-supertool/issues/1333)). `_mcp_stop_server` captures the child's stderr into `_StopOutcome.detail`, which is printed for a human under `SUPERTOOL_DEBUG`. CPython colourises its own tracebacks from 3.13 on, and `_colorize` consults `FORCE_COLOR` **before** it asks whether the stream is a tty — so a parent with that variable set gets an escape-laden traceback out of a child whose stderr is a pipe. `detail` is now stripped of CSI, OSC and two-character escapes, before the cap rather than after: the cap keeps the *last* 500 characters, and every escape byte was budget spent on something that renders as nothing, so a long enough coloured traceback evicted the exception line — the only part worth keeping.

  The second of this issue's two permanent local reds, and it is a product defect rather than the environment limit the acceptance assumed. The standing hypothesis was the local interpreter (CPython 3.14.6, outside CI's 3.9-3.12). Half right: the trigger is two conditions, ≥3.13 **and** `FORCE_COLOR` in the environment, and this repo's own agent harness exports `FORCE_COLOR=3`. So skipping with a stated reason would have buried a real defect that CI's Python range happens to hide — every 3.13+ user in a coloured terminal reads escape sequences out of that debug line today.

  With this and [#1499](https://github.com/Digital-Process-Tools/claude-supertool/issues/1499) fixed, a local full-suite run carries no known permanent reds. What the count still cannot tell you is whether the tree has accumulated a new one from a stale artefact git does not see, and nothing here makes that class legible rather than remembered.
