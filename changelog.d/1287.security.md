- **Preset ops sat outside the core's path chokepoint entirely, and the next one written reproduced that by default** ([#1287](https://github.com/Digital-Process-Tools/claude-supertool/issues/1287)). `_PATH_ARG_POSITIONS` is the core's per-op table of which argument is a path, gating every builtin since [#146](https://github.com/Digital-Process-Tools/claude-supertool/issues/146). **No preset op was ever in it.** So a preset op with a path argument enforced containment itself or not at all, and "not at all" was the default for anything newly written. [#1283](https://github.com/Digital-Process-Tools/claude-supertool/issues/1283) — `claims:/etc/hosts` reading the file in the same call that `read:/etc/hosts` refused it — was one instance, fixed inside that op, and nothing about the fix made the next preset op safe.

  Every preset and custom op now passes through one gate in `_resolve_custom_op`, above the subprocess. What the core cannot supply is the **boundary**: `claims` resolves a relative argument against the repository root, so imposing the core's cwd would refuse `claims:docs/x.md` run from `docs/` — a call that works today and should. So the op declares both and the core enforces both:

  ```
  "paths": { "args": [1], "root": "repo" }
  ```

  `args` are argument positions counting the op name as `0`; `root` is `"cwd"` (the core's boundary) or `"repo"` (the repository root). `"args": []` declares that no argument here is a filesystem path — `gl-api:PATH` is an API route, and that is now a claim someone made rather than a default nobody noticed.

  **An op whose `syntax` names a path and declares nothing is refused**, not skipped. A path argument that reaches no check is not a check that could not run; it is an unchecked read, and it renders identically to a checked one.

  Four ops declare today: `claims` (`repo`, the boundary [#1283](https://github.com/Digital-Process-Tools/claude-supertool/issues/1283) established) and `xml` / `xml_attr` / `xml_count` (`cwd`, which closes a real hole — `xml:/etc/passwd:...` parsed and reported on the file). **Twenty of the twenty-four shipped ops that name a path are grandfathered by name** in `_UNDECLARED_PATH_OPS`, because refusing them in the release that introduced the rule would break every one of them. That set only shrinks, and `tests/test_preset_path_chokepoint_1287.py` goes red if a name is added to it or if a new op with a path argument skips the declaration — which is the point: a convention a careful author misses on the day they read it is not a convention, it is a trap, and this one now fails the build instead.

  Several of the twenty cannot be expressed as an argument position at all — the publish ops carry their file inside a `|`-separated blob, `git-commit` takes a `:::`-separated tail, `git-resolve` a comma list. Draining that register is per-op work and is filed, not done here.

  A declaration the core cannot honour is refused rather than ignored. `{"args": [-1]}` — a plausible spelling of "the last argument" — passed the shape check in the first cut of this change and was then silently dropped by the range filter, so the op ran completely unchecked while looking exactly like a gated one. That is this repo's standing defect, an absence produced by the tool read as an absence in the world, reintroduced inside the fix for it; found in review and pinned. Negative indices are refused because `parts[-1]` on a bare call is the op name, so the core cannot resolve the slot the author meant.

  The core's opt-outs (`SUPERTOOL_ALLOW_OUTSIDE_CWD=1`, `"allow_outside_cwd": true`) are honoured at **every** boundary and the refusal names them. `_safe_path` grew a `root` parameter rather than a repo-root twin: [#882](https://github.com/Digital-Process-Tools/claude-supertool/issues/882) and [#889](https://github.com/Digital-Process-Tools/claude-supertool/issues/889) are what a second copy of this rule costs. `presets/claims/check.py` keeps its own check underneath as defence in depth, since the script is also runnable directly.

  **A correction to the write-up, not only to the code.** The maintainer skill's containment section said read-side containment has one universal boundary and one chokepoint, and that only write-side needs a domain-specific one. That half was wrong, and [#1283](https://github.com/Digital-Process-Tools/claude-supertool/issues/1283)'s agent said so from a call that would break. The chokepoint is universal; the boundary never was.
