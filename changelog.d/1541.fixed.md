- **The watch channel name no longer ships in `.mcp.json`.** That file is the *plugin's* — its `args` use `${CLAUDE_PLUGIN_ROOT}` and `channel:health` reads it at the plugin root — so a name true of exactly one checkout reconfigured every install: their consumer bound `/tmp/supertool-watch-oss-supertool.sock` while their own pollers bound the default, the half-configured state `presets/watch/README.md` calls worse than setting neither. The name is workspace state and now has one home, this clone's `.supertool.json`, which `bin/supertool-workspace` reads and exports before launching. Measured against claude 2.1.219: a stdio MCP server the harness spawns inherits the launching process's environment, which is what carries it to the consumer (#1541).
- **`channel:health` no longer reports a consumer that declares nothing as a consumer on another channel.** With the name arriving by inheritance, an `.mcp.json` naming no channel variable says nothing about where the consumer bound — and this process cannot read the environment the session was launched with. It is now the third state, naming what it could not establish, instead of a flat "nothing a poller emits here reaches it" printed under a `FORWARDING` verdict that contradicts it (#1541).
- **`bin/supertool-workspace` says when it does not append its own prompt.** `claude` reads only its first positional as the prompt and silently ignores later ones, and a variadic option such as `--add-dir` swallows whatever follows it — so `... "$@" "/opensource-manager"` delivered the prompt only when there were no arguments, and dropped it in silence otherwise. It is appended when there is nothing else to pass, and otherwise the argv is left exactly as given and the omission is stated on stderr (#1541).
- **The launcher's shipped mode is checked in git's index, not in the checkout.** `st_mode & S_IXUSR` is a fact about the runner's filesystem, and NTFS has no execute bit, so it reddened all four `windows-latest` legs at `mode 0o100666` while the committed `100755` was correct. `git ls-files -s` answers the question that was meant on every platform, so the check is not skipped anywhere (#1541).
- **`assert_change_is_findable` no longer accepts a number found inside a longer number.** `1541` occurs inside `154177` in `CHANGELOG.md`, so the guard passed for a module whose change was documented nowhere. Exactly one call site depended on the loose match — that one (#1541).
