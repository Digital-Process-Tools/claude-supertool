- **`tests/test_op_workspace.py` failed ~10 of its 16 tests on one full-suite run and passed on the next, and passed in isolation either way** ([#1030](https://github.com/Digital-Process-Tools/claude-supertool/issues/1030)). `_load_config()` parses the optional `mcp` block into the module-level `_mcp_specs` dict **in place**, and nothing ever cleared it. `tests/conftest.py` hands every test `_CONFIG = {}` and restores `_CONFIG`, `_CONFIG_CHECKED` and `_CONFIG_PATH` around it, but `_mcp_specs` — derived from exactly that config — was not in `RESET_GLOBALS`, so one test that forces a real config load left this repository's own `py-lsp` spec (`match: "*.py"`, tools `refs`/`diag`) in the table for the rest of that xdist worker's life. `tests/test_at_file_route.py::TestPayloadRoutePin` is that test, legitimately: it chdirs to the repo root and rebuilds the `@payload` registry, which is the only way to pin the shipped routes. Ten of the sixteen `op_workspace` tests drive a `.py` file, so every one of them then routed References and Diagnostics to an LSP no test had configured. `--dist load` decides run by run whether the leaker and the victims share a worker, which is the whole of the intermittency — nothing about the file itself is order-sensitive. Reproduced deterministically as `pytest -n0 tests/test_at_file_route.py::TestPayloadRoutePin tests/test_op_workspace.py`: 10 failed, 7 passed.

  **The guard that exists to catch precisely this could not see it.** `test_every_mutable_global_in_supertool_py_is_reset_or_deliberately_exempt` ([#397](https://github.com/Digital-Process-Tools/claude-supertool/issues/397)) selected candidates with `name == name.upper()`, so the one lowercase mutable global in `supertool.py` was never a candidate: the assertion passed on an empty difference and read as "every mutable global is accounted for" while the only unaccounted one was structurally invisible to it. Case is not the contract, mutability is; the filter is `not name.startswith("__")` now, and `_mcp_specs` is per-run scratch like the other config-derived state.

  **A second, product-side defect on the same code path.** `op_workspace`'s References renderer split each hit with `str.index(":")` twice, which is safe only for the heuristic grep path that produces `file:line:content` by construction. An MCP `refs` server answers in its own shape — cclsp, the server this repository's own `.supertool.json` routes `*.py` to, leads with a prose header and bullet lines — so the first line carries one colon and no second one and `ValueError` escaped `op_workspace` entirely, reaching the user as `ERROR: argument parsing: substring not found`, which names neither the argument nor the problem. That is what turned the leak from a wrong References section into ten hard errors. A line that is not `file:line:content` is now rendered as the server wrote it: dropping it would trade a loud failure for a quiet one, and inventing a line number for it would be worse than either. Reachable in production by anyone who configures `mcp.tools.refs`, independently of the test leak.
