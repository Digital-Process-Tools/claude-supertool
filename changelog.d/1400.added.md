- **`help:OP` prints the `@-` payload route and the field names it derives** ([#1400](https://github.com/Digital-Process-Tools/claude-supertool/issues/1400)). `help:paste` printed `paste:::PATH:::CONTENT` and stopped, so the payload route every multi-line write needs was discoverable only by guessing — an implementation agent used it and reported that it had guessed `path` and `content`. An entry listing one of two invocation forms is worse than one listing neither, because it reads as complete.

  The block is rendered from the two registries that grant the route, never typed beside them: the `:::` field names are derived from the very `syntax` string printed above it (`_fields_from_syntax`, [#770](https://github.com/Digital-Process-Tools/claude-supertool/issues/770)), and the read ops take theirs from `_READ_OP_AT_FIELDS`. So `edit`, `replace`, `replace_dry`, `replace_lines`, `paste`, `append`, `vim`, every preset op with a `:::` syntax, and `read`/`grep`/`grep_around`/`around`/`between`/`validate` all gained it at once, and a syntax reword that silently deletes a route now deletes the documentation with it instead of leaving prose describing a route that is gone.

  An op with no payload route prints no block. That silence is now an answer rather than a gap, because every op that has one prints.
