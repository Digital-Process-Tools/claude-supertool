- **`node --check`'s line number was published under a different definition of "line"** ([#1507](https://github.com/Digital-Process-Tools/claude-supertool/issues/1507)). V8 treats U+2028 and U+2029 as ECMAScript LineTerminators; `split_lines`, `source_context` and a reader's editor do not ([#1486](https://github.com/Digital-Process-Tools/claude-supertool/issues/1486)). So one U+2028 inside a string literal — legal since ES2019, ordinary in a minified bundle — shifted every line number after it, and the shift was in the gift of the file under validation. Measured on node v22.22.1: a two-line file whose first line held one had its line-2 syntax error published as **line 3**, with `source_context` rendering lines 1-2 and the arrow on neither. `node-check` and `html-check` now map the reported number back through `linebreaks.lf_line_of_v8_line`, and a number no counting of the file can reach is published as `line: null` with the number disclosed in the message rather than as a location the file does not have.

  `html-check` reached it through its own arithmetic: a block is padded with LF so node's numbers already are the page's, which holds exactly until the body carries one of the two. The page's line 4 was published as line 5. It maps against the exact text node read, so nothing depends on the temp file outliving the check.

- **The forge #1507 was filed about turned out to be unreachable, and that is now pinned rather than asserted** ([#1507](https://github.com/Digital-Process-Tools/claude-supertool/issues/1507)). The shared `LOCATION` pattern really does mis-capture across an inline break — `"real.js:12<U+2028>forged.js:99"` yields `("real.js:12<U+2028>forged.js", "99")`, [#1500](https://github.com/Digital-Process-Tools/claude-supertool/issues/1500)'s shape in two more adapters. What neutralises it is not the pattern but `diagnostic_line`, which compares the captured path's `normcase(realpath(...))` against the target's: a capture carrying a break and a second path cannot resolve to the file, so the forged number is discarded with it and `finditer` walks on to node's own header, which is the first physical line of the report and cannot have anything printed before it. Nothing is lost either — the genuine location is still matched, so this is not the "rejected, and the finding lands unattributed" outcome the issue's third branch describes. Tests pin the mitigation for both adapters and all five separators, so a later rewrite to a basename or suffix match cannot quietly re-open it, and pin the residual in the safe direction: where a fragment does reach a capture, the number is **lost**, never forged.
