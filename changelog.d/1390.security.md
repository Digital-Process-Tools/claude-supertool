- **`SUPERTOOL_PYTHON` was a silent off-switch for the raw-command guard, and the hook no longer reads it** ([#1390](https://github.com/Digital-Process-Tools/claude-supertool/issues/1390)). `hooks/pre-bash-guard.sh` put the variable at the head of its interpreter ladder and `exec`d the first candidate that survived `-c pass`. Every binary that exits 0 survives that, so `SUPERTOOL_PYTHON=/usr/bin/true` produced rc 0, no stdout and no disclosure — the gate off, from one environment variable, which is exactly the hatch `guard_command`'s own docstring says was refused on purpose. `/bin/echo` was worse: its output landed in the slot the hook's JSON verdict occupies.

  Three things changed. A candidate must now identify itself as a Python 3 rather than merely exit 0. `SUPERTOOL_PYTHON` does not participate in this ladder at all — it exists for supertool's own op subprocesses, and a gate deciding whether a command may run is a different trust context; `VIRTUAL_ENV` stays because on some hosts it is the only interpreter there is, and is required to look like a venv (`pyvenv.cfg`) rather than merely to be set. That narrows the exec-before-every-Bash-call primitive rather than closing it, and the wrapper says so in a comment instead of implying otherwise: the ladder cannot be made environment-free, because `PATH` is an environment variable too.

  Third, **"could not run" is now reachable when a candidate ran and produced nothing.** Previously only an empty ladder disclosed, so an interpreter that started and said nothing rendered byte-identically to a clean verdict — the three-state contract present in `guard_command`, present in `pre_bash_guard.py`, and lost at the shell layer under both. `pre_bash_guard.py` therefore writes an envelope on every path, including the one where nothing is replaced, so silence from the interpreter is now a fact the wrapper can act on.
