- **The GitHub error relays let the server choose which line its text landed on** ([#1606](https://github.com/Digital-Process-Tools/claude-supertool/issues/1606)). `gh` echoes the GitHub API's own error body on stderr, and five renders in `presets/github/` printed it into a line at column 0 with no `_untrusted.flat` — `gh-issue`, `gh-job`, `gh-run`, `gh-prs` and `gh-issue-create`. `_untrusted.split_lines` cuts on LF/CR/CRLF alone by design, so a U+2028 survives inside what the render treats as one line and puts everything after it back at column 0 for any consumer that splits the way `str.splitlines()` does. Every one of the five renders **above** the trailer the core appends, so a forged `[result]` sorts first at all of them — the answer does not differ per site. `presets/github/pr.py` was already correct ([#1475](https://github.com/Digital-Process-Tools/claude-supertool/issues/1475)) and is the shape the five adopted; this is the GitHub half of what [#1485](https://github.com/Digital-Process-Tools/claude-supertool/issues/1485) did for GitLab, predicted by the [#628](https://github.com/Digital-Process-Tools/claude-supertool/issues/628) parity survey.

  `gh-issue-create` did not import `_untrusted` at all, and relays `stderr or stdout` — both arms, so the fallback is a second relay and a fix that only covered stderr would have left it raw.

  **Ten more sites in the same directory went with them, found by sweeping for the shape rather than by reading the filed table**: `gh-labels` and `gh-branch`'s `_format_error` terminal arms, both `gh-issues` relays (its repo lookup and its list failure), `gh-check` (flattened once in `GhCall`'s constructor, which covers all three prints that render `.error` plus the not-found probe's), `gh-pr-create`, and `gh-following`, `gh-starred`, `gh-find-followable` and `gh-find-starable` — the last four the sharpest, since [#981](https://github.com/Digital-Process-Tools/claude-supertool/issues/981) flattened every login, repository name and description those files render and walked past the error relay a few lines above them. In the two `find-*` ops the relay is sliced to 200 characters, and the flatten goes first: a cut made first leaves whatever the separator started ([#970](https://github.com/Digital-Process-Tools/claude-supertool/issues/970)), which is the ordering both files already spell out for a description twenty lines below. Fifteen sites, not five.

  `gh-pr-create` is the one where the harm is not hypothetical about a consumer's trailer: it prints the remote's body on the line directly **above** its own `[result] no PR created (...)`, so the forged verdict sorts above a real one this op wrote itself.

  **Named here rather than left silent, and fixed in [#1648](https://github.com/Digital-Process-Tools/claude-supertool/issues/1648)**: seven sites dumped an unparseable remote body verbatim — four spelled `ERROR: invalid JSON from gh` (`gh-run`, `gh-pr` twice, `gh-issue`) and three `ERROR: bad JSON` (`gh-following`, `gh-starred`, `gh-find-starable`) — which is a multi-line relay by design and wanted a fence rather than a flatten, and `gh-pr-merge`'s `_gh_json` took `str.splitlines()[-1]` of the remote's text — which selects the *forged* line rather than forging one, and landed in a merge gate. `presets/github/check.py`'s three `.error` prints, `gh-following`, `gh-starred`, `gh-find-followable` and `gh-find-starable` were all invisible to [#1475](https://github.com/Digital-Process-Tools/claude-supertool/issues/1475)'s per-file census, which counts `.stdout`/`.stderr` attribute reads reaching a sink and so sees neither a helper's `.error` field nor a `sys.stderr.write`.

  Disclosed, not stripped: the operator still reads the remote's sentence, with the separator spelled `[U+2028]` and a cursor command spelled `␛`. `tests/test_gh_error_relay_untrusted_1606.py` asserts on what a `[result]` consumer counts rather than on `_untrusted.flat` having been called, and asserts the separator reached the render — a site that dropped the text would otherwise pass for the wrong reason.
