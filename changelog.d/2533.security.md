- **YouTube preset no longer leaks the API key to stderr on a same-origin redirect** ([#2533](https://github.com/Digital-Process-Tools/claude-supertool/issues/2533)). `presets/youtube/_yt.py::get()` is the first `presets/_http.py::urlopen()` caller to put its credential in the request URL's query string (`query["key"] = api_key`) rather than in a header; every other credentialed client (bluesky, devto, hashnode) sends its secret as a header instead. `urlopen()`'s same-origin redirect disclosure prints both the requested and the answering URL to stderr on every followed hop — deliberately, so a silently-followed redirect is never mistaken for the call the caller actually asked for — but that NOTE fires on the success path, before any caller-level exception handler (`_yt._scrub`, which only runs from `RedirectRefused`/`ResponseTooLarge`/`DeadlineExceeded`/`HTTPError` handlers) ever gets a turn, so the key rode straight through it in plain text. `ResponseTooLarge`, `DeadlineExceeded`, `RedirectRefused` and `DestinationRefused` all carried the same raw URL into `self.args` (and, for the first two, into their `__str__` too) and relied on each caller's own handler to scrub it before printing — every one of the four now scrubs known credential-shaped query parameters (`key`, `api_key`, `apikey`, `access_token`, `token`, `secret`, `client_secret`, `password`, `auth`, `id_token`, `refresh_token`, `session_token`, `csrf_token` -- hyphenated spellings like `api-key` normalise to the same rule) out of the URL at construction, before `Exception.__init__` ever stores it, so `str(exc)`, `repr(exc)` and `exc.args` all read the redacted value. The redirect-NOTE print inside `urlopen()` itself took four rounds to land: redacting the query string and printing the result satisfied a human reader but not GitHub's default CodeQL setup, which flagged `py/clear-text-logging-sensitive-data` on that exact `print()` three times running — first against an inline redaction call, then against the same redaction hoisted into two named locals, then again against an inline `# codeql[...]` suppression comment, because this repo's default (non-advanced) CodeQL setup does not honour inline suppressions and because a caller-defined redaction function is not a sanitizer to CodeQL's dataflow model regardless of what it actually does. The fourth round stops redacting and instead builds the two disclosed strings from `urlsplit(...)`'s `scheme`/`netloc`/`path` components alone (`_origin_and_path()`), never reading `.query` at all — a structural break in the data-flow path from the query string (where the credential lives) to the print, rather than a better-worded redaction of it. The accepted trade-off: the redirect NOTE no longer discloses *any* query parameter on a followed redirect, secret-shaped or not, where every earlier round kept a non-secret one like `q=hello` visible. Self-review on this round found two gaps in `_origin_and_path()` itself: its malformed-URL fallback stripped only the query, not a credential-bearing fragment, and had no test of its own even though the sibling `_scrub_query_secrets()` fallback did -- both fixed, with a test covering each. It also found that a redirect changing only the query string (rotating a token, say) now makes the disclosed requested and final strings identical, since the query is the one part this function never reads -- the NOTE now names that case explicitly (`only the query string differed between them`) rather than printing what would otherwise read as a no-op bug report.
