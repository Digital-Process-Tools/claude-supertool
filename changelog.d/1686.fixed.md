- **A forged `$VIRTUAL_ENV/bin/python3` rung could assert `silent` and suppress a real `deny` from the interpreter further down `hooks/pre-bash-guard.sh`'s ladder, with zero trace in the transcript** ([#1686](https://github.com/Digital-Process-Tools/claude-supertool/issues/1686)). [#1625](https://github.com/Digital-Process-Tools/claude-supertool/issues/1625) closed the route where a rung asserted `allow`, but `silent` was left standing: it writes the bare `{"hookSpecificOutput":{"hookEventName":"PreToolUse"}}` envelope, which is bit-identical to the wrapper's own genuine no-op, so a fake `python3` never had to run `hooks/pre_bash_guard.py` at all -- it could print `supertool-guard-v1 silent`, exit 0, and end the ladder walk right there, before a real interpreter ever inspected the command. `silent` is no longer a word a rung may assert: `attempt` in `hooks/pre-bash-guard.sh` discards it exactly like output that does not match the wire protocol, and the walk continues to the next candidate. `hooks/pre_bash_guard.py`'s own "nothing to say" now crosses as `note` with an empty body instead of `silent`, so a genuinely clean command still gets no decision, but the wrapper never again writes an envelope a rung could claim for free without running anything. Self-review found the same bypass still open for a forged `silent` carrying a trailing `\r` -- `$(...)` strips only a trailing newline, so that variant slipped past the new match, reached `relay`, had its `\r` stripped there (the same tolerance `relay` already gives a legitimate `deny` on that platform), and came back out as the bare word `silent`, which `relay` declined -- but `decline` exits, so the ladder still stopped one rung early instead of continuing. The `attempt` match now covers the `\r`-suffixed form too.
