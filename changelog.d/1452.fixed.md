- **The example quoted three times as the reason the ambiguous help slot blocks does not block** ([#1452](https://github.com/Digital-Process-Tools/claude-supertool/issues/1452)). `git push --force -h` is `clean`: `--force` is an `unless_flag` of every `git push` entry, so all five are un-claimed before the help classifier is reached. The sentence shipped in `_guard_help_state`'s docstring, in `docs/contributing.md` and in the v0.36.0 changelog entry. The argument survives untouched and only the illustration was wrong — `git push origin -o -h main`, the other example in the same paragraph, does block and is the case the trade-off is actually about.

  `tests/test_guard_help_example_and_project_entries_1452.py` now extracts every command those three files call a wrong block and runs it against the guard, so the next example that stops matching the code fails a test rather than teaching a wrong fact.

- **`docs/contributing.md` now says that a `replaces` entry must not name a command whose `-h` is a real option.** The guard treats `-h` and `--help` as terminal for every entry in every registry, which is measured-correct for the shipped mappings — every one of them a `git` or a `gh` invocation, pinned by a test rather than by the entry count the paragraph used to carry — and wrong for `ls -h`, `du -h`, `sort -h` and `grep -h` — a `clean` verdict on a command that runs, reintroduced by configuration rather than by code. Not reachable in this tree, so this is a schema rule rather than a code change; the behaviour it warns about is pinned by a test, so the warning cannot come to describe a guard that does something else.
