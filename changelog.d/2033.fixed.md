- **`_git`/`_git_verbatim` no longer SIGKILL a stalled WRITE and strand `.git/index.lock`** ([#2033](https://github.com/Digital-Process-Tools/claude-supertool/issues/2033)): `presets/git/_git_common.py`'s shared chokepoint drove `subprocess.run(timeout=)`, whose `TimeoutExpired` arm is `Popen.kill()` -- SIGKILL, no grace -- before either function ever got a chance to react, so a stalled `git commit`/`checkout`/`merge`/`push`/`stash push` left `.git/index.lock` behind, wedging every later `git add`/`commit`/`checkout`/`stash` in that repository until a human deleted the file by hand. `--no-optional-locks` (#1945) fixed this for the read-only calls the same chokepoint also makes and said so in its own comment: it is a documented no-op on a write command. Both functions now drive `Popen` directly and, on `TimeoutExpired`, send SIGTERM, wait a bounded 2s grace, then SIGKILL only if the child is still alive -- the same `_stop()`-shaped arm `validators/git-status/git-status.py` already carries for its own git calls (#1882), including its lesson that a `communicate()` failure is a statement about the pipes, not about the child (#1888/#1912), so a broken pipe on the first read no longer skips the SIGTERM step. `TIMEOUT_RC = 124` and the `"timed out after {budget}s"` stderr are unchanged, so no caller of `_git`/`_git_verbatim` needs to change. On Windows, `terminate()` and `kill()` are the same call, so the grace period buys nothing there -- reasoned rather than separately observed for this file, by the same argument `validators/git-status/git-status.py::_stop` already makes and partially observed on CI.
