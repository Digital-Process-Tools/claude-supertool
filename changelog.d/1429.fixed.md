- **An operator's ambient `FORCE_COLOR` no longer reaches a spawned child, so a captured receipt (an error tail, a validator's stdout, `_mcp_stop_server`'s `detail`) never carries terminal control bytes** ([#1429](https://github.com/Digital-Process-Tools/claude-supertool/issues/1429)). CPython 3.13+ colourises its own tracebacks purely because `FORCE_COLOR` is set -- even when stderr is a pipe -- and this repo's own agent harness exports `FORCE_COLOR=3`, so any of the ~130 `subprocess.run`/`Popen` call sites across `_supertool.py` and the presets could hand back ANSI escapes baked into a rendered field. Fixed at the one choke point that actually reaches all of them: `_disable_force_color_for_children()` pops `FORCE_COLOR` and sets `NO_COLOR=1` on `os.environ` once, at import, before anything can spawn a child. Every call site that inherits its child's environment (the default, `env=None`) sees the scrubbed value directly; every one that builds an explicit `env=` does so by copying/merging `os.environ` first (`{**os.environ, ...}` or `os.environ.copy()`), so the merge already excludes it -- no per-call-site audit needed, and a declared preset's own `.supertool.json` `env:` block is applied after this merge and still wins for an operator who deliberately wants colour on one command. `_mcp_stop_server`'s existing strip-on-ingest (#1333) is unaffected and stays as defence in depth for anything spawned outside this process's own environ. No op deliberately requests colour today (`--color`/`FORCE_COLOR`/`NO_COLOR` do not appear in any op's own command construction), so nothing lost the option it was using.
