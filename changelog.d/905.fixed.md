- **Four printed remedies that hardcoded `./supertool` — wrong the moment they are read from a linked worktree, which is where this repo says agents work — now route through a new shared helper, `presets/_st_hint.py::st_hint`, that picks the invocation the environment it is running in can actually run** ([#905](https://github.com/Digital-Process-Tools/claude-supertool/issues/905)). The issue's own filed count was seven; measured on this tree, 71 line matches across 22 files, of which 63 remain — this fix routes the four sites the issue named (`_branch_locale.py`'s `MISMATCH` remedy, `_repo_target.py`'s two `no_repo_error` messages, three sites in `presets/gitlab/job.py`, four in `presets/github/check.py`) and leaves the rest as tracked debt rather than doubling the diff into modules #905 never asked for.

  **`_st_hint.st_hint` is new, not a re-export of `presets/git/_git_common.py::st_hint`.** The two duplicate the same three states — a `./supertool` wrapper, `sys.executable supertool.py`, or neither — because `test_printed_invocation_worktree_1012.py` pins `_git_common.st_hint`'s globals identity (`conflicts.st_hint.__globals__ is vars(git_common)`) and several tests monkeypatch `_git_common.install_dir` and read the effect back through `_git_common.st_hint`; a re-export from a different module would answer to neither. The new helper is also variadic (`st_hint(*args)`), because `_repo_target.py`'s message chains two ops in one call (`repo:OWNER/NAME` ahead of the op it scopes) and that is one invocation, not two hints with no shared route between them.

  **A build gate, not only a paragraph.** `tests/test_supertool_hint_register_905.py` AST-scans every `presets/**/*.py` string constant naming `./supertool`, classifies each as `DEFINITION` (the two functions whose job is deciding the spelling), `PROSE` (docstring history, never printed) or `REMEDY-DEBT` (an actual hardcoded remedy, not yet fixed), and refuses an unregistered site or a `REMEDY-DEBT` count above the pinned ceiling — so a new hardcoded `./supertool` fails CI on the PR that adds it, the same way #905 itself would have failed had this existed in 2026-08-05. A second, non-AST test census-checks the whole `presets/` tree by plain substring count, so a comment, a JSON description field or a README code block — none of them `ast.Constant` nodes — cannot drift unnoticed either.

  **Putting `sys.executable` in a printed message made one existing assertion a measurement of the host, and #1917 found it on seven CI legs.** `tests/test_repo_target_no_repo_error_1789.py::test_a_very_long_reason_is_capped` asserted `len(msg) < 600` on the whole message; the total is `545 + len(sys.executable)`, so every ubuntu leg passed at 594 and macOS (61-char framework path, 606) and Windows (55-char hostedtoolcache path, **exactly 600**) did not. The Windows leg reads as an off-by-one — `600 < 600` against a cap that clamps at 600 — and is not one: the only clamp in `no_repo_error` is `_DETAIL_CAP`, it is 200, and it applies to gh's stderr. Nothing produces 600; that runner's interpreter path is 55 characters and `545 + 55` is 600. `<=` would pass it and fail the next runner at 56. So the assertion now measures the message **minus the invocation it contains** — 498 on every host, against 5307 with the cap removed — and the hint is left whole, because a shortened one no longer runs, which is the defect #905 exists to fix. Two new tests pin it: one drives a 226-character interpreter path through a `tmp_path` install with no wrapper (so the interpreter arm fires on every host rather than vacuously passing on one with a `./supertool` symlink), and one runs all three real runner paths and asserts they differ by exactly the spread of the paths themselves.

  **`presets/watch/README.md`'s ten occurrences and `README.md`'s own stale example transcripts (the `no_repo_error` messages this fix changed, quoted verbatim at two places) are reported, not edited** — both files are held by other work in flight at the time of this fix.
