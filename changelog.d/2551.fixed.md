- **`serialize_once`'s cold-cache lock no longer fails open on Windows** ([#2551](https://github.com/Digital-Process-Tools/claude-supertool/issues/2551)). `tests/_go_warmup_lock.py` distinguished "someone else holds the lock" from "the lock file itself could not be created" by exception type alone -- `FileExistsError` retried, any other `OSError` ran `fn()` immediately. On Windows, a lock file another process still has open, or one mid-`unlink` and delete-pending, makes `os.open` raise `PermissionError` rather than `FileExistsError`; being an `OSError` and not a `FileExistsError`, it landed in the immediate-fallback branch and ran `fn()` concurrently with the actual holder -- the exact hazard the lock exists to prevent, caught by `tests/test_go_warmup_lock_2331.py::test_two_racing_calls_do_not_overlap` failing on `windows-latest, 3.12`. The fix disambiguates by whether the lock file actually exists rather than by exception type: an existing lock file means contention (retry, like `FileExistsError` already does), and only a lock file that was never created falls back to running `fn()` immediately -- so the existing `test_an_unwritable_lock_dir_falls_back_to_running_fn` still holds unchanged. Two new tests pin the fix: one simulating the Windows sharing-violation shape directly, one a positive control asserting serialization still holds -- across three racing callers -- when contention itself raises `PermissionError` instead of `FileExistsError`.
