- **`gl-api:PATH[?query][:full]` — a GET-only read of any GitLab REST path** ([#831](https://github.com/Digital-Process-Tools/claude-supertool/issues/831)). The `gl-*` family is specialised — MR, MRs, pipeline, job, runners, issue — and everything else in the API had no op at all, so an access-review session went out as raw `glab api` eight times and tripped the `use-supertool` reminder eight times. A guard that fires on correct behaviour is one that stops being read, including on the calls where it is right; this op is what lets the reminder be honest.

  It is not the thin wrapper the issue proposed, in three places.

  **The method is pinned rather than defaulted, and no caller flag is forwarded.** `glab api` switches to POST on its own the moment a `-f`/`-F` is present, so "supertool passed no method" would not have meant "supertool sent a read". The op takes one thing, a path, sends `--method GET`, and refuses a path that is flag-shaped, contains whitespace, or is `graphql` — naming `glab api -X POST PATH -f key=value` in the refusal rather than guessing. A passthrough that accepted `-X POST` would not be a larger read op; it would be a write surface reachable from every alias and batch that can spell `gl-api`, with no validator, no rollback and no confirmation in front of it. The guarantee is about what supertool sends, not a claim that GitLab treats every GET as free of side effects.

  **A full page is not a complete list.** `projects/:id/members/all` returns twenty rows whether the project has twenty members or a hundred and thirty-seven, and nothing in the body tells them apart — this repo's own defect class, an absence produced by the tool read as an absence in the world, landing on an access review where it is the failure that matters most. Three states, never two: fewer rows than `per_page` says `complete`, exactly `per_page` says `INCOMPLETE` with the count and the boundary it compared against, and `:full` follows every page and says that instead. The boundary is `min(per_page, 100)` because GitLab silently caps `per_page` at 100 — `?per_page=200` returning 100 rows is a *full* page, and comparing against the 200 that was asked for would call it complete, which is the same defect one layer down. A `page=` above 1 discloses that the earlier pages were never fetched. An object response carries no completeness line at all: it was never paged.

  **The whole body is remote text.** Every other op here knows which of its fields a stranger wrote; a generic passthrough cannot, so nothing is exempt — the body is fenced, control characters are disclosed and fence glyphs are neutralised. Inside JSON the encoder does most of that, but `ensure_ascii=False` (kept, so a non-ASCII name stays readable) leaves U+2028 and U+2029 raw, and a non-JSON body has no encoder in front of it at all. A body that is not JSON is labelled `NOT JSON` and shown verbatim rather than parsed with a shrug.

  Emission is budgeted by `GL_API_MAX_BYTES` (default 65536), and the two shapes are cut differently on purpose: an array is cut **by item** so what prints is still a valid JSON array (`CAPPED: 41 of 4820 items shown`), and anything else is cut by characters and says `the JSON above is cut and does not parse` rather than letting the reader find out in a decoder.

  Not shipped: the `gh-api` half of the issue. `presets/github/` is under active change on another branch, and the GitHub pagination contract is a different one (`Link` headers, no `per_page` echo), so it is a separate change rather than a copy of this one.
