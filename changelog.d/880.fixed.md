- **`git-resolve` no longer prints `markers: clean` for a file whose syntax validator declined to run** ([#880](https://github.com/Digital-Process-Tools/claude-supertool/issues/880)). `_digest_block` condensed each file's validator rows and matched only two shapes, `tool : ok` and `tool : N err`. A validator that matched the file and then declined emits a third — `phplint : skipped — php not installed` — which set neither counter, so the file condensed to `None`: the value meaning "the validators ran and none handles this file type", which the receipt deliberately prints as nothing. A `.php` conflict staged on a machine without php therefore reported `markers: clean`, byte-identical to a file whose parser ran and passed.

  This is one layer in from the four routes #883 fixed. Those are failures of the *batch* — the child crashed, timed out, was never found, folded to the wrong block count — and every one is caught before a single row is read. Here the child ran fine and emitted a well-formed block, and the decline is a row inside it. It is also the likeliest of the five to be met, because it needs no crash at all, only a missing interpreter.

  A decline beside a pass costs a word rather than the whole verdict: `validate: ok | ⚠ not checked by phpstan (php not installed)`. The reader takes this line as the verdict for the file, and half-checked may not render as checked. A block with no rows at all is still `None` and still silent — that is the one state which really is an answer about the world, and widening it would put a warning under every `.md` in every resolve.

  Two of the three routes named in the issue were already fixed by #883; the third — a path excluded for containing `:` or `,` — stopped existing when #878's sender-side filter was replaced by the `@payload` route, so nothing is excluded any more. The route fixed here is a fourth the issue did not name.
