- **`git commit -a -h` was refused toward `git-commit`, an op that commits** ([#1832](https://github.com/Digital-Process-Tools/claude-supertool/issues/1832)). It prints usage and commits nothing (measured, git 2.46.2, exit 129), but `_guard_help_state` could not tell a help flag standing behind another flag from that flag's value, so it scored the segment and blocked — naming a next step that does the thing the caller had just declined to do. `_GUARD_VALUELESS_FLAGS`, added on [#1815](https://github.com/Digital-Process-Tools/claude-supertool/issues/1815)/[#1816](https://github.com/Digital-Process-Tools/claude-supertool/issues/1816), already carried what settles it: `-a` consumes no separate value, so `-h` behind it is unambiguously a request for help. `git commit -m -h` is unmoved, because `-m` takes the message.

  This is the one edge in the family that turns a **block** into an allow, so it is only as good as the table. Every spelling the four rows generate — 101 of them — was run against git 2.46.2 and every one printed usage; the five value-taking controls (`-m`, `-am`, `-c`, `--author`, `git push origin -o -h main`) do not, and stay ambiguous. The test re-derives that set from the table itself, so a value-taking flag added to a row later fails there rather than shipping as a wrong allow. A cluster is answered whole: `-as` un-blocks, `-am` does not. Known residual, pinned rather than fixed: `git commit -uall -h` stays blocked, because `-uall` is `-u` with an attached value and telling that from a letter cluster needs an arity fact the table does not carry.
