- **`radar` no longer reports a PR that left the filter as one that stopped being open** ([#1024](https://github.com/Digital-Process-Tools/claude-supertool/issues/1024)). Both delta tiers computed the departed set as "in the previous snapshot, not in the live population", and the live population is filter-scoped — `author=@me` by default. Merged, closed unmerged, reassigned to somebody else, stripped of the label the filter selects on, and "the filter itself changed between runs" all arrived as the same absence and all rendered as `N no longer open`. Three of those five are still open and still need work, so a maintainer who read that line and stopped tracking the PR had been told the opposite of the truth by a footer doing exactly what it was written to do.

  The board now says what it can support: `N left this board` in the footer, and a `radar: NOTE` naming the departed identifiers, listing the histories it cannot tell apart, and giving the op that answers which — `gh-pr:<number>` or `gl-mr:<iid>`. Deciding merged-versus-reassigned from the board would cost one live lookup per departure, and that lookup can itself fail, so it would need this three-state sentence anyway; the sentence alone costs no call and cannot be wrong. Absent departures the line is absent, so its absence stays the positive claim.

  On the GitLab tier the departed set is computed against the whole open population rather than the board, so an excluded MR is never counted as departed — an exclusion removes a row, not a member, and counting one would report the operator's own standing decision back to them as a merge.

  **On a full page the board declines the word "departure" entirely.** The live fetch is a single page with no pagination loop, so an entry pushed past the page limit by newer ones is missing from the live population while being open and still matching the filter — a fourth history none of the three offered covers. Calling it a departure sends the reader to a lookup that shows it open, from which the only remaining conclusion is also wrong. When the population reaches the page size the footer reads `N off this page` and the disclosure becomes a WARNING naming the page limit alongside the other three. A departure also makes the tier report unhealthy, because `healthy` feeds `quiet_when_healthy`, which drops the tier's whole output — and a departure-only tick is elided rows plus one summary line, so a healthy verdict there suppressed the notice completely.

  A tick whose only event is a departure now reads `radar: no rows changed` rather than `radar: no change`. The departed entry has no row left to print and every survivor legitimately elides, so the summary line used to announce that nothing had happened on the one tick where something fell off the board. The named identifiers are sorted, too: the cap at twelve makes which ones get named load-bearing, and the snapshot is written in the order the upstream page returned.
