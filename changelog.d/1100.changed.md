- **A green `py-syntax` row says what it did not check: `ok (parsed; not imported)`** ([#1100](https://github.com/Digital-Process-Tools/claude-supertool/issues/1100)). A payload write landed bytes that parsed and could not be imported; the file was `_supertool.py`, so every subsequent supertool call in that worktree died behind this validator's green. `compile()` answers "does this parse" and is read as "is this a working module" — between them sits everything that only fails at import: a regex compiled at module level, an undefined name at class-body scope, a circular import.

  **The validator does not import the file, and that is a decision rather than a gap.** Import executes module-level code, and running arbitrary just-edited bytes is a containment question — the file that produced this report was the tool's own core, being edited by the tool, in a worktree its author was mid-change in. `py_compile` is not an import and would have passed the same file, so the cheap version of that option buys nothing. The scope replaces `(no new errors)` rather than sitting beside it, so no version of the row still carries the old reading. Any validator may declare a `scope` string; on a red row it is suppressed, because there the finding is the line to act on.
