- **`git-commit`'s refusals named the fault and not the remedy** ([#1003](https://github.com/Digital-Process-Tools/claude-supertool/issues/1003)). A payload that would not load — the plain message file that is the obvious thing to write, a mistyped key, an `@` reference left in the colon slot — produced either a bare TOML line-and-column or `takes the @reference as the only argument`. Three agents in one evening met one of those, each guessed `message` and `paths` from scratch, and one mangled its own commit message past the shell instead, which is permanent in that history. Every such refusal now ends with the keys the op actually wants and a call that would work, derived from the same registry that drives the `@payload` route, so it cannot drift into describing a shape the loader would reject. This applies to every op with an `@payload` route, not only `git-commit`.

  **A refusal on an unstaged tree now names what is unstaged.** `ERROR: nothing staged.` was correct and unhelpful: the op had just read the working tree, and the caller's only remaining move was a raw `git add -A` — the command this op exists to replace, and one the repo's own hook flags. The refusal stays, because committing files the caller did not name is not a default anyone wants; it now lists the modified tracked and the untracked paths separately and hands back a `git-commit:::MESSAGE:::…` call naming the first few. Three states again: a genuinely clean tree says it is clean, and a `git status` that did not answer says *that*, rather than printing two empty lists that read as clean.

  **The first claim in the report is false and is pinned as false.** `git-commit` has had an `@payload` route since [#340](https://github.com/Digital-Process-Tools/claude-supertool/issues/340); [#400](https://github.com/Digital-Process-Tools/claude-supertool/issues/400) reported it missing once already. What was missing was any way to find out it existed from the error you were looking at, which is what the change above is.
