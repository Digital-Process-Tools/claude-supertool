- **Serialized the go-vet cold-cache warm-up across `-n auto` workers instead of racing it** ([#2331](https://github.com/Digital-Process-Tools/claude-supertool/issues/2331)). `--durations` on one CI leg showed 48s landing on a single test that pays a cold `go vet` standard-library compile — measured, not assumed, to be a race: under `-n auto` each xdist worker is a separate process, so the module-scoped warm-up fixture in `tests/test_validators_go_vet_669.py` and the real end-to-end spawn in `tests/test_go_vet_stall_1461.py` could land on different workers at the same moment and each pay the full cold compile concurrently, contending for the one machine-wide `GOCACHE`. `tests/_go_warmup_lock.py` adds a lock file shared by every worker in a session (`serialize_once`), so only the first caller pays the cold cost and everyone after it runs against an already-warm cache; a caller that cannot acquire or read the lock still falls back to running the warm-up itself, so correctness never depends on the lock succeeding. Measured locally with a cold `GOCACHE` under `-n2`: two racing workers both paying ~6.2s concurrently before the fix, one 3.6s pay plus one blocked wait after it — the two other CI durations hypotheses in #2331 (whole-suite guards sharing a tree walk, duplicated git/cargo fixtures) are not addressed here and remain open.
