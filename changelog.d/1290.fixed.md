- **The #1280 ignored-files gate was disarmed by an ordinary git preference, and then stated the guarantee it had not checked** ([#1290](https://github.com/Digital-Process-Tools/claude-supertool/issues/1290)). `_worktree_dirt` ran `git status --porcelain --ignored` with **inherited** config. `status.showUntrackedFiles=no` suppresses `!!` records as well as `??`, so the gate received an empty list, could not tell "nothing there" from "not looked", authorised the removal, and reported in the same sentence that it had found nothing untracked or ignored. Reproduced against real git: an ignored `secret.env` present before the call and gone after it.
- **The display settings are now pinned on the command line**, where they outrank every config file and `GIT_CONFIG_*` both — `git -c status.showUntrackedFiles=normal -c core.quotePath=true status --porcelain --ignored --untracked-files=all`.
- **And the empty answer is no longer taken from one read**, because pinning closes the instance and not the shape. A second read, `git ls-files --others --directory --no-empty-directory`, answers the untracked-and-ignored half through plumbing that has no display setting to suppress; `status` stays because it is the only one of the two that sees modified tracked files. The two results are unioned and de-duplicated, so the refusal counts files rather than reads.
- **Either read failing is `could not check`, never `checked and found nothing`.** That third state already existed for the single read (#1280) and now covers both, and the reason names which command failed — `git ls-files could not be run: ...` rather than a bare "git status".
- The success receipt states only what was established: `removed <path> — two reads with different failure modes both came back empty first (git status --porcelain --ignored with the untracked display pinned on, and the plumbing git ls-files --others)`.
