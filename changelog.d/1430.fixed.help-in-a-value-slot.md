- **A `-h` anywhere before the `--` un-claimed all 28 `replaces` mappings, including `git push`** ([#1430](https://github.com/Digital-Process-Tools/claude-supertool/issues/1430)). The help exclusion scanned `_guard_options(argv)` — the argv slice up to a bare `--`, which is *every* token, not only the flag-shaped ones — and returned "no op replaces this" if any of them equalled `-h` or `--help`. So `git commit -m -h` was `clean` and committed with the message `-h`, and `git push origin -o -h main` was `clean` and pushed. `clean` is not `undecided`: it is a positive claim that nothing in the command is replaced.

  Restricting the scan to flag-shaped tokens, the obvious repair, is a no-op — `-h` and `--help` are flag-shaped wherever they stand. The discriminator that matches what the programs actually do is whether the help token was consumed as the value of the option before it. Measured on git 2.46.2 and gh 2.50.0: `git push origin -h`, `git push -h`, `git status -h` and `gh issue list -h` all print usage and run nothing, so their `clean` verdicts were already right; only a help token sitting immediately after another flag is in doubt.

  `_guard_help_state()` now answers in three states — `help` (un-claims every entry, as before), `none`, and `value` for the ambiguous slot. Telling an option's value from a request for help needs per-subcommand option arity this guard deliberately does not carry, so the ambiguous case is scored and blocked with a note saying why, rather than allowed: a wrong block on `git push --force -h` is legible and one flag away from a working `git push -h`, while the other direction is a silent `git push`. The exclusion also moved from `_guard_excluded()` to `guard_command()`, because it is a property of the whole segment rather than of one entry.

  A refusal now prints the guard's notes too, under `Also:`. A `BLOCKED` verdict used to discard them — including "an op's `replaces` entry was dropped" — so a positive match rendered as though nothing in the command had been left unread.
