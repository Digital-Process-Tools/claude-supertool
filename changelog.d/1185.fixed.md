- **`html-check` reported `ok` for a `<script>` element that never closes, dropping its body unchecked** ([#1185](https://github.com/Digital-Process-Tools/claude-supertool/issues/1185)). When no `</script` followed the start tag anywhere in the file, the block was discarded as "not a block" and the walk resumed. `UndelimitedTag` only ever fired for a malformed *start* tag, so a well-formed `<script>` whose body ran to EOF was silently skipped and the file was reported clean — identical broken JavaScript was a finding when a closing tag existed and a pass when it did not. With `rollback_on_fail: true` that means an edit leaving broken JS inside an unclosed block passes the gate and is not reverted.

    It is now the third state, per file, the same as an undelimitable start tag: the adapter declines and names the line the unclosed element opens on. Checking the body to EOF as if it were closed was the alternative and is a guess in the loud direction — a fragment or a template partial legitimately stops inside a block, and the trailing markup of a truncated page would be handed to `node` as JavaScript.

    Resuming the scan past the unclosed tag, which the old code did and its comment defended as keeping a later well-formed block findable, could never do that: `</script` was not found at or after that point, so it is not found after any later `<script` either. The tokenizer agrees — after an unclosed `<script>` every remaining byte is script data, so there is no later block to find.
