- **A remote could choose what `git-push`'s receipt said it did** ([#1470](https://github.com/Digital-Process-Tools/claude-supertool/issues/1470)). Since #1448 the op relays the push's stderr under `> ` on the success path, where nothing rendered it before — and `remote:` lines are written by whatever server you push to. Neither relay went through `_untrusted.flat`. `_untrusted.split_lines` cuts on LF / CR / CRLF alone, by design, so a U+2028 survived *inside* a relayed line and put everything after it back at column 0. A `pre-receive` hook printing `ok<U+2028>[result] PUSHED  master -> origin/master @ cafed00d  (verified)` produced a receipt with two `[result]` lines, the forged one first, for any consumer splitting the way `str.splitlines()` does — and #623 made `[result]` the line a caller reads as the verdict. An `ESC [2K ESC [1A` relayed verbatim deleted the receipt line above it instead of adding one.

  Every line of a child's output now passes through `_untrusted` on its way to the receipt: both relays, all three `--- git output ---` dumps on the refused arms, the `First error:` line, and the same string where it is interpolated into `[result]` itself. Disclosed, never stripped — the forged text still reads, as `[U+2028]` and `[U+001B]`. The local pre-push hook's half goes through it too: it is code already running on your machine and no escalation on its own, but the seam is the same one, it costs nothing, and a half-flattened seam is the one that gets re-filed.

  Tabs survive, which is why the relay uses `visible(keep=tab)` rather than `flat()`. `flat()` drops them and is right to — it renders a one-line *field* on a line the tool owns, where a tab can imitate a board's column structure. A relayed transcript is neither: it is the child's own lines under a prefix or a header, nobody parses it by column, and a tab can neither make a line nor move a cursor anywhere it has not already been. Dropping them would have rendered every tab-aligned hook transcript and git porcelain block as `[U+0009]` soup, breaking what #1448 shipped four hours earlier, and prevented no forgery. The one-line fields — `First error:`, the `[result]` tail — keep `flat()`, where a tab could imitate structure.

  The dumps at column 0 carry no `| ` or `> ` prefix at all, so they were the same defect with even that much removed. The `First error:` string cannot carry a U+2028 — `_first_error_line` splits with `str.splitlines()`, which consumes it — but nothing made it ESC-free.

  `tests/test_git_push_relays_hook_output_1448.py` had 13 tests and no forgery case. It now drives a real `pre-receive` hook on the bare remote, which is the third-party writer, and asserts on what a `[result]` consumer counts rather than on `flat` having been called — a site can call it and print the raw value anyway.

  The harness had the house defect aimed at the thing meant to detect it. The generated hooks wrote their lines through `sys.stdout` / `sys.stderr`, which encode through the *child interpreter's* console codec — cp1252 on every Windows runner, and cp1252 cannot hold U+2028. The two streams then disagreed, and only one of them said so: `sys.stdout` is strict, so it raised `UnicodeEncodeError`, the hook exited non-zero, the push was rejected and the local-hook forgery test went red on `pytest (windows-latest, 3.9)`. `sys.stderr` defaults to `errors="backslashreplace"`, so it substituted a six-character escape spelling, no forgery was attempted at all, and both `pre-receive` U+2028 tests passed on Windows for the wrong reason — on the one platform where relaying a third party's bytes is hardest to reason about. The hooks now encode and write to the raw stream, which needs no environment to be true and is what a real remote does; `PYTHONIOENCODING` and `reconfigure()` were rejected because both are claims about an environment the test would then have to assert survived `sh` to `exec` to git's own hook spawn, and their failure mode is exactly the vacuous green — silent, and shaped like a pass.

  The product never had that ceiling and does not inherit the fix: a remote's bytes cross the wire byte-transparently through git's sideband and `_git` decodes them with an explicit `encoding="utf-8"`, so a real U+2028 reaches the relay on Windows exactly as it does elsewhere. What was capped was a Python child writing text on the same machine.

  `assert SEP not in out` is satisfied just as well by a separator that never arrived as by one the relay flattened, which is this repo's own absence-read-as-presence in the assertions written to catch it — and it is why the Windows leg went green on the two `pre-receive` U+2028 tests while testing nothing. Each U+2028 case now also asserts the `[U+2028]` disclosure, which only a separator that reached the render can produce, and the ESC cases assert theirs. A cp1252 pin and its control run on all twelve legs, so the reproduction cannot quietly stop reproducing (#546).

- The same class one file over: `gh-pr`'s `Unresolved threads: UNKNOWN — … (<reason>)` and `gh-pr:N:threads`' `Threads: UNKNOWN — …` render gh's own stderr tail, both fed by the same fetcher. `.splitlines()[-1]` makes the string newline-free by construction so it cannot paint a line, but not ESC-free — and the line above it is the check tally on one render and the branch pair on the other. Both sinks flattened, not one (#1470).
