- **`edit` spliced LF into a CRLF file, and two other receipts miscounted what they had done** ([#1049](https://github.com/Digital-Process-Tools/claude-supertool/issues/1049)). Review of the three passes above, each finding checked against `master` rather than against the previous commit on the branch — all three are regressions this work introduced, and all three were invisible while the read still flattened every file to LF before this code saw it.

  `edit` re-terminated the text you supplied only when your `old` had needed re-terminating to match. A single-line `old` matches literally, so a multi-line `new` went in verbatim and left a CRLF file mixed, silently. The bug is the inconsistency more than the silence: `old` spanning a line boundary and `old` on one line produced *different bytes for the same intent*, decided by an accident of how much text you happened to quote. `edit` now matches the convention of any file that uses one throughout and discloses it, exactly as the multi-line path already did; a mixed file still takes your bytes as typed, and says so.

  The other two are receipts describing work correctly done. On a CR-only file every line number came out as 1, because the arithmetic counted `\n` characters and a CR-only file has none — correct only while the read was translating `\r` to `\n` first. And `replace_lines` stripped `\n` but not `\r` from its preview, shipping a stray carriage return into the terminal on every context line of a CRLF file.
