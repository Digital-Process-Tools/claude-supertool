- **On a Windows host with no bash, one dead hook was disclosed and the other was not** ([#1401](https://github.com/Digital-Process-Tools/claude-supertool/issues/1401)). `hooks.json` runs both shipped hooks through `bash`, so the same missing shell kills both — and the two failures are not alike. The guard's is *silent* — it is asked (the matcher has been `Bash|PowerShell` since [#1413](https://github.com/Digital-Process-Tools/claude-supertool/issues/1413)), it cannot run, and a session where the gate never ran reads exactly like one where it ran and found nothing. `SessionStart` is gated by nothing at all, fires under any tool configuration, and its failure opens the session with no `./supertool` wrapper and no op roster. `hooks/guard-selftest.py` — the one channel that needs no shell — reported only the guard, and the README's platform section pointed a reader at that note as if it were the whole cost. The more visible loss was the unwritten one.
- The self-check's `could not run` state now names `hooks/session-start.sh` alongside the guard, says what the session loses, and gives the way back, which needs no shell either: call the tool by path — `py -3 supertool.py 'ops:roster'` on Windows — and read `./supertool` in the docs as that path (#1401).
- **The gap itself is accepted and disclosed, not fixed, and the reasoning is now written down rather than re-derived.** Adding `args` switches the hooks to exec form, where `command` *is* resolved on `PATH` — the `CreateProcess` search that finds System32's WSL launcher under the name `bash` — so the obvious repair introduces the defect; `tests/test_hook_interpreter_windows_1401_1402.py` refuses it. Rewriting the hooks in Python does not escape it, because exec form would still have to name an interpreter and none is portable: `python`/`python3` are the App Execution Alias stubs [#572](https://github.com/Digital-Process-Tools/claude-supertool/issues/572) banned for blocking rather than erroring, `python3.9`–`python3.14` are absent on a standard Windows install ([#1402](https://github.com/Digital-Process-Tools/claude-supertool/issues/1402)), and `py -3` is absent everywhere else. Resolving that is what `hooks/python-ladder.sh` is for, and it is itself a shell script (#1401).
- Every claim here about native `cmd.exe`/PowerShell is graded **reasoned, not observed** (the [#627](https://github.com/Digital-Process-Tools/claude-supertool/issues/627) convention): nobody on this project has that host, and CI's twelve legs cannot reach it either. What is observed is that both `hooks.json` entries name `bash`, that `SessionStart` carries no matcher, and that denying a macOS host a usable bash produces exactly the state described (#1401).
