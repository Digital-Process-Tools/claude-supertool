- **`gh-branch`'s watch poller no longer re-announces the same anomaly every time a single-poll upstream blip recovers** ([#2436](https://github.com/Digital-Process-Tools/claude-supertool/issues/2436)). Observed live: `master`'s poller flapped `went_green` -> `unknown` -> `went_green` six times in 32 minutes on one unchanged, already-concluded, already-green commit -- confirmed not rate limiting (`gh api rate_limit` read 5000/5000 throughout). Each `unknown` was individually correct per #2333's own direction guard (a previous poll confirmed runs on this sha; this poll's run list came back empty, read as a fetch that did not answer rather than the commit losing its history), but that guard absorbed only ONE empty read before surfacing `unknown`, and re-armed itself the instant a blip recovered -- so an upstream endpoint that flakes in short, isolated, self-recovering bursts got announced and un-announced once per burst, training a channel reader to skim past the exact signal #2333/#2355 exist to keep loud. `UNKNOWN_CONFIRM_STREAK` now requires two consecutive empty reads on the same sha before `unknown` is ever reported -- fewer than that is discarded as if the poll never happened -- while a genuinely persistent absence still surfaces, first as `unknown` and then, one more consecutive empty read later, as the real `no_run`: the same finding #2333 made, never suppressed, only no longer re-announced on a blip that already recovered.
