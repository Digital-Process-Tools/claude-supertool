- **A `ci-lint` validator: `glab ci lint` against the resolved GitLab CI root config** ([#1797](https://github.com/Digital-Process-Tools/claude-supertool/issues/1797)). For a CI config, the failure that costs a round-trip is almost never a parse error -- `yaml-check`/`prettier-check` already catch those. It is a misspelled key, a stage that does not exist, an `extends` pointing at a template that does not define what the job assumes -- all valid YAML, all green under every validator that shipped before this. `glab ci lint` is the only thing that can confirm GitLab would actually accept a merged config.

  Both traps the issue named are handled. **Trap 1**: linting an included file directly is wrong, because an include is never a standalone document -- `validators/ci-lint/resolve_root.py` is wired as this validator's `resolve` command, so `ci-lint.py` always runs against the repo's root `.gitlab-ci.yml`, whichever include a caller actually edited. **Trap 2**: a network or auth failure must never read as an invalid config, since `rollback_on_fail: true` would then silently revert a correct edit during an outage. `ci-lint.py` tells `glab`'s two literal reply strings (`"<file> is invalid."` and `"CI/CD YAML is valid!"`, confirmed against the shipped binary's own compiled string table) apart from every other non-zero exit -- an unresolved GitLab host, an HTTP 401/403/404 from the lint endpoint itself, a timeout -- and routes the latter through the third state, `skipped`, never a verdict.

  Split from #1797 per its own scope note: `actionlint` (`.github/workflows/*.yml`, no network, no resolve step) is #1798 and out of scope here.
