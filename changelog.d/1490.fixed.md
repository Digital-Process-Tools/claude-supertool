- **`git-push`'s rebase-recovery route now carries the pre-push hook disclosure and the same output bound as the straight route** ([#1490](https://github.com/Digital-Process-Tools/claude-supertool/issues/1490)). A non-fast-forward hands the push to `_recover_by_rebase`, which runs its own `git push` and prints its own receipts — and neither the hook relay ([#1448](https://github.com/Digital-Process-Tools/claude-supertool/issues/1448)) nor the head/tail bound on a relayed git dump ([#1454](https://github.com/Digital-Process-Tools/claude-supertool/issues/1454)) had ever followed it there. `Status: pushed OK (rebased onto remote)` was therefore the one landed-push receipt in the op that said nothing about the local gate at all.

  That is #1448's premise turned back on it. A push that lands *after* a rebase is precisely a push whose hook has just run, so it was the receipt most in need of the line. The success arm now prints the three-state `Pre-push hook:` line plus the relay above its status, and the rejected-after-rebase arm prints the state line only, exactly as the straight route's rejected arm does — the dump beneath it already carries the child's own words.

  Both of that route's `--- git output ---` dumps are bounded to head 5 / tail 30 with the elision counted. The rejected-after-rebase arm is where the transcript is largest for the same reason the arm exists: the hook has just run the suite, and #1454 measured an unbounded dump at ~11,000 lines inside a receipt. The `rebase could not start` arm prints no hook line, deliberately — no push of that route's own has run yet, so there is nothing about a hook it could state that would be about the failure it is reporting.
