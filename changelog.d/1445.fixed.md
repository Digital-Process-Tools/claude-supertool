- **`gh-pr:NUMBER` indexes the review threads it had only ever counted** ([#1445](https://github.com/Digital-Process-Tools/claude-supertool/issues/1445)). The header printed `Unresolved threads: 2 / 2` and then nothing, with `## Comments (0)` — a true statement about a different population — as the next thing a reader saw, so the only route to two real bot findings was `gh api repos/OWNER/REPO/pulls/N/comments`. The count is now followed by one row per thread: state, `path:line`, author, and the comment's first line, capped at 20 with the remainder stated. Resolved threads are shown too, lowercased and sorted last, because "resolved" is one person's decision about another person's finding and a reader who cannot see it cannot disagree with it; the count line states the split. The bodies stay behind `gh-pr:NUMBER:threads`, which each row names — a bot review runs to kilobytes per thread and the dashboard is not where that belongs.

- **A thread fetch that failed used to render as no line at all** ([#1445](https://github.com/Digital-Process-Tools/claude-supertool/issues/1445)). The dashboard ran a second, lossy fetcher that returned `[]` for a rate limit, a 404, a timeout and a genuinely empty list alike, and the caller printed the count only when that list was non-empty. So the two most different answers — "this PR has threads and I could not read them" and "this PR has none" — produced the same silence. There is now one three-state fetcher behind `gh-pr`, `gh-pr:NUMBER:threads` and `gh-prs`, and the header prints in all three: a count, `0 / 0 — read, not assumed`, or `UNKNOWN — they could not be read (<reason>)`. `gl-mr` has answered this way since #812; GitHub was the side that had drifted.

- **`gh-prs` counted an unreadable thread call as zero and dropped the flag** ([#1445](https://github.com/Digital-Process-Tools/claude-supertool/issues/1445)). Same fetcher, worse position: the board is the read that decides which PR to open, so a PR whose per-PR GraphQL call declined rendered without the `threads` marker and looked clean. It now flags `threads?`, which is a third state — distinct from `threads`, from no flag, and from a PR past the enrichment cap that was never asked at all.

- **A malformed GraphQL reply aborted the whole PR dashboard** ([#1445](https://github.com/Digital-Process-Tools/claude-supertool/issues/1445)). The thread reply was walked with an `or {}` chain, so a `data` that arrived as a list — GraphQL's error envelope is one shape that does this — raised `AttributeError` out of the fetcher and killed a render the caller wanted for its checks and its diff stat. Each hop is now type-checked and a reply of the wrong shape declines by name. The deleted lossy fetcher happened to catch that exception and return `[]`, which is how one line of code was both a crash and a silence.
