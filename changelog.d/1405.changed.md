- **`gh-since-tag` is retired into `gh-prs:merged-since=TAG,state=merged`, and the release boundary became a commit rather than an instant** ([#1405](https://github.com/Digital-Process-Tools/claude-supertool/issues/1405)). Two changes in one, because the second is what made the first cheap.

  **The defect.** The gate excluded the PR whose merge *is* the tagged commit by comparing instants — keep rows strictly after the boundary. That only holds if GitHub's `merged_at` equals the merge commit's committer date, and it does not: GitHub stamps `merged_at` after writing the commit. Measured across this repository's own releases, tagged commit vs the release PR's `merged_at` — v0.30.0 `06:29:26Z`/`06:29:26Z`, v0.31.0 `15:13:43Z`/`15:13:43Z`, **v0.32.0 `22:35:33Z`/`22:35:34Z`**, v0.33.0 `00:39:57Z`/`00:39:57Z`, **v0.34.0 `13:34:34Z`/`13:34:35Z`**. Two in five, not "every release" as the issue title said. On the two that lost the coin flip the release PR was counted as merged-since *and* reported absent from `TAG..master` — which excludes the tagged commit by construction — so the gate rendered `UNVERIFIED` with the count off by one, at the exact moment it is read. `merge_commit_sha` equalled the tagged sha in all five, so the exclusion is identity on `mergeCommit.oid` now, disclosed in the footer rather than dropped silently. A row carrying no `mergeCommit` is not guessed at, and a tagged commit **amended** after its merge no longer matches, so that row keeps its refusal — history was rewritten under the tag and the two sources genuinely do disagree.

  **The fold, and why a tag name.** supertool splits an op argument on `:`, so `merged-since=2026-08-11T18:57:19Z` is three segments and the value is gone before any filter is parsed; the op's own refusal says there is no escape. That left a bare date, which is midnight UTC, and against v0.35.0's real boundary `merged:>2026-08-11T00:00:00+00:00` returns **75 PRs** where `merged:>2026-08-11T18:57:19+00:00` returns **20**. A tag name contains no `:`, which is what makes the boundary expressible on a listing at all. `AMBIGUOUS` now **refuses** rather than printing a count with a warning: that was right for an op owning its whole render, and wrong for a filter, because the board underneath the warning would be a real board answering a question nobody asked. A filter value may be refused; it may not be picked between.

  **What it costs, stated rather than absorbed.** The `changelog.d/` read and the `repo:` refusal did not become unnecessary — they relocated onto this repository's most-called op. `gh-prs` was one `gh` call and on the boundary slice it now also reads tags, walks `git log` and scans a directory; the guard is one predicate with one input, and on every other call nothing local runs. The `repo:` refusal is narrower than it was: only `merged-since=<tag>` is refused, since a date boundary reads nothing local and follows a target whole. And **one thing is genuinely lost** — there is no default boundary any more. `gh-since-tag` with no argument chose the newest version-shaped tag reachable from the default branch; a filter value cannot, because that choice has three outcomes and a listing has nowhere to carry "two boundaries are defensible here". The tag must be named.

  **Every conditional read states whether it ran.** The boundary-row exclusion, the local-history cross-check and the `changelog.d` count each report their own state on every boundary call — `RAN and AGREED`, `RAN and DISAGREED`, or `DID NOT RUN` with the reason (a role filter narrows the API side only; a `repo:` target means two populations; `git log` did not answer). A cross-check that did not run counts as unreconciled, so the count renders `UNVERIFIED` rather than `EXACT`: `EXACT` means two sources agreed, and "I did not look" is not agreement. `failed` beside `merged-since=` is refused rather than answered from `statusCheckRollup`, which the boundary slice deliberately does not fetch.

  Two assertions in `tests/test_gh_prs_merged_since_1411.py` are **deliberately reversed** and say so where they sit: `gh-prs` was pinned against acquiring the changelog read and the `repo:` refusal, and against accepting a tag name as a filter value. Both were right for the shape #1411 left behind. `gh-since-tag` survives as a tombstone printing the mapping, because an op that vanishes becomes an unknown token and that is the wrong sentence for a name whose capability is still here.
