- **`map` says `could not read` instead of describing a file it never opened** ([#1680](https://github.com/Digital-Process-Tools/claude-supertool/issues/1680)). `chmod 000 secret.py && supertool 'map:secret.py'` printed three claims nothing had earned: `tier: regex`, naming a tier that read no bytes; `(0 lines)`, which is `_count_lines` swallowing the `OSError` and returning its documented `on_error` sentinel; and `(no symbols)`, the tool's own failure stated as a property of the file. That is this repository's canonical defect — an absence produced by the tool, read as an absence in the world — sitting inside the [#887](https://github.com/Digital-Process-Tools/claude-supertool/issues/887) render built to make exactly that shape visible.

  `map` had three states and now has four: parsed, no parser, no symbols, and **could not read**. An unreadable file renders `(unreadable)` with the reason the operating system gave, no line count and no tier, and it never contributes a tier name to the header — a file that was the only one asked about reports `tier: none`.

  **The state is established once, ahead of the three functions that each swallowed the error.** `_count_lines`, `_ts_extract` and `_regex_extract` all catch `OSError` independently, and composing a verdict from them is not available: `_count_lines`'s `on_error` sentinel is contracted to differ per caller ([#388](https://github.com/Digital-Process-Tools/claude-supertool/issues/388)), so a `0` arriving at the render cannot be told from a genuinely empty file. The distinction is destroyed one layer down, not merely unreported. One `open` and one byte per file, before anything reports on it.

  A permission-denied file is the easy reproduction; the same arm covers a file removed between the directory walk and the read, a dangling symlink, and an ACL — all of which arrive as `OSError`, which is why the reason is reported rather than classified. `read:PATH` in abstract mode also falls back to raw source on the new marker, as it already did on `(no symbols)`.
