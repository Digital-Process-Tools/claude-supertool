- **The GitLab read ops answer about another project** ([#676](https://github.com/Digital-Process-Tools/claude-supertool/issues/676)). A leading `repo:GROUP[/SUBGROUP]/PROJECT` now points `gl-issue`, `gl-mr`, `gl-pipeline` and `gl-job` at a project other than the cwd's, closing the asymmetry [#673](https://github.com/Digital-Process-Tools/claude-supertool/issues/673) left on this side: `gl-issue-create` had taken a project in its payload since it shipped, and no read op could name one at all.

  It is not [#673](https://github.com/Digital-Process-Tools/claude-supertool/issues/673)'s mechanism under a new name. `glab api` has no repo flag — the project *is* a path segment — so the target replaces glab's `projects/:id` placeholder as a url-encoded full path rather than being appended beside it, and leaving the placeholder in place would have meant the call still resolved from the directory it was made in. Only `glab issue view` and `glab mr view` take a flag (`-R`).

  The accepted shape now follows the call's own ops rather than one fixed rule. GitLab allows subgroups and GitHub does not, so core reads which preset each repo-targetable op is declared in and applies that forge's shape: a three-segment path in a `gh-*` call is refused instead of reaching `gh`, and a call naming both families is refused outright because one target cannot be a repository on both forges. Every segment must also be letters, digits, `.`, `_` or `-`, because the value is substituted into an API path and handed to a CLI that attaches the live `Private-Token`.

  `gl-mrs`, `gl-runners` and `gl-api` are **not** opted in, and a `repo:` call naming one refuses rather than half-applying. The first two feed `radar`, which respawns watchers off a `(source, id)` watch-state key with no project dimension — under a target that key would attribute one project's `!12` to another, and a supervisor acting on that is not a display bug. `gl-api` names its own path, so a project is already sayable there.

  `gl-issue-create` now gets the accurate refusal rather than the generic one. It routes its target through its own payload exactly as `gh-issue-create` does, but reads `project` where the GitHub op reads `repo`, so a manifest may now declare `"repo_target": "payload:KEY"` and the message quotes the field the payload validator actually looks at instead of naming one it does not.
