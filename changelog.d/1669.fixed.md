- **`git-push` names the wrong line, and the wrong word, on a push that never reached the remote** ([#1669](https://github.com/Digital-Process-Tools/claude-supertool/issues/1669)). Three fields of the receipt asserted things the `[result]` line under them denied. All three now come from one state.

  `First error:` promoted a footnote out of the pre-push hook's own **success** disclosure — a `^ counts skips carrying that token only …` continuation from a skip counter — while the real cause, `Connection to github.com closed by remote host.`, sat last and unselected. The selector was measured rather than guessed, because the issue asked which of three candidates it was: not proximity (the line sat ~200 lines earlier in a passing summary), not the head/tail elision, but a bare `"error" in line.lower()` matching inside the identifier `OSError`. That keyword scan is now word-anchored, and the pick itself is partitioned on the `To <url>` boundary `_split_hook_stdout` already draws — git's stderr and its own output first, the hook's transcript second. A hook-blocked push still surfaces its failing assertion, because git writes only `error: failed to push some refs to '<url>'` on that arm and a line naming nobody is never the answer while another line exists.

  The same push's verdict read `NOT PUSHED - REJECTED`, one line above a `Hint:` that correctly said the push was stopped before it reached the remote and that a rebase would not help. `_ref_status` already knew — git reported no per-ref line at all — so the headline and the verdict read it too now: `PUSH STOPPED BEFORE THE REMOTE` where git never spoke to the remote, `REJECTED` only where it did.

  There is exactly one `Status:` line per receipt now, which is the load-bearing half: the rebase-recovery route printed its own `Status: pushed ✓ (rebased onto remote)` and then let the shared receipt print a second one below it, so the two disagreed on a rebase that turned out to move nothing. A caller with something to say about *how* the push got here adds a clause to the one line. `tests/test_git_push.py::test_main_non_ff_rebase_clean_pushes` had been asserting `pushed ✓` on a fixture whose own `[result]` read `NOT PUSHED - already up to date` — this issue's contradiction, sitting green in the suite.

  On a no-op push, `Status: pushed ✓` sat three lines above `[result] NOT PUSHED - already up to date`, with the sentence that reconciles them between them and outside the two-field window a reader greps for precisely because the receipt is long. The `Status:` line is now rendered by `_success_receipt` from the same `moved` state as the verdict, and reads `nothing to push ✓ — the remote ref already matched`. git exiting 0 was never the same claim as the ref having moved.
