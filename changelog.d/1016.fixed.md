- **`git-commit` printed a green tick over a partial commit** ([#1016](https://github.com/Digital-Process-Tools/claude-supertool/issues/1016)). `Files committed: 5` under a `✓` does not distinguish "these five are what you asked for" from "these five are all that made it", and the tick above actively argues nothing was left out. The failure mode is a branch pushed and a PR opened believing the change is complete, silent until CI fails on a half-change — or worse, passes, because the files left behind were the tests. The op now names the modified tracked files that are still uncommitted after the commit lands, with a `git-commit:::MESSAGE:::…` call for them. Named rather than counted: "2 not included" costs a second call to find out which, and a reader who has to make that call usually does not.

  **Untracked files are counted and not listed, on purpose.** Nearly every worktree carries some, and a list of them under every commit is a list nobody reads on the commit that needed it. A *modified tracked* file is the one that means "you edited this and did not commit it". A run that left nothing behind prints none of this at all.

  **And the check itself has three states.** A `git status` that does not answer renders `⚠ Left-behind check SKIPPED` with git's own reason, never silence — silence there is byte-for-byte the receipt of a complete commit, which is the same defect one layer along. The scan reads `--porcelain=v1 -z` rather than the newline-terminated form, because git *quotes* a path containing a space or a non-ASCII byte in the latter, and a quoted path pasted back into a `git-commit:::MSG:::PATH` call is not that path; the `-z` stream also lets a rename's second record be consumed rather than parsed as a status line of its own, which would have invented a modified file out of a path that no longer exists.
