- **The shipped raw-command guard can now find a Python on a standard Windows install** ([#1402](https://github.com/Digital-Process-Tools/claude-supertool/issues/1402)). `hooks/pre-bash-guard.sh` probed `python3.9`-`python3.14` and nothing else, and neither python.org's installer nor GitHub's `hostedtoolcache` creates those names - both create `python.exe` and `python3.exe`, and the bare `python3` is permanently banned because on Windows it can resolve to an App Execution Alias stub that blocks rather than errors ([#572](https://github.com/Digital-Process-Tools/claude-supertool/issues/572)). So on that whole population the ladder ran out and the guard declined on every `Bash` call - honest, and off, while `raw_command_guard` defaults to on.

  `py -3`, the Windows Python launcher, is added as the **last** rung, after an activated virtualenv and after every versioned name, so a host with a real `python3.12` keeps using it. A candidate still has to print the probe's exact token, which is what rejects a launcher that writes a preamble of its own - such a launcher is skipped and the guard declines in words rather than a verdict being built on an interpreter it could not identify.

  Graded **reasoned, not observed**: nobody on this project has a Windows box. The load-bearing claim is that Windows ships no default App Execution Alias for `py.exe`. Putting the rung last bounds the cost if that is wrong, since any host with a versioned interpreter never reaches it.

  **This reverses a decision [#572](https://github.com/Digital-Process-Tools/claude-supertool/issues/572) made deliberately**, and only for this script. That entry recorded `py -3` as "considered and dropped: this is a bash script that only ever runs under Git Bash or WSL, where a Windows launcher shim is the wrong layer to reach for" - a preference about layering, argued without the fact this issue supplies. #572 established that versioned names are not *aliased* on Windows, which is true and is why they are safe to try; it did not establish that they are *present*, and they are not. Under WSL `py` is simply absent and the rung costs one `command -v`. `.githooks/pre-push` keeps the shorter ladder: it refuses the push and lists every name it tried, and documents `PYTHON=` as the way through, so a loud refusal with an escape hatch does not need the rung the way a disclosed allow does.
