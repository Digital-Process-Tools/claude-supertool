- **`gl-job:ID:trace` and `gl-pipeline:ID:traces` write a full CI trace to disk instead of into context** ([#626](https://github.com/Digital-Process-Tools/claude-supertool/issues/626)). `:raw` floods context and `:grep` truncates by design; a trace here runs to tens of thousands of lines, and the working pattern had become leaving supertool entirely for a raw `glab api .../trace` loop into a scratch file — "exactly the Unix reflex the tool is meant to remove", per the issue. `:trace` writes the whole log under the process's own proven-ours temp root ([#1493](https://github.com/Digital-Process-Tools/claude-supertool/issues/1493)'s attachment-root mechanism, not `.max/`, which this repo's own credential-directory list prunes from every `grep`/`glob` walk — writing there would have silently defeated the issue's own "then read it with the ordinary ops" premise) and prints only the path plus a receipt: line/byte count, a PHPUnit-style failures/errors count when the trace actually carries one (never a guessed zero when it does not — "could not tell" instead), and the first `N) Class::method` failure header when present. Comma-separated ids (`gl-job:A,B:trace`) concatenate into one file under a per-job header, deduped; a job whose fetch failed is named and skipped rather than aborting the others, and the call only fails when every id does. `gl-pipeline:ID:traces` reuses `:failed`'s own job list and hands it to the same writer, since "pipeline failed" is the actual starting point, not a job id — closing the gap the issue named between `gl-pipeline:ID:failed` and the trail going cold at the job IDs.
