- **The five LSP-family ops are documented in a new `lsp` preset instead of in `builtin-ops`** ([#2025](https://github.com/Digital-Process-Tools/claude-supertool/issues/2025)). `workspace`, `resolve`, `diag`, `hover` and `rename` still dispatch from core and still run in every repo — only their documentation moved. Four of the five reach a language server through the `mcp` block, so a project with none configured was paying listing bytes for ops it could not run: measured on this repo, dropping the preset takes 69 bytes off `ops` and `ops-compact` and 641 off `ops:full`. Enable it with `"presets": ["lsp"]`, which this repository does. The class of each op still comes from `_OP_SAFETY_BUILTIN` — `rename` writes — because a `safety` key in a preset is never consulted for a built-in's name, and one that reads as authoritative and is never enforced is worse than none.
- **A preset may now document a built-in without vanishing from the "not loaded here" hint** ([#2025](https://github.com/Digital-Process-Tools/claude-supertool/issues/2025)). `_shipped_preset_ops` skipped every preset op whose name was a built-in. That filter stood in for "a preset must not shadow a built-in", which `dispatch` already guarantees structurally — `_resolve_custom_op` is reached only on the fallthrough, after every built-in branch has declined — so its only remaining effect was to hide such an op from the index behind [#614](https://github.com/Digital-Process-Tools/claude-supertool/issues/614)'s hint. Left in place, an unknown-op error would have answered `hover` with "no such op" in a binary that dispatches it: the tool under-reporting its own capability, which is the defect #614 was filed about.
