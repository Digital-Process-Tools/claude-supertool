- **A preset can now document a built-in, in its own `builtin-ops` section** ([#2025](https://github.com/Digital-Process-Tools/claude-supertool/issues/2025)). A manifest's `ops` section means "ops this preset defines", and four guards depend on it: every entry must resolve to a script ([#1269](https://github.com/Digital-Process-Tools/claude-supertool/issues/1269)), declare a safety class ([#1231](https://github.com/Digital-Process-Tools/claude-supertool/issues/1231)), declare a path-containment boundary ([#1287](https://github.com/Digital-Process-Tools/claude-supertool/issues/1287), [#1350](https://github.com/Digital-Process-Tools/claude-supertool/issues/1350)) and appear in the `replaces` census ([#1384](https://github.com/Digital-Process-Tools/claude-supertool/issues/1384)). A built-in's documentation can satisfy none of those and should not have to — its script is `_supertool.py`, its class is `_OP_SAFETY_BUILTIN`, its paths go through the built-in chokepoint. Entries in the new section merge into the config's own `builtin-ops` (a project entry wins key-for-key) and reach `ops`, `ops:full` and `help:OP` unchanged, while the four sweeps never see them. `_merge_presets` stamps the contribution so a doc-only preset is not mistaken for one that resolved and contributed nothing.
- **The five LSP-family ops are documented in a new `lsp` preset instead of in `.supertool.json`** ([#2025](https://github.com/Digital-Process-Tools/claude-supertool/issues/2025)). `workspace`, `resolve`, `diag`, `hover` and `rename` still dispatch from core and still run in every repo — only their documentation moved. Four of the five reach a language server through the `mcp` block, so a project with none configured was paying listing bytes for ops it could not run: measured on this repo, leaving the preset unlisted takes 69 bytes off `ops` and `ops-compact` and 641 off `ops:full`. Enable it with `"presets": ["lsp"]`, which this repository does. `help:hover` answers either way — the shipped reference folds in the shipped presets' `builtin-ops` behind the `help:OP` fallback, so only the listing is affected.
- **A preset may name a built-in without vanishing from the "not loaded here" hint** ([#2025](https://github.com/Digital-Process-Tools/claude-supertool/issues/2025)). `_shipped_preset_ops` skipped every preset op whose name was a built-in. That filter stood in for "a preset must not shadow a built-in", which `dispatch` already guarantees structurally — `_resolve_custom_op` is reached only on the fallthrough, after every built-in branch has declined — so its only remaining effect was to hide such an op from the index behind [#614](https://github.com/Digital-Process-Tools/claude-supertool/issues/614)'s hint. Left in place, an unknown-op error would have answered `hover` with "no such op" in a binary that dispatches it: the tool under-reporting its own capability, which is the defect #614 was filed about.
