- **`radar` no longer stops pollers on a run that spawned nothing** ([#957](https://github.com/Digital-Process-Tools/claude-supertool/issues/957)). The duplicate-poller reap from [#749](https://github.com/Digital-Process-Tools/claude-supertool/issues/749) sat in `main()`, above every tier, so it ran on every `radar:*` invocation — including the ones that established no coverage at all. A tier that raised before it could spawn (live GitLab unreachable: exit 1, no board, nothing healed) had already stopped somebody's process on the way in, and so had a radar configured with only a fleet tier like `gl-runners`, which keeps no watchers to begin with. Those runs cannot have contributed a duplicate, so they now remove none.
- The reap moved onto the spawn path rather than being made opt-out. A flag would have put the same fusion one layer up and needed remembering at the exact moment nobody is thinking about it; the honest bound is already in the code — a call that spawns nothing has nothing of its own making to reap. It now fires from radar's `_watch`, once per run, immediately before the run's first spawn. Ordering is unchanged and still pinned: reaping *after* a spawn would judge the poller this run just started.
- Nothing changes for the tick you actually run. `radar` heals, healing spawns, so it reaps first and names every PID it stopped at the top of the board, exactly as before. A run that reaped nothing is still silent — "reaped nothing" and "did not reap" are the same fact for a reader (no process of theirs was stopped), and a disclosure line on every board is the furniture the Windows scan decline was already trimmed back for.
- `radar:--state` was never affected: it returns before `main()` reached the reap, and it never spawned. That is now covered by a test, so the read-only contract survives the reap moving rather than being an accident of an early `return`.
- Also fixed, from the same edit: the radar test fixture in `tests/test_watch_radar.py` spawns for real through radar's spawner, so an unpatched suite run could reach the machine's own `ps` and signal a developer's live pollers. It stubs the reap now; the reap's own behaviour stays pinned against the fake fleet in `tests/test_watch_radar_reap_749.py`.
