- **The suite asserted a validator verdict where the core's own spawn wall could fire** ([#1501](https://github.com/Digital-Process-Tools/claude-supertool/issues/1501)). `master` went red on `pytest (windows-latest, 3.12)` with `assert 1 == 2` in `tests/test_validator_warm_unsafe_345.py`, on a commit touching nothing near validators, on a leg that took 8m41s. The `1` was not the adapter's: `_validator_run_one`'s `TimeoutExpired` arm fabricates `count: 1` with `timeout: True` when a cold CPython spawn misses the spec's 10s, and `assert out["count"] == 2` cannot tell that from two real findings. A machine limit was being published as a verdict about the file — this repo's own defect class inside the thing built to detect it.

  The arm is unchanged: it is an absence, it says so, and [#969](https://github.com/Digital-Process-Tools/claude-supertool/issues/969) pins that it never rolls an edit back. The assertion sites moved instead. `tests/_adapter_verdict.py` gains `core_timed_out` / `skip_if_core_timed_out` — the sibling of [#794](https://github.com/Digital-Process-Tools/claude-supertool/issues/794)'s `skip_if_stalled`, which classifies a stall at the *adapter's* own wall and cannot see this one — and `run_one_or_skip`, the adopted call form at all 42 sites across seven files that hand the core a `cmd` it really spawns.

  **`timeout is True` is the only clause, and that is the design.** It is written in exactly one place in `_supertool.py` and `_validator_strip_core_keys` drops it from anything an adapter or a cache entry says ([#1036](https://github.com/Digital-Process-Tools/claude-supertool/issues/1036), [#1044](https://github.com/Digital-Process-Tools/claude-supertool/issues/1044)), so nothing else can claim it. Declining on `count == 1` — the number in the log — would mute every genuine one-error verdict in the suite, and matching the message would swallow a real finding about somebody's `timeout` setting. Both directions are pinned.

  **The sweep is enforced, not asserted in a PR body.** An `ast` walk fails on any raw `_validator_run_one` call left in `tests/` whose spec can spawn. Two exclusions, both mechanical rather than a line-number list: a `{"builtin": ...}` spec returns in-process before any subprocess ([#477](https://github.com/Digital-Process-Tools/claude-supertool/issues/477)), and a `# core-timeout: asserted on` comment marks a test that provokes the wall deliberately. That marker exists because the blanket conversion silently muted `test_adapter_timeout_stays_loud`, which is the one test whose subject *is* the arm — caught by running it, not by reading the diff.
