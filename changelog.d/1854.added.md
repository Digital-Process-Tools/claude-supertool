- **The version sites are now guarded as a set, not one test per site** ([#1854](https://github.com/Digital-Process-Tools/claude-supertool/issues/1854)). `tests/test_version_sites_agree_1854.py` derives the five sites from `.oss.json`'s `version_sites` — the repository's own declared list, previously read by nothing in this tree — and asserts they all agree with `supertool.VERSION`. Declaring a **sixth** site now reds the suite until somebody says how to read a version out of it, which is the case `CLAUDE.md` named as the hand-sweep's real value and left to whoever remembered to run it.

  **The premise the issue was filed on was already false, and that is the more useful finding.** #1854 says the `README.md` badge is guarded by nothing; `test_readme_version_badge_matches_code` has pinned it since the badge was caught fifteen releases stale. What was actually unguarded was the *set*: five hand-written tests across four files covering five hand-written paths, with nothing tying them to the list. `CLAUDE.md` and `.claude/jit-context/paths/00-manual/version-sites.md` both said "only four are guarded" and are corrected here — the sentence is what produced the issue.

  The control is the point: a fixture freezes one site at an older version while the other four agree, parametrised over all five, and asserts exactly one disagreement is reported. A checker that reads four of five returns `[]` against a frozen fifth site — measured — so without that control the guard would pass exactly as the repository did while the badge rotted. An unreadable site and a site with no reader are findings in their own words, never folded into agreement.

  No new gate was needed for the release path. The suite runs on every pull request and `.githooks/pre-push` runs it again for a push whose destination is `master`, which is the path release commits actually take.
