- **A repository under inspection could get one of its own files executed as a program, on Windows, by `shutil.which()`'s implicit search of the current directory** ([#2575](https://github.com/Digital-Process-Tools/claude-supertool/issues/2575)). `shutil.which()` inserts `os.curdir` at the front of its search path unless `NoDefaultCurrentDirectoryInExePath` is set -- and does this even when a caller passes an explicit `path=`, since the insertion happens after the `path is None` branch in CPython's own source, not inside it. Every validator/formatter chokepoint spawns its adapter subprocess with no `cwd=`, inheriting supertool's own cwd -- the repository being inspected -- so a clone shipping `ruff.cmd`, `markdownlint.cmd` or similar at its own root had that file resolved ahead of every real `PATH` entry and executed the moment the matching adapter ran, a composition defect assembled from #2540's (correct, on its own) fix and this pre-existing CPython behaviour. A second, narrower path to the same shape: `_already_a_path`/`_is_executable`'s raw `os.path.isfile(name)` fallback also resolved a bare name relative to the current directory, with no `which()` call involved at all, whenever the configured or default binary name matched a file sitting in the repo root. `which_excluding_cwd()` in `validators/common/spawnable.py` is the shared chokepoint now used by `argv0()`, `spawnable()`, and `bin_resolve.py`'s `_is_executable()`/`_spawnable()`: it walks `PATH` itself, in `shutil.which()`'s own order, skipping any entry whose directory is the current one, so a genuine PATH-installed copy still resolves and only the implicit, attacker-reachable cwd match is refused; the bare-name `isfile()` fallbacks are now gated on the name actually containing a directory component. `tests/test_which_excludes_cwd_2575.py` asks the mechanism directly rather than the platform, so it is measured on every OS the suite runs on rather than only reasoned about.
