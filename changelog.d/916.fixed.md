- **`gh-job:N:fail` claimed a complete answer on a job that never failed** ([#916](https://github.com/Digital-Process-Tools/claude-supertool/issues/916)). `:fail` selects error blocks, which is right for a job GitHub calls `failure` and close to the worst possible filter for one it calls `cancelled`: a cancellation writes exactly one error line, `##[error]The operation was canceled.`, and puts everything diagnostic outside it. The render nevertheless headlined its selection `All error blocks (11 lines matched, no tail truncation)` — two claims that are true of the *selector* and false of the *log*. On the job in the issue, thirty lines further down in teardown output carrying no error marker of any kind, sat six `Terminate orphan process: pid (…) (python)` lines: the difference between "the suite is slow" and "the process tree was still populated when the runner pulled the plug", and the strongest available evidence on a hang whose cause was still open ([#914](https://github.com/Digital-Process-Tools/claude-supertool/issues/914)). It cost a day, and an issue body asserting "the log says nothing" as though that were a property of the log.
- **The op already knew.** `Status: cancelled` is printed two lines above, from the same value the selection branch reads — so it held, at selection time, the fact that error blocks were the wrong selector, and applied it anyway. It now drops the completeness claim (`## Error blocks (N lines matched) — but see below`) and appends a note naming the conclusion, saying error-block selection is a poor fit for it, and giving two ops that do reach the evidence: `gh-job:N:raw:-80` and `gh-job:N:grep:orphan`. Both verified against the live job — `:grep:orphan` returns all six `Terminate orphan process` lines.
- **Disclosure rather than a wider pattern set, deliberately.** Teaching the patterns to match `Terminate orphan process` would fix that one log and trade a loud wrong answer for a quiet one: the next cancelled job's tell is some other unmarked line, and a larger set that still misses it produces a longer and more confident-looking block. A pattern set cannot be complete, so the honest output is that these N lines matched *and* that this selector is not where the cause lives here. It is the three-state move of `docs/validators.md` §"Declining instead of guessing" applied to a selector rather than a checker.
- **Not suppression either.** Every matched line is still printed in full. Answering nothing, or clamping the selection down to a tail, would be the same defect pointed the other way — trading "it told me the wrong thing loudly" for "it quietly gave me something else".
- Keyed on the complement — `display_status != "failure"` — rather than on a list of the other conclusions, so a state GitHub adds later, or an in-progress job whose display status is `queued`, lands on the disclosure instead of on the silent overclaim. The `failure` path is byte-identical and pinned by its own test.
- **The sibling is deliberately untouched.** `gl-job:N:fail`'s pattern set does not match Playwright's `Error: JS errors detected:`, and on one e2e job it reported `All error blocks (6 lines matched)` where all six were teardown boilerplate. Same symptom — but there the conclusion *is* `failure`, so no signal exists to key a disclosure on, and extending this fix's claim to cover it would be the same overclaim one repo over. Filed as its own problem rather than folded into this one.
