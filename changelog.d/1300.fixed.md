- **A `~/` path was refused as not found, and the receipt named a path that had never been stat-ed** ([#1300](https://github.com/Digital-Process-Tools/claude-supertool/issues/1300)). `_safe_path` — the containment gate — has expanded `~` before checking since [#146](https://github.com/Digital-Process-Tools/claude-supertool/issues/146), but it returned only a verdict, so every op then opened the caller's literal `~/x`. `os.path.abspath` turns that into `<cwd>/~/x`, which never exists: the gate approved one path and the op tried a different one. Measured before the fix across the thirteen read ops that take a path — `read`, `head`, `tail`, `wc`, `stat`, `ls`, `tree`, `map`, `grep`, `grep_around`, `around`, `around_line`, `between` — and every one of them failed, while `cwd:~/dir` had expanded correctly all along in the CLI pre-pass, so the tool disagreed with itself about what a tilde meant.

- **The containment boundary did not move.** `_gate_paths` returns the check *and* the string the caller must use, in one call, so a route cannot clear one path and open another. The expansion it hands back is the same `os.path.expanduser` the check already applied, written back only after the check passed — a `~` resolving outside the boundary is still refused with `path escapes cwd`, and `tests/test_tilde_path_1300.py::TestContainmentIsNotWidened` pins both halves. Deliberately narrower than the gate's own normalisation: no `realpath`, which would silently redirect a write through a symlink, and no `expandvars`, because `$` is a legal filename character and expanding it would break files that read fine today.

- **`glob` is the deliberate exception, and now says so instead of answering `(0 files)`.** It is not in `_PATH_ARG_POSITIONS` and resolves its own pattern, so there is no containment gate for an expansion to sit behind — expanding `~` there would widen what the op can reach rather than fix what it can say. It refuses with `unsupported path form: glob does not expand ~`, naming the absolute spelling that works. The zero it used to return was the house defect in miniature: an absence the tool manufactured, reading exactly like an empty directory.

- **`tried:` now prints the string that was actually opened.** `_path_not_found` ran its own `expanduser` purely for display, so the receipt named an expanded path that existed — one the reader had listed seconds earlier — while the tool had touched a different one. That line is `os.path.abspath(path)` and nothing else. A `~user` that cannot expand keeps its literal spelling in the receipt and gets a hint saying `~` was not expanded, in place of the `wrong CWD?` advice that provably cannot fix it (same reasoning as [#734](https://github.com/Digital-Process-Tools/claude-supertool/issues/734) and [#921](https://github.com/Digital-Process-Tools/claude-supertool/issues/921)).
