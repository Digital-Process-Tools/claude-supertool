- **`gh-issue` and `gl-issue` say whether the linked work is green, not only that it exists** ([#815](https://github.com/Digital-Process-Tools/claude-supertool/issues/815)). `gh-issue:803` printed `#808 (OPEN)` at a moment when #808 had a failed leg. `OPEN` is true and it was the whole story the op told: a reader on a triage tick concludes "the fix is in flight" and moves on, when the fix is in flight *and currently red* — one of those says wait and the other says go look. The linked-PR block now carries `checks: 18 total: 13 passed, 1 failed, 4 pending ⚠ NOT ALL GREEN`, in the vocabulary `gh-pr:N:status` already uses, from `_checks.summarize` rather than a second hand-rolled sum ([#454](https://github.com/Digital-Process-Tools/claude-supertool/issues/454)).

  **The cost question the issue asks to be answered: it is zero, so there is no opt-in gate.** The obvious objection is one extra API call per linked PR, on a tracker where most issues have one. There is none — `closedByPullRequestsReferences` is already fetched over GraphQL and `commits(last: 1) { commit { statusCheckRollup } }` hangs off the same selection set. Measured against the live API on 2026-08-07: issues 1007, 803 and 969 returned 20, 18 and 20 contexts respectively, one request each. Gating a free field behind `:full` would only hide it.

  **Three states, because a PR with no run must not read like one that is waiting.** A null `statusCheckRollup` renders `no check runs on this commit — whether one is still coming is UNKNOWN`, never a zero tally (`0 passed, 0 failed, 0 pending` reads as "accounted for, nothing outstanding", which is [#452](https://github.com/Digital-Process-Tools/claude-supertool/issues/452)'s exact wrong reading) and never as pending. Classifying *whether a run is coming* needs the head commit's age and mergeable state, so the line names `gh-pr:N` rather than re-fetching its evidence. A tally the response did not carry says `UNKNOWN`, because an omitted tally reads as "nothing to report". A matrix wider than the 100-leg page size is disclosed with `⚠ INCOMPLETE — 100 of 137 legs read`.

  **`gl-issue` lands in the same change**, which is what the issue's own comment asks for — a fix on one family only would become the parity gap it was meant to close. Each related MR now carries `pipeline: failed (#154290) ⚠ NOT ALL GREEN` from `head_pipeline`, already in the payload, so no extra call there either. It is a **status, not a leg tally**, and the asymmetry is deliberate: GitLab puts no per-job breakdown in an MR, so matching the GitHub shape would mean `projects/:id/pipelines/N/jobs` once per related MR — a real, uncapped, per-MR request on a list that holds up to ten. A missing or null `head_pipeline` declines with the sentence `gl-mr` already prints for that state rather than asserting there is no pipeline.
