- **The `supertool-no-cut` JIT rule no longer blocks on the repo's own directory name** ([#1221](https://github.com/Digital-Process-Tools/claude-supertool/issues/1221)). A checkout of this repo is commonly named `claude-supertool`, and every command that `cd`s into it and pipes to `head`/`tail`/`sed`/`cut`/`awk` shares that substring with a real `supertool 'op'` invocation. Verified against the shipped pattern with the same awk harness `hooks/pre-tool-hook.sh` runs: the command-position anchor landed in #1426 (the same day this issue was opened) already requires `supertool`/`python3 supertool.py` to be the executed command rather than a substring anywhere in the line, so a `cd <path containing "supertool">` can no longer reach the anchor at all. `tests/test_jit_no_cut_path_name_1221.py` pins every command this issue and its comments recorded as wrongly blocked, alongside a positive control that a real op piped to a cutting tool — including the `python3 supertool.py` shape a worktree checkout legitimately uses — still fires. A third, distinct false positive from the issue's own comments (a **write** op's receipt, `paste ... | tail`, still being blocked) is confirmed still present and left untouched here; the rule's own rationale is about a read's verdict-then-body layout, which does not describe a write receipt, so that one is reported for filing as its own issue rather than folded into this fix.
