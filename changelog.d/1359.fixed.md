- **A call's exit code could be the previous call's verdict** ([#1359](https://github.com/Digital-Process-Tools/claude-supertool/issues/1359)). `dispatch_verdict` returned `_call_failed()`, a pure read of the thread-local `_DISPATCH_STATE.call_failed`, whose only reset lived inside `dispatch` at depth 0 — a function `dispatch_verdict`'s own docstring records as one callers replace ("both the tests and the MCP layer monkeypatch it"). Under that documented contract the reset never ran and the bit carried over from whatever last refused on the thread. It now establishes the flag immediately before the call it is about to judge. Before the call, never after: a sub-op that refuses at any depth must still reach its parent's verdict, so the depth-0 clear inside `dispatch` is unchanged.

- **The tally said "all 2 refused" about two ops that had not.** Reproduced on macOS with no pytest involved: a real refusing `read`, then `main(["edit:@-", "@-"])` over a replaced `dispatch`, printed `[batch] 2 ops ran — all 2 refused.` and exited 1. The exit code was the visible half; [#1284](https://github.com/Digital-Process-Tools/claude-supertool/issues/1284)'s tally turned the same stale bit into an explicit false sentence. The sibling counters beside it — `_SKIP_COUNT`, `_ROLLBACK_COUNT`, `_NOT_CHECKED` — are all read as per-call deltas for exactly this reason ([#680](https://github.com/Digital-Process-Tools/claude-supertool/issues/680)); this bit was the one member of the group with neither a delta nor a reset.

- **It is what turned `master` red on macOS only, and the platform was never the cause.** At `df34db5`, `tests/test_stdin_clash_341.py::test_bare_dash_arg_is_not_treated_as_stdin` failed `assert 1 == 0` on macOS 3.10/3.11/3.12 with ubuntu and windows green. xdist `--dist load` schedules individual tests, so which test follows a real refusing dispatch inside one worker is decided by core count — the same mechanism recorded in `tests/conftest.py` for the [#689](https://github.com/Digital-Process-Tools/claude-supertool/issues/689) macOS red. `tests/test_repo_target_673.py` stubs `dispatch` from the same shape and was exposed to the identical leak; both files were in the unexplained `8 failed` set reported and deliberately not cleared during [#1329](https://github.com/Digital-Process-Tools/claude-supertool/issues/1329).
