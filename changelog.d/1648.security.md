- **The eight GitHub relays [#1606](https://github.com/Digital-Process-Tools/claude-supertool/issues/1606) named and left, closed** ([#1648](https://github.com/Digital-Process-Tools/claude-supertool/issues/1648)). `gh-pr-merge`'s `_gh_json` relayed a failing `gh` call's body as `str.splitlines()[-1]`, and `str.splitlines()` cuts on U+2028 while `_untrusted.split_lines` deliberately does not — so a server that controls the error body chose which segment became the *whole* error, unflattened, at column 0, inside the receipt the merge gate prints (`ERROR: PR #N could not be read ...: {err}`). Seven more sites dumped an unparseable remote body verbatim: four spelled `ERROR: invalid JSON from gh` (`gh-run`, `gh-pr` twice, `gh-issue`) and three `ERROR: bad JSON` (`gh-following`, `gh-starred`, `gh-find-starable`). Pre-existing — every one of them ships in v0.41.0 — and disclosed rather than left silent, which is why they were findable at all.

  **`flat` and `split_lines` are not one decision, and the eight sites split three ways.** A *selection* picks which segment **is** the error, so the split has to be right even after a flatten: `_gh_json` now takes `_untrusted.split_lines(...)[-1]` and flattens the segment it selected. A *verbatim body* is a block by design and keeps its lines, so the four `invalid JSON` dumps are fenced, not flattened — `scrub()` inside `_untrusted.fence` discloses every separator and neutralises the marker shape, so the fence cannot be closed from inside it, and the slice comes first because the markers are the outermost thing. A *one-line inline diagnostic* has nowhere to put a fence, so the three `bad JSON` writes flatten and then slice, the order those same three files already spell out for the descriptions below them ([#970](https://github.com/Digital-Process-Tools/claude-supertool/issues/970)). Each of the four fenced sites prints `_untrusted.banner()` above the fence, because markers with nothing explaining them are a convention the reader has not been let in on.

  **Two more, neither on the disclosed list, both found by sweeping for the shape rather than reading the table.** `gh-pr-create` has its own copy of `_gh_json` with the same `str.splitlines()[-1]` and the same defect, one file over — its `read_err` renders above the op's own `[result] no PR created`. And `gh-issue-create`'s `url=` fallback selects the last line `gh` printed the same way; the harm there is the selection rather than a column-0 forgery, since the server's chosen segment silently replaces the URL on an `OK` receipt.

  **And the reasoning that kept four of them, which was half an argument.** `tests/test_preset_twin_splitlines_register_1119.py` registered `pr.py::_fetch_review_threads_detailed`, `issue.py::_print_linked_prs` and both `_gh_json` twins as *deliberate* `str.splitlines()` sites, on the ground that narrowing them would be worse — `str.splitlines()` **consumes** an exotic separator, where `_untrusted.split_lines` would leave a forged U+2028 inside the extracted string, and [#1346](https://github.com/Digital-Process-Tools/claude-supertool/issues/1346) pinned that claim with a test. It is true, and it is not the whole argument: consuming the separator means discarding everything before it, so the server still chose which segment became the message and the real error was dropped rather than disclosed — an absence produced by the tool, wearing a green test. All five entries are retired, the remaining two sites (`pr.py`'s threads decline, `gh-issue`'s linked-PR decline) are fixed the same way, and the #1346 assertion now says which half of the question it answers.

  `tests/test_gh_remote_body_relay_1648.py` feeds a U+2028-bearing body through each real relay and asserts on what a `[result]` consumer counts, never on `_untrusted.flat` having been called — a site can call it and print the raw value anyway. It also asserts the separator reached the render, so a site that dropped the text cannot pass for the wrong reason, and that a body which types the fence's own closing marker cannot close it. The [#1475](https://github.com/Digital-Process-Tools/claude-supertool/issues/1475) census ratchet caught every sink going away and is re-baselined at 158 sites in 34 files, with `UNRESOLVED` at 106 after locating the added site rather than before.
