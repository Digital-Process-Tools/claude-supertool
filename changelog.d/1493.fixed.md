- **`gl-issue` downloaded attachments into a fixed `/tmp` path any local user could own, and the containment check could not tell** ([#1493](https://github.com/Digital-Process-Tools/claude-supertool/issues/1493)). `IMAGE_DIR` was the literal `/tmp/supertool-images` — a fixed name in a world-writable directory, so a co-tenant could take it first, as a directory of their own or as a symlink pointing anywhere. `_is_inside` calls `os.path.realpath` on **both** of its arguments, so a symlink planted at the root was resolved through on both sides and containment answered `True` about the attacker's directory. The check was never wrong; nothing established what it was checking against. `#1484`'s fix constrained the value the *remote* chooses and is untouched by this — this is the root that value is joined onto.

  The root is now `presets/_image_root.default_root()`: `tempfile.gettempdir()` plus a per-uid suffix, created non-recursively at `0700`, then held open as `O_RDONLY | O_DIRECTORY | O_NOFOLLOW` so the tightening (`fchmod`), the ownership check and the mode check are three questions about one descriptor rather than three independent path resolutions. A root that is a symlink, a reparse point, not a directory, owned by another uid, or reachable by group or other after the chmod is a **refusal naming which of those it was** — three states, not two, per `docs/validators.md` §"Declining instead of guessing". `os.makedirs` no longer raises out of the op when something non-directory sits on the name.

  **`tempfile.mkdtemp()` per invocation was rejected on purpose.** It is the airtight answer and `gl-issue` prints the attachment paths under `## Images` for the reader to open, so a root that moves every call makes the receipt a path that existed only during the call that printed it. Stability is kept and its safety comes from proof rather than from luck.

  **What is not closed, stated rather than implied.** Another local uid can still squat `<temp>/supertool-images-<your uid>` before you, and the op then refuses rather than writing into it — attachments stop working until it is removed. A loud refusal is the correct side of that trade, and the per-uid suffix keeps two ordinary users on one machine from colliding by accident.

  **Windows.** The old value was a POSIX literal: a leading-slash path is anchored to the current drive there, so it landed in a `tmp/supertool-images` at the drive root rather than under the platform temp directory. `gettempdir()` on Windows resolves inside the user profile, which is not the shared world-writable directory the finding rests on, so moving off the literal is most of the repair. There is no `O_NOFOLLOW` or `O_DIRECTORY`; that branch uses `os.lstat`, which does not follow the final component, and refuses a symlink or a reparse point — a junction is a directory that `stat.S_ISLNK` denies, so `st_reparse_tag` is the only way to see one. The ownership and mode arms are **skipped** there rather than faked: `st_uid` is a constant on Windows and the permission bits are synthesized, so a verdict from either would be a sentence with no measurement behind it. Those Windows claims are **reasoned from CPython's documented behaviour, not observed on a Windows host** — the grade #627 recorded for itself.

  `_is_inside`'s docstring said what it compares and left a reader to infer a property it never had. It now states that it is a containment test and not an ownership test, and that realpathing both sides — which is correct for the leaf, and is what makes a remote-chosen `..` resolve to where the write would land — establishes nothing about the root.

  The ownership and mode arms are pinned through `_image_root.refusal`, a pure function of a stat result, precisely because the filesystem cannot reach them on Windows: a `skipif` there would have reported a coverage the suite does not have on the one platform whose reds are load-bearing in this repo.
