- **`gh-branch`'s conjunction now covers every run on the commit, not the newest run of each workflow name** ([#1640](https://github.com/Digital-Process-Tools/claude-supertool/issues/1640)). GitHub's default code-scanning setup emits **two distinct Actions runs per push**, sharing one `workflow_id`, one `path` and the one name `gh` renders. `latest_per_workflow` kept the higher run id, so on `d1bb0837` — the v0.42.0 release candidate — the release gate reported `GREEN … 18 legs across 2 workflows` over a population of 21 legs across 3 runs, and the run it dropped carried `Analyze (actions)`, a scan no other run on that commit performed. Everything was green, so the verdict was true by luck; a failure in the dropped run would have rendered identically.

  **The justification in the code named the wrong mechanism.** It kept one run per workflow because "a re-run supersedes the run it replaces" — but `gh run rerun` reuses the run id and bumps `run_attempt`, which the table's own note has said since [#1409](https://github.com/Digital-Process-Tools/claude-supertool/issues/1409). Attempts and runs are two axes; the code collapsed the second while naming the first. Attempts still collapse, now keyed on the run id that actually performs the supersession, highest `run_attempt` winning.

  **The discriminator cannot be the display name, the `workflow_id` or the `path`**, because the two runs share all three. Selection is keyed per run (`runs_on_sha`), and a workflow with two runs on one commit shows **both** rows, labelled `NAME (run ID)`, because a reader who cannot see the second row cannot check the verdict; a name with one run keeps its bare name and every ordinary render is unchanged. The green counts what it covered — `21 legs across 3 runs` rather than `across 2 workflows`. Workflow-scoped questions (the declared-set comparison, the previous-head comparison) read the names off the run objects through `workflow_names()` / `missing_workflows()`, so they still ask about workflows while the verdict asks about runs — `presets/dashboard/dashboard.py` and `presets/watch/tiers/gh_prs.py` go through the same seams and are fixed with it.

  **Ties break towards strictness.** A run whose `databaseId` cannot be read becomes its own entry rather than merging into another: two runs that cannot be told apart are counted twice and the conjunction gets stricter. A gate that over-reports pending is recoverable; this issue is what the other direction costs.
