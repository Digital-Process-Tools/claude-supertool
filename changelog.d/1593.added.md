- **`channel:probe` — put one byte through the bridge on demand, and refuse to call the result arrival** ([#1593](https://github.com/Digital-Process-Tools/claude-supertool/issues/1593)). `channel:health` and `radar`'s delivery line both report on traffic that already happened: a consumer that is bound, verified and counting publishes the same numbers whether it is reading its socket or wedged on it, because those numbers were written by whatever last happened to flow. Nothing could put an event through the path *now*, so the one time it was needed it was done with hand-written Python against `transport.emit_socket` — a private module, and a record shape (`ts`, `source`, `id`, `event`, `payload`, `first_tick`) a caller had to reverse-engineer from the producer to fake correctly. `transport.probe_record()` is now that shape as a function, and `channel:probe` writes one event and reports which of the consumer's own counters moved.

- **The value of the op is the refusal it makes about its own result** ([#1593](https://github.com/Digital-Process-Tools/claude-supertool/issues/1593)). Arrival inside a Claude session is observable only from inside that session — the bridge sends a JSON-RPC notification, which has no id and no response to wait on — so a probe that renders `forwarded` as receipt would rebuild [#554](https://github.com/Digital-Process-Tools/claude-supertool/issues/554) inside the fix for this issue. Instead every verdict prints the exact `<channel watcher_source="channel-probe" id="probe-XXXXXXXX" event="probe">` tag the caller should now look for, with a per-run id so a stale tag on screen cannot answer for a fresh probe; states that the increment is not attributable, because a poller emitting in the same window advances the same counter; and says which half of the bridge is left to suspect when the tag does not appear. `tests/test_watch_channel_probe_1593.py` asserts against the vocabulary, not only the verdict.

- **Three counters, not one, so a slow consumer and a broken one are different answers** ([#1593](https://github.com/Digital-Process-Tools/claude-supertool/issues/1593)). The issue proposed reading `forwarded`. The consumer also moves `lines_read` when it takes a line off the wire and `dropped` when it refuses one, and reading only the first folds *has not read it yet* into *read it and handed it nowhere*. Six verdicts follow, each with its own exit code: `FORWARDED` (0), `NOT DELIVERING` (1), `CANNOT DETERMINE` (3), `CONTRADICTED` (4), `ACCEPTED, NOT FORWARDED` (6 — a finding about the read loop) and `ACCEPTED, DISCARDED` (7 — the burst budget or an over-long routing key, which the consumer's own stderr names). The wait is bounded at 3s, so a consumer slower than that renders exactly like one that did nothing: every non-advance arm prints the budget it waited, and the arm where nothing was even read is `CANNOT DETERMINE` rather than a finding.

- **A cold baseline is the question, not a reason to decline** ([#1593](https://github.com/Digital-Process-Tools/claude-supertool/issues/1593)). The first cut of this op aborted with `CANNOT DETERMINE` whenever the consumer's counters were already stale, copying `channel:health`'s verdict — which is `health`'s correct answer, because the file is all it has. Measured 2026-08-15: the consumer over this clone was holding the socket with counters 607s cold, the probe declined, and the event it had just written arrived in a separate session as a rendered `<channel>` tag anyway. The read-and-forward path was working and only the heartbeat was dead, which is exactly the state nothing else can resolve — so the probe was declining in the one case that most needed it. `_health_objection` now takes `allow_stale`, passed on the baseline read and nowhere else: the re-read after the emit waives nothing, a positive still requires the file to come back both fresh and advanced, and a stamp that never comes back is still `CANNOT DETERMINE`. Reports that started from cold counters say so on their own line, because "the path works and the heartbeat is dead" is not "everything is fine".

- **The probe leaves no footprint that could later be read back as evidence** ([#1593](https://github.com/Digital-Process-Tools/claude-supertool/issues/1593)). Its `source` is the reserved `channel-probe`, so no watcher is impersonated in a session that routes on `watcher_source`, and the reservation is checked against the contents of `presets/watch/sources/` rather than promised in a comment. It goes through `emit_socket` and not `emit_event`, so no watcher state file is written or overwritten — one with a reserved source would show up on `watches` and in `radar`'s delivery survey as a watcher that does not exist, which is the op's own footprint read back as a fact about the fleet.
