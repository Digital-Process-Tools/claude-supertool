- **`gl-issue` created the attachment directory the API response chose, and checked containment against that same directory** ([#1484](https://github.com/Digital-Process-Tools/claude-supertool/issues/1484)). `iid` comes out of the `glab issue view --output json` reply, so the directory `_download_images` writes into was named by the remote host. `os.makedirs` ran before anything validated it, and the per-file guard was anchored to that already-derived directory — a boundary derived from the value it is meant to constrain, which is [#1246](https://github.com/Digital-Process-Tools/claude-supertool/issues/1246)'s shape one layer down. `_is_inside` itself was correct; it was asked the wrong question.

  Reproduced against the real guard and the real root: an `iid` of `../../../../tmp/audit_pwned` gave `realpath` `/private/tmp/audit_pwned` from an `IMAGE_DIR` of `/tmp/supertool-images`, with `_is_inside(local, out_dir)` answering `True` and `_is_inside(local, IMAGE_DIR)` answering `False`. An absolute `iid` makes `os.path.join` discard the root outright.

  A non-numeric `iid` is now refused **before** any directory exists — a directory created is already a write — and every containment check is anchored to `IMAGE_DIR`, never to the derived path. The tests assert on the filesystem, on what exists under and outside the root after the call, never on a guard having been called: a site can call a guard and write anyway.

  Precondition is a hostile or compromised GitLab host, since `iid` is server-assigned; it is not reachable from an issue author alone.
