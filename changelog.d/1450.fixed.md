- **An `unless_flag` token sitting in another option's value slot un-claimed the entry, so `gh pr create -t --dry-run -b y` was `clean` and really opens a pull request titled `--dry-run`** ([#1450](https://github.com/Digital-Process-Tools/claude-supertool/issues/1450)). The guard read the `--dry-run` in `-t`'s value slot as an exclusion — the same defect [#1430](https://github.com/Digital-Process-Tools/claude-supertool/issues/1430) had for help flags, one function over. `clean` is a positive claim that nothing in the command is replaced, made about a command that opens a PR.

  **It is disclosed, not blocked, and that is the opposite call to the help fix.** A help flag is terminal and rarely combined, so blocking its ambiguous slot costs a legible wrong block. The flags entries exclude are the ones people put together: seven shipped invocations flip clean → blocked if this slot is scored, five of them previews of a destructive push — `git push --force-with-lease --dry-run`, `git push --no-verify --dry-run`, `git push -u --dry-run origin main`, `git push --set-upstream --dry-run origin main`, `git push --force-with-lease -n` — and a refusal that names `git-push` under a blocked `--dry-run` performs exactly what the blocked command declined to do.

  So `_guard_excluded()` becomes `_guard_exclusion_state()` with three answers — `none`, `excluded`, and `value` for a token the guard cannot tell from the preceding option's value. `value` un-claims the entry exactly as before, nothing new is blocked, and the segment is `undecided` with a note instead of `clean`. One unambiguous exclusion anywhere in the argv decides the whole argv, so `git commit --amend --dry-run`, `git push --dry-run` and `git status -s -z` stay silently clean; a long option carrying its value attached (`--title=x --dry-run`) leaves no slot open either.
