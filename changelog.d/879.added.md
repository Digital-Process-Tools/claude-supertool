- **`git-push:set-upstream` and `git-push:to-upstream` — the two intents behind the ambiguous-upstream refusal, said in this op's own vocabulary** ([#879](https://github.com/Digital-Process-Tools/claude-supertool/issues/879)). When `@{upstream}` resolves to a branch that is not this one, the op still refuses to guess. These are how the caller answers it without leaving the op:

  ```bash
  ./supertool 'git-push:set-upstream'   # push <branch> under its own name, retargeting tracking to <remote>/<branch>
  ./supertool 'git-push:to-upstream'    # push onto the tracked ref on purpose, explicit HEAD:<ref> refspec
  ```

  `:set-upstream` is the usual first push for a worktree branch. Its receipt names what it retargeted away from rather than rendering the branch as if it had never had an upstream — saying `Upstream: none` there would hide the exact thing the flag authorised.

  `:to-upstream` never issues a bare push: a bare push is precisely the input `push.default=simple` refuses, so the refspec is explicit and the header names the destination, since that destination is routinely a shared base branch. The rebase-recovery re-push carries the same refspec, or a non-fast-forward would silently turn a deliberate target back into the bare push git already rejects.

  **Asking for both is refused** (exit 2, nothing pushed) naming the two refs. They are different destinations; resolving the contradiction by precedence would be exactly the guess the refusal exists to prevent, and on the `:to-upstream` side the wrong choice writes to a branch everyone shares. Neither flag has a default and neither is implied — the caller still has to say which one they meant, which is the whole value of the decline.
