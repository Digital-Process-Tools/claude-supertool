- **`hooks/guard-selftest.py` — a bash-free check for whether the raw-command guard is enforcing on this host** ([#1378](https://github.com/Digital-Process-Tools/claude-supertool/issues/1378)). `hooks.json` invokes the guard through `bash`. Under native `cmd.exe` or PowerShell with no Git Bash and no WSL it never executes, every raw command an op supersedes runs unguarded, and the session is byte-identical to one where the guard ran and had nothing to say — the house defect at the platform layer, with no disclosure channel at all.

  **The disclosure cannot be a hook.** Every hook this plugin ships is a bash script, `session-start.sh` included, so a line added to one is a line that cannot run on the host it would describe; and [#1382](https://github.com/Digital-Process-Tools/claude-supertool/issues/1382) has already ruled that a non-zero SessionStart hook is a broken session on every platform to report a missing interpreter on one. So it is a check the user runs — `py -3 hooks/guard-selftest.py` on Windows, `python3 hooks/guard-selftest.py` anywhere else — written in Python because Python is what such a host has.

  Three states, the guard's own: `enforcing` (the wrapper ran here and denied a command the registry replaces, end to end through the shell it will really use), `could not run` (naming what was tried), and `nothing to test` (the registry replaces nothing, so `enforcing` would be an empty claim). It says plainly that it **cannot tell** whether Claude Code invokes the hook — that is not observable from there, and claiming otherwise would be the same absence-read-as-presence one layer up. A `bash` is chosen by what it does, not by what it is called: on Windows `bash.exe` on PATH is commonly the WSL launcher, which is not a shell and cost PR [#1399](https://github.com/Digital-Process-Tools/claude-supertool/pull/1399) four `windows-latest` legs.

  **The README said the opposite, which is what made the gap invisible.** Its platform section stated that a native `cmd.exe`/PowerShell host has no `Bash` tool "so there is nothing for the raw-command guard to gate". That is contradicted by this repo's own [#1413](https://github.com/Digital-Process-Tools/claude-supertool/issues/1413): where the PowerShell tool is enabled Claude treats PowerShell as the primary shell and routes shell commands through it, which is why `hooks.json` matches `Bash|PowerShell`. There are commands to gate and no bash to gate them with. The sentence is gone and the check is documented in its place.

  Windows evidence grade, the [#627](https://github.com/Digital-Process-Tools/claude-supertool/issues/627) convention: everything here about native `cmd.exe` and PowerShell is **reasoned, not observed** — nobody on this project has that host. What is observed is that the wrapper is bash, that `hooks.json` names bash, and that denying a POSIX host a usable bash produces exactly the state described.
