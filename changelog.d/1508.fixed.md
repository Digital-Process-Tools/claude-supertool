- **`gh-prs` counted unresolved review threads over one capped page, so a busy PR could lose its thread flag entirely** ([#1508](https://github.com/Digital-Process-Tools/claude-supertool/issues/1508)). #1491's defect one op over, and it lands on a flag rather than on a number: the board never printed the count, it printed `threads` when the count was non-zero. At `reviewThreads(first: 100)` that count is a floor, and a floor of **zero** carries no information — so a pull request with more than 100 threads whose first page happens to be all-resolved rendered with no thread marker at all, indistinguishable from one that has none. GraphQL returns threads in creation order, which puts the newest and least-resolved ones on the page nobody fetched.

  That is [#1445](https://github.com/Digital-Process-Tools/claude-supertool/issues/1445)'s mechanism reached by a second route. Not an omitted number: the removal of the one marker that would have made somebody look, on the read that decides which PR to open next. A row at the page cap with nothing unresolved on it now flags `threads?` — the same "could not be established" state a declined GraphQL call already used — and a line above the board says how many rows hit the cap, so that `threads?` is not confused with a call that failed.

  A floor **above** zero is untouched and still flags a plain `threads`. Once the render is a boolean, `at least 1 unresolved` and `1 unresolved` make the same claim, and hedging a number the reply does establish would be the same defect pointed the other way. The cap constant is imported from `gh-pr`, which is where the query that fetched under it is built, rather than copied.
