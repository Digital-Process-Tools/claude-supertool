- **A doubled-backslash escape sequence exempted via `literal_backslashes` into a `.py` file now carries an advisory note on the write receipt, naming the field and byte offset, instead of landing silently** ([#2493](https://github.com/Digital-Process-Tools/claude-supertool/issues/2493)). `_payload_double_backslash_refusal` (#1087) already blocks this shape unconditionally in a TOML literal-block payload unless the author exempts it — so the scenario the issue reported (a doubled backslash-n where a real newline escape was meant, `py-syntax` reporting `ok` because both parse) can only reach disk once an exemption is in play. The residual gap: `literal_backslashes` exempts a whole *field*, not one occurrence, so a single legitimate doubled run (a regex, a Windows path) in a `content`/`new` field silently waives every other doubled run in that same field too, including a genuine typo. The new advisory reuses the refusal's own scan, fires only for occurrences the payload already exempted and only for `.py` targets, and is appended to the receipt after the `[validators]` block — never to `py-syntax`'s own verdict, which correctly stays `ok`, and never blocking or rolling back the write.
