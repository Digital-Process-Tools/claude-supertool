- **`read:PATH:::grep=PATTERN` answered `(no lines matching 'PATTERN')` about a file that contains it** ([#1052](https://github.com/Digital-Process-Tools/claude-supertool/issues/1052)). The filter was never the problem — the window was. `op_read` applied the `read.max_lines` default (300) before handing off to `render_file`, and the filter ran inside that window, so on a 351-line file the inline filter looked at lines 1-300, never saw the match at line 328, and reported its zero in the tool's own voice. The standalone `grep` op found the same string in the same file in the same session, which is the only reason it was caught. It cost a wrong step: the zero was read as "this checkout does not have that test" and the next few minutes went into branch divergence.

  A filter is not a window. `read.max_lines` bounds how much a read **emits**; it never had a reason to bound how much a filter **searches**, and a filtered read emits only the lines that matched. `grep=` with no explicit LIMIT now searches the whole file — the 20 KB byte cap still bounds the output, and still discloses itself when it fires.

  **And the zero has three states now, not two.** Whenever the scan did not cover the file — an explicit `read:PATH:0:10:grep=X`, an offset, a byte cap — the answer names the range it searched and the number of lines it did not: `(no lines matching 'X' in lines 1-10 of 340 — the other 330 lines were NOT searched, so this is not an answer about the whole file)`. A filter that matched something but stopped short says so too. The sibling `grep` op's zero has always carried `scanned N files`, which is what makes it trustworthy; this one carried nothing at all.

  **A third state on the same code path, one layer up.** A `grep=` value that does not compile as a regex falls back to `re.escape` and a literal search. The fallback is right — an unusable pattern should not fail a read — but it was silent, so a rejected pattern's zero was spelled exactly like a real absence. The receipt now names the `re.error` and says the search was literal.
