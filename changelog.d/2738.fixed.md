- **`grep`, `glob`, `tree` and `map` skip gitignored files, not only gitignored directories** ([#2738](https://github.com/Digital-Process-Tools/claude-supertool/issues/2738)). Since #449 the walks pruned directories git ignores and searched ignored files anyway. Measured on a scratch repo on 2026-10-04: `grep` printed an ignored file's contents, `glob:*` auto-read one, `tree` listed an ignored file and an ignored directory (it pruned neither), and `map` extracted `def leaked` from an ignored `.py`. Credential files were kept out only by the default exclude list, which stays; `.gitignore` is now a second layer on top of it. The single `git ls-files --others --ignored --exclude-standard --directory` each walk already ran answers for files too, so it is still one git call per walk root, never one per file. The header says what was skipped (`3 gitignored files hidden`), so a filtered search never reads like an empty one. A path named directly is always searched: `grep:X:DIR/` on a gitignored directory finds X (unless the exclude list also names it), and `grep:X:FILE`, `glob:FILE` and `map:FILE` read a gitignored file you name, the way `rg` does. The opt-outs (`"gitignore": false`, `SUPERTOOL_NO_GITIGNORE=1`, `:no-exclude`) are unchanged. Outside a git repository, without `git`, or when the listing fails, the header says `gitignore filter not applied (WHY)` rather than showing an unfiltered walk as a filtered one. Inside a repository, `grep` does not delegate to rtk when an ignored file the exclude list does not cover would be walked, or when the listing failed, because the system grep rtk runs knows nothing about `.gitignore`; outside one there is nothing to hide, so it delegates and the delegated header carries the same `not applied` clause. `replace` walks through the same candidate list as `grep`, so it skips gitignored files too.
