- **`grep`, `glob`, `tree` and `map` skip gitignored files, not only gitignored directories** ([#2738](https://github.com/Digital-Process-Tools/claude-supertool/issues/2738)). Since #449 the walks pruned directories git ignores and searched ignored files anyway. Measured on a scratch repo on 2026-10-04: `grep` printed an ignored file's contents, `glob:*` auto-read one, `tree` listed an ignored file and an ignored directory (it pruned neither), and `map` extracted `def leaked` from an ignored `.py`. A gitignored `.env` was kept out only by hardcoded exclude entries. Now the single `git ls-files --others --ignored --exclude-standard --directory` each walk already ran answers for files too, so it is still one git call per walk root, never one per file. The header says what was skipped (`3 gitignored files hidden`), so a filtered search never reads like an empty one. A path named directly is always searched: `grep:X:.max/` on a gitignored `.max/` finds X, and `grep:X:FILE`, `glob:FILE` and `map:FILE` read a gitignored file you name, the way `rg` does. The opt-outs (`"gitignore": false`, `SUPERTOOL_NO_GITIGNORE=1`, `:no-exclude`) are unchanged. Outside a git repository, without `git`, or when the listing fails, the header says `gitignore filter not applied (WHY)` rather than showing an unfiltered walk as a filtered one, and `grep` does not delegate to rtk then, because the system grep rtk runs knows nothing about `.gitignore` and its report has nowhere to say so. `replace` walks through the same candidate list as `grep`, so it skips gitignored files too.
