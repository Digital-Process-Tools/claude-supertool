- **A missing dev.to CSRF token no longer blames a redesign that did not happen, and the encoding scan no longer reads `open(timeout=...)` as a file open** ([#766](https://github.com/Digital-Process-Tools/claude-supertool/issues/766)). Two reports about conditions neither check had actually looked at.

  `devto`'s session-cookie path scrapes an `authenticity_token` out of `/settings`. When it found none, it had exactly one thing to say — `authenticity_token not found in /settings HTML — Dev.to layout may have changed` — and the common cause is the other one: `dev.to` answers `/settings` with a same-origin 302 to `/enter` once the session cookie expires, the redirect is legitimate and is followed, and the login page carries no token. Every noun in that message was then wrong: the HTML was `/enter`, the layout was fine, the cookie was dead. [#761](https://github.com/Digital-Process-Tools/claude-supertool/issues/761) added a `NOTE:` line disclosing the hop, but the line an operator acts on still pointed at a dev.to redesign.

  There are three outcomes now rather than two, and the difference between them is a fact the op already had — the URL that answered. Token found; token absent from a page that answered under a *different* URL, which names the expired cookie and tells you to re-copy it; token absent from `/settings` itself, which says so, states that no redirect happened and therefore that the session is live, and only then says the layout may have changed. The unknown case stays unknown: replacing one confident wrong cause with a different confident wrong cause is the same defect facing the other way.

  Separately, `tests/test_encoding_seam.py`'s AST scan treated every `X.open(...)` as `Path.open` — one carve-out for `os.open`, nothing else — so `presets/_http.py`'s `OpenerDirector.open(req, timeout=timeout)`, which touches no file and decodes nothing, was reported as `open() without encoding=` and failed the build. #761 worked around it by binding the method to a plain name, a contortion of shipped source to satisfy a false positive that would have bitten the next author calling `.open()` on something that is not a path.

  The scan now declines a call that names a keyword neither `open` nor `Path.open` declares. That is a fact about two signatures rather than a guess about a receiver, so it cannot be widened by accident: every keyword they *do* declare still flags, and `**kwargs` — where the names are unknown at parse time — still flags too, on the rule the scan already used for a non-literal `mode`. The plain-name binding in `_http.py` stays, but as the deliberate patch seam the redirect tests need, and its comment now says that instead of citing a false positive that no longer exists.
