- **A workflow name could arrive as `gh-branch`'s own `(run ID)` annotation, byte for byte** ([#1687](https://github.com/Digital-Process-Tools/claude-supertool/issues/1687)). `runs_on_sha` labels a row `NAME (run ID)` when one workflow name has two runs on the commit ([#1640](https://github.com/Digital-Process-Tools/claude-supertool/issues/1640)), and `NAME` is `workflowName` — remote text, chosen by whoever controls the repo's `.github/workflows`. A workflow literally named `Analyze (run 12345)` therefore rendered identically to supertool's annotation of a workflow named `Analyze`, in the first column of the table the merge gate and the release gate are both read off.

  `_untrusted.flat` does not reach it: every character is printable, and what was missing is a *boundary*, not a control-character strip. The tool's own shape is now neutralised where it appears in a name — `(run-tag in name, neutralised)`, ASCII so it survives every console this repo supports — which is what `_untrusted.scrub` already does for the fence markers. After it, the only `(run <digits>)` in a label is the one supertool wrote, and `run_id_note()` says so instead of teaching the reader to trust the ambiguous form.

  Declined rather than censored: the rest of the name survives, and a name with one run is neutralised too, since a bare row that looks annotated is the same forgery with a shorter reach. Only the *label* changes — `workflow_names()` reads the name off the run object, so the declared-set check and the previous-head comparison still see the real name, and #1640's two rows are still both listed and both still have to pass.

  Bound: this needs write access to the repository's workflow files, which is an actor who can already affect the verdict by editing what runs. The class is what makes it worth recording rather than the reach.
