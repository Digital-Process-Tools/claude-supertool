- **`gh-job:N:fail` says when it elided something and how much, and the count that settles legs-versus-tests is printed** ([#1050](https://github.com/Digital-Process-Tools/claude-supertool/issues/1050)). The gap between two matched error blocks was rendered as a bare `...`, which is the *log's* own vocabulary — a truncated `AssertionError: ...`, a pytest diff elision, a `gh` field cut short. Reading PR #1047's Windows red, that `...` covered a `[validators]` block whose single line, `fake : ok (no new errors)`, was the entire discriminator between three candidate causes; it read as part of the assertion above it, was never looked for, and recovering it cost a second call with `:grep:`. The op was not truncating at the end — it said `no tail truncation` — it was eliding the middle, which is the harder case to notice because the output looks complete. Markers now name the cause and the size, and every withheld line, including any past the last shown block, is accounted for by exactly one of them.

  Two more defects were on the same lines. A phantom marker was emitted before the very first block whenever the first match was line 1, claiming an elision over nothing at all — an absence the op invented, printed directly above the log's own first line. The same off-by-one sat in `:grep:`.

  Separately, `checks: 20 total: 16 passed, 4 failed` counts **legs** and nothing said so. Read as four *tests*, with three names visible past the elision, it looked like some legs passed where their structurally identical twins failed — which points at ordering or shared state, a completely different investigation. It was six-of-six uniform across all four legs, which points at the fixture, and the agent handed that diagnosis had to correct the premise before it could work. `gh-job` now prints the job's own terminal summary as a `Suite:` line — the only number in the render that counts tests — and `gh-pr` adds a one-line unit note under a tally that has something in the failed bucket, and only then. A log that states no summary prints no line rather than a zero. The line is matched by its shape rather than by pytest's `=` rule, because GitHub Actions is not a tty and writes none: a first version required the fences, passed against a fixture built from the issue's quote, and would have matched nothing in any real CI log.
