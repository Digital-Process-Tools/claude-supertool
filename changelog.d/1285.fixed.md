- **Three registries named `blame`, an op the dispatcher stopped accepting in April** ([#1285](https://github.com/Digital-Process-Tools/claude-supertool/issues/1285), folding in #1152). `b4099a5` moved `blame` out of the builtins into the `git` preset as `git-blame` and removed it from four places; `_PARALLEL_SAFE_OPS`, `_PATH_ARG_POSITIONS` and `_READ_OP_TARGETS` kept their rows, as did three doc pages. `git log --all -S` settles the question the issue could not: it was **removed**, not left unfinished. The `git blame --line-porcelain` machinery still in the core is `git-investigate`'s blame-hotspot section, not an abandoned op. The risk was nil while nothing dispatched — an op that cannot be invoked cannot misbehave — but two of those tables are containment-adjacent, saying which argument is a path and what may be read, so the row is inert by coincidence: the day a preset or config op is named `blame`, it applies to that. `tests/test_registry_names_dispatch_1285.py` now holds all four op registries against the dispatcher, structurally and by probing `dispatch` itself. PR #1418's equivalent check derives its denominator from the docs, so it did not cover these. There turned out to be a **fifth** registry the issue does not name and the only one anybody copies: `.supertool.example.json` documented `blame` under `builtin-ops` with a syntax, a description and an example, so every project started from that file listed the op in `ops` and produced a full `help:blame` reference for a name answering `unknown operation`. Both config files are checked now, against the op named at the head of each entry's `syntax` rather than against its key — `grep-count` and `read-grep` are deliberately labels for a mode of `grep` and of `read`, and their syntax says so.
- **`_PATH_ARG_POSITIONS` moved from a local literal inside `dispatch` to module scope** ([#1285](https://github.com/Digital-Process-Tools/claude-supertool/issues/1285)). No behaviour change — it is a constant, rebuilt on every dispatch call until now — but as a local it was unreadable from outside the function, which is why the one table whose rows declare *which argument is a path* had never had its membership checked against anything.
