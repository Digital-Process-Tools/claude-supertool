- **An absent-tool gate could say "found" while its own spawn said "not found," across every validator and formatter that migrated to #2575's cwd-safe spawn** ([#2579](https://github.com/Digital-Process-Tools/claude-supertool/issues/2579)). #2575 routed the *spawn* side of `argv0(name)` and `resolve_bin_cmd()` through `which_excluding_cwd()`, so a repo-planted `ruff.cmd` at the project root can no longer be executed -- but the *gate* that decides whether to spawn at all was left calling raw `shutil.which()` in every one of those adapters, which still finds a cwd-planted shim via the current-directory search that guard exists to exclude. The two calls then searched different `PATH` lists: a cwd shim passed the gate and then failed to spawn, landing on the "tool vanished between the two checks" arm rather than being recognised as never genuinely findable. Not a security regression -- the #2575 fix still held -- but a correctness gap that would mislead anyone debugging a validator failure without reading both call sites. Fixed by routing every gate through `spawnable()`, the same chokepoint the spawn already used, across the 25 adapters affected: 23 in `validators/` (the ~18 #2575 named, plus `shellcheck`, `phpstan`'s sibling `ci-lint`, and the `jit-index` adapter's own `awk` presence check, which had never gone through the chokepoint on either side) and all 4 in `formatters/`, which shared the identical compound-gate shape but had not been part of either prior sweep. `validators/phpstan/phpstan.py` is the one adapter deliberately left unchanged: its `_BIN` value is spliced into `php`'s argv as a literal script path, never resolved through `argv0()`/`spawnable()`/`resolve_bin_cmd()` at all, so its gate has nothing to be inconsistent *with* -- fixing it alone would not close anything, and it is tracked separately. `tests/test_gate_matches_spawn_2579.py` is the register that keeps the class closed: it flags any adapter that spawns through the cwd-excluding chokepoint while still gating on raw `shutil.which()`.
