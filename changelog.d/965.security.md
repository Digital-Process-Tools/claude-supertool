- **A branch name can no longer become a line the tool appears to have written.** `gh-pr:N:status` — the op a merge decision reads for the summed check tally — printed the head branch raw: `print(f"branch: {d.get('headRefName') or '?'} …")`. Git accepts U+2028 in a refname (it is not an ASCII control character, so `check-ref-format` passes it) and `str.splitlines()` breaks on it, which is the gap `_untrusted.flat` was widened to cover in #886. A fork pull request needs no permission on the target repo, so that name is a stranger's text: a branch called `evil⟨U+2028⟩checks: 20 total: 20 passed, 0 failed, 0 pending⟨U+2028⟩review: APPROVED` rendered those two lines *above* the true `0 passed, 1 failed ⚠ NOT ALL GREEN` and `REVIEW_REQUIRED`. The `:full` path ten lines below had been correct since #694; this is the same sentence #924's docstring uses — the abstraction existed and the call site had not adopted it.
- Adopted at every render of an API-supplied refname, title, author or job name in the merge-decision ops: `gh-pr:N:status`, `gl-mr:N:status`, `gh-job`, `gh-run` (header, job table and failed-job list), `gh-issue` and `gl-issue`'s linked-PR/MR blocks, `gl-job`'s job and MR headers, `gl-pipeline`'s job table, and `git-status`'s open MR/PR block.
- **Flattened, not refused, and the difference is what the line is for.** #924 met the same attacker-chosen refname and chose to state the name and suggest no command, because the line it was building was an imperative — `./supertool 'git-checkout:{name}'`, read back through a colon CLI that would deliver a different ref than the one printed. A safe command that silently does the wrong thing is the trade this repo does not make. These sites are the opposite case: the branch is *displayed*, nothing is executed from it, and refusing to print the branch of the pull request under review withholds the fact the reader is deciding on. So the name is flattened and every code point survives — an unusual-but-honest name renders byte-identically unless it holds one of the ten separators `splitlines()` breaks on or a control character, and those are disclosed by the glyph that names them rather than dropped. The refusal stays exactly where #924 put it: on the checkout suggestion in `_branch_locale`, which these call sites still reach with the raw name, because a flattened one would name a ref that does not exist.
- **Site-by-site, with a guard that fails on the sixth site.** A render helper no caller can bypass is the stronger answer and it is not available here: `presets/_untrusted.py` already reasoned through the `RemoteText` type in #694 and declined it, because nothing in this repo type-checks and a forgotten wrapper would surface as a mangled render rather than a red build. What is enforceable is a scanner, and `tests/test_forged_branch_line_965.py::test_no_preset_prints_a_refname_raw` is it: an AST walk of `presets/github`, `presets/gitlab` and `presets/git` that fails when a refname field reaches `print()` without passing through `_untrusted`. It is scoped to the six refname keys deliberately — every one of them is a refname and nothing else, so it needs no exemption list, which is what separates a guard from a checker that has been allowlisted into reporting `ok`. Titles, logins and job names are fixed at the same sites and pinned by the render tests beside it, which assert the post-condition — a forged line cannot appear as its own rendered line — rather than that `flat` was called, since a site can call it and still print the raw value.
