- **`watches` on a named channel listed the default channel's pollers as its own orphans, and `radar`'s reap stopped them ([#1514](https://github.com/Digital-Process-Tools/claude-supertool/issues/1514)).** `transport.poller_argv` writes the label every reader matches on, and it carried `(source, id)` with no channel dimension. So a scan under `SUPERTOOL_WATCH_NAME=oss-supertool` enumerated every labelled poller on the machine, found no pid file for the other channel's ones under *its* state directory, and rendered four of them with `no pidfile` — the one marker an operator acts on, and `unwatch:SOURCE:ID` on any of them would have stopped a watcher belonging to a different channel. Two renders in one call disagreed: the board listed four watchers, `channel:health` said that channel had never spawned anything.

  **The reap was the sharper half and the issue had left it open.** `dispatcher.reap_duplicate_pollers` reads the same scan. One poller per channel on the same `(source, id)` grouped as one slot with two pollers; the survivor is the PID *this* channel's pid file names, so the other channel's was signalled. A cross-channel kill, reached through a listing bug.

  **The label now carries the state directory, digested, as a trailing `chan=` token.** The slot is a pid file held `O_CREAT|O_EXCL` by one process per state directory (#476), so two pollers are on one slot only when they contend for one pid file — which makes `STATE_DIR` the right dimension, not the channel name: a name and an explicit `SUPERTOOL_WATCH_STATE_DIR` can name one directory, and two names can be pointed at one. A digest and not the path, because `ps` output is split on whitespace and an operator-supplied directory may contain some, because `ps` is world-readable, and because a fixed 12 characters keeps the command line readable. Appended rather than inserted, so `dispatcher._parse_args` — which already ignores unrecognised trailing tokens — parses a re-exec'd poller back unchanged.

  **Three states, and only one is acted on.** `transport._labelled` now answers `(channel, source, id)` where the channel is this one, another one, or `None`. `scan_poller_pids` returns only the first, because every caller of it decides an action: `unwatch`'s multi-kill, the reap's signal, the board's `no pidfile` marker. A PID is acted on only when its own argv proves it is ours.

  **What that costs, stated rather than hidden.** A poller started before the `chan=` token carries no channel and becomes invisible to the scan. It is not reported as this channel's and not as another's, because nothing in its argv can tell them apart. That is the same by-design blindness `docs/presets/watch.md` already describes for pollers predating the #511 labelling, one generation later, and it clears the same way — `pkill -f 'presets/watch/'` once, or a `radar` tick that respawns the fleet. A poller whose pid file this channel holds is unaffected: `watcher_pids` unions the pid file's own PID, and the pid file is per state directory by construction.

  **Windows.** No platform-specific code and no path literal. The key is `hashlib.sha256` over `os.path.normpath(STATE_DIR)`, so a trailing separator cannot split one directory into two channels, and the parent and its exec'd child agree by construction because `poller_env` pins the resolved value into the child's environment rather than letting it re-derive. Pinned by `tests/test_watch_channel_scoped_labels_1514.py`, which spawns, signals and reaps nothing: the process table is a list, liveness is a set, and `_stop_pid` only records.
