- **The render-size pin measured how deep your checkout was and reported it as documentation drift** ([#1877](https://github.com/Digital-Process-Tools/claude-supertool/issues/1877)). Every render it grades carries `_preset_disclosure()`, which names the absolute path of the config it read, so a raw byte count is partly a measurement of the developer's directory layout. The pin absorbed that into its 0.1KB tolerance on a sample of one — PR #1876 had compared two paths six characters apart and got a six-byte difference, and 100 bytes is generous against six. The sample was six; the range is not bounded by anything. Measured 2026-08-21 at `c6dd83ae`, one tree at two paths: `ops` renders 3,724 bytes from a 43-character worktree and 3,811 from a 130-character one. 87 characters of path, 87 bytes of render, 87% of the whole tolerance. `ops` at ~3.7KB is where it bites hardest — 100 bytes is 2.7% there, against 0.14% at `ops:full`.

  **The trigger was a maintainer's false positive, and that is the most useful thing in this entry.** A disposable clone taken under a 129-character scratchpad path failed four rows with `README.md says ops is ~3.7KB; this checkout renders 3.81KB (3,810 bytes)`. That was diagnosed as a composition defect between this pin and [#1881](https://github.com/Digital-Process-Tools/claude-supertool/issues/1881) — two pull requests each green on its own merge-base, the theory being that a changed op description had moved the `ops` render — and briefed to an agent as a red `master` needing an urgent figure bump. None of it was true. `master` was green (`21 legs, 21 passed`), and all four renders are byte-identical either side of that merge: 3,724 / 72,712 / 14,705 / 1,966, re-measured at one path on both commits. Had the brief been followed, the four sites would have been bumped to ~3.8KB and made wrong at every normal checkout, CI included. The next person to hit this will be holding the same confusing evidence: a red naming a documentation figure, produced entirely by their own working directory.

  **The path is now normalised away before grading rather than tolerated.** `graded_bytes` substitutes one fixed path — CI's own checkout path, pinned as a literal so no environment can move it — for whatever the running checkout is, so the graded figure is the same number everywhere and on every platform. A Linux runner at `/home/runner/work/...` and a Windows runner at `D:\a\...` differ by 12 characters today and by whatever the runner images decide tomorrow. Tolerating the path was worse than it looked in *both* directions: a deep checkout false-fires, and a shallow one hides real drift byte for byte, since a figure measured 90 characters deeper than the reader's checkout eats 90 bytes of the same budget. With the variable gone, 0.1KB means only what [#1884](https://github.com/Digital-Process-Tools/claude-supertool/pull/1884) argued it meant — room for prose to round — and stays two orders below the 2,129-byte drift the registry exists for.

  **Substituted rather than deleted, and no documented figure moved.** Stripping the path outright was the first fix written here and it was wrong: it grades a render nobody receives. `ops:roster` comes to 1.907KB stripped, which rounds to ~1.9, so the honest consequence would have been correcting `README.md`, `docs/operations/index.md` and `hooks/session-start.sh` away from the ~2.0KB a reader at any real checkout actually sees — making the prose less true to make the grader more convenient. With a stand-in of realistic length every one of the five stated figures stays exactly as it is, and the tightest of them now sits 68 bytes inside the tolerance rather than 13.

  **`graded_bytes` refuses rather than answering when it cannot normalise.** Caught by the audit of this change, in the guard the change adds: the first version substituted the path only `if path:` and otherwise fell through to the raw byte count. `_preset_disclosure` names `os.getcwd()` when `_CONFIG_PATH` is falsy, so a render in that state is still checkout-dependent while the one string that locates it is gone — the un-normalised number in the shape of a normalised one, failing with the same "this checkout renders N bytes" sentence that started all of this. It now asserts, and the refusal is pinned by a test of its own, because every row reaches the helper through a fixture that always sets a path and a refusal nobody can produce is indistinguishable from one that was never written.

  **The new row asserts the property with a positive control, because on its own it would pass on silence.** If the disclosure ever stopped naming the path, both renders would come back the same length and "the graded size does not move with the path" would pass while checking nothing — the guard reduced to the exact absence it detects. So it first requires the raw sizes at two config paths to differ by *exactly* the path difference, and only then compares. All fifteen rows fail the property before this change and pass after, and the same suite at the 130-character scratchpad path goes from eight red to green.
