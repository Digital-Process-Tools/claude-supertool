- **`watches` no longer dies on a state directory no spawn has created** ([#1502](https://github.com/Digital-Process-Tools/claude-supertool/issues/1502)). Adding `watch_name` to an op block and running the first read raised `FileNotFoundError: '/tmp/supertool-watch-oss'` out of `os.listdir` and refused every other op in the same call — `[batch] 2 ops ran — all 2 refused`. The default state directory is `/tmp` itself, so that enumeration was unreachable-by-luck on the default and guaranteed to fire on the first read after naming a channel, which is the headline feature of the release before it.

  Three states, not two. An absent directory is a *knowable* fact — zero watchers, nothing has ever spawned on this channel — and now renders as one line saying so, naming the directory and the variable that chose it. A directory that exists and could not be listed is *unknown*: it prints a warning and never the words `No active watchers`, which would be a claim about the fleet built on a listing that never ran. An empty directory that exists still reads exactly as it did.

  Nothing on a read path creates the directory, deliberately. Only a spawn creates a *derived* one, and a `SUPERTOOL_WATCH_STATE_DIR` the operator supplied is never manufactured at all ([#693](https://github.com/Digital-Process-Tools/claude-supertool/issues/693)) — a read with side effects is a worse trade than a read that says which of the two states it is in.

  Swept rather than patched at the reported line: every enumeration of the state directory in `transport.py` now goes through one guarded reader, and a test refuses a bare `os.listdir` there. `radar:--state` survived this by never enumerating, which was luck and not a guard.
