- **`radar`'s default-branch row and `gh-branch:<ref>` are pinned to the same composition** ([#1951](https://github.com/Digital-Process-Tools/claude-supertool/issues/1951)). Reported as a live contradiction: `gh-branch` named three concluded, successful runs on a commit, and `radar`'s default-branch member row, run minutes later, reported zero and named a workflow (`Dependabot Updates`) that is not declared in `.github/workflows` at all -- GitHub's own implicit repository-level workflow, visible only through the repo-level `/actions/workflows` listing. Read against `presets/watch/tiers/gh_prs.py::default_branch_report` and `presets/github/branch.py::main`: both call the identical sequence -- `_head_commit` then `_run_list(ref)` (branch mode, not commit mode) then `runs_on_sha` then `verdict` -- so the two entry points cannot structurally disagree given the same `gh run list` answer. A regression test (`tests/test_watch_gh_branch_poller_integration_1953.py`) now pins that composition end to end, mocked only at the `gh` subprocess boundary the two share. The `Dependabot Updates` name is a downstream symptom, not an independent bug: it surfaces only because `missing_workflows` names every workflow from the previous head once the current head's selection is empty. The residual divergence -- two calls against the same commit disagreeing minutes apart -- is external to this composition: GitHub's own run-listing endpoint is already documented elsewhere in this codebase (`stale_listing_lines`, #1618) as observably eventually consistent, in one measured case by seventeen days. `presets/watch/sources/gh-branch/` (#1953) narrows the exposure in practice by re-polling every 30 seconds rather than answering once at report time, so a stale listing self-corrects on the next tick instead of standing as a report a maintainer loop trusts.
