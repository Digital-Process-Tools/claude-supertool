- **A line range handed to `between` now names the op that answers it, and a correct range read is no longer told it was wrong** ([#983](https://github.com/Digital-Process-Tools/claude-supertool/issues/983)). Two halves of the same defect: the op that cannot do ranges pointed nowhere, and the op that can do them called its own caller mistaken.

  `between` is `SYMBOL:PATH`, so `between:file.py:12420:12700` tokenized `12700` as the path and failed with `ERROR: path not found: '12700'` — a filesystem complaint about a number, which is the tokenizer's own mis-split wearing the shape of an absence on disk. Since the path token held a colon it then reached the payload hint and advised a `between:@-` TOML body, which cannot fix a line range either. Three agents in one evening read that as "supertool cannot do this" and fell back to `sed` or the harness `Read`. The error now says `between does not take line ranges` and names `read:PATH:START-END` with the caller's own numbers substituted in; the single-token case, `between:file.py:12420`, names `around_line:PATH:LINE[:N]` as well. No new op and no new form: `between` still does exactly one thing, and the redirect only fires when the numeric token is not itself a real path and the path in front of it resolves — otherwise this would be guessing at an ordinary typo.

  The range form it points at, `read:PATH:START-END`, has shipped since 0.19.0 and was being actively discouraged by the tool. A successful `read:supertool.py:16116-16120` closed with `OFFSET is a skip count, not a start line — for lines 16115-16119 use read:supertool.py:16115-16119`: a lecture about a form the caller did not use, naming a span one line off from the one they asked for. The window note only ever sees the OFFSET the range was already converted into, so it could not tell the two spellings apart; it is now told which one was typed. The disclosure itself is unchanged — a range read still states the window it returned — and the offset form still gets the correction it was written for.
