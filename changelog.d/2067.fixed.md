- **A nested `pytest` child that died before running is now reported as a harness failure, not a product one** ([#2067](https://github.com/Digital-Process-Tools/claude-supertool/issues/2067)). `tests/test_gl_repo_target_676.py::test_the_env_var_main_sets_does_not_survive_into_the_next_test` spawns a child `pytest` to prove an env-var leak does not survive into the next test, and used to assert `result.returncode == 0` directly -- so a child that died at *collection* (pytest exit 2: a stale Windows temp path in this case) rendered identically to a real product failure, `assert 2 == 0`. That cost a log read, a filed issue and a CI re-run on 2026-08-28 to learn the env-var leak was never in question. The assertion now reads pytest's own documented exit codes: exit 1 is "the child ran and disagreed" (a real product failure); every other code is "the child never produced a verdict" and fails loudly with which one and why, rather than being absorbed into the same message. A grep for the same `subprocess.run([..., "-m", "pytest", ...])` shape found it at eight other call sites across `tests/` (`test_symlink_gating_1205.py`, `test_symlink_gating_register_1232.py`, `test_prepush_utf8_mode_1875.py`, `test_core_timeout_skip_floor_1523.py`, `test_repo_target_673.py`, `test_git_state_guard.py`, `test_git_env_leak_416.py`) -- not fixed here, reported separately, because they span unrelated subsystems and widening this one site was already the whole of this issue.
