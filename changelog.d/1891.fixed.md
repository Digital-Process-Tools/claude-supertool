- **A watch poller's slot could be claimed by more than one process at once** ([#1891](https://github.com/Digital-Process-Tools/claude-supertool/issues/1891)). `claim_pidfile`'s exclusivity rested on `O_CREAT|O_EXCL`, but the PID was written into the file as a second, separate syscall — so for the interval between "the name now exists" and "the name now holds a PID", the file sat there empty. A second claimant hitting `FileExistsError` in that interval read the empty file the same way it reads a genuinely corrupt one (`content is not a PID`, deliberately reclaimable so a crashed poller cannot wedge a slot shut forever) and reclaimed a slot whose real owner was still mid-claim rather than dead. The first claimant, already holding a descriptor open on what was now an orphaned inode, went on to write its own PID into a file nobody could see any more and returned success regardless. Reproduced with two real, unmodified processes racing the function: more than one reported ownership in roughly half of repeated trials on an otherwise idle machine — not a rare edge, closer to a coin flip.

  This is the half of [#1881](https://github.com/Digital-Process-Tools/claude-supertool/issues/1881) that [#1890](https://github.com/Digital-Process-Tools/claude-supertool/pull/1890) did not reach: that PR's own arithmetic showed all 564 pollers on the original report carried one channel token, so the accumulation was entirely intra-directory, and this is what defeated the singleton inside it. The reporter's six same-minute `write_state` temporaries are not themselves reproduced or explained by this fix — `write_state` has no relationship to slot ownership (`record_death` is reached from plain readers with no lock between them, by design) and a positive-control test now pins that several concurrent non-owning writers on one state file is expected, corruption-free behaviour rather than evidence of a duplicated poller.

  The fix writes the PID into an unpredictable temporary name first and publishes it with `os.link`, which is atomic and — unlike `os.rename` — refuses outright rather than replacing when the destination already exists. There is no longer an interval in which the pidfile's name exists without its content: a second claimant either finds nothing, or finds a fully-written PID it can check for liveness.
