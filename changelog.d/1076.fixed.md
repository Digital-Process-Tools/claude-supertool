- **`gh-job`'s `Suite:` line no longer presents the log author's number as the job's own count** ([#1076](https://github.com/Digital-Process-Tools/claude-supertool/issues/1076)). The count is read out of the job log with a regex anchored at column 0, after timestamps and ANSI have been stripped — so the anchor is satisfied by ordinary program output, and on a pull request the code writing that output is the pull request's code. `flat()` was doing its job throughout: no forged *line* reached the render. What it cannot do is make the number authoritative, and the wording called it "the job's own summary line" under a header reading "These count TESTS". The provenance caveat was also conditional on there being two or more summaries, so a job that ran no suite at all and emitted one stray matching line got the number with nothing attached at all.

  The line now states unconditionally that it is what the log claims rather than a count supertool made, and it is cross-checked against the job's conclusion as the Actions API reports it — the one fact in this render the log does not write. `Suite: 0 failed, 9999 passed` on a job the API calls `failure`, or failures on a job it calls `success`, prints that the two do not agree. Agreement is not narrated, because a cross-check that speaks on every render is one nobody reads, and a conclusion that is not yet an answer (`cancelled`, `timed_out`, `skipped`, `in_progress`, empty) manufactures no contradiction — reading "not success" as "the suite failed" would be the same over-claim pointed the other way.

  Reading the count from `junit.xml` instead was the audit's suggestion and the better source, and it is **not reachable from this op**: `.github/scripts/junit_summary.py` writes that file to the runner's working directory, nothing uploads it as an artifact, and `gh-job` reads `gh run view --log` and only that. Its *output* is log text like everything else, and a workflow file is part of a pull request's diff in any case. Hardening the regex was declined for the same reason it always is here — a pattern set cannot be complete, and a tighter one that still matched would produce a more confident-looking wrong answer.

  One bug found on the same line while fixing it: the "did this invocation report a problem" test was `"failed" in body`, which is true of `0 failed, 9999 passed`. It now reads the counts as numbers, so a summary reporting zero failures is no longer selected over a later clean one as though it had failed.
