- **A conflicted `_supertool.py` took the whole tool down with a traceback** ([#1015](https://github.com/Digital-Process-Tools/claude-supertool/issues/1015)). A rebase that touches the core leaves it holding live `<<<<<<<` markers, which is not valid Python, and `supertool.py` is a thin entry point that imports it ([#931](https://github.com/Digital-Process-Tools/claude-supertool/issues/931)) — so the failure was a `SyntaxError` pointing at a conflict marker, and it took out **every** op rather than one, for exactly as long as the conflict existed. A traceback there reads as *the tool is broken* rather than *the tool cannot describe this state*, and what it cost in practice was a fall back to `git diff --name-only --diff-filter=U` plus `awk` on the marker range: the hand-rolled resolver `git-conflicts` exists to replace. The entry point now refuses by name — which file, which lines carry markers, that no op can run, and that this is not a report of what is conflicted — and prints a recovery that does not go through the module under conflict, because `presets/git/conflicts.py` and `presets/git/resolve.py` import only `_git_common` and `_env` and run standalone against the tree you are standing in. A syntax error with no markers in it keeps its own diagnosis rather than being reported as a merge conflict.

  **The issue as filed is wrong about the mechanism, and the title is narrower than the defect.** It reports `git-conflicts` "parsing its own conflict markers as Python". It does not parse anything: `_all_conflict_blocks` reads the file as text and already survives a file it cannot read. The crash is at `import _supertool`, before dispatch — which the issue's own comment worked out independently, and which is why the fix is in the entry point and not in the preset.
