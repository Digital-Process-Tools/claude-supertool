- **A rolled-back edit is now named as one, in the footer and next to the claim it retracts** ([#952](https://github.com/Digital-Process-Tools/claude-supertool/issues/952)). A validator with `rollback_on_fail` rejects an edit, the previous bytes are restored — and the receipt still said `edited src/Foo.php (line 40-44)`, a positive claim about a mutation that no longer existed. Two agents reported it independently on the same day, which is what said this is the normal shape of a failed edit on the payload route rather than a corner.

  Both of the ways this output is actually read agreed with the claim. `grep -E 'edited|ERROR'` returned the `edited` line and nothing else, because the `[rolled back]` marker below it shared no token with it. And `| tail -1` returned `[result] 3 ops run, 2 writes` — `M writes` had correctly excluded the retracted write since #621, but only the single-op case rendered that exclusion as a sentence (`0 writes — nothing changed on disk`). In a batch where other ops did write, a reverted edit became an arithmetic mismatch the reader has to notice before they can explain it.

  A rollback is now its own state, counted where it is decided and rendered as a word: `[result] 3 ops run, 2 writes, 1 rolled back — 1 edit was reverted after validation and did NOT land`. It is deliberately not `skipped` — a skipped op declined and left the disk alone, a rolled-back one wrote and had the write undone, and the remedies differ — and it is not folded into `— nothing changed on disk`, because a plain no-match prints exactly that too. Those were the two most confusable outcomes on this path and they now render differently.

  The `edited` line is **not** suppressed. Printing nothing on a rollback would make "written, then reverted" indistinguishable from "never ran", which is the same absence-read-as-fact defect wearing different clothes. The claim stays and is retracted in place, in a line that quotes it back and names the file:

  ```text
  [rolled back] phplint regressed; src/Foo.php restored — retracts "edited src/Foo.php (line 40-44)"; the file was NOT edited
  ```

  Any filter that caught the claim now catches the undo, adjacent to it. The old wording — `[rolled back] phplint regressed; file restored` — named no file at all, so in a batch it could not say which of several ops had been reverted.

  A rollback also makes the call exit non-zero, on the same grounds as #680's skip: `batch:@ops && git commit` committed a set with one edit reverted and exited `0`. The counter is bumped inside `_retract_write`, the single chokepoint both rollback paths already pass through, so a third path added later cannot be silently invisible; it is read as a per-call delta so one reverted edit cannot poison the exit code of every later call in a warm daemon process.
