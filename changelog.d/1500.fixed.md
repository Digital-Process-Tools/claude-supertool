- **A fragment of the file under validation could take the location off a real `lsp-diag` finding** ([#1500](https://github.com/Digital-Process-Tools/claude-supertool/issues/1500)). `parse_cclsp_diagnostics` reads a diagnostic's `at line N, col M` with an end-of-line anchor, so the tail it picks is whichever one is **last** on the line. That anchor is what defends against a tail sitting mid-message, and it works. What it does not survive is [#1486](https://github.com/Digital-Process-Tools/claude-supertool/issues/1486): U+2028, U+2029, U+0085, VT and FF are deliberately no longer line ends for an adapter parsing a line-oriented protocol, so a fragment after one of them now sits on the *same* line as the real diagnostic and its tail is the last one. One record, well formed, pointing at a line the language server never mentioned.

  Only the segment before the first inline break is parsed now. The remainder is not dropped — a message may legitimately contain one of the five — but it is carried into the message labelled as the rest of one line rather than as a second diagnostic and not as a location. A line that *opens* with a fragment publishes no location at all.

  Found while fixing it, same mechanism, fixed here: all five characters are `str.isspace()`, so `str.strip()` deletes a **leading** one. The infrastructure probe read `ln.strip().startswith("diag:")`, so a fragment at the start of a physical line still imitated supertool's own message prefix — and that does not move one field of one record, it replaces the whole receipt with `skipped` and discards every real finding on the file ([#482](https://github.com/Digital-Process-Tools/claude-supertool/issues/482)'s shape, with the file under validation choosing it).
