- **`cargo-check` blamed the file you edited for a sibling module's compile error** ([#754](https://github.com/Digital-Process-Tools/claude-supertool/issues/754)). `cargo check` analyses the whole crate, and the adapter matched every short-format diagnostic in the output without once comparing the path cargo printed to the path it was asked about. Editing a healthy `src/main.rs` in a crate whose `src/sibling.rs` does not type-check produced `ok: false` with `file` naming main.rs, `line: 1, col: 29` — a location in sibling.rs — and an empty `source_context`, because the crate-relative path was resolved against wherever the adapter happened to be running rather than against the crate. Three false statements about a file that compiled fine, and with `rollback_on_fail` set, grounds to revert an edit that was never the problem.

  Split out of [#753](https://github.com/Digital-Process-Tools/claude-supertool/issues/753), which fixed the misclassification and left this deliberately open, because the answer is a schema decision rather than a regex change: what should a clean file in a crate that does not compile report?

  **The diagnostic is kept and only the attribution changes.** A crate error caused by another file is real; what was wrong is the claim about which file caused it. Filtering it out would leave the caller with a clean-looking file in a crate that does not build — a misreport traded for a silent loss, the worse of the two. A diagnostic naming another file now reports `code: "adapter"`, `line: null` and `col: null`, carries no `source_context`, and names the real `path:line:col` plus the rustc code in its message, so it can still be read and acted on but never mistaken for a line of this file. `ok` stays `false` and no error is dropped. A diagnostic that does name this file is untouched and keeps its own line, column and rustc code.

  `adapter` rather than a new code because every guarantee it already carries is the one wanted: the result is never cached, since a whole-crate verdict is not a function of this file's content while the cache key is a content hash, and it never triggers rollback. `skipped` was rejected for the reason a tool fault is — it omits `errors` entirely, and the crate error would disappear.

  **Paths are compared by suffix on segment boundaries, not by joining onto the crate root.** The obvious fix is wrong for any crate in a workspace: verified on cargo 1.97.1, running from `ws/member` makes cargo print `member/src/sib.rs`, relative to the workspace root and not to the crate root it was invoked in, so `crate_root / src_file` yields `ws/member/member/src/sib.rs` and matches nothing — every genuine finding about the file under validation would have been demoted to a non-verdict, the same defect pointing the other way and the quieter of the two. A suffix match needs no base and touches no disk, so one rule covers crate-relative, workspace-relative and absolute paths alike, and the separator boundary keeps `src/xmain.rs` from matching `src/main.rs`.

  `source_context` for a diagnostic about this file is now read from the target the adapter was handed rather than from a path reconstructed out of cargo's output, which is what was returning empty. The rule is written up in `validators/SCHEMA.md`, and `tests/test_cargo_sibling_attribution_754.py` drives it in process on every platform and against a real two-file crate wherever cargo is installed — the attribution depends on cargo's own relative paths, which a stub would have to guess at.
