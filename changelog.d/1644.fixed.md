- **`gh-branch` now says when it could not rank the previous head by time** ([#1644](https://github.com/Digital-Process-Tools/claude-supertool/issues/1644)). [#1618](https://github.com/Digital-Process-Tools/claude-supertool/issues/1618) replaced list position with `createdAt` as the previous-head ordering, and `_created` reads exactly one spelling — `%Y-%m-%dT%H:%M:%SZ`. `2026-08-13T21:52:04+00:00` is the same instant in legal RFC3339 and parses to nothing, so an undated run was dropped from the ranking silently, and a listing where *no* candidate parsed fell back to list position — precisely the behaviour #1618 was written to remove. The previous-head line read identically in all three cases.

  **Disclosure, not a wider parser.** Accepting more spellings would make the assumption invisible again rather than declared; the third state is "I could not date these N runs". `previous_head_basis()` reports `time` / `position` / `none` with the counts, and `previous_head_lines()` renders one sentence naming how many candidates went unranked and whether the answer therefore came from position. Nothing prints when every candidate parsed, which is every call against GitHub today — `gh run list --json createdAt` emits the `Z` form on this repo, verified rather than assumed.

  **It prints above the `Workflows with a run on the previous head …` block and independently of it.** An empty missing-list derived from the wrong previous head is a false negative, and it is the one that would otherwise print nothing at all. The position fallback itself is kept: refusing to name a previous head would delete the only evidence there is for "ran last time and not this time", which is a worse trade than qualifying it.
