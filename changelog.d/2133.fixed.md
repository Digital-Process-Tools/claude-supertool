- **A session launched with two channel MCP servers for the same socket now leaves a readable trace of the collision, and `channel:health` stops calling it `subscribed`** ([#2133](https://github.com/Digital-Process-Tools/claude-supertool/issues/2133)). `.mcp.json` can declare `claude-channel` and the launcher's `--dangerously-load-development-channels server:NAME` flag can name a second one, both resolving the same watch socket; one binds and the other correctly refuses (#550), but until now the refusal went only to a process nobody was left reading — the harness had already reported both servers `CONNECTION_CLOSED` — while the bound consumer kept forwarding events into a transport the session held no live connection to, and `channel:health` read `FORWARDING`, `session : subscribed`. The losing process now also writes a small marker beside the socket it lost (`channel.ts`'s `refuse()`), which the *winning* consumer clears the instant it (re)binds so only evidence from the current run survives; `channel:health` renders it as a `refused` line, and `subscription()` no longer returns `subscribed` when that marker is present for the tag it is about to accept — it lands in `CANNOT DETERMINE` instead, naming the collision. This does not touch `_configured`'s use of `claude mcp get`, whose "Failed to connect" reading a live singleton's own second lookup was already established as uninformative (#1558) — the new signal is first-hand evidence a rival was refused *this run*, not a fresh probe racing the same collision. Which of the two declarations should be dropped is a decision about this repository's own conventions and is out of scope here.
