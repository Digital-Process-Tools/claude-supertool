- **The GitHub discovery ops printed repository descriptions and logins raw** ([#981](https://github.com/Digital-Process-Tools/claude-supertool/issues/981)). `gh-starred`, `gh-following`, `gh-find-starable` and `gh-find-followable` render text from **arbitrary public repositories and accounts**, chosen by a topic search rather than by us — the widest untrusted-input surface in the tool — and every one of those fields reached `print()` with no marker. A newline breaking the alignment is the lesser half: the text after an injected separator is unconstrained, so it can be padded to the block's own shape and read as a row supertool emitted. These ops exist to decide who to follow and what to star, so a forged row is a recommendation the tool did not make. Every remote field now goes through `_untrusted.flat()` and each block carries one `_untrusted.flat_note()` disclosure — the convention [#819](https://github.com/Digital-Process-Tools/claude-supertool/issues/819) and [#970](https://github.com/Digital-Process-Tools/claude-supertool/issues/970) already established, not a second one. Nothing is fenced and nothing is censored: every word survives, on the one line it was given.

- **The disclosure on the two `find` ops is a `#` comment, because their output is another op's input.** `gh-find-starable` and `gh-find-followable` are written to be redirected into a candidates file and handed to `gh-batch-star` / `gh-batch-follow`, which skip `#` lines and take every other line as a target. `gh-batch-follow` does not require an `OWNER/REPO` shape either, so a bare banner there would be an account it tries to follow — and a login carrying a separator was already an extra follow the reviewer never approved.

- **`gh-find-starable`'s `.replace("\n", " ")` was the shape of a fix rather than one.** It answered one of the ten separators `str.splitlines()` breaks on and none of the escape sequences that can erase a row off the screen, which is worse than nothing there: a site that visibly handles the case is the one nobody re-reads. Flattening now happens **before** the 120-character slice, in that order, for the reason [#970](https://github.com/Digital-Process-Tools/claude-supertool/issues/970) gives — a cut made first leaves behind whatever the separator started.

- **Swept the rest of the family rather than the four files the issue named.** `gh-star`, `gh-follow`, `gh-batch-star` and `gh-batch-follow` echo `gh`'s stderr, which quotes back the name it was given; the two batch ops print it as a row in a list a reader skims for exactly the `ERR` lines a forged one imitates. Those are flattened too.
