- **`go vet` ran out of wall on a cold Windows runner and the suite read that as a dirty package** ([#1461](https://github.com/Digital-Process-Tools/claude-supertool/issues/1461)). `test_a_clean_package_is_clean` reddened `pytest (windows-latest, 3.10)` on a PR touching `presets/_checks.py` and nothing else. The adapter was right — a timeout is `ok: false, count: 1` with `code: "adapter"`, which is the channel `validators/SCHEMA.md` gives an absence and which the core renders `NOT CHECKED`, keeps out of the delta, never caches and never rolls an edit back over. What was wrong was a test asserting a lint verdict about a package no tool had finished analysing.

  `_adapter_verdict.skip_if_stalled` has existed for this since #794 and was extended for it in #1296. `tests/test_validators_go_vet_669.py` is the fourth adapter suite to hit the failure and the first not to have adopted it; it does now, at the one spawn site, so a stall declines once instead of at nine call sites. A real printf finding, a clean package reported dirty, an absent toolchain, a `skipped` third state and a timeout claimed in 12ms all still reach the assertion written for them.

  **The guard could not see the payload that produced the report.** `stalled_at_its_own_wall` matched the substring `timeout`, and this adapter says "timed out"; every other clause of the predicate matched, so the one shape it was built to classify was the one it read as a verdict. It now matches either spelling. `validators/pyright/pyright.py` is invisible to it for the same reason and for a second one — it codes that error `timeout` rather than `adapter`, so the core does not render it `NOT CHECKED` either. Filed separately, not fixed here.

  **The budget is unchanged at 60s, deliberately.** Measured on macOS/go1.22.3 with `GOCACHE` pointed at an empty directory: a cold `go vet` costs **3.54s** against **0.24s** warm, because it compiles the standard library before analysing anything. That is once per build cache and it is a property of the machine, so raising a product timeout to cover a first run on a CI image would slow the real failure mode — a `go vet` that hangs on somebody's edit — for every user, to fix a test. The suite pays the cold cost once instead, vetting a throwaway module before any adapter spawn: `GOCACHE` is content-keyed rather than module-scoped, so a second, never-seen module vets in 0.22s after it. The warm-up is a convenience and never a gate; when it does not fit its own budget it reports the reason through the warnings summary rather than skipping the module or failing it.

  **The macOS runners have no Go, and nothing in CI installs one.** There is no `setup-go` step in `.github/`, so each leg gets whatever its image ships; the ubuntu and windows images ship Go and the macOS images do not. `needs_go` therefore skips 10 of `tests/test_validators_go_vet_669.py`'s 27 tests on every macOS leg — every test of what `go vet` actually says about a package: the clean verdict, the printf finding, sibling attribution, the receipt cap and its truncation notice, the package that does not type-check. That is why only Windows ever hit the timeout: the other four legs were not exercising the path at all. It also caught this change's own first attempt, which provoked the timeout arm without stubbing the binary lookup `main()` runs before it spawns anything — four red macOS legs asserting on a payload that cannot exist where there is no toolchain, which is #1205's shape landing inside the fix for #1205's shape. The four assertions that are about the adapter's *error routing* rather than about Go now stub that lookup and run on every runner; the one test that genuinely executes `go` is gated on the suite's existing `needs_go`, whose reason ("go not on PATH") is not confusable with the one `skip_if_stalled` writes ("adapter spent its whole 60s internal budget without reaching a verdict"). Absent toolchain and slow toolchain are different facts and the skip list keeps them apart.

  Whether a first `go vet` on a GitHub Windows runner is reliably over 60s remains unmeasured, and this change no longer depends on the answer: over it, the suite declines with a named reason instead of publishing a machine limit as a product defect.
