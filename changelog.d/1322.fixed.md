- **A test-only cache exempted from the per-test reset could preserve an *empty* answer for a whole xdist worker** ([#1322](https://github.com/Digital-Process-Tools/claude-supertool/issues/1322)). `conftest.RESET_EXEMPT_GLOBALS` listed `_REPO_TARGET_MODES` and `_SHIPPED_PRESET_OPS` as process-lifetime state, on the reasoning that they describe the install rather than the run. True of their inputs, false of the values: both are `None` at import and built at first use from `_INSTALL_DIR`, which tests patch. A cache built under that patch is empty, and being exempt it survived the teardown that would have rebuilt it — after which `_repo_target_ops()` reported that no op accepts a repo target and every `repo:` call refused every op it was handed.

  Both names moved to `RESET_GLOBALS`, and `_reset_module_state` learned to rebind a `None` sentinel rather than clear a dict in place: clearing leaves a *built and empty* map, which is indistinguishable from "this install declares no repo-targetable ops" and is the defect itself.

  **The reported flake no longer reproduces on this base, and that is not the same as fixed.** A full run under `-n 8` with a teardown probe on the cache saw 12246 pass and zero poisoned teardowns, so nothing in the suite currently populates it under a patch. The mechanism was still live: adding one test that patches `_INSTALL_DIR` and calls the builder took `test_repo_target_673.py` from `32 passed` to `6 failed, 26 passed`, and back to `32 passed` with this change. `tests/test_lazy_cache_lifetimes_1322.py` now fails the build when any new `None`-sentinel name is added to the exempt tuple, so the classification cannot go stale again in silence.
