- **A refusal no longer prescribes an op that does something the blocked command declined to do** ([#1684](https://github.com/Digital-Process-Tools/claude-supertool/issues/1684)). `git push origin v0.2.0` was BLOCKED and told to run `git-push`, which pushes the **current branch**: obeying the refusal published a ref the caller never named, reported success, and left the tag uncreated. The matcher keyed on the verb and not on the invocation.

  **`replaces` entries gain `unless_args: N`** — the entry does not claim an invocation carrying more than N positional arguments past its declared `argv`. Every `git push` entry declares `1`, so a remote is still claimed and a refspec is not. The discrimination the schema docs called impossible ("telling `git push origin master` from `git push origin v0.34.0` means asking the repository whether a ref is a tag") is not the one needed: **both** name an explicit refspec, `git-push` names none, and arity decides it from the argv alone without asking git anything.

  **A fourth verdict state, `uncovered`, rather than silence.** The command runs and the guard says *no op covers this form — raw `git` is correct here*, naming the op as the same invocation without those arguments rather than as a substitute for it. Not folded into `undecided`: that state says the guard could not answer, and rendering a decided "no op covers this" as "the guard did not run" is the same misdirection one layer down.

  **What it costs, stated rather than hidden.** `git push origin master` is no longer refused — a missed block on a command `git-push` does answer when you happen to be on `master`. That is the direction this guard is allowed to be wrong in: a wrong block has no per-command escape short of `raw_command_guard: false`, which disarms every mapping in the repository. The retirement gate for the `git-push-has-an-op.md` JIT rule ([#1376](https://github.com/Digital-Process-Tools/claude-supertool/issues/1376)) is weakened with it, from a block that also named the op to a disclosure that names the op on every such call.

  **And the refusal quotes the command that was typed.** `git push origin v0.2.0 2>&1` was echoed as `git push origin v0.2.0 2` — `shlex` splits `2>&1` into `2`, `>&`, `1`, and the file descriptor stayed on the end of the argv. Descriptors are now dropped by POSIX's own rule (a run of digits that begins a word and is immediately followed by `<` or `>`), so `git push origin 2 >&1` keeps its `2`, which really is an argument. The word **after** a redirection is dropped too: `git status > gh` left `gh` standing where a command word is read, a wrong block waiting for the first single-token `argv` anyone declares.

  The second instance reported — `git checkout REF -- PATH` refused with `git-checkout:REF`, which switches branches — **does not reproduce against the shipped registry**: no `replaces` entry for `git checkout` exists in this tree or anywhere in its history. The mechanism is pinned against an injected entry that reproduces the reported refusal exactly.
