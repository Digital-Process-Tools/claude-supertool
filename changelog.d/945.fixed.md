- **`read` now states the window it returned, and `grep` refuses `LIMIT 0`** ([#945](https://github.com/Digital-Process-Tools/claude-supertool/issues/945)). Two numeric arguments were accepted, produced confident output, and meant something other than what the caller typed.

  `read:PATH:OFFSET:LIMIT` takes OFFSET as a skip count, so `read:file.py:19:1` renders line 20 and line 19 is absent from the output entirely. Nothing in the render distinguished "here is line 19" from "here is a line near 19", so anyone quoting the result into a brief, a commit message or an issue quoted the wrong line with full confidence. Every read with a non-zero OFFSET now carries one line — after the count header, before the content — naming the window asked for and the window returned: `window: offset 19 + limit 1 = lines 20-20; returning lines 20-20 of 403`, plus a pointer to the 1-based `read:PATH:19-19` range form. The semantics are unchanged: re-basing OFFSET would have broken every caller who already had it right, trading a visible wrong answer for an invisible one.

  The same render used to sign off a windowed read with `[complete file — no more lines]` — false, because lines 1 to OFFSET were never emitted, and outright backwards when OFFSET sat past EOF, where *zero* lines were emitted and the output still said the whole file had been shown. A windowed read that reaches EOF now closes with `[end of file — lines 1-OFFSET not shown]`, and a window past EOF says `returning nothing — the file has N lines`.

  `grep:PATTERN:PATH:0` used to accept the `0`, ignore it, and quietly substitute the default limit; the filed case spent about 18 KB of the caller's context before that was visible. `0` is now refused by name. Honouring it as unlimited would hand a caller who typed one character an unbounded dump into a shared output budget, and substituting the default means the LIMIT that ran was never the LIMIT that was typed — so neither is guessed. `grep_around` and the `grep:@payload` route refuse it on the same terms.
