- **`read` now states the window it returned, and `grep` refuses `LIMIT 0`** ([#945](https://github.com/Digital-Process-Tools/claude-supertool/issues/945)). Two numeric arguments were accepted, produced confident output, and meant something other than what the caller typed.

  `read:PATH:OFFSET:LIMIT` takes OFFSET as a skip count, so `read:file.py:19:1` renders line 20 and line 19 is absent from the output entirely. Nothing in the render distinguished "here is line 19" from "here is a line near 19", so anyone quoting the result into a brief, a commit message or an issue quoted the wrong line with full confidence. Every read with a non-zero OFFSET now carries one line — after the count header, before the content — naming the window asked for, the window returned, and why the window ended: `window: offset 19 + limit 1 = lines 20-20; returning lines 20-20 of 403, stopping at line 20: the limit was reached`, plus a pointer to the 1-based `read:PATH:19-19` range form. The semantics are unchanged: re-basing OFFSET would have broken every caller who already had it right, trading a visible wrong answer for an invisible one.

  A window ends for one of three reasons and the note names which of them it was: the LIMIT was reached, the file ended, or the 20 KB byte cap cut the render short. Only two of those were ever distinguished, so a capped read announced `stopping at line 54, the end of the file` at the top of a body whose own footer, 20 KB further down, said 146 lines remained — the false claim first, and the one a caller quotes. When two reasons land on the same line the note says they coincide instead of picking one, and a read that ends for a reason it cannot attribute says that rather than inventing one.

  Every count in the render is now taken from the last line the read actually *looked at*, not the number of lines it printed. The two differ under compact mode, which skips blanks and comments without counting them: a `read:mix.py:10:50` whose body visibly ended at line 60 was headed `returning lines 11-35 of 200, stopping at line 35, the end of the file` — a window that was not returned, a stop that did not happen, and an end-of-file 140 lines early. The same miscount drove the `... (N more lines)` footer, which reported 165 where 140 remained; it predates the window note, but leaving two disagreeing counts in one render is worse than either alone, so both now come from the same number. A note over a compacted window also states how many of the lines in its span were suppressed, because a range that reads as contiguous when it is not is the same defect one level down.

  The same render used to sign off a windowed read with `[complete file — no more lines]` — false, because lines 1 to OFFSET were never emitted, and outright backwards when OFFSET sat past EOF, where *zero* lines were emitted and the output still said the whole file had been shown. A windowed read that reaches EOF now closes with `[end of file — lines 1-OFFSET not shown]`, and a window past EOF says `returning nothing — the file has N lines`.

  `grep:PATTERN:PATH:0` used to accept the `0`, ignore it, and quietly substitute the default limit; the filed case spent about 18 KB of the caller's context before that was visible. `0` is now refused by name. Honouring it as unlimited would hand a caller who typed one character an unbounded dump into a shared output budget, and substituting the default means the LIMIT that ran was never the LIMIT that was typed — so neither is guessed. `grep_around` and the `grep:@payload` route refuse it on the same terms.
