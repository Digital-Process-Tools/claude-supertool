- **`read` elides a repeat read of a byte-identical file** ([#1329](https://github.com/Digital-Process-Tools/claude-supertool/issues/1329)). A second bare `read:PATH` within 15 minutes, when the file's sha256 has not moved **and both reads share the same parent process**, returns one line instead of the content — carrying the sha, the file's size on disk, and the exact command that hands the bytes over. It says "on disk" rather than "withheld" on purpose: a file over `read.max_bytes` is byte-capped on the way out even under `:full`, so the file's size and what the first read actually handed over are different numbers, and naming the former as withheld would overstate it on exactly the files where the cap bites. Off with `read.elide: 0` or `SUPERTOOL_READ_NO_ELIDE=1` — and that first switch is read directly rather than through `_get_op_int`, which is built for positive-integer thresholds and treats a configured `0` as "unset". `read.elide` is the first boolean in this file whose default is on, so through that helper the switch was documented in three places and inert; it is the only site of the class, and every other `_get_op_int` call is a genuine threshold.

- **On this repo the saving is 0.0% of result bytes, and the prose should not borrow anyone else's number.** Measured with `claude-log:cost` over real transcripts: unchanged re-reads are 0.0% of result bytes on the supertool corpus, because batching already prevents the pattern. The 8.7% often quoted is the `Read`-tool-driven corpus — 252,851 B, one `portfolio.json` read sixteen times — and is a statement about a different tool. This is built for what it prevents.

- **What it must not do drove the whole shape.** The op cannot observe whether the caller still holds the first copy, and a re-read after a context compaction is the normal case rather than the edge case: the earlier result was evicted and the model is asking again precisely because it no longer has it. Nothing distinguishes that from a redundant second ask, so the design bounds the damage instead of guessing at it. The elision is always one round-trip from the bytes and names that command in the line, not in the docs. The recency window is measured from the last read that actually **returned** content and is never bumped by an elision, so a file polled every minute is not elided forever. A file whose bytes changed is never elided at any age — repeat reads of files that moved are the ones that carry information. A state file that cannot be read or written returns the content: an unanswered cache is `skipped`, not silence. `read:PATH:full` never elides and re-arms the window. An explicit offset, limit, range or `grep=` filter neither elides nor arms one, because a recorded whole-file read says nothing about a slice request.

- **Keyed on `(session, realpath, sha256)`, where session is `USER | PPID | realpath(cwd)`.** Not mtime, which changes on a no-op rewrite and misses a same-second edit. PPID is the session proxy supertool's call log already uses; the resolved cwd is mixed in because nine worktrees were live on one machine on 2026-08-11 and one agent's read must never suppress another's. The two failure directions are not symmetric — over-keying costs one file returned again, under-keying withholds content the caller never saw — so the key is the narrower one on purpose. One small sidecar per `(session, file)` under `~/.cache/supertool/read-elide/`, never a shared index two concurrent processes would clobber; `gc` reaps the kind after a day, since a PPID in the key makes yesterday's entries unmatchable by construction.

- **Where that fires, measured, because the key is the invoking shell.** `os.getppid()` for `supertool` is the process that ran it, and Claude Code starts a new shell per Bash tool call, so the key changes on every turn: two bare reads of one unchanged file in separate calls both returned 3,840 bytes and left two keys under `~/.cache/supertool/read-elide/`; the same two reads on one command line returned 276 bytes, the elision. It fires for two invocations inside one shell — the case batching already covers — and not for the repeat read after a compaction it was aimed at. Filed as [#1352](https://github.com/Digital-Process-Tools/claude-supertool/issues/1352). The 0.0% above is unaffected either way: it is a property of the transcript corpus, measured from result bytes, not of the key.
