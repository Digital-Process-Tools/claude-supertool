- **`gl-runners:host` and `gl-runners:host:<description>` read each runner box over SSH, next to its GitLab row** ([#ISSUE](https://github.com/Digital-Process-Tools/claude-supertool/issues/ISSUE)). GitLab can say a runner is `online` and idle; it cannot say the box behind it is swapping, at 90% on the docker root, or promising more `concurrent` jobs than it has CPUs. Per host the op prints RAM total/used/available and swap (`free -b`), load average against the CPU count (`/proc/loadavg`, `nproc`), disk use of `/` and of the docker data root (`df -P`, one call each so a missing docker root cannot hide `/`), the running-container count and a `docker stats --no-stream` table, and `concurrent` plus each `[[runners]]` `limit` from the runner's `config.toml`, naming which file it read: `/etc/gitlab-runner`, `/srv/gitlab-runner/config`, `~/.gitlab-runner`, or the `/etc/gitlab-runner` bind mount of a running gitlab-runner container (helper job containers skipped). Where the SSH user is not in the `docker` group or cannot read the file, docker `ps`/`stats`/`inspect` and the `awk` that reads `config.toml` are retried as `sudo -n` — never a prompt, never a password — and the output says so. Every reading that could not be taken says `unreadable (<reason>)`; none renders as zero.
  The op never learns where hosts come from. The project declares `gl-runners.host_resolver` in `.supertool.json`, an argv list run with the runner description as its last argument, answering one JSON object (`host`, optional `user`, `port`, `password`) or exit 3 for "no host entry". Its stdout is never printed on any path; a password reaches `sshpass -e` through the environment, never argv. One SSH call per host, one fixed read-only command string with nothing interpolated into it; `config.toml` is filtered on the host to section headers and the three keys shown, so the runner tokens it holds never cross the wire.
