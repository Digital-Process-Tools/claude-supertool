- **`paste` over an existing file now keeps the bytes it displaces** ([#1650](https://github.com/Digital-Process-Tools/claude-supertool/issues/1650)). An agent writing a working note pasted 1990 bytes over a path it believed did not exist. It did: an earlier agent had left 8922 bytes there. The receipt was honest and complete — `rewrote ... 8922 -> 1990 bytes` — and it printed one step after the only moment it could have helped. The path was gitignored, so there was no git copy, and the disposable clone used for the suite did not carry it. Unrecoverable. The outgoing bytes are now copied to `~/.cache/supertool/paste-backup/` **before** the write, and the receipt names the copy: `previous contents kept at PATH`.

  **Nothing is refused, and that is the design.** A guard that blocked the overwrite would have to offer a `force` token, `paste` over an existing file is documented and ordinary, and a `force` typed by reflex is the guard deleting itself. A copy has no case it was not written for — the write the caller asked for happens either way, and a false positive costs one cache file that `gc` reaps in seven days.

  **`paste` is guarded alone because of an asymmetry, not because it is the biggest hammer.** `edit` and `replace` match a string first; `replace_lines` refuses an `END` past the file length; `vim` errors on a path that does not exist and echoes the removed text back as a diff. `vim` can still empty a file completely with `ggdG`, so this is not a claim that nothing else destroys bytes — it is that nothing else can do it to a file the caller believes is not there, which is the mechanism that produced the incident. A test pins `vim` refusing a missing path, so a future create-if-missing arm cannot open that hole silently.

  **There is no shrink ratio and no byte-loss floor.** The issue proposed both. Both are blind to 8922 bytes replaced by 9000 different ones, which loses exactly as much and is exactly as unrecoverable, so the trigger is the op's own semantics — `paste` replaces the entire file — and there is no number to tune. The one number present is a resource bound, not a trigger: a file over 8 MB is not copied, and the receipt says so rather than staying silent, because an unbacked overwrite that reads like a backed one would land on the largest files, where the loss is worst.

  **A write a validator rolls back still leaves a copy.** The snapshot is taken before the write and validation happens after it, so a rolled-back `paste` prints `previous contents kept at PATH` above `[rolled back] … the file was NOT edited`. Both sentences are true — the file on disk is the original and PATH holds those same bytes — so the copy is redundant rather than wrong, and `gc` reaps it with the rest.

  Three states, never silence: `previous contents kept at PATH`, no line at all when nothing was displaced, and `no backup of the previous contents — WHY` when the copy failed. The store is registered in the cache reaper at seven days; a writer without a retention entry is how `~/.cache/supertool` reached 1.0 GB in the first place.
