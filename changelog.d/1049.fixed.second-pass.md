- **The first cut of the CRLF fix left `replace` reporting replacements it had not written** ([#1049](https://github.com/Digital-Process-Tools/claude-supertool/issues/1049)). `op_replace` reads the file twice — once to count matches, once to write — and only the write pass was given `newline=""`. On a CRLF file the counting pass saw universal-newline-translated content and found an LF `old`; the write pass saw the real bytes and found nothing. `content.replace()` returned the file unchanged, `_atomic_write` wrote it back, and the receipt printed the *counting* pass's number: `(2 replacements in 2 files)` over two files that had not moved a byte. A fix for an absence-read-as-presence defect had produced a fresh one, in the same op, one function apart.

  Both passes read the same way now, and the convention is resolved once during the scan and carried to the write rather than re-derived. The receipt's count comes from the bytes about to be written, never from the scan. A file that matched during the scan and no longer matches when the write reads it back — it changed on disk in between — is named as **not modified** rather than counted or silently dropped.

  **`replace_lines` was re-terminating content the caller had written deliberately.** Giving the inserted block the file's local ending is right for a newline the op has to *invent*, and wrong for the endings inside a block the caller typed: `test_mixed_line_endings_preserved` has stated that contract since before this issue, and the first cut broke it. Caller content now passes through verbatim, mixed endings and all; the local convention is consulted only for the trailing newline, and only when the block does not end a line at all.

  **And the line-ending receipt fired where nothing had been decided.** A clean edit of a uniform CRLF file, matched literally, every byte outside the match unchanged — and the receipt said so at length, under the `↳` marker that means "something here needs your attention". On Windows every file is CRLF, so that note appeared on every edit ever made; it also collided with `test_successful_edit_has_no_diagnostic`, which reads `↳` as "a diagnostic was emitted" and was right to. The note is now emitted only where the ending used had more than one defensible answer: a mixed file, or the caller's own text re-terminated to match. Silence is the correct receipt for a choice that was never made.

  **All four were caught only by the Windows legs, and only because those fixtures use `write_text`.** `Path.write_text` translates `\n` to `os.linesep`, so every such fixture is CRLF on Windows and LF everywhere else — which is why the tests are worth leaving exactly as they are. Converting them to `write_bytes` would make them deterministic and would delete the only CRLF coverage in the suite. The new pins alongside them write bytes explicitly, so the same ground is covered on every platform without giving up the accidental coverage the matrix provides.
