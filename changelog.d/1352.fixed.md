- **The docs described `read`'s elision as a live saving; measured, it never fires between two Bash tool calls** ([#1352](https://github.com/Digital-Process-Tools/claude-supertool/issues/1352)). `_read_elide_session_key()` carries `os.getppid()`, which for `supertool` is the shell that ran it — and Claude Code starts a new shell per tool call, so the key changes every turn. Re-derived here rather than taken on trust: two bare reads of one unchanged file in separate calls both returned 3,840 bytes and left two keys under `~/.cache/supertool/read-elide/`; the same two reads on one command line returned 276 bytes, the elision line. It fires inside one shell, which is the case batching already covers, and not for the repeat read after a compaction it was built for. `README.md`, `docs/operations/reads.md`, `docs/configuration.md`, `.supertool.example.json` and the pending [#1329](https://github.com/Digital-Process-Tools/claude-supertool/issues/1329) fragment all now name the condition instead of implying it always holds. **No behaviour changed** — the key is a separate decision and stays open, because the reasoning behind it is still right and only lacked this measurement.

- **The condition is pinned by a test, not only by prose.** `tests/test_read_elide_session_boundary_1352.py` runs `supertool` under two different parent processes and asserts the second read returns content, with a same-parent arm as the positive control — without which "content came back" is equally consistent with the feature being off, the cache unwritable, or the test spawning wrongly. Whoever changes the session key gets a red test naming the boundary rather than a paragraph they have to notice. Written against the shipped claim first, where it failed on `assert "elided" in second`.
