- **`html-check` matches `*.htm`, and every bundled adapter is now in `.supertool.example.json`** ([#1159](https://github.com/Digital-Process-Tools/claude-supertool/issues/1159)). `.htm` is the same document with a shorter suffix — identical content, identical checker — and a page saved that way got no inline-JS check at all. One entry covers both, in this repo's own config and in the catalogue, rather than a second `html-check-htm` row: unlike the `yaml-check` / `tsc-check` pairs there is no second tool and no second decision to record.

  `docs/validators.md` tells the reader to "enable any of these by copying the relevant entry from `.supertool.example.json`". **Eight adapters had no entry there**, not the seven the issue counted, and the list differs as well as the number: `changelog-fragment`, `lsp-diag`, `phpmd`, `phpmd-mcp`, `phpstan`, `phpstan-mcp`, `phpunit-mcp`, `rector-mcp`. The issue named five of those plus `common/`, which is a library the adapters import and not an adapter at all; it missed `changelog-fragment`, `phpstan` and `rector-mcp`. Counting the directories rather than copying the number is what turned that up, and the guard below now produces the list rather than a person doing it.

  With the violations gone the guard is buildable and is landed with them: every directory under `validators/` must be reachable from a `cmd` in the catalogue, and every catalogue `cmd` must point at a directory that exists. `common/` is excluded by name, so a future non-adapter directory is a visible decision rather than a pattern that happens not to match it. This asserts nothing about this repo's own `.supertool.json`, deliberately — it is correct for a Python repo not to run `phplint` on itself.

  Each new entry's `timeout` is set **above** the adapter's own internal budget, not equal to it. `docs/validators.md` already states the rule on the `html-check` row — when the two match, the core's timer always wins the race and the row reads `NOT CHECKED` with nothing naming what hung, where with headroom the adapter's own arm fires first and reports a cause. All seven of the new entries with a readable budget were written wrong first and caught by review: `phpstan-mcp` allows itself 60s to spawn plus 180s per call and had been given 120. A guard reads each adapter's own budget out of its source and fails on any of the seven that does not clear it, with a second test asserting the reader still finds all seven — a sweep that quietly stops reading must not pass as a clean sweep.

  Note for whoever picks this up next: **several adapter READMEs publish a `timeout` that violates the same rule** — `validators/phpmd/README.md` offers 30 against a 120s subprocess budget, `validators/phpstan/README.md` 60 against 120, and the `phpunit-mcp` and `rector-mcp` READMEs offer figures equal to their adapters' own. Those are pre-existing and are left alone here rather than swept inside a PR about two other issues.
