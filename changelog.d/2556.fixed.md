- **A genuinely unusable `lock_dir` now falls back to running `fn()` immediately instead of waiting out the whole `timeout_s`** ([#2556](https://github.com/Digital-Process-Tools/claude-supertool/issues/2556)). #2555's fix for #2553 replaced a single 0.05s absence-recheck with a retry loop on `os.open()` in `tests/_go_warmup_lock.py::serialize_once`, correctly closing the race where an absent lock file was misread as "lock_dir unusable" when it could also mean "the holder just released it" -- but that retry loop was bounded by the same `deadline` used for genuine lock contention, so a `lock_dir` that is actually unusable (unwritable, wrong permissions, missing) waited the full `timeout_s` before falling back, instead of the ~0.1s the pre-#2553 code took. Real call sites pass `GO_WARMUP_S` -- minutes, scaled by `platform_factor()` -- as `timeout_s`, so every `go-vet`-family test that happened to hit an unusable `lock_dir` would burn minutes of wall clock per call before falling back. Writability of `lock_dir` itself is not ambiguous the way a single absent lock file is: a new `_lock_dir_usable` probe creates a unique throwaway filename in `lock_dir` at the point the retry would otherwise begin. Because the probe name is unique, it can never collide with a real holder's lock file or with the Windows delete-pending window `_exists_or_assume_so` tolerates (#2551) -- any `OSError` from the probe means the directory itself is unusable, with no race left to lose. A new test, `test_an_unwritable_lock_dir_falls_back_fast_even_with_a_long_timeout`, pins this by asserting the fallback lands in a small fraction of a multi-second `timeout_s` rather than waiting it out; the two existing tests that simulated the delete-pending race by booming every `os.open()` call regardless of filename (`test_a_transient_exists_check_miss_is_rechecked_before_falling_back`, `test_the_absence_recheck_keeps_waiting_past_one_beat_before_giving_up`) were updated to boom only the specific lock file, matching the real-world Windows behaviour where delete-pending affects one file, not the whole directory. This is a performance/cost fix layered on top of #2555's already-correct control flow, not a correctness change to it.
