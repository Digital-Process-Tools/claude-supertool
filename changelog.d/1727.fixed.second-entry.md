- **#654's sweep boundary was a regex over single lines, so two files sat inside it unswept — and both crashed on the value it exists to catch** ([#1727](https://github.com/Digital-Process-Tools/claude-supertool/issues/1727)). `tests/test_env_knob_parsing_654.py` declares `BARE_PARSE_ALLOWLIST` empty and says the empty set is "a claim this test keeps honest rather than a formality". It was not: the scan ran `(?:int|float)\(\s*os\.(?:environ\.get|getenv)\(` against one line at a time, and a Python call expression is not a line. `presets/github/find_starable.py` and `presets/github/find_followable.py` each spelled it

  ```
  n = int(parts[1]) if ... else int(
      os.environ.get("SUPERTOOL_DEFAULT_LIMIT", "30"))
  ```

  with the `int(` and the `os.environ.get(` on different lines, so the pattern could never match and the empty allowlist read as "the sweep reached every site" for two files it had never looked at. `SUPERTOOL_DEFAULT_LIMIT=abc python3 presets/github/find_starable.py python` ended in `ValueError: invalid literal for int() with base 10: 'abc'` — [#654](https://github.com/Digital-Process-Tools/claude-supertool/issues/654)'s own reproduction, inside #654's own boundary. Both now read the knob through `_env.env_int`, so the same command prints `note: SUPERTOOL_DEFAULT_LIMIT='abc' is not a whole number - ignoring it and using 30.` and carries on.

  **The scan is parsed now, not grepped** — `bare_parse_lines`, walking the AST, the same move `non_ascii_print_literals` in `tests/test_encoding_seam.py` already made for the same reason. It raises `SyntaxError` on source it cannot read and `_scan_bare_parses` turns that into a named refusal, so a file the scan cannot parse is never counted as a file with nothing in it. `test_the_bare_parse_scan_sees_a_call_wrapped_across_lines` is the positive control the guard should have carried from the start: it pins the wrapped case, the one-line case, and a decoy that must stay unflagged.

  Measured while fixing it, because it cuts both ways: the old regex also matched `int(os.environ.get(` inside a **comment** describing the defect, so prose about the bug would have reddened the build the bug did not. The AST scan reports neither.

  Found only because an unrelated change in this same PR reflowed those two expressions onto one line and the register went red. A guard that cannot see the thing it forbids, in a file whose docstring says it keeps the claim honest, is this repository's standing defect class pointed at one of its own checks.
