- **`batch:@file` accepts a single op’s own fields as a one-op batch instead of refusing** ([#1026](https://github.com/Digital-Process-Tools/claude-supertool/issues/1026)). `echo {"op":"git-status"} | supertool batch:@-` used to refuse with "this payload has no 'ops' array", correctly naming the shape but leaving the caller to re-wrap a payload that was already unambiguous — a dict carrying its own `"op"` key can only be one op's fields, never a batch wrapper.

  A dict with no `"ops"` array is now run as a one-op batch when it carries a string `"op"` key; the deciding signal is that key alone, checked before the existing wrapper-typo detection (`_BATCH_WRAPPER_KEYS`) ever runs, since that check only applies once an `"ops"` array is present. The four other op-message defects filed under the same issue (#983, #1073/#1771, and two read/glob hint fixes) were already fixed by earlier, unrelated work and are unchanged here.
