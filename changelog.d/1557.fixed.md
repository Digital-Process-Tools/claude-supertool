- **A directory name could write lines into `git-status`'s own report** ([#1557](https://github.com/Digital-Process-Tools/claude-supertool/issues/1557)). The copied-worktree banner added in [#1536](https://github.com/Digital-Process-Tools/claude-supertool/issues/1536) interpolated two paths raw, and both come off disk: `.git/worktrees/<name>/gitdir` holds whatever wrote it, and git itself writes the path handed to `git worktree add` into that file. So a worktree whose directory name contains a line separator put text at column 0 of the render — a fabricated `### Staged (0)` / `nothing staged, tree is clean` pair, indistinguishable from the sections the op writes itself, and equally so to a consumer grepping the output. No hostile file and no attacker were required; a newline in a directory name was enough.

  Both values are now flattened by `foreign_worktree()` itself rather than at any render, because there were four renders and not the one the finding named: the banner, the prose line under it in `git-status`, the same line in `git-worktrees`, and `repo_label()` — the `Repo:` line of `git-commit` and `git-push`, i.e. the ops that write. `repo_label()`'s own `git rev-parse --show-toplevel` is flattened too, which needed no copied worktree at all.

  The separator is **disclosed**, not elided: it renders as `␊` (or `[U+000A]` on a stream that cannot carry the control pictures), so the banner still names a directory the reader can identify on disk. `_untrusted.flat()` takes a `disclose_newline` keyword for this — a title cannot contain a newline and reads better with a space in its place, a path can and does not.
