- **`youtube_comment`'s could-not-verify arm, and `youtube_auth`'s loopback bind, could surface raw or unescaped failure text** ([#227](https://github.com/Digital-Process-Tools/claude-supertool/issues/227)). Two findings from a release audit of the OAuth2 write half landed in this repo's `trap.d/`: `verify()`'s `could-not-verify` arm returned the HTTP error body via a bare `str(e)`, unescaped and untruncated -- a newline embedded in the body (Google's, not a caller's) put the remainder at column 0 of a receipt a calling agent parses, while the `MISMATCH` arm two lines below already reprs/truncates the same kind of text. And `authorize()`'s loopback callback server could lose the free-port race between `_free_loopback_port()` freeing the socket and `http.server.HTTPServer` re-binding it -- another local process taking the port in that window raised a bare `OSError`, which `auth.py:main` (catching only `OAuthError`) let through as a raw traceback instead of the sentence-naming-the-next-command every other failure path in this module gives. Both fixed: `verify()` now returns `repr(safe_short(str(e), 300))`, matching the `MISMATCH` arm's convention; `authorize()` now catches the bind `OSError` and re-raises it as an `OAuthError` naming `youtube_auth` as the next command. Neither is a security issue -- the race is benign, since a hijacker still cannot pass the `state` check -- both are misreports. `tests/test_youtube_writes_227.py` pins both: a newline-carrying error body must not leak a raw newline into the read-back detail, and a `HTTPServer` bind failure must surface as `OAuthError`, not a bare `OSError`.
